# Quick 260806-o96 — SUMMARY

**One commit `85c3aa9` on `master`. Gate-green, NOT deployed.**

## G-5 is ANSWERED, and the answer inverted the question

Measured from run `368ff3a0`'s GCS audit blobs — 7 gate calls, all carrying an **identical** 576-char
decision context against a 1200 cap. **The 1200 never bound** (624 chars, 52%, spare).

**What bound was `workshop._LABEL_MAX_CHARS = 120`.** The gate's TEST 2 — *"does the client's
decision actually turn on this claim?"* — was answered against three questions cut mid-word:

> …op brandstof en/of shopproducten, **hoe wordt dit operat** · …welke impact hebben deze gehad
> **op koff** · …door ruimere openingsuren **in de retailmar**

Every KEEP/DROP decision in that run was made against half-sentences. **The cap everyone suspected
was innocent; the cap nobody suspected was the whole defect.**

## What changed

- `_gate_decision_context` resolves each label to the client's **full question** via the ONE existing
  resolver `synthesis.steps.focus_area_questions` (from `70f9f11`/G-10), falling back to the label.
  No second mapper, no second copy of the 120.
- **Both caps 1200 → 4000 and 2000 → 4000, in the same commit**, because they truncate the same
  string **in series**.
- `_LABEL_MAX_CHARS` **not widened**, and pinned at 120 by a test.

## The three things that could have gone wrong and didn't

1. **The series trap.** Raising only the pipeline-side cap past 2000 changes the number, produces no
   observable effect, and reads as *"the cap was not the problem."*
   `test_the_two_caps_stay_in_series_order` pins the **relationship, not the values**.
2. **The DISPLAY-ONLY contract.** The reused resolver is documented *"the label stays the join key
   everywhere it is a key."* The decision context is prompt text — nothing is keyed, joined or
   stored by it — so this honours the rule. The docstring now says so, or the next reader concludes
   the rule was broken.
3. **A wrong justification, corrected rather than propagated.** The 1200's comment claimed it
   protected *"the 4096-token gate budget"*. That 4096 is `max_output_tokens` — what the model
   **writes back** — and input text cannot consume an output budget. The bound was right; the stated
   mechanism was not, and anyone sizing the constant against 4096 would size it against the wrong
   number.

## Why both caps had to move now, not later

| Feed the gate | Total | Fits the OLD 1200? |
|---|---|---|
| 3 labels at 120 (what shipped) | **576** | yes, 624 spare |
| 3 **full** questions | **1164** measured / 1165 live | **yes — by 35 chars** |
| 4 full questions | ~1484 | **no** |
| 5 full questions | ~1803 | **no** |

The intake admits **1 to 5** questions. The cap was **latent, not dead** — it wakes the moment the
truncation stops, and the failure mode is the client's last question silently vanishing from the
gate's view.
