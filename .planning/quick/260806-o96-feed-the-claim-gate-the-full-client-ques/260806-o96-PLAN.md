# Quick 260806-o96 — Feed the claim gate the full question; raise both caps together

## The measurement this rests on (G-5, ANSWERED)

Read from run `368ff3a0`'s GCS audit blobs — 7 gate calls, all carrying an **identical** decision
context of **576 chars against a 1200 cap**. Arithmetic reconciles exactly:
`216 fixed overhead + 3 × 120 = 576`.

**The 1200 does not bind. It never did.** 624 chars — 52% — of headroom. What binds is
`workshop._LABEL_MAX_CHARS = 120`, and the gate's TEST 2 (*"does the client's decision actually turn
on this claim?"*) has been judging against three questions cut mid-word. Verbatim from the audit:

> …dynamic pricing toe op brandstof en/of shopproducten, **hoe wordt dit operat** · …welke impact
> hebben deze gehad **op koff** · …door ruimere openingsuren **in de retailmar**

Every KEEP/DROP decision in that run was made against half-sentences.

| Feed the gate | Total | Fits 1200? |
|---|---|---|
| today — 3 labels at 120 | 576 | yes, 624 spare |
| 3 **full** questions (288+309+352) | **1165** | **yes — by 35 chars** |
| 4 full questions | 1484 | **no** |
| 5 full questions | 1803 | **no** |

The intake allows **1 to 5** questions, so the cap is **LATENT, not dead** — it wakes up the moment
the truncation stops. That is why both caps move in the same commit as the fix.

## The trap this plan exists to avoid

**The two caps sit IN SERIES.** `pipeline._GATE_DECISION_CONTEXT_CHARS` (1200) truncates, then
`gates._CONTEXT_MAX_CHARS` (2000) truncates **again**. Raising 1200 past 2000 alone would change the
number, produce no observable effect, and read as *"the cap was not the problem."* Both move to
**4000**, together.

⚠ There are **THREE** similarly-named constants in this tree. Do not confuse them:
`pipeline._GATE_DECISION_CONTEXT_CHARS` (1200) · `gates._CONTEXT_MAX_CHARS` (2000) ·
`workshop._CONTEXT_MAX_CHARS` (2000, unrelated, **not touched**).

## Locked rulings

- **`_LABEL_MAX_CHARS = 120` IS NOT TOUCHED.** It is an IDENTITY key, not a size guard — a dict key,
  the join key 15.2-11's D4 superset assertion compares on, and the key for `_propagate_stakes`
  facets and `assignment_identity.client_question`. Widening it renames every stored label and
  breaks comparability. Its own comment says so in place. The parked note calling it *"safe to
  remove"* was **wrong** and is recorded as wrong.
- **Neither cap is REMOVED.** The brief is client-typed text going verbatim into a prompt, and
  unbounded client text in a prompt is the injection surface this codebase bounds everywhere else.
  A bigger bound, not no bound.
- **ONE resolver, reused.** `synthesis.steps.focus_area_questions` (landed in `70f9f11` for G-10).
  `pipeline.py` already imports `relabel_facets` from that module and already carries the rule at
  `:4293` — *"the resolver (`synthesis.steps.focus_area_questions`), not a second copy of"*. No
  second mapper, and no second copy of the 120.
  ⚠ That resolver's docstring says **DISPLAY ONLY — the label stays the join key everywhere it is a
  key.** The gate decision context is PROMPT TEXT, a read path, so this use honours that rule rather
  than bending it. Say so in the comment, or the next reader will think the rule was broken.
