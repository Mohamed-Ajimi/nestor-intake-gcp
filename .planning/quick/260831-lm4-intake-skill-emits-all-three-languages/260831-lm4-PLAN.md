<objective>
Close defect 1 from the 2026-08-31 intake test: the client answered in English and asked for a French
report, and Nestor proposed its modifications in **Dutch**.

**Cause (corrected during investigation).** `NESTOR_INTAKE_SKILL_PROMPT` (`prompts.py:56-127`) carries
NO language instruction at all. It is simply written **entirely in Dutch**, field descriptions
included (`"de huidige waarde uit intake"`, `"jouw scherpere herformulering"`), so the model answers
in Dutch. (An earlier note in this session attributed `prompts.py:141`'s explicit
*"Schrijf in vloeiend Nederlands"* to this prompt — that line belongs to
`CONTEXT_PACK_SKILL_PROMPT`, a DIFFERENT skill. See "Out of scope" below.)

The data was there and was ignored: `report_language` is a real radio in the canonical template, and
`_format_intake_markdown` renders every answer, so the model already received `**report_language**: fr`.

**OPERATOR RULINGS (2026-08-31, both confirmed):**
1. The model emits **all three languages in ONE call** — not a second translation pass.
2. The research brief resolves to **`report_language`**.
</objective>

<design_decisions>
**D-1 — Do NOT translate the prompt's principles.** Keep the Dutch body verbatim
(`"Niet braaf zijn. Slechte vraag? Zeg dat en herformuleer."` and the rest). Those lines are tuned
behaviour; rewriting them in English risks silently changing WHAT the model produces while we are
trying to change only WHAT LANGUAGE it produces it in. Change the OUTPUT CONTRACT only. The Dutch
bias stops mattering once all three languages are explicitly required.

**D-2 — Only GENERATED strings are localized; ECHOED strings stay scalar.** `current` and `original`
are the client's own words quoted back. Translating them would put words in the client's mouth and
would also make the diff UI compare a translation against the original. This also roughly halves the
output growth, which D-3 depends on.

Localized (object): `suggested`, `rationale`, `additional_questions[].text`,
`additional_questions[].rationale`, `dropped_questions[].reason`, `bias_radar`,
`blind_spots.{upstream,downstream,perspectief}`, `gaps_flagged`.
Scalar (unchanged): `current`, `original`, `original_index`, `type`, `domain`.

**D-3 — `_APPLY_MAX_TOKENS` 8192 → 20000, and it MUST stay under ~21333.** The call is NON-STREAMING
(`apply.py:126` `messages.create`), and the Anthropic SDK refuses non-streaming requests above
roughly 21333 output tokens. Tripling 8192 to 24576 would therefore break the call outright. 20000
sits under the ceiling and, because D-2 keeps the echoed text scalar, gives ~2.4x headroom on a
payload that grows by less than 3x. Record the 21333 ceiling in a comment so nobody "fixes" it upward.

**D-4 — Fail loudly on truncation.** Tripling the output makes a `max_tokens` cut-off realistic for
the first time. Check `message.stop_reason == "max_tokens"` and fail the run with an explicit message.
Without this the JSON is merely invalid and the operator gets a generic parse error that looks like a
model defect rather than a budget one.
</design_decisions>
