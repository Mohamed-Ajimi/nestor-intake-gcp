## THE GREP — what to read after deploy

### Exact event names

| event name | when |
|---|---|
| `run_heartbeat_started` | once, at `_heartbeat_loop` entry, before the first sleep |
| `run_heartbeat` | every iteration, after the UPDATE executes — carries `rowcount` |
| `run_heartbeat_failed` | pre-existing; only on a raised exception |

structlog is **never configured** in this codebase (no `structlog.configure` call anywhere
in `tribunal/`), so it renders with the default `ConsoleRenderer` to stdout and Cloud
Logging receives it as **`textPayload`**, not `jsonPayload`. The literal shape is:

```
2026-09-09 01:30:37 [info     ] run_heartbeat_started          interval_s=30.0 run_id=abc wid=host-1-deadbeef
2026-09-09 01:30:37 [info     ] run_heartbeat                  rowcount=1 run_id=abc wid=host-1-deadbeef
2026-09-09 01:30:37 [info     ] run_heartbeat                  rowcount=0 run_id=abc wid=host-1-deadbeef
```

⚠ **SUBSTRING TRAP.** `run_heartbeat` is a substring of both `run_heartbeat_started` and
`run_heartbeat_failed`. A grep for `run_heartbeat` matches all three and will make an empty
result look non-empty. **Disambiguate on `rowcount=`** — only the per-iteration line has it.

### The command an operator should run

```bash
export GOOGLE_PROJECT=project-cb01b861-cb4a-438d-b9a   # verify with: gcloud config get account
                                                       # expect tools@dotto.be

# (1) Pull the window. Widen --limit if the run is long; the diagnostic emits ~2 lines/min
#     per run, ~8/min at NESTOR_WORKER_RUN_CONCURRENCY=4.
gcloud logging read \
  'resource.type="cloud_run_revision"
   AND resource.labels.service_name="tribunal-worker"
   AND timestamp>="2026-09-09T00:00:00Z"' \
  --project="$GOOGLE_PROJECT" --limit=2000 --order=asc \
  --format="value(timestamp,textPayload)" > hb.txt

# (2) Score it. Run all four — a zero count is a finding, not an absence of one.
grep -c "run_heartbeat_started" hb.txt                       # entry lines (task created?)
grep    "rowcount=" hb.txt | grep -c "rowcount=1"            # heartbeats that MATCHED
grep    "rowcount=" hb.txt | grep -c "rowcount=0"            # heartbeats that matched NOTHING
grep -c "run_heartbeat_failed" hb.txt                        # the loop raising
```

### The four-outcome reading table

| after deploy | reading |
|---|---|
| `run_heartbeat_started` **+** `run_heartbeat rowcount=1` | heartbeat healthy — cause is elsewhere |
| `run_heartbeat_started` but **no** `run_heartbeat` lines | task **starved** — the event loop never gives it a turn |
| `run_heartbeat` lines with `rowcount=0` | the UPDATE's WHERE clause does not match — a silent no-op the code never reports |
| **neither** line | the task was never created |

**One refinement to that table, discovered while reading the code — read the TIMESTAMPS,
not only the counts.** A fifth outcome hides inside row 2: the loop could emit N
`run_heartbeat` lines and then stop dead. That is *not* starvation — it is the task dying.
`except Exception` deliberately does not catch `BaseException`, so a `CancelledError` or a
`GeneratorExit` reaching the loop kills it permanently, writes no `run_heartbeat_failed`,
and is then swallowed a second time by `execute_run`'s
`finally: with contextlib.suppress(asyncio.CancelledError)`. Counts alone fold that case
into "starved". So also check:

```bash
# Do the run_heartbeat lines STOP, or are they merely sparse?
grep "rowcount=" hb.txt | awk '{print $1}' | tail -5    # last 5 heartbeat timestamps
```

If they stop cleanly early in the run and never resume, the task **died**; if they are
spread thin across the whole run, it is **starved**. Those two need different fixes.

## The STOPGAP marker, and the condition for reverting it

`NESTOR_WORKER_STALE_MINUTES=90` in `deploy-worker.sh` is a **STOPGAP**, marked as such in
the file with a ⚠ block, in the commit message, and here. It is **not** a tuning
improvement and **not** permanent.

**Why 90:**
* While the heartbeat does not land, this value is **effectively the maximum length of a
  healthy run** — past it a live run is reclaimed and restarted from the top of the
  pipeline, re-billing the ~$25–45 it already spent.
* 60 is SHORTER than 64.2 minutes, the longest run that has ever completed normally
  (`7dcf51d5` — the same figure `RUN_TIMEOUT_MINUTES` is derived from at
  `worker.py:120-140` and quoted in `_timeout_message()`). The shipped setting would reset
  the longest known good run, and on 2026-09-08 it did exactly that to two healthy ones.
* 90 clears 64.2 by ~26 minutes and stays **strictly below**
  `NESTOR_WORKER_RUN_TIMEOUT_MINUTES=120`, so the run-level ceiling and the stale reclaim
  cannot tie or race. 120 was NOT used because it ties the ceiling.

**REVERT CONDITION — revert to 60 when, and only when:** production logs show
`run_heartbeat` lines with `rowcount=1` arriving at roughly the
`HEARTBEAT_INTERVAL_SECONDS=30` cadence for the whole length of a run. With a working
heartbeat a live run never goes stale at **any** value, so 60 is correct in principle and
gives the fastest recovery of a genuinely dead worker. 90 only buys headroom while we wait.

The **code default stays 60** at `worker.py:91` — confirmed unchanged, see below. The
deploy sets the value explicitly; changing the default would invalidate the 120× ratio
arithmetic in the comment above `HEARTBEAT_INTERVAL_SECONDS`.

## Hypothesis about the root cause — WRITTEN, NOT IMPLEMENTED

Per the plan's hard constraint, nothing below was acted on. Recording it so the next
session does not re-derive it.

**What the code review rules OUT:**

* **Not "the task was never created" via a second dispatch path.** There is exactly one.
  `worker_loop` → `_dispatch_one` → `runs/execute.py::execute_run_locked` → (lazy import)
  `worker.execute_run`, and the heartbeat `create_task` sits inside `execute_run` before
  the engine await. There is no alternate route that skips it.
* **Not a `worker_id` mismatch introduced by the fencing token.** `_CONSUME_CLAIM_SQL`
  bumps `started_at` only; it never touches `worker_id` or `heartbeat_at`. That also
  explains the observed arithmetic exactly: `COALESCE(heartbeat_at, started_at)` picks the
  non-null `heartbeat_at` stamped by `CLAIM_SQL`, so the reclaim fires 60 min after
  **claim**, which is the measured +3600.20s.
* **Not the SQL or its binds.** Now proven three ways: `_heartbeat_once` (pre-existing),
  and my new live loop test, both give the owner `rowcount=1` against a migrated schema.

**Leading hypothesis — the loop DIES rather than being starved.** `except Exception` does
not catch `BaseException`. Any `CancelledError` or `GeneratorExit` reaching
`_heartbeat_loop` terminates it permanently and **silently**: no `run_heartbeat_failed`
(the handler never sees it), and `execute_run`'s
`finally: _hb.cancel(); with contextlib.suppress(asyncio.CancelledError): await _hb`
swallows the corpse on the way out. This fits every observed fact — zero writes, zero
failure lines, both runs otherwise healthy and progressing — better than starvation does,
because a merely starved loop would still land *some* of 120 due heartbeats across 60
minutes, and we saw exactly zero.

**Second hypothesis — event-loop starvation by synchronous work.** `google-cloud-storage`
2.19.0 is a **synchronous** client. If audit-blob uploads run on the loop thread without
`run_in_executor`, at `NESTOR_WORKER_RUN_CONCURRENCY=4` with hundreds of audited LLM calls
the loop could be blocked for long stretches. `worker.py`'s own `RUN_TIMEOUT_MINUTES`
comment already warns that a hang inside a synchronous call or a C extension never yields.
I rate this second because it should have produced *sparse* heartbeats, not zero.

**These two are distinguished by the timestamp check in the grep section above, not by the
counts.** Do that check first.
