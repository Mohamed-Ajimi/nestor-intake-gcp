# 260909-168 — Heartbeat rowcount diagnostic + stale window 60 → 90 (STOPGAP)

**Defect:** DEF-23.3-01 — the run liveness heartbeat never lands, so healthy runs are
reclaimed as "dead" at exactly 60 minutes and restarted from the top of the pipeline.

This task does **NOT fix** the heartbeat. We do not yet know which of three causes it is,
and guessing would burn another hour of production evidence. Task 1 makes the cause
observable; Task 2 buys headroom while we wait for that evidence.

## Measured evidence — do NOT re-derive

Production, 2026-09-08, two concurrent runs:

```
21:21:14.014  run_claimed                     53afdc83-90fa-4ea5-bce5-8d6842dc8036
21:21:14.149  run_claimed                     6c762dc7-4733-40b1-b329-290886e36439
22:21:14.215  run_reclaimed_from_dead_worker  53afdc83  reclaim_count=1 max_reclaims=2
22:21:14.367  run_reclaimed_from_dead_worker  6c762dc7  reclaim_count=1 max_reclaims=2
```

Claim **+3600.20s** and **+3600.22s** — the same 200 ms offset on both runs.

Staleness is `COALESCE(heartbeat_at, started_at) < NOW() - make_interval(mins => :stale)`
and `CLAIM_SQL` stamps `heartbeat_at = NOW()`. Firing at *exactly* 3600 s therefore proves
`heartbeat_at` never moved after the claim — **zero** writes in 60 minutes on either run,
where ~120 were due at `HEARTBEAT_INTERVAL_SECONDS=30`. A single landed heartbeat would
have shifted the deadline and knocked the two runs off that identical offset.

Also established:
* **Zero** `run_heartbeat_failed` lines — the loop is not raising.
* `NESTOR_WORKER_HEARTBEAT_S` is unset on the live service → default 30. Not config.
* Both runs were healthy and in final report assembly when they were reset.
* `tests/test_run_ownership_fence.py::owner_heartbeat_advances_heartbeat_at` passes against
  a real Postgres, so the SQL and its binds are not obviously broken in isolation. That
  weakens the zero-rows theory but does not settle it — production runs at
  `NESTOR_WORKER_RUN_CONCURRENCY=4` under real engine load, the test does not.

## The four outcomes this must distinguish

| after deploy | reading |
|---|---|
| `run_heartbeat_started` **+** `run_heartbeat rowcount=1` | heartbeat healthy — cause is elsewhere |
| `run_heartbeat_started` but **no** `run_heartbeat` lines | task **starved** — the event loop never gives it a turn |
| `run_heartbeat` lines with `rowcount=0` | the UPDATE's WHERE clause does not match — a silent no-op the code never reports |
| **neither** line | the task was never created |

## Task 1 — make the heartbeat's outcome observable

**File:** `tribunal/nestor_pulse_sdk/runs/worker.py`, `_heartbeat_loop` (~lines 286–297)

Current body awaits `session.execute(_HEARTBEAT_SQL, ...)` and **discards the result**; the
only log is the `except Exception` warning. Add:

* **(a)** one line at loop entry, BEFORE `while True`:
  `log.info("run_heartbeat_started", run_id=str(run_id), wid=WORKER_ID, interval_s=HEARTBEAT_INTERVAL_SECONDS)`
* **(b)** capture the result and log EVERY iteration:
  `log.info("run_heartbeat", run_id=str(run_id), rowcount=result.rowcount, wid=WORKER_ID)`

Log the rowcount INSIDE the `try`, after the execute, but note it must be read while the
`session.begin()` block is still open or immediately after — `CursorResult.rowcount` for an
UPDATE is available as soon as the statement executes.

Volume is ~2 lines/min/run at concurrency 4 → ~8/min. Acceptable for a diagnostic.

**Hard constraints:**
* Keep the exception-swallow contract EXACTLY as-is. A liveness write must never break the
  run it reports on. `asyncio.CancelledError` derives from `BaseException`, so `except
  Exception` must NOT be widened — that is what lets the `finally` cancel this task.
* Do NOT change `_HEARTBEAT_SQL`, the D-23.1-06 ownership fence (`worker_id = :wid` bound to
  the module `WORKER_ID`, never to `claimed["worker_id"]`), the `status = 'running'` guard,
  or any bind value.
* **This task adds observability ONLY.** It must not attempt a fix. If you think you see the
  bug, write it in the SUMMARY — do not change behaviour.

**Do not confuse this with a different heartbeat.** `tests/test_own_researcher.py:1288`
records that a *strided polling* heartbeat was REMOVED on operator request 2026-08-31.
That is the own-researcher poll log, unrelated to run liveness. Leave it removed.

## Task 2 — widen the stale window 60 → 90 (STOPGAP)

**File:** `tribunal/infrastructure/cloud-run/deploy-worker.sh` — line 250 inside
`--set-env-vars`, the comment at line 51, and any nearby doc line stating 60.

`NESTOR_WORKER_STALE_MINUTES=60` → `90`.

Record this rationale in the code comment AND the SUMMARY:

* While the heartbeat is not landing, this value is **effectively the maximum length of a
  healthy run**.
* 60 is SHORTER than the longest run that has ever finished normally — 64.2 min (run
  `7dcf51d5`, the figure already quoted at `worker.py` `RUN_TIMEOUT_MINUTES` and in
  `_timeout_message()`). The current setting would reset the longest known good run.
* 90 clears that by ~26 minutes and stays **strictly below** `NESTOR_WORKER_RUN_TIMEOUT_MINUTES=120`,
  so the run-level ceiling and the stale reclaim cannot tie or race.
* ⚠ **STOPGAP.** Revert to 60 once the heartbeat is proven to land. With a working
  heartbeat a live run never goes stale at any value, so 60 is correct in principle and
  gives the fastest recovery of a genuinely dead worker. This is not a tuning improvement.

Do NOT set 120 (ties the ceiling). Do NOT change `RUN_TIMEOUT_MINUTES`.

**Leave `STALE_RUN_MINUTES = int(os.environ.get(..., "60"))` at `worker.py:91` UNCHANGED** —
the deploy sets it explicitly, and changing the default would invalidate the ratio
arithmetic in the comment at lines 96–99. If you touch that comment block at all, keep its
warning intact.
