# 260909-3ow — Run the worker under ONE module identity so every fenced write matches

**Defect:** DEF-23.3-01 ROOT CAUSE (supersedes the heartbeat-only framing of `260909-168`).

## The cause — measured 2026-09-09 00:39Z on run `9b79e10f`, do NOT re-derive

```
Dockerfile:36   CMD ["python", "-m", "nestor_pulse_sdk.runs.worker"]
```

`-m` executes `worker.py` as `__main__`. At import it evaluates
`WORKER_ID = f"{hostname}-{pid}-{uuid4().hex[:8]}"` → e.g. `localhost-1-d35c5630`. That copy runs
`worker_loop` and `claim_one`, so `CLAIM_SQL` stamps `run.worker_id = d35c5630`.

Dispatch then goes `_dispatch_one` → `execute.py::execute_run_locked` → **`execute.py:135`**:

```python
from nestor_pulse_sdk.runs.worker import execute_run   # lazy, "to avoid a circular import"
```

Python does not know `__main__` IS that module, so `worker.py` is imported a SECOND time under its
canonical name — a second module object, a second `uuid4()` → `localhost-1-cbcd49a4`.
`execute_run` and `_heartbeat_loop` live in that second copy and bind `wid = cbcd49a4`.

Observed on the live revision `tribunal-worker-20260908-233038-013724`:

```
worker_started          worker_id=localhost-1-d35c5630     (instance 00a41e8c1d9656…)
run_claimed             run_id=9b79e10f                    (same instance)
run_heartbeat_started   wid=localhost-1-cbcd49a4           (same instance)
run_heartbeat           rowcount=0  wid=localhost-1-cbcd49a4  — every 30 s, for 55+ minutes
```

**Same process, two `WORKER_ID`s.** The row says `d35c5630`; every fenced statement says
`cbcd49a4`; `WHERE worker_id = :wid` matches zero rows.

## Why this is bigger than the heartbeat

Every D-23.1-06 ownership-fenced write in `execute_run` uses the module constant from the SECOND
copy: the heartbeat, the `needs_input` park, the `needs_report_spec` park, the success finalize,
the failure write. **All match zero rows.** The report-body INSERT is gated on `completed.rowcount`,
so a run can finish perfectly and the worker cannot record it — the report is discarded, silently.
The 2026-09-08 "finished report thrown away" was THIS, not the reclaim. Since the fence shipped on
the worker (`20260907-161728`) no run has been able to complete. The consume step in `execute.py`
passes only because it binds `claimed["worker_id"]` — the value FROM THE ROW — not the constant.

## The fix — one identity, structurally

**Primary:** never run `worker.py` as `__main__`. Add a launcher and point the container at it.

**Task 1 — launcher + alias**

* NEW `tribunal/nestor_pulse_sdk/runs/worker_main.py`:
  ```python
  """Container entrypoint. Exists so `worker.py` is only ever imported under its canonical
  name — running it via `python -m nestor_pulse_sdk.runs.worker` made it `__main__`, and
  execute.py's lazy `from nestor_pulse_sdk.runs.worker import execute_run` then loaded a
  SECOND copy with a SECOND `WORKER_ID`, so every ownership-fenced write matched zero rows
  (DEF-23.3-01, 2026-09-09)."""
  from nestor_pulse_sdk.runs.worker import main

  if __name__ == "__main__":
      main()
  ```
* `infrastructure/cloud-run/worker/Dockerfile:36` → `CMD ["python", "-m", "nestor_pulse_sdk.runs.worker_main"]`,
  and the comment at line 5.
* **Belt-and-braces in `worker.py`'s `if __name__ == "__main__":` block**, BEFORE `main()`:
  ```python
  import sys
  sys.modules.setdefault("nestor_pulse_sdk.runs.worker", sys.modules[__name__])
  ```
  so the OLD invocation (`-m nestor_pulse_sdk.runs.worker`, still used locally) can no longer
  double-import either. Update the `main()` docstring at `worker.py:1087` to name the launcher.
* Do NOT remove or "fix" `execute.py:135`'s lazy import. The cycle is real; the launcher makes it
  harmless. Restructuring the import graph is out of scope.
