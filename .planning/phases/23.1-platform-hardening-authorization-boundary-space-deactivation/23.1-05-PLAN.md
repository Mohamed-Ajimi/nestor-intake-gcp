<objective>
Close D-23.1-06. `23.1-CONTEXT.md` § 4 verified that a fencing token DOES exist —
`execute.py:88` `_CONSUME_CLAIM_SQL` gates on `worker_id = :wid AND started_at = :token` under
a per-run advisory lock, making a claim dispatch at-most-once — but that two writes escaped it:

- `worker.py:198` `_HEARTBEAT_SQL` gates on `status='running'` only. A displaced-but-alive
  worker keeps asserting liveness on a run it no longer owns, which suppresses the very
  reclaim that is supposed to rescue the run.
- `worker.py:565` (success) and the failure twin below it gate on `status='running'` only, so
  a displaced worker can stamp a terminal status, a report `Output` and a rejected-claims
  `Output` onto a run the new owner is still executing.

Purpose: this is the difference between "at-most-once dispatch" and "at-most-once dispatch
whose bookkeeping is also fenced". The mitigations that keep this Medium rather than Critical
(`STALE_RUN_MINUTES=60` against a 30s heartbeat = 120 consecutive misses, `MAX_RECLAIMS=2`,
`REAP_SQL`) are exactly the mitigations the un-fenced heartbeat defeats.

Output: one extra predicate on three UPDATE statements, and a LIVE test file that proves each
of them matches zero rows for a displaced worker and one row for the real owner.

## THE PARAMETER TO BIND, AND WHY IT IS THE MODULE GLOBAL

Bind `:wid` to the module-level `WORKER_ID` — "this process" — and NOT to
`claimed["worker_id"]`. At claim time the two are equal, so a test that only exercises the
happy path cannot tell them apart. They diverge exactly where it matters: after a stale
reclaim the ROW's `worker_id` is the new owner's, and `claimed["worker_id"]` is a stale copy
this process is still carrying in memory. Fencing against the stale copy fences against
nothing. Write a comment saying this at each of the three sites — it is the single way this
fix can be silently undone by a later reader "simplifying" it.

## WHAT THIS PLAN MUST NOT DO

- **Do NOT remove the `status = 'running'` clause anywhere.** D-23.1-06 says both, not one.
  That clause is what lets a user cancel end the heartbeat and win over a late terminal write;
  the `worker.py:194-197` comment and the `:571-575` comment both state it, and both must
  survive.
- **Do NOT touch `CLAIM_SQL`, `REAP_SQL`, or `execute.py`'s `_CONSUME_CLAIM_SQL` /
  `_ADVISORY_LOCK_SQL`.** They are correct. `execute.py` belongs to plan 23.1-06 in this same
  wave — editing it here is a merge conflict AND a scope violation.
- **Do NOT add a `started_at` fence to the heartbeat.** `_CONSUME_CLAIM_SQL` bumps
  `started_at = NOW()` on consume, so the claim token the worker holds is stale by
  construction the moment execution begins. `worker_id` is the durable ownership fact.
- **Do NOT change `MAX_RECLAIMS`, `STALE_RUN_MINUTES`, `HEARTBEAT_INTERVAL_SECONDS`** or any
  env-var default. This plan changes SQL predicates and nothing else.
- **Do NOT trigger a run.** ZERO provider spend. The tests drive the DB and a stubbed engine.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker process -> run row | Two worker processes may believe they own the same run after a stale reclaim |
| worker process -> output table | A terminal write also writes the report body and the rejected-claims ledger a human will read |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23.1-16 | Spoofing | a displaced worker asserting liveness for a run it lost | mitigate | `AND worker_id = :wid` on `_HEARTBEAT_SQL`, bound to the module `WORKER_ID`; LIVE displaced test asserts `heartbeat_at` unchanged |
| T-23.1-17 | Tampering | a displaced worker stamping a terminal status over the real owner's run | mitigate | `AND worker_id = :wid` on both terminal UPDATEs; LIVE displaced tests assert status and `error_message` unchanged |
| T-23.1-18 | Repudiation | two `Output` rows for one run, so the audit chain has two report bodies | mitigate | The `completed.rowcount` gate now inherits the fence; the displaced test counts `Output` rows before and after |
| T-23.1-19 | Denial of Service | dropping `status='running'` while adding the fence, so a cancel no longer wins | mitigate | Every shape test asserts BOTH clauses separately; the cancelled LIVE tests are kept |
| T-23.1-20 | Elevation of Privilege (cost) | a run executed twice at full paid cost | transfer | Out of scope: CONTEXT § 4 notes nothing re-checks the fence DURING execution. This plan fences the WRITES, not the execution. Record it as a deferred item; do not silently claim it is closed |
