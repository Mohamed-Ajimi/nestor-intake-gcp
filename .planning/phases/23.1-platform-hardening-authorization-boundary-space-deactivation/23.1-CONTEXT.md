## 4. VERIFIED — tribunal run ownership

A fencing token DOES exist and the audit missed it: `execute.py:88` `_CONSUME_CLAIM_SQL`
gates on `worker_id = :wid AND started_at = :token` under a per-run advisory lock
(`execute.py:69`), making a claim dispatch at-most-once. What is missing:

- `worker.py:198` `_HEARTBEAT_SQL` gates on `status='running'` only — **no `worker_id`**. A
  displaced-but-alive worker keeps asserting liveness on a run it no longer owns.
- `worker.py:565` terminal write gates on `status='running'` only — no `worker_id`.
- Nothing re-checks the fence DURING execution, so a reclaimed run can be executed twice at
  full paid cost.

Mitigations already in place (why this is Medium, not Critical): `STALE_RUN_MINUTES=60`
(`deploy-worker.sh:183`) against a 30s heartbeat = 120 consecutive misses required;
`MAX_RECLAIMS=2`; and `REAP_SQL` (`worker.py:240`) fails a run that exhausts recoveries.

### Tribunal API non-idempotency (verified)

- **`GET /{run_id}/report-proposal`** (`runs/api.py:371`) — on a cache miss it calls
  `build_audited_client()` + `build_report_proposal(...)` and INSERTs an `Output`
  (`api.py:405-415`). A **billable, side-effecting GET**. Two concurrent reads = two paid
  calls.
- **`POST /{run_id}/answer`** (`runs/api.py:269`) — reads the run, checks
  `status != "needs_input"` -> 409, THEN writes. Two concurrent callers both pass the check
  and both queue a new run. `idempotency_key=uuid.uuid4()` at `api.py:374` is freshly random
  per row and protects nothing.

## 7. PINNED DECISIONS

- **D-23.1-01** — Promote `_superadmin_gate` out of `research_routes.py` into a shared
  module (`app/auth/gates.py`). `research_routes.py` imports it. Behaviour identical
  (existence-hidden 404) so its existing denial suite stays green untouched. NO per-route
  role-comparison copies — one gate, one convention, one test surface.
- **D-23.1-02** — Apply the gate to exactly the nine verbs in section 1's table, and to
  `ai_router` at the ROUTER level (one dependency, not seven). Section 1's stay-open list is
  a hard non-goal — a test must pin each stay-open route as still reachable by role=`user`.
- **D-23.1-03** — Space deactivation CASCADES inside `deactivate_space`'s existing
  transaction, reusing the per-user machinery at `admin_routes.py:246`. Reactivate gets the
  inverse. **Rejected alternative:** an org-status lookup in `get_current_identity` —
  `dependencies.py` deliberately has no DB call (D-06) and already pays one `get_user`
  round-trip (D-04); a cascade costs zero per request and reuses a tested path.
- **D-23.1-04** — AI dedup is a DB invariant, not an app check: an alembic partial unique
  index on `skill_runs (intake_id, skill) WHERE status='running'`, with
  `create_running_skill_run` translating the IntegrityError into a 409. A pure app-level
  check races.
- **D-23.1-05** — `context_pack` uses a compare-and-swap on the `decomposed` transition
  mirroring `_next_review_status`. On a disallowed source status the SKILL RUN finalizes
  `failed` with a readable message — it must never corrupt the intake lifecycle, and it must
  never leave a `running` row behind.
- **D-23.1-06** — Tribunal: add the `worker_id` clause to `_HEARTBEAT_SQL` and to the
  terminal write. Keep the `status='running'` clause as well; both, not one.
- **D-23.1-07** — `GET /report-proposal` keeps its URL and its on-demand generation (the
  shaping panel depends on it) but wraps generation in the SAME per-run advisory lock
  `execute.py` uses, re-reading the cache UNDER the lock. **Rejected alternative:** moving
  generation to a POST — a breaking API change for a live UI that buys nothing the lock does
  not.
- **D-23.1-08** — `POST /answer` becomes a conditional UPDATE (compare-and-swap on the
  `needs_input` status), not read-then-write.
- **D-23.1-09** — CI widening lands LAST; the red tests are fixed FIRST or the gate lands
  red. **CORRECTED 2026-09-03 — the original environment claim in this decision was FALSE.**
  This machine HAS `Python 3.12.6` at
  `C:\Users\ajimimo\AppData\Local\Programs\Python\Python312\python.exe`, Docker Engine
  29.6.2 running, and `pgvector/pgvector:pg16` + `testcontainers/ryuk:0.8.1` already pulled.
  The full backend suite (integration included) runs locally in ~80s. **Measured baseline at

- **D-23.1-11** (added 2026-09-03, not in the original audit) — Reactivating a space must
  NOT resurrect a member who was deactivated individually. The cascade marks memberships
  `space_deactivated`; reactivate restores only those. No migration: the column is a plain
  String and every membership-status read in `backend/app/` is an allow-list (`== "active"`)
  at five sites, with no deny-list anywhere. That survey is pinned by test.

  **CORRECTED 2026-09-03 — the survey was INCOMPLETE.** There is a SIXTH site,
  `_find_membership` (`auth/session.py:95` and `:108`), and it is not an allow-list at all: it has
  no status predicate whatsoever. See D-23.1-13, which closes it. The five allow-list sites
  are `admin_routes.py:236`, `intake_routes.py:748`, `me_routes.py:123`,
  `admin_repo.py:113`, `admin_repo.py:166`; `admin_routes.py:122` merely surfaces the value
  in a view and carries no logic.
- **D-23.1-13** (added 2026-09-03, found while verifying D-23.1-11 — NOT in the audit and
  NOT in the plans as committed at `2ca7336`) — **`_find_membership` filters on NO status.**
  Verified at `backend/app/auth/session.py` (the two `.where()` clauses at `:95` and `:108`): both arms (the `provider_user_id` match
  and the `email` match) select `OrganizationMembership` with no status predicate. So
  login-sync will mint claims for a `deactivated` OR `space_deactivated` membership, and the
  ONLY thing preventing that today is the IdP-side `disabled=True` + `revoke_refresh_tokens`.

  This is pre-existing (it applies to the per-user path already) but it becomes materially
  more dangerous with D-23.1-03's cascade: the cascade makes **N IdP calls for N members**,
  and a partial failure leaves the DB saying `space_deactivated` while those members can
  still authenticate and have claims minted. The IdP call becomes load-bearing for the whole
  space instead of one user.

  **Fix: add `status == "active"` to both arms of `_find_membership`**, making the DB a
  backstop rather than trusting the IdP round-trip alone. One line per arm, defense in depth,
  and it is what makes the cascade safe under partial failure. It also must NOT change the
  existing `SyncResult.NO_MEMBERSHIP` -> 403 contract for a user with no row at all.

  **THE EXACT WINDOW (traced 2026-09-03).** `auth_routes.py:99` calls
  `sync_claims_from_membership(decoded)`, and per its docstring at `session.py:60-70` that
  function **short-circuits with NO DB READ AT ALL** when the token already carries a role
  (`ALREADY_SYNCED`). So the missing filter bites in exactly one window: a token WITHOUT
  baked-in claims requesting a sync. That window IS the partial-cascade-failure scenario —
  DB says `space_deactivated`, the IdP disable did not land for that member, their
  still-valid ID token hits `/auth/session`, and `_find_membership` returns the row and
  mints fresh `role` + `space_id` claims for someone the operator just cut off. A test that
  only exercises the happy path proves nothing about this.

  **This is a SIXTH membership-status site, and D-23.1-11's survey missed it.** It is not a
  deny-list gap like the other five — it is a **no-list**: no status predicate at all, which
  is strictly worse. Correct that sentence wherever it appears.

  history is recorded here because this line flip-flopped three times and a future reader

  The one substantive argument for a standalone plan — that the fall-through change below

  **THE UID ARM IS AN EARLY RETURN — adding the predicate CHANGES FALL-THROUGH.** Found at

  deactivated uid row short-circuits and the email arm never runs. Once the predicate lands,
  the uid query returns `None` and control FALLS THROUGH to the email arm — so a user with a
  deactivated uid row AND a separate ACTIVE email row is now admitted where they were
  previously refused.

  **Ruled: KEEP the fall-through**, and pin it with a test. It is correct: that active email

  arm so a self-registered address cannot walk in. Note in the plan that the PRE-FIX
  behaviour was ALSO wrong — it minted claims from the deactivated row — so this is not a
  loosening; both paths were broken and this one is now right.

  **Consequence of the `admin_routes.py:236` interaction, to be kept verbatim in the code

## 10. ACCEPTED DEFERRALS AND ONE TRANSFERRED RISK (recorded 2026-09-03, at planning time)

- **DEF-23.1-01 — dropping `rehype-raw` costs two badges.** `BattlecardMarkdown.tsx`

- **DEF-23.1-02 — frontend lint is NOT a CI gate this phase.** Measured at HEAD:
  `npm run lint` is red with 61 errors + 38 warnings on an LF checkout (54 `no-explicit-any`,
  4 `no-empty`, 2 `prefer-const`, 1 prettier), plus ~29,300 CRLF artifacts on this machine

  `tsc` + `vitest` (both green: tsc clean, 140 tests passing) and deliberately omits lint.
  A lint-cleanup phase should be scheduled separately.
- **T-23.1-20 — TRANSFERRED, not mitigated.** Section 4 notes that nothing re-checks the
  fence DURING execution, so a reclaimed run can still be executed twice at full cost. This
  phase fences the WRITES (heartbeat + terminal), not the execution. No acceptance criterion
  in this phase may imply otherwise. Booked as a deferred item in the threat register.
- **Tribunal suite is not reliably runnable locally.** Full local run: 178 failed / 2273
  passed / 13 errors, order-dependent, several failing with `role "worker_user" does not
  exist`. Tribunal plans therefore measure PER-FILE deltas against a baseline the executor
  records first; `tribunal/cloudbuild.test.yaml` is authoritative and the operator runs it.
