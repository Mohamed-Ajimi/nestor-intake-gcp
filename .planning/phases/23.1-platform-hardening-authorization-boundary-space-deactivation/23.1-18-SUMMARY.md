# Phase 23.1 Plan 18: Gate the Research SSE Stream Summary

`GET /intakes/{intake_id}/research/stream` — the last ungated route on `research_router` —
is now superadmin-only, closing the authorization boundary at **11 of 11**, proved by
walking the live router's resolved dependency tree rather than by grep.

**Commit:** `45e6196` — `fix(23.1-18): gate the research SSE stream — the router is now 11 of 11`

## What was wrong

The route took a bare `Depends(get_current_identity)`. It is a READ, not a spend, but what
it reads is the operator's diagnostic frame: the run id, the engine's `current_stage` /
`stage_detail` trace, `cost_usd_total`, the Phase-17 chain-guard state (`chain_status` /
`chain_broken_at` / `bundle_key`) and the 15.3-06 run-event cursor `event_seq`.

`D-23.1-16` excluded it on the grounds that "it is SSE, an `EventSource` cannot set an
Authorization header, so gating it blind could break the live run feed". **That premise is
false for this codebase.** Re-verified independently here, not taken on the addendum's word:

| Claim | Verification | Result |
|-------|--------------|--------|
| No `EventSource` anywhere | `grep -rn "EventSource" frontend/src \| wc -l` | **0** |
| The stream carries a Bearer header | `frontend/src/lib/api/research.ts:566-577` | `fetch(apiUrl(...), { headers: { Authorization: \`Bearer ${token}\` } })`, token from `currentIdToken()` — the same source `apiFetch` uses |
| Admin-only mount points | `grep -rln "openResearchStream" frontend/src` + route grep | `ResearchRunProgress.tsx`, mounted only from `admin.pulse.intakes.$id.tsx` and `admin.pulse.runs.$runId.index.tsx` |

A bonus the client already handles: `openResearchStream` treats **404 as expected** and
degrades to a bounded poll (`research.ts` fallback arm), so the gate produces the response
shape the caller was already written for.

## Measured RED — what the ungated route actually did

Measured with a throwaway probe against live Postgres (deleted after measuring), seeding one
space + one `in_research` intake + one `completed` `research_runs` row:

```
RED [role=user OWN space]  status=200  content-type='text/event-stream; charset=utf-8'
   frames=1
   first={"id": "8f297bc4-...", "status": "completed", "current_stage": null,
          "stage_detail": null, "cost_usd_total": null, "started_at": null,
          "completed_at": null, "error_message": null, "chain_status": null,
          "chain_broken_at": null, "bundle_key": null, "event_seq": null}

RED [role=user NULL space] status=403  content-type='application/json'
   frames=0
   raw=b'{"detail":"No space \xe2\x80\x94 not authorized"}\n'
```

So: **a role=`user` in the intake's own space received the complete operator frame**, and a
null-space caller received an existence oracle telling them the endpoint is real.

The same RED was then re-observed through the committed suite (`test_research_stream_gate.py`,
pre-fix): `2 failed, 1 passed, 1 deselected` — the two denial arms red, the counterweight
green, which is the correct RED shape (the positive arm must pass before AND after).

## After the fix — both denials are EXACTLY 404

| Caller | Before | After |
|--------|--------|-------|
| role=`user`, intake's OWN space | `200 text/event-stream` + full frame | **`404 {"detail":"Intake not found"}`**, JSON content-type, zero `data:` frames |
| role=`user`, `space_id=None` | `403 {"detail":"No space — not authorized"}` | **`404 {"detail":"Intake not found"}`** |

Both asserted byte-exact on the detail string, and both additionally assert the response is
*not* `text/event-stream` and contains no `data:` frame — a 404 that still opened a stream
would be a different bug.

## The change

`backend/app/api/research_routes.py`:

```python
async def stream_research_run(
    intake_id: str,
    request: Request,
    identity: Identity = Depends(_superadmin_gate),   # was Depends(get_current_identity)
) -> StreamingResponse:
```

**On ordering.** The instruction was to declare the gate before `get_tenant_repo` *if that
dependency is present*. It is not — this signature has no repo at all; the handler reaches
the DB through `stream_session`'s scoped helpers. So there is nothing to order against. What
still does the work is the gate being a **dependency**: FastAPI resolves dependencies before
the handler body runs, so the gate's 404 pre-empts the in-body pre-flight's null-space 403.
That is recorded in a comment on the parameter so a future reader does not conclude the
ordering rule was forgotten.

**The pre-flight was kept, not deleted.** `check_intake_in_scope`'s `PermissionError → 403` /
falsy → 404 arms are still in the body. They are defence in depth now rather than the outer
wall — and the 404 arm is still live: it is what answers a *superadmin* asking about an
intake that does not exist.

**`get_current_identity` is no longer imported** by `research_routes.py` — no route uses it
directly any more. The identity is still verified on every call, one level down, because
`superadmin_gate` itself depends on it. A comment at the old import site says so, and the
walk below confirms it empirically (`IDENT=yes` on all eleven).

## The ordering guard: 10 → 11, and a new completeness check

`test_every_gated_research_route_resolves_the_gate_before_the_repo` was raised **10 → 11**,
never relaxed to `>=`. Its comment claimed 10-of-11 was the ceiling "because the eleventh is
`stream_research_run` ... an `EventSource` cannot set an Authorization header — a known gap,
not an oversight repeated". That comment is now false twice over and was rewritten to record
both the new count and the fact that the SSE rationale was wrong.

Rewriting it exposed a real limitation, so a second test was added rather than left implicit:

> **The count guard cannot catch a new ungated route.** It counts routes that *do* resolve
> the gate. A twelfth route added to `research_router` without a gate leaves `checked` at 11
> and passes. The count catches the gate *breaking*; it does not catch a new hole — which is
> exactly the failure mode D-23.1-16 was (`research_routes.py` surveyed by eye, one route
> missed, ~$45 a call).

`test_every_research_route_is_gated` closes that: it computes the ungated set from the
router's own route list, so a new ungated verb fails by construction. It is non-vacuous —
at the base commit `stream_research_run` made it false — and it pins `total == 11` so it
cannot go vacuously true on an empty router.

## The superadmin stream still works — proved on the frame, not the status line

This is the half that mattered most: the run feed is a live operator feature. Two positive
arms, because one was not enough.

**`test_stream_superadmin_still_streams`** — asserts 200 *and* `text/event-stream` *and* that
the yielded frame is **the seeded run**: `frame["id"] == str(run_id)`, `status == "completed"`,
and the seeded `current_stage == "finalize"` came back. A "200 with an empty body" cannot pass.
It also asserts the full RUN-01 / RUN-03 / 15.3-06 wire shape survived the gate
(`stage_detail`, `cost_usd_total`, `chain_status`, `bundle_key`, `event_seq` all present).

**`test_stream_superadmin_emits_on_change`** — the snapshot alone would still pass if the
*per-tick* scoped read had stopped working under the gated identity, because the handler
would simply close. So this arm seeds a **non-terminal** `running` run, lets the snapshot
emit, mutates the row mid-stream, and requires a **second, different** frame carrying the new
status before the terminal close: `len(payloads) >= 2`, `payloads[0]["status"] == "running"`,
`payloads[-1]["status"] == "completed"`, `payloads[-1] != payloads[0]`.

That second test was rewritten once. The first version consumed `resp.iter_lines()`
incrementally to interleave the DB flip, and **hung for the full 10-minute
`MAX_STREAM_SECONDS`** — httpx did not hand back the first SSE line mid-stream under
`TestClient`. The fix is not a sleep-and-hope race: `read_latest_research_run_dict` is wrapped
in a **counting pass-through** (it still calls the real helper — nothing about the read is
stubbed) and the flipping thread waits on the first call, so the ordering is deterministic;
the body is then drained after close with the existing `_data_payloads`. Runs in ~10s.

## Pre-existing tests converted — fixture only, no assertion weakened

**Two SSE cases in `test_research_routes.py`** (flagged in the brief): `_user(space)` →
`_superadmin()` plus the `superadmin_engine` fixture and `_patch_superadmin_engine`, exactly
as plan 17 converted the eight trigger cases, including D-05's both-namespaces requirement
(`session.py` and `ai_session.py`). Not one assertion changed — those cases exist to pin the
RESEARCH terminal set (`completed` / `cancelled`, never the skill-run success vocabulary) and
they still pin exactly that. The file's module docstring and `_superadmin()` docstring both
claimed "the SSE-stream cases deliberately keep `_user` because `stream_research_run` is NOT
gated"; both were rewritten.

**A THIRD case the brief did not list — and it had pinned the defect as correct behaviour.**
`test_research_cross_tenant.py::test_stream_null_space_403` asserted
`r.status_code == 403` for a null-space user on this exact route, with the message
"null-space user must be default-denied 403 on the pre-flight". It went red on the gate.

That is the "a pre-existing test pinned the defect as expected behaviour" trap, and the wrong
move would have been to relax the new gate to keep it green. It was **strengthened** instead:
renamed to `test_stream_null_space_404`, asserting the existence-hidden 404 plus the
byte-exact detail. The justification is in the file and is not novel — the two sibling rows
in the *same file*, `resume_null_space_404` and `cancel_null_space_404`, have asserted exactly
this since their routes were gated. This row was the one exception; it now matches.

A fourth, `test_stream_cross_tenant_404`, stayed green and its assertion was left untouched —
but its docstring claimed the 404 is "raised pre-stream" by the tenant pre-flight, which is no
longer which wall answers. A mechanism note was added rather than leaving a stale claim.

## Zero provider spend

No research run was triggered. `research_routes.run_poll_driver` is replaced by a recorder in
**every** test in the new file, and every test asserts the recorder stayed empty. The stream
is a read and reaches no dispatch today — the recorder is a tripwire, so if a future edit ever
wires a dispatch into the read path, this file fails instead of billing ~$45.
