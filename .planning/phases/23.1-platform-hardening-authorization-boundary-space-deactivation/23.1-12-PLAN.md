## ⚠ PLANNING FINDING — THE MIGRATION MUST RESOLVE EXISTING DUPLICATES FIRST

Neither CONTEXT nor D-23.1-04 mentions this, and it will fail the deploy if you skip it:
**`CREATE UNIQUE INDEX` fails outright if the table already violates it.** The live database
has been running with no such constraint since Phase 7, and `sweep_orphaned_skill_runs`
(`ai_session.py:195`) only runs at app startup and only clears rows older than 30 minutes — so
duplicate `running` rows can and probably do exist.

`upgrade()` must therefore, in this order:
1. Resolve duplicates: for each `(intake_id, skill)` group with more than one `running` row,
   mark all but the NEWEST `created_at` as `failed` with an explanatory `error_message` in the
   register of `sweep_orphaned_skill_runs`' ("superseded by a newer run of the same skill;
   closed when the single-active-run invariant was introduced"). Keep the newest so an actually
   in-flight run is not killed by its own migration.
2. Create the index.

Write the resolution as ONE idempotent SQL statement so a re-run is harmless, and log nothing
to stdout beyond what alembic already prints.

## WHAT THIS PLAN MUST NOT DO

- **Do NOT add an app-level "is one already running?" pre-check.** D-23.1-04 rejects it by
  name: it races. The DB is the arbiter; the app only translates the refusal.
- **Do NOT include `space_id` in the index.** `intake_id` is a UUID primary key of a
  space-owned table, so `(intake_id, skill)` is already globally unambiguous. Adding `space_id`
  would widen the key and weaken the invariant.
- **Do NOT touch `sweep_orphaned_skill_runs`.** It is the D-01a backstop and stays as-is.
- **Do NOT change `_dispatch_skill_run`'s existing 404 / 403 arms.** You are ADDING a third.
- **Do NOT introduce a new RLS policy or grant.** Following 0012/0013's precedent: an index
  added to an already-granted, already-policied table needs no re-grant and no re-policy. State
  that in the docstring the way 0013 does.
