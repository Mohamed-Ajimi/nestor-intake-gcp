## Did the drop need the FORCE-RLS dance? No — and it was checked, not assumed

`skill_runs` carries ENABLE + FORCE ROW LEVEL SECURITY (`0009:194-195`) with the
`skill_runs_space_isolation` policy, and FORCE binds the table OWNER — the role alembic runs
as. That is exactly why 0014 had to lift FORCE around its pre-flight: that statement was a
cross-space `UPDATE`, and a row policy with no `app.current_space_id` GUC set matches ZERO
rows **silently**.

It does not apply to 0015. Row-level security governs **DML** — which rows a
SELECT/INSERT/UPDATE/DELETE may see or touch. `ALTER TABLE ... DROP COLUMN` is **DDL**:
authorised by table ownership, and no row policy is consulted. So `upgrade()` is a bare
`op.drop_column` with no `NO FORCE`/`FORCE` bracket and no `SET row_security` (which, on a
FORCE-RLS table, ERRORS rather than bypasses anyway).

The conclusion was not taken on faith. `test_0015_drops_started_at_from_skill_runs` reads
`information_schema.columns` after a real `alembic upgrade head` against a FORCE-RLS-enabled
database; a drop that had been silently filtered would leave the column visible and turn that
test red. It is green.

## Findings not in the plan

**F1 — `0001_baseline_schema.py:300` must NOT be edited, and the plan does not say so.**
The plan's blast-radius grep lists this hit but gives no instruction about it, and "remove
`started_at` from the schema" invites editing the CREATE. That would be wrong: 0001 is an applied
historical revision, and rewriting it desynchronises every database already past 0001 (including
production) while leaving `alembic_version` claiming the old file's content. The forward revision
is the only correct removal point. Recorded as a decision and in 0015's docstring.

**F2 — the ⛔ operator warning in `infra/DEPLOY-RUNBOOK.md:5790` is now stale.**
It reads *"`skill_runs.started_at` IS A DEAD COLUMN — do not 'improve' this by switching to it"*
and goes on to describe the column as existing-but-unwritten. After 0015 it describes a column
that does not exist. The plan's success criterion says `started_at` must be gone from "the
database, the ORM **and the prose**", so this is arguably in scope; its verification step 4,
however, greps only `backend/`, which this file is outside of. **Not edited** — the execution
brief restricts this plan to its `files_modified` pathspec, and the runbook is an append-only
deploy log where rewriting a past dated entry falsifies history. Logged to `deferred-items.md`
for the team lead to route. The operational advice it gives (use `created_at`) remains correct.

**F3 — `REVISION = "0014"` in `test_ai_dedup.py:68` is dead.**
Only `PREVIOUS_REVISION` is referenced by any assertion; `REVISION` is defined and never used. Not
a defect and not touched (23.1-12's file, no behaviour depends on it), but it is the kind of
constant a later reader will trust as "the revision this file targets" — which, after 0015, it no
longer is. The new section defines its own `REVISION_0015` / `REVISION_0014` rather than mutating it.
