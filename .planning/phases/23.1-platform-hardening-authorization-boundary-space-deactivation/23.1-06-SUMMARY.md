# Phase 23.1 Plan 06: Tribunal Run-API Concurrency + Brief Bound Summary

Two paid, non-idempotent paths on the Tribunal run API closed with the two
different mechanisms each actually needs — a per-run advisory lock plus a cache
re-read *under* it for the billable proposal GET, and a conditional UPDATE as
the admission ticket for the answer verb — plus a 1 MB ceiling on `brief` at the
schema boundary.

---

## What changed

### 1. `GET /{run_id}/report-proposal` — D-23.1-07

`_ADVISORY_LOCK_SQL` in `runs/execute.py` is now the public `ADVISORY_LOCK_SQL`,
one object, imported at module level by `runs/api.py`. `get_report_proposal`
takes that lock immediately after the 404 lookup and **before** the first
`_latest()` read, so the proposal cache is re-read while the lock is held.

The URL, the method and on-demand generation are unchanged. The lock does not
introduce a long-held transaction: `get_db_session` yields inside
`session.begin()`, so this handler already held one transaction across the
`build_report_proposal` await. That is written into the handler docstring so a
later reader does not "fix" it.

`_CONSUME_CLAIM_SQL` and `execute_run_locked`'s behaviour are untouched. The key
expression is unchanged and is asserted **by identity**
(`api_mod.ADVISORY_LOCK_SQL is execute_mod.ADVISORY_LOCK_SQL`), not by eye and
not by string equality.

### 2. `POST /{run_id}/answer` — D-23.1-08

```sql
UPDATE run SET status = 'cancelled', completed_at = NOW()
 WHERE id = :id AND status = 'needs_input'
RETURNING id
```

The cancel is the ticket; the replacement child is what the ticket buys — the
inverse of the old order. The initial `select(Run)` is kept for the 404 and for
`brief` / `engine` / `project_id` / `comparison_id`, and the handler docstring
says explicitly that it reads for DATA while the CAS decides ADMISSION.

- Single branch: zero matched rows → the existing
  `HTTPException(409, "run is not awaiting clarification")`.
- Comparison branch: one CAS per answered paused sibling; a sibling whose CAS
  matches nothing is skipped, not fatal — the per-engine contract is preserved.
- `idempotency_key=uuid.uuid4()` left exactly as it was, with a comment at both
  sites saying it protects nothing here and that `POST /runs/compare` derives
  its children's keys deterministically, so changing the derivation would
  disturb that.

### 3. `brief` bound — CONTEXT § 5

`max_length=1_000_000` on `CreateRunRequest.brief` and
`CreateCompareRequest.brief`; `min_length=1` untouched. A shared
`_BRIEF_BOUND_DESCRIPTION` carries the derivation and the cross-phase warning
that ROADMAP Phase 24 D-RR-3 adds an intentionally **uncapped** steering note to
this field, so 1 MB is chosen to leave that room.

## Proof: observed RED, then GREEN

Every concurrency claim below was observed failing before it was observed
passing. Local venv (Python 3.12.6, `tribunal/requirements.txt`) against a real
testcontainers Postgres.

### Proposal double-spend

| Condition | Result |
|-----------|--------|
| Against the **unfixed** code (commit `a9601b8`, before any source change) | `test_concurrent_proposal_reads_generate_exactly_once` **FAILED**: `assert 2 == 1`, two recorded generation calls for the same `run_id` |
| After the fix | 6 passed |
| Fix present but the lock line **commented out** (the literal probe the criterion names) | **1 failed, 5 passed** — again `assert 2 == 1`, two recorded calls |
| Lock line restored | 6 passed |

The stub sleeps 0.4 s so the two coroutines genuinely overlap; an instant stub
would pass with no lock at all.

### Answer race

Against the unfixed code, with the harness described below:

- Single branch: `ok=2, errs=[]` — **both** callers got a 201, and the database
  held **two** queued replacement runs (`assert 2 == 1`).
- Comparison branch: `{'tribunal': 2, 'adk': 2}` — each paused arm replaced
  **twice**.

After the CAS: exactly one 201 and one 409, exactly one queued run;
`{'tribunal': 1, 'adk': 1}`. **16 passed**, stable over three consecutive runs
(12.1 s / 15.1 s / 17.6 s).

### The harness defect I had to fix first — the race did not exist

My first version of the two-caller answer test **passed against the unfixed
code** (`ok=1`, one 409). The two coroutines were not overlapping: the first
finished and committed before the second read, so the second simply saw the
committed `cancelled` status. That test would have been exactly the vacuous
shape this phase keeps finding.

The fix is `_call_answer(..., hold=)`, which keeps the first caller's
transaction **open** for 0.6 s after the handler returns and before the commit.
The rival's read then lands inside that window and sees the last committed row
version, `needs_input` — which is precisely where the production race lives. The
reasoning and the measured false-green are both written into the helper's
docstring so the next reader cannot delete the hold as noise.

A second harness defect in the same file: `Base.metadata.create_all` ran before
`nestor_pulse_sdk.db.models` was imported, so the metadata was empty and the
call created nothing. It only worked when an earlier test in the file had
already imported the models — an order-dependent green that failed the moment a
test was run alone (`relation "org" does not exist`). Now imported explicitly.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 — Missing critical functionality] Deterministic lock order on the comparison CAS loop**
- **Found during:** Task 2
- **Issue:** The paused-sibling `select` had no `ORDER BY`. With one CAS per
  sibling, two concurrent callers could acquire the sibling row locks in
  opposite orders and deadlock — a failure mode the plan's own design
  introduced and did not address.
- **Fix:** `.order_by(Run.id)` on the paused select, with the reason in a comment.
- **Files modified:** `tribunal/nestor_pulse_sdk/runs/api.py`
- **Commit:** `6a3a6c5`

**2. [Rule 1 — Bug] Order-dependent `create_all` in the new test harness**
- **Found during:** Task 2
- **Issue:** `create_all` before the model modules were imported registered
  nothing on `Base.metadata`.
- **Fix:** explicit `import nestor_pulse_sdk.db.models` before `create_all`.
- **Files modified:** `tribunal/nestor_pulse_sdk/tests/test_run_api_idempotency.py`
- **Commit:** `932d1e8`

### Plan-vs-code reconciliations (A is a plan mismatch; B is MY error)

**A. "add `synchronize_session` handling or re-read as needed so the response
payload reports the real post-update state … verify the response body's
`status` for a retired run is `cancelled`."**

Neither branch serialises a retired run. The single branch returns
`{"mode": "run", "run": <the NEW child>}`; the comparison branch returns
`{"runs": [<children>]}`. There is no retired run in any response body, so there
is nothing to un-stale. I deliberately did **not** mirror the CAS back onto the
ORM objects: assigning `run.status = "cancelled"` would mark them dirty and emit
a redundant UPDATE at flush that overwrites the CAS's `NOW()` with a Python
timestamp. The retirement is asserted on the **database** instead
(`status == 'cancelled'` and `completed_at is not None`).

**B. The brief-bound derivation — I WAS WRONG, the plan was right.**

⚠ **This entry originally recorded a false accusation against the plan. Corrected
2026-09-04 after the team lead re-measured. Read the correction, not the claim.**

I originally reported that the plan's derivation cited constants that do not
exist — that there was no `brief_input.py` and that a repo-wide grep for
`_QUESTION_MAX_CHARS` and `_REPORT_VALUE_MAX_CHARS` returned zero. **That was my
error, and it was an error of method.** The plan (line 71) writes
`brief_input._QUESTION_MAX_CHARS = 400` with **no path prefix**. Task 3's
`<read_first>` list happens to name two `backend/…` files, so I inferred the
third reference was also under `backend/`, scoped my grep to `backend/`, found
nothing, and concluded the premise was false rather than concluding I had looked
in the wrong tree.

Measured repo-wide, all three clamps exist, all three are 400, in a module
literally named `brief_input.py` — in the **tribunal** package, not the backend:

| Constant | Location | Clamps |
|----------|----------|--------|

The name also appears as `own_researcher.py:159` (600) and computed at

`DATABASE_URL` so LIVE tests skip there. The outcome is right; the mechanism is
different and worth recording. That config **does** mount the Docker socket

execute; the **10 LIVE** ones skip. Reproduced deliberately with an unreachable
Docker daemon: **6 passed, 10 skipped**, clean skips, no errors.

`cloudbuild.test-critical.yaml` names four files
(`test_schema_isolation`, `test_advisory_lock_exactly_once`,
`test_hash_chain_replay`, `test_verification_report_endpoint`) and this is not
one of them. I did **not** edit any build config — that is plan 23.1-14's
territory.

What I did instead, inside my own files: the `run_api_engine` fixture now
prefers an explicit `DATABASE_URL` (the pattern `cloudbuild.test-critical.yaml`
and `cloudbuild.test-rls.yaml` already use) and falls back to the container
fixture, resolved lazily. **Verified against a disposable `postgres:15` on a
DSN: 16 passed**, no testcontainers involved. So plan 23.1-14 can wire a gate by
