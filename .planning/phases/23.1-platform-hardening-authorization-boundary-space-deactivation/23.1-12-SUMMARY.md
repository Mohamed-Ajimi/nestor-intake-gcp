### The exact `upgrade()` ordering — duplicate resolution BEFORE index creation

```
1. ALTER TABLE nestor.skill_runs NO FORCE ROW LEVEL SECURITY
2. UPDATE ... SET status='failed', error_message=..., completed_at=COALESCE(completed_at, now())
     WHERE status='running' AND EXISTS (a NEWER running row in the same (intake_id, skill) group)
3. ALTER TABLE nestor.skill_runs FORCE ROW LEVEL SECURITY      [in a finally:]
4. op.create_index(uq_skill_runs_one_running_per_intake_skill, ...,
                   unique=True, postgresql_where=text("status = 'running'"))
```

`downgrade()` is `op.drop_index(...)` and nothing else. The pre-flight's resolution is
deliberately NOT un-done: those rows' pre-migration status is gone and there is no record of
which were genuinely in flight, so inventing a reversal would fabricate state. The comment
says so.

### Two things the plan did not specify, both of which decide the deploy

**1. FORCE RLS would have made the pre-flight a silent no-op (Rule 2).** The plan describes
the resolution as "ONE idempotent SQL statement" and says nothing about row security.
`skill_runs` carries `ENABLE` + `FORCE ROW LEVEL SECURITY` with the
`skill_runs_space_isolation` policy (0009:194-195), and **FORCE binds the table owner**,
which is the role alembic runs as. With no `app.current_space_id` GUC set the policy
evaluates to NULL and a plain cross-space `UPDATE` matches **zero rows — silently** —
leaving every duplicate in place for `CREATE UNIQUE INDEX` to abort on. That is precisely
the failed production deploy D-23.1-12 exists to prevent, arrived at by a different route.

`SET row_security = off` is not the fix: per the Postgres docs it makes a statement that
would apply a policy **ERROR** rather than bypass, and a table owner under FORCE is not
exempt. So the migration drops FORCE for the length of the one statement and restores it in
a `finally:` inside the same transactional migration — if anything raises in between, the
rollback restores FORCE with it. No policy is dropped, altered or re-created.

**2. "all but the newest `created_at`" is not a total order (Rule 1).** `created_at` has
`server_default func.now()`, and `now()` is fixed for a whole transaction — two rows
inserted in one transaction carry the SAME timestamp to the microsecond. Ordering on
`created_at` alone leaves both of them `running` and the index creation still aborts. The
resolution therefore compares the tuple `(created_at, id)`, which is total. The pre-flight
test seeds both shapes: group A with distinct timestamps, group B with a deliberate tie.

The statement is idempotent — afterwards no group has more than one `running` row, so a
re-run matches nothing.

## Task 2 — the 409

`ActiveSkillRunExistsError(RuntimeError)` sits beside `IntakeNotInScopeError` in
`app/db/ai_session.py` and carries `.skill`. `_dispatch_skill_run` in `app/api/ai_routes.py`
gains a **third** arm; the existing 404 and 403 arms are untouched. All six dispatching
routes inherit it because they all come through that one function. The three arms are
disjoint types (`LookupError` / `OSError` / `RuntimeError`), so none can shadow another
whatever the order.

**Scope of the `except`.** It wraps ONLY the `create`/`create_in_space` call — the flush that
populates the server-side id, which is exactly where the index fires (`repository.py:194`
and `:221`). The scope check above it has its own error and nothing below can raise an
`IntegrityError`.

**Discrimination.** `_is_one_running_violation` matches on the **constraint name**. pg8000 —
the driver in both the test container and Cloud Run — returns the server's error fields as a
dict in `exc.orig.args[0]`, where `n` is the constraint name and `C` the SQLSTATE; observed
directly during the RED run:

```
{'S': 'ERROR', 'C': '23505',
 'M': 'duplicate key value violates unique constraint "uq_skill_runs_one_running_per_intake_skill"',
 's': 'nestor', 't': 'skill_runs', 'n': 'uq_skill_runs_one_running_per_intake_skill', ...}
```

A driver reporting no structured fields falls through to a substring check on the rendered
message — weaker, but never broader: it still requires the index name. Any OTHER
`IntegrityError` (a genuine FK or NOT NULL violation) is re-raised as itself; dressing one up
as "already running" would hide a real defect behind a 409 (T-23.1-53). A comment records
which approach was taken and why.

### The 409 body — asserted, not assumed

Actual detail string:

```
A 'apply-intake-skill' run is already in progress for this intake. Wait for it to finish before starting another.
```

`test_409_detail_names_the_skill_and_leaks_no_driver_string` asserts on the **response
body**, not just the status: `detail` is a plain string (so the frontend transport's
raw-fallback path is unchanged), it contains the skill name, and the whole body contains
**none** of `IntegrityError`, `UniqueViolation`, `psycopg`, `pg8000`, `sqlalchemy`, `SQL:`,
`23505`, `duplicate key`, or `uq_skill_runs_one_running_per_intake_skill` (case-insensitive).

`grep -rn 'IntegrityError' backend/app/api/` → **nothing**. The DB exception type does not
leave `app/db/`.

### Poisoned session

`test_a_conflict_does_not_poison_the_following_request` drives a further request through the
same machinery after the 409 and asserts 202. `tenant_session`'s `maker.begin()` exit rolls
the failed transaction back and returns the connection, and the session is never reused —
verified rather than assumed, because a reused rolled-back session raises
`PendingRollbackError` and would turn the clean 409 into a 500 (T-23.1-52).

### Zero provider spend

The route tests no-op all six `ai_routes` background handlers, which both freezes the first
run in flight (the real-world double-click state) and guarantees no Anthropic/OpenAI client
is ever constructed. The point under test is the SYNCHRONOUS dispatch step, which precedes
the background task on every dispatching route. No provider call was made anywhere in this
plan.
