## WHY ROUTER LEVEL, AND WHAT THAT BUYS

D-23.1-02 says "to `ai_router` at the ROUTER level (one dependency, not seven)". Two concrete
benefits beyond tidiness:

1. A route ADDED to this router later is gated by construction. Seven per-route copies would
   leave route number eight open, which is exactly how the original six extra verbs in
   CONTEXT § 1's table came to exist.
2. FastAPI PREPENDS router-level dependencies to each route's own list, so the gate resolves
   before every handler dependency. The ordering contract in `gates.py`'s docstring is
   satisfied structurally rather than by remembering to put a parameter in the right place.

Write BOTH of those into the comment above the router construction, because "one dependency,
not seven" reads like a style preference otherwise.

## THE DENIAL MUST LAND BEFORE THE DISPATCH — ASSERT IT, DO NOT ASSUME IT

Every one of the four skill routes calls `_dispatch_skill_run` (`ai_routes.py:58`) as its
FIRST statement, which INSERTS a `running` `skill_runs` row before scheduling the background
task. If the gate somehow resolved after the handler body, a denied caller would still leave a
`running` row — and after plan 23.1-12 lands its partial unique index, that orphan row would
block the real operator's next run with a 409. So the denial tests must assert **zero new
`skill_runs` rows**, not merely a 404.
