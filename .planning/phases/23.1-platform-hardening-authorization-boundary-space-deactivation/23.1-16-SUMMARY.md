# Phase 23.1 Plan 16: The Login-Sync Membership-Status Backstop Summary

`_find_membership` now filters `status == "active"` on both the `provider_user_id` arm and the
`email` fallback, so login-sync refuses to mint `role`/`space_id` claims for a `deactivated` or
`space_deactivated` membership even when the IdP-side disable never landed.

the select lines that gained a trailing comma):

Three of the new cases deserve a note on *why* they are not decoration:

- **`test_partial_cascade_failure_is_refused_by_the_db_alone`** is the window. What is
  deliberately absent from it is any simulation of IdP-side disablement — that absence IS the
  test. The token carries no `role` claim (asserted explicitly, so the `ALREADY_SYNCED`
  short-circuit demonstrably does not fire) and the row is `space_deactivated`. If login-sync
  only refused this member when the IdP also refused them, the IdP would be the sole control
  and the cascade's accepted partial-failure mode would be a live authorization hole.
- **`test_deactivated_member_is_indistinguishable_from_a_non_member`** asserts
  `deactivated_result == stranger_result` directly. Two separate `is NO_MEMBERSHIP` assertions
  would still pass if a future change gave one of them its own state, and would say nothing
  about the pair.
- **`test_cr01_unverified_email_refused_against_an_active_row`** seeds an **ACTIVE** superadmin
  row on purpose. Against an inactive row the new status predicate alone would refuse it, and
  the case would stay green with the `email_verified` gate deleted. Against an active row, CR-01
  is the only thing left standing.

The fall-through test asserts on the **space the claim carries**, not merely on `WROTE`:
pre-fix it also returned `WROTE`, from the *deactivated* row's space. Asserting the active row's
`space_id` is what distinguishes the two behaviours — which is why it is RED pre-edit.

## False / Inaccurate Criteria Found

**1. Task 1 `<done>`: "expected 5 failures — four status refusals plus the partial-cascade
case". The measured count is 7.**

The plan's own `<behavior>` block mandates two further cases it then forgot to count:
INDISTINGUISHABILITY and FALL-THROUGH. Both are genuinely RED pre-edit —

- indistinguishability: pre-fix the deactivated member returns `WROTE` and the stranger returns
  `NO_MEMBERSHIP`, so the equality assertion fails;
- fall-through: pre-fix the claim carries the *deactivated* row's `space_id`, so the assertion
  on the active row's space fails.

Reported rather than reconciled: writing only 5 failing cases would have meant dropping two
cases the plan itself requires. 7 is the correct number for the suite the plan specifies.

**2. Task 2 `<done>`: "`grep -n 'status' backend/app/auth/session.py` shows the predicate on
BOTH selects — read the two hits". There are 10 hits, not two.**

The criterion's own instruction ("read the two hits, do not count them") saves it — I read them
and confirmed `:139` in the uid arm and `:172` in the email arm. But the *number* is wrong by
construction: the same plan mandates a `_STATUS_ACTIVE` comment block and a docstring rule that
between them contain eight further occurrences of the word `status`. Any future gate that
counts this grep instead of reading it will report a false failure.

**3. Task 2 `<action>`: "Four characters of duplication is a smaller price than that edge."**

`"active"` is six characters, eight with the quotes. Written as "Six characters" in the code
comment. Cosmetic, no behavioural consequence, noted only because the comment is permanent.

**4. `<interfaces>`: the cited line numbers had drifted.** The plan cites `_find_membership` at
`:77-113`, the CR-01 gate at `:145-147` and the short-circuit at `:139-142`. Pre-edit the file
had `_find_membership` at `:77-113` (correct), CR-01 at `:147` (correct) and the short-circuit
at `:141` (off by two). Trivial, and the plan told me to trust the tree over the line numbers.
