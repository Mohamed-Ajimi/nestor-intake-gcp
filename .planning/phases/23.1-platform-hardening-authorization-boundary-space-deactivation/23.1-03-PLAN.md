## PLANNING RULING #1 — THE INVERSE MUST BE SELECTIVE, AND THAT NEEDS A THIRD STATUS VALUE

`23.1-CONTEXT.md` D-23.1-03 says "Reactivate gets the inverse" and stops there. A naive
inverse — set every membership in the space to `active` — silently un-fires a member who was
individually deactivated BEFORE the space went down. Deactivate-then-reactivate would become
an undocumented way to restore revoked access.

The fix needs no migration. `models/membership.py:43` declares the status set as app-level
`{"active","deactivated"}`, a plain `String` with NO PG enum and NO CHECK constraint, and
0006 confirms it. VERIFIED at `047dcfe`: the five membership-status reads in `backend/app/`
that carry LOGIC are all ALLOW-LISTS (`== "active"`) — `admin_repo.py:113`,
`admin_repo.py:166`, `admin_routes.py:236`, `intake_routes.py:748`, `me_routes.py:123`.
There is NOT ONE deny-list comparison (`!= "deactivated"`). So a third value is inert
everywhere it is not explicitly handled, which is the safe direction.

⚠ **CORRECTED 2026-09-03 — THAT SURVEY WAS INCOMPLETE, AND THE MISSING SITE IS THE DANGEROUS
ONE.** `23.1-CONTEXT.md` D-23.1-11 now records a SIXTH membership-status site:
`_find_membership` (`auth/session.py:92-113`), which is not a deny-list gap — it is a
**no-list**, no status predicate at all, which is strictly worse. Login-sync therefore mints
claims for a `space_deactivated` member, and this plan's cascade is what makes that
load-bearing: a partial IdP failure commits the DB flip while those members keep
authenticating. **D-23.1-13 closes it. Do not restate "five sites, no deny-list anywhere" as
if it were the whole picture** — say five allow-list sites plus one no-list site closed by
D-23.1-13. (`admin_routes.py:122` also reads `status`, but only to surface it in a view; it
carries no logic and is not a seventh site.)

**Ruling: the cascade writes `status="space_deactivated"`. The inverse restores EXACTLY the
rows carrying that value and leaves `"deactivated"` rows alone.**

## PLANNING RULING #2 — THE IdP IS NOT IN THE TRANSACTION, SO THE VERB MUST BE RETRIABLE

`admin_users.deactivate_user` (`auth/admin_users.py:115`) is a Firebase Admin SDK call:
`update_user(disabled=True)` + `revoke_refresh_tokens(uid)`. It cannot join the request's DB
transaction. A partial cascade — some members disabled, then a rollback — leaves the IdP and
the DB disagreeing, and a member the IdP call FAILED for keeps working while the UI says the
space is off.

**Ruling: DB first, then IdP, then report honestly.**
1. Inside the request transaction: flip the space status and every `active` membership in it
   to `space_deactivated`, and write the audit row. Commit.
2. Then call `admin_users.deactivate_user` for each affected `provider_user_id`, collecting
   failures instead of raising on the first one.
3. If every call succeeded -> 200 with the space view.
   If any failed -> **502** whose detail names how many members are still enabled in the IdP,
   WITHOUT listing emails or uids in the response body (T-06-09: no identifiers in an error
   body). The uids go to the audit `metadata` and the log, not to the browser.
4. Because step 1 is idempotent and step 2 is idempotent, **re-issuing
   `POST /spaces/{id}/deactivate` retries the failed IdP calls.** The handler must therefore
   collect members whose status is `active` OR already `space_deactivated`, so a retry still
   has someone to disable. State this in the docstring — it is the whole reason the verb is
   safe to press twice.
