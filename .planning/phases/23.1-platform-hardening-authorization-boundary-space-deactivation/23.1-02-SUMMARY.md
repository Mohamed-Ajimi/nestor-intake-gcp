## Key Findings

### FastAPI 0.141 does not flatten `include_router` — and this silently defeats the obvious check

**This is the single most important thing this plan learned, and 23.1-10 / 23.1-11 need it.**

`app.routes` on this FastAPI version holds lazy `fastapi.routing._IncludedRouter` placeholders
that keep a live reference to the included router plus an `include_context` carrying that
include's `prefix` and `dependencies`. Consequences, both measured:

1. **A non-recursive read of `app.main.app.routes` filtered to `/intakes` returns ZERO
   routes.** The first enumeration attempt printed `count 0`. Any inventory or audit written
   as a flat loop over `app.routes` is vacuously green.
2. **Include-level dependencies never appear in a leaf route's `route.dependant`.** Measured
   on `GET /intakes/{intake_id}/skill-runs`:
   - `route.dependant.dependencies` → `[get_skill_run_repo]` only.
   - `get_current_identity` — which `protected_router` attaches via
     `APIRouter(dependencies=[...])` — arrives only through the include context.

   So a gate applied the way D-23.1-02 prescribes for `ai_router` would be **invisible** to a
   check that reads `route.dependant` alone. `_resolved_dependency_calls` walks both arms and
   each arm carries its own positive self-check assertion, so the gate assertion cannot go
   green by the walker finding nothing.
3. Conversely, `APIRouter(prefix=..., dependencies=[...])` on the router that OWNS the routes
   IS baked into each leaf's dependant at `add_api_route` time (verified by probe, then
   confirmed by mutation 2). Both shapes are therefore covered.

Identity is compared with `is`, never a name string — a name check passes on a lookalike and
fails on a legitimate re-export.

### Order-independence of the inventory guard, verified

`_build_app()` mutates the module-global `protected_router` (the house pattern), and the lazy
`_IncludedRouter` reads `original_router.routes` at access time — so the inventory guard could
in principle see routes appended by a test module that ran earlier. Forced my file to run LAST
behind five router-mutating modules:

```
$ pytest tests/test_storage_upload.py tests/test_research_routes.py tests/test_mail_endpoints.py \
         tests/test_skill_run_full.py tests/test_intake_cross_tenant.py \
         tests/test_client_surface_open.py -q
55 passed in 49.86s
```

Set semantics make it duplicate-immune, and every router any test includes is already mounted
in `app.main`.

## Deviations from Plan

### One plan claim was FALSE about the code

**[Rule 1 — Bug in the plan's `<behavior>`] `GET /intakes/{id}/skill-runs` does not return a list**

- **Found during:** Task 1
- **Issue:** The plan's `<behavior>` specifies `GET /intakes/{id}/skill-runs -> 200, and the
  body is a list.` The handler (`intake_routes.py:604`) returns `SkillRunsView`, a Pydantic
  object with `latest` and `runs` fields. `assert isinstance(resp.json(), list)` would have
  failed against correct code.
- **Resolution:** Asserted `isinstance(body["runs"], list) and len(body["runs"]) == 1` — the
  true shape, and stronger than the plan asked for (it proves the seeded run is actually
  present, not merely that a list came back). Recorded in the test's docstring so the next
  reader is not surprised.
- **Files modified:** `backend/tests/test_client_surface_open.py` only.

### One of the plan's own done-criteria was a grep trap I walked into and backed out of

**[Rule 3 — self-inflicted blocking issue] My module docstring quoted the banned tokens**

- **Found during:** Task 1 verification.
- **Issue:** Task 1's `<done>` requires
  `grep -n '!= 404\|< 400' backend/tests/test_client_surface_open.py` to return nothing. The
  intent is obviously "no tolerant comparisons in the assertions". My first draft's docstring
  *explained the ban* using the literal tokens — `No !=404, no <400, no in (200, 201)` — and
  the grep matched **prose about the thing**, exactly the failure mode this project's own
  gate-integrity notes warn about.
- **Resolution:** Reworded the docstring to say the same thing without the literal tokens
  ("never a not-equal-404 comparison, never a less-than-400 range check, never a
  tuple-membership test"). The criterion is now genuinely satisfied rather than gamed, and no
  assertion changed. Recorded because the *next* person to add an explanatory comment to this
  file will hit the same trap.
- **No criterion was contorted and nothing was deleted to satisfy it.**
