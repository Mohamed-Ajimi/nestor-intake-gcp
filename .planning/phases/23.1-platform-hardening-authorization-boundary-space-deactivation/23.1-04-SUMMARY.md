# Phase 23.1 Plan 04: Context-Pack Compare-and-Swap Summary

The `decomposed` bump in `context_pack.py` is now an allow-listed compare-and-swap
(`{"validated_by_client": "decomposed"}`) executed as one conditional UPDATE via a new
`TenantRepository.patch_if`; a refused transition keeps the paid artifact unlinked and
finalizes the skill run `failed` in the same transaction, so no `running` row survives.

## What changed

**`backend/app/db/repository.py`** — added `patch_if(row_id, expected: dict, **values)`
directly beneath `patch`. It ANDs one `WHERE` predicate per `expected` entry onto the
already-scoped statement and returns `rowcount`. `expected` is an explicit dict rather
than `**kwargs` because the predicate dict and the value dict have the same shape, and
mixing them would be silent. It carries `patch`'s `synchronize_session="fetch"`. The diff
over this file is **40 insertions, 0 deletions** — `patch` itself is byte-identical.

**`backend/app/ai/skills/context_pack.py`** — added `_CONTEXT_PACK_TRANSITIONS` and
`_refusal_message`, replaced the unconditional `patch(intake_id, status="decomposed", ...)`
at the old `:171` with a loop over the transition map calling `patch_if`, and added the
refusal branch. Docstrings at module, function and map level record the derivation and the
artifact-retention ruling.

**`backend/tests/test_ai_context_pack_cas.py`** (new, 22 tests) — five repo-level cases for
`patch_if` plus five end-to-end groups for the skill, four of them parametrized over the
disallowed source statuses `draft`, `decomposed`, `in_research`, `delivered`.

**`backend/tests/test_ai_context_pack.py`** — one-line fixture seed change. See Deviations.

## The allow-list and where it was derived

`{"validated_by_client": "decomposed"}` — one entry.

Traced through the only caller. `backend/app/api/ai_routes.py:114` dispatches
`run_context_pack` from `POST /intakes/{id}/skills/context-pack`, which the frontend calls
from exactly one button. That button renders in exactly one phase:

- `frontend/src/components/intake/NextStepBanner.tsx:270` — `case "awaiting_context_pack"`
  is the only branch containing `onGenerateContextPack`.
- `frontend/src/lib/intake-phase.ts:55-58` — `awaiting_context_pack` is returned only from
  `status === "validated_by_client"` when `context_pack_artifact_id` is unset.

Verified at HEAD, not taken from the plan. `reviewed` maps to `awaiting_validation_send` /
`awaiting_client_validation` (`intake-phase.ts:49-53`) and has no context-pack button;
`decomposed` maps to `awaiting_research_start` (`:61`). No second caller of
`run_context_pack` exists — `grep -rn "run_context_pack" app/` returns only the definition,
the `__init__` re-export, and the single `bg.add_task` at `ai_routes.py:114`. So no status
was added, and none was widened.

## How the no-orphan guarantee was proved

The refusal is finalized in the *same* control flow and the *same* transaction that
rejects the transition — there is no early `return` between the failed CAS and the
`SkillRunRepository.patch(run_id, status="failed", ..., completed_at=_now())`. Routing it
through `on_error` was rejected because that runs in a fresh transaction after the write
transaction rolls back, which would discard the paid artifact insert.

Proven two ways, both parametrized over all four refusal statuses
(`test_refused_context_pack_never_leaves_a_running_skill_run`):

1. The newest `skill_runs` row for the intake is `failed`, never `running`, with
   `completed_at` non-null and `applied_at` null.
2. `SELECT count(*) FROM nestor.skill_runs WHERE intake_id = :iid AND status = 'running'`
   returns **0**. This second assertion was added deliberately: 23.1-12's index is
   `UNIQUE (intake_id, skill) WHERE status='running'`, so the invariant it depends on is a
   count over the table, and a `LIMIT 1` check on the newest row would miss an older
   orphan.

Both assertions fail on the pre-change code (the RED run recorded `succeeded` for all four
statuses), so neither is vacuous.

## Deviations from Plan

### [Rule 1 — Bug] A pre-existing test pinned the defect as expected behaviour

**Found during:** Task 2 GREEN.

**Issue:** The plan's Task 2 `<done>` criterion states that
`backend/tests/test_ai_context_pack.py` must pass unedited, and that file is not in
`files_modified`. That criterion is **false and unsatisfiable** alongside a correct
allow-list. `_seed_intake` (`:76-84`) inserted the intake at status `'reviewed'`, and the
test then asserted the skill advanced it to `'decomposed'`. That is the defect: a jump from
`reviewed` straight to `decomposed` skips `validated_by_client` entirely — it skips client
validation, which is exactly the lifecycle corruption D-23.1-05 exists to prevent.

**Measured:** at HEAD, `tests/test_ai_context_pack.py tests/test_ai_status_contract.py` =
**3 passed** in 16.29s. With the allow-list in place and no test edit:
**1 failed, 24 passed** —
`test_context_pack_writes_artifact_and_decomposes`, with
`AssertionError: context-pack must advance the intake to 'decomposed', got 'reviewed'.`

**Fix:** the fixture seed moved from `'reviewed'` to `'validated_by_client'`, with a comment
recording why. **Every assertion in that test is unchanged** — artifact row written,
`text_content` populated, `embed_status='pending'`, status advances to `decomposed`,
`context_pack_artifact_id` linked, run `succeeded` with `applied_at`. Only the arbitrary
setup value moved to the status the UI actually launches from.

**Rejected alternative:** widening `_CONTEXT_PACK_TRANSITIONS` to include `"reviewed"`.
That would have satisfied the plan's criterion literally while re-opening the defect, and
the plan's own instruction — "do not add a status without a caller" — forbids it. There is
no caller that launches this skill from `reviewed`.

**Files modified:** `backend/tests/test_ai_context_pack.py` (outside `files_modified`).
**Commit:** `d693d38`
