## Proof the gate is ONE router-level dependency, not seven

Read off the live `app.main.app` with the plan-02 walkers (65 routes flattened):

```
ai_router.dependencies -> ['superadmin_gate']

POST /intakes/{intake_id}/skills/apply
    route.dependant only  : ['superadmin_gate', 'get_current_identity']
    include-ctx inherited : ['get_current_identity']
    RESOLVED              : ['superadmin_gate', 'get_current_identity', HTTPBearer, ...]
    gate count = 1
```

Identical for all seven. `superadmin_gate` is **first** in `route.dependant`, which is the
prepend that makes the ordering contract structural. Code-level occurrences of
`Depends(superadmin_gate)` in `ai_routes.py`, counted with `tokenize` (comments and strings
excluded): **1**.

**Non-leak, measured not assumed.** `ai_router` and `intake_router` are separate `APIRouter`
objects sharing the `/intakes` prefix. `GET /intakes` and `GET /intakes/{id}/answers` resolve
**zero** gates in the same walk — asserted inside
`test_no_ai_handler_declares_its_own_superadmin_gate`, so it is a standing CI check rather than
a one-off observation.

## Deviations from Plan

### 1. [Rule 2 — the fixture list was wrong in both directions] `test_ai_context_pack_cas.py`

The plan authorised fixture edits in ten files. **Four of them needed none** —
`test_ai_cross_tenant.py`, `test_ai_search_cross_tenant.py`, `test_ai_search_explain.py` and
`test_scope_guard_ai.py` never make an HTTP request; they call `tenant_session` /
`search_artifacts` directly, so the gate cannot reach them. **One file that DID break was
absent from `files_modified`**: `test_ai_context_pack_cas.py`, whose 17 route-driving tests are
**63% of the entire fallout**. Found by running the suite (30 failed) rather than by trusting
the list — the same failure mode plan 10 reported with `test_mail_locale.py`. Treated
identically: fixture only, every assertion untouched.

This also makes the plan's `<interfaces>` instruction about `test_ai_cross_tenant.py` — "read
it closely… after this change that suite's `user`-role arms become gate denials rather than
scope denials" — **false about the file as it exists**. There are no route-driving arms in it.
No superadmin arm was added, because adding one would have proved nothing the file does not
already prove; the plan's underlying concern (a test passing for a different reason) is real
and was checked, it simply does not apply here. It DOES apply to
`test_ai_context_pack_cas.py::test_refused_context_pack_never_leaves_a_running_skill_run`,
which asserts a refused pack leaves no `running` row — under a `user` identity the gate's 404
would have satisfied it vacuously. Re-identifying the caller as superadmin keeps it measuring
`run_context_pack`'s own refusal path, which is what it was written for.

### 2. [Rule 1 — false premise in the task brief] D-23.1-14 does not apply to this shape

The brief warned that a router-level gate would read as **zero** gates and pressure me toward
seven per-route copies. **Measured against fastapi 0.141.1, that is not what happens here.** A
dependency on the router that OWNS its routes is merged by `add_api_route` and lands in
`route.dependant`:

```
route.dependant only  : ['superadmin_gate', 'get_current_identity']   # gate visible, count 1
include-ctx inherited : ['get_current_identity']                       # protected_router's
```

D-23.1-14's invisibility is real but is about the **including** router's dependencies —
`get_current_identity`, attached when `protected_router` includes `ai_router`, which is exactly
the case it documents. Both `test_client_surface_open.py`'s helper docstring (point 1: "a
router-level dependency IS baked into the leaf's dependant at `add_api_route` time") and my own
isolated probe agree. The prescribed mitigation was followed regardless — the walkers are
imported, not re-derived — so the audit is correct either way, and it now sees the gate through
the recursive arm rather than the include arm. No architecture was changed to satisfy a
measurement.

### 3. [False criterion, reported not worked around] the `grep -c` done-criterion

Task 2's done-criterion is `grep -c "Depends(superadmin_gate)" backend/app/api/ai_routes.py == 1`.
Measured: **3**. Lines 15 and 60 are prose — the module docstring's SEC-01 invariant and the
router comment that D-23.1-02 **explicitly required** ("Write BOTH of those into the comment
above the router construction, because 'one dependency, not seven' reads like a style
preference otherwise"). Line 79 is the only code occurrence. A tokenized count with comments
and strings excluded gives **1**. The criterion as written cannot distinguish a second
dependency from a sentence about the first one; deleting the documentation to make it pass
would have satisfied the letter and destroyed the point. The claim it was reaching for is
proved much more strongly by `test_no_ai_handler_declares_its_own_superadmin_gate`, which
asserts **exactly one** gate in the resolved tree of every mount of all seven routes —
catching a per-route copy that no grep count of 1 would.

### 4. [Deferred by scope, not skipped] `app/main.py`'s mount comment

`main.py` is not in `files_modified` and the executor brief said to touch only listed files, so
its `ai_router` mount comment (`main.py:153-162`) still says the router inherits
`get_current_identity` and nothing else. Comment-only, no behavioural effect. The intended
clause, for plan 23.1-15's hand-off:

> …Mounted UNDER protected_router so it inherits get_current_identity; the router additionally
> carries ONE router-level Depends(superadmin_gate) of its own (D-23.1-02 / plan 23.1-11), so
> the whole AI surface is superadmin-only and a route added to it later is gated by
> construction. Each handler depends on Identity ONLY (never get_tenant_repo — the long
> Claude/OpenAI call must not hold the request tx) and dispatches the work via BackgroundTasks
> (D-05).

Booked in `deferred-items.md`.

### 5. [Deliberate, documented] the provider-fake asymmetry

Denial arms install the fakes and leave the REAL background runners in place, so a gate that
stopped biting would record a provider call and fail loudly. Superadmin arms stub the six
runners to no-ops — their happy paths belong to `test_ai_apply_skill` et al., and this file's
superadmin arms exist only to prove the gate did not brick the operator. Written into the
module docstring so it does not read as an oversight.
