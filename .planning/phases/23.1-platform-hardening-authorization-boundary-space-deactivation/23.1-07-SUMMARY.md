# Phase 23.1 Plan 07: Explicit Identity Threading + the D-03 Guard Fix Summary

Moved the pool-check engine accessor into the `app/db/` seam so the D-03 raw-DB guard
passes against the real tree without touching the guard script, and replaced
`run_task.py`'s process-global `_ACTIVE_IDENTITY` slot with a required keyword-only
`identity` on `_patch_run` and the three `finalize_*` writers.

## What was built

### Task 1 — the D-03 guard offender (commit `b4ac330`)

`scripts/ci_no_raw_db_access.sh` was RED at HEAD on one line:

```
app/research/run_task.py:247:    return get_engine()
```

`get_engine_for_pool_check()` moved verbatim — body and docstring — from
`app/research/run_task.py` into `app/db/session.py`, immediately above `get_tenant_repo`,
with one added paragraph recording the D-03 rationale. `session.py` gained
`from typing import Any` (it had none) and needed no new app import: line 40 already did
`from app.db.base import get_engine, ...`.

**Why that location is inside the seam.** The guard scans `backend/app/` and passes
`--exclude-dir=db`, so every file under `app/db/` is out of scope by directory; `session.py`
is additionally excluded by name. The guard's own comment states the principle — "calling
the seam's interface is the allowed path, not a bypass" — and `get_engine_for_pool_check`
is exactly a thin call onto the seam's public accessor. It is a db-seam concern that
happened to live in a research module.

`run_task.py` now imports the name back (`from app.db.session import
get_engine_for_pool_check`) and its `from app.db.base import get_engine` is gone —
`get_engine(` no longer appears anywhere in the file.

The two monkeypatch targets (`tests/test_research_run_task.py:303` and `:520`) still
resolve: `monkeypatch.setattr(run_task, "get_engine_for_pool_check", ...)` patches the name
in `run_task`'s namespace and a `from ... import` binds exactly that name. Verified, not
assumed — both pool-safety tests pass. No circular import: `import app.research.run_task`
succeeds.

### Task 2 — explicit identity threading (commit `7b6f509`)

`_patch_run(session, research_run_id, *, identity: Identity, **values)` uses the identity it
is given. `finalize_completed`, `finalize_failed` and `finalize_parked` each gained a
required keyword-only `identity` and forward it. `run_poll_driver`'s four call sites pass
`identity=identity` — already a parameter of that function and in lexical scope at each.
The park branch's prior-row read became `ResearchRunRepository(session, identity)`.

`_ACTIVE_IDENTITY`, `identity_of` and the `global _ACTIVE_IDENTITY` assignment are deleted.
The module comment that introduced the slot is replaced by a comment recording why there is
no slot, including CONTEXT § 6's finding that this was never a tenant-scope bug.

**Behaviour is unchanged on the finalize path.** Per `23.1-CONTEXT.md` § 6, every caller is
superadmin-gated and the repo `_scope` is a no-op for a superadmin, so what a concurrent
overwrite of the slot could corrupt is `actor_uid` only — a repudiation risk (T-23.1-26),
not a cross-tenant one. No repo scoping, no `_scope`, and no write path was altered.

### The two docstring occurrences

At HEAD, `grep '_ACTIVE_IDENTITY\|identity_of'` returned nine hits in `run_task.py`, two of
them prose rather than code:

- `:522` — inside `_patch_run`'s docstring: "``identity_of`` recovers the driving identity
  stashed on the session binding". Rewritten in place. The paragraph about the superadmin
  `_scope` no-op above it is kept verbatim, as the plan required; only the identity-sourcing
  sentence changed.
- `:545` — `identity_of`'s own docstring, removed with the function.

Both are gone, so a name-based grep over `backend/app/` returns 0 rather than tripping on
prose describing the thing that was removed.

## False Criterion

**`<success_criteria>` line 2 / `<verification>` item 3 is unsatisfiable as written.**

> "`_ACTIVE_IDENTITY` and `identity_of` no longer exist anywhere in `backend/`."
> "`grep -rn '_ACTIVE_IDENTITY\|identity_of' backend/` returns nothing outside `.planning/`."

The same plan's `<behavior>` block mandates `assert not hasattr(run_task, "_ACTIVE_IDENTITY")`
and `assert not hasattr(run_task, "identity_of")`. Those assertions *must* name the symbols.
Satisfying the literal grep would require deleting the regression test the plan itself
demands, or obfuscating the names into concatenations to hide them from grep — contorting
code to satisfy a measurement.

Measured at `7b6f509`:

| Scope | Hits |
|-------|------|
| `grep -rn --include='*.py' '_ACTIVE_IDENTITY\|identity_of' backend/app/` | **0** |
| `... backend/tests/` | **6** — all inside `test_the_module_level_identity_slot_is_gone` and two docstrings that explain what was removed |

Task 2's own `<done>` criterion scopes the grep to `backend/app/` and is met exactly. That is
the correct form; the phase-level restatement over all of `backend/` is the false one.
Nothing was weakened to pass it — the test stays.

Secondary note: an unqualified `grep -rn ... backend/` also matches `__pycache__/*.pyc`
byte-strings, which are build artifacts, not source. Any future gate on this must use
`--include='*.py'`.
