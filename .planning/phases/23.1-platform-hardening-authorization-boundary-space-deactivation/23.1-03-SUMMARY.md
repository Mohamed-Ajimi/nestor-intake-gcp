# Phase 23.1 Plan 03: Space-Deactivation Cascade Summary

Deactivating a space now disables every member in the IdP and revokes their refresh
tokens, marks each cascaded membership with a third status (`space_deactivated`) so the
reactivate inverse can restore only what the cascade took down, refuses before any write
when the cascade would lock out the acting superadmin or empty the active-superadmin set,
and reports a partial IdP failure as a count-only 502 whose DB flip survives — so pressing
the verb again retries exactly the members it failed for.

## What was broken

`admin_routes.py:511` flipped `organizations.status` and audited it. Nothing in any auth
path reads that column (23.1-CONTEXT § 2), so a space marked "deactivated" kept serving
every one of its members with working sessions. The operator saw "off"; the tenant was on.

## What was built

**`backend/app/db/admin_repo.py`**

- `_STATUS_SPACE_DEACTIVATED = "space_deactivated"`, beside the two existing status
  constants, with a comment recording (a) why a third value exists, (b) that no migration
  is needed (plain `String`, no PG enum/CHECK — `models/membership.py:43`, migration 0006),
  and (c) the survey that makes it safe: five allow-list (`== "active"`) read sites, **plus
  the sixth NO-list site** `_find_membership` in `app/auth/session.py` that D-23.1-13 closes
  in plan 16. The comment states the survey is not complete on its own — it does not
  restate "five sites, no deny-list anywhere" as the whole picture.
- `AdminRepo.list_memberships_for_space(organization_id)` — every membership of one space,
  **all statuses**, `str` or `UUID` accepted via the existing `_as_uuid` helper. Its
  docstring records why it is status-blind: the retry path needs rows that are already
  `space_deactivated`.

**`backend/app/api/admin_routes.py`**

- `_apply_to_idp(uids, apply, verb=...)` — calls an `admin_users` verb once per uid, never
  returns early, logs each failure with its uid, returns the failed uids.
- `deactivate_space` — 404 → read memberships once → **both guards before any write** →
  flip memberships + space → IdP loop → audit row carrying `members_cascaded`,
  `idp_disabled` and `idp_failed_uids` → 200, or explicit commit + 502 with a count-only
  detail.
- `reactivate_space` — the selective inverse: restores **exactly** the
  `space_deactivated` rows, leaves `deactivated` rows and their IdP accounts alone.
- Both docstrings state that `organizations.status` is bookkeeping and the IdP flag is the
  enforcement, that D-23.1-03's rejected alternative (an org-status read in
  `get_current_identity`) was not added, and why the verb is safe to press twice.

**`backend/tests/test_space_deactivation_cascade.py`** — 16 tests, all green. The Admin SDK
is patched in every one; no live IdP call, zero provider spend.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug] The plan's last-superadmin guard formula 409s every space deactivation on
an installation with no active superadmin memberships**

- **Found during:** Task 2.
- **Plan text:** "count how many `role == "superadmin" AND status == "active"` rows the
  cascade would take down and refuse if that number is `>= repo.count_active_superadmins()`".
- **Issue:** `count_active_superadmins()` is global. A space holding **no** active
  superadmin cascades 0 of them; if the installation has 0 active superadmin memberships
  anywhere, the guard reads `0 >= 0` and refuses. **Measured:** with the literal formula,
  `tests/test_admin_routes.py::test_space_create_edit_deactivate_and_no_delete_route`
  (a space created via the API with zero members) would 409 instead of 200 — a
  pre-existing passing test. Superadmins in this system commonly have no membership row at
  all (`Identity.space_id is None`; `admin_repo` docstrings, Open Q1), so this is the
  normal production shape, not a test artifact.
- **Fix:** `cascaded_superadmins > 0 and cascaded_superadmins >= repo.count_active_superadmins()`,
  with a comment stating why the `> 0` is there. Intent is preserved exactly: the guard
  bites when this space holds active superadmins **and** they are all of the remaining ones.
- **Files modified:** `backend/app/api/admin_routes.py`
- **Commit:** `9aeb1ef`

**2. [Rule 3 — Blocking] The 502 path rolls the DB flip back unless the handler commits
explicitly**

- **Found during:** Task 2.
- **Issue:** PLANNING RULING #2 requires the flip to be committed and then a 502 raised, but
  `get_admin_session` yields inside `with maker.begin()`. FastAPI throws the endpoint's
  exception into that generator, so the transaction **rolls back** — the flip and the audit
  row would vanish while the members already disabled in the IdP stay disabled. That is the
  exact DB/IdP divergence the ruling exists to prevent.
- **Fix:** `repo.session.commit()` immediately before the `raise`. Probed against SQLAlchemy
  2.0.52 first (an explicit commit inside `sessionmaker.begin()` survives a subsequent
  raise and the generator exits cleanly), then proved end-to-end by
  `test_partial_idp_failure_...`, which reads the committed rows from PG after the 502.
  The audit row is written **before** the commit, so action + audit still land in one
  transaction (T-5-16).
- **Files modified:** `backend/app/api/admin_routes.py`
- **Commit:** `9aeb1ef`

**3. [Rule 1 — Bug] Two repo-level tests deadlocked the suite rather than failing it**

- **Found during:** Task 1 verification.
- **Issue:** The `repo` fixture held one open transaction for the whole test. A test that
  mutated through the repo and then let `finally: _cleanup_space(...)` run a
  `DELETE FROM organizations` on another connection blocked forever — the FK cascade onto
  the uncommitted membership row waits on that transaction, which cannot end until the test
  body returns. Confirmed in `pg_stat_activity`: `DELETE FROM nestor.organizations` in
  `Lock/transactionid`, the repo session idle in `ClientRead` on its `UPDATE`.
- **Fix:** the `repo` fixture uses a plain `Session` (not `maker.begin()`, which forbids
  further commands after an explicit commit — that was the second failure mode), and the two
  mutating tests commit right after the write. Both reasons are recorded in the code.
- **Files modified:** `backend/tests/test_space_deactivation_cascade.py`
- **Commit:** `9aeb1ef`

### Judgement calls, not deviations

- The plan's `<action>` says "Structure it as: ... flip memberships and the space and write
  the audit row on `repo.session` -> then loop the IdP calls". The audit row is written
  **after** the loop instead, so its `metadata` can carry `idp_failed_uids` and
  `idp_disabled` — which the same ruling requires ("the uids go to the audit `metadata`").
  Written before the loop it could only record intent, not outcome. Everything is still one
  transaction and the audit row still commits with the flip.
- The status constants are imported into `admin_routes.py` from `admin_repo.py` rather than
  re-typed as string literals (the house style at these call sites), so the cascade value
  cannot drift between the write side and the allow-list reads.

## Acceptance criteria found false

**One**, reported above as auto-fix #1: the last-superadmin guard formula in the plan's
`<action>` block. It is wrong in the `cascaded == 0, count == 0` case and would have turned
an existing green test red. The plan's `must_haves` truth ("can never drop the count of
active superadmins to zero") is what was implemented, and it is what the test asserts.

The rest of the criteria held. Two were checked specifically for the "already true at HEAD"
and "true while the defect persists" traps:

- `grep -rn 'status != "deactivated"' backend/app/ --include='*.py'` returns nothing — but
  that criterion was **already true at HEAD** and stays true trivially, so it is a
  regression tripwire, not a proof of this plan's work. The real proof that the third
  status reads as inactive is the two behavioural repo tests, which measure it.
- `grep -n 'deactivate_user' backend/app/api/admin_routes.py` showing the call inside
  `deactivate_space` is satisfiable by a mere mention in a docstring. It is genuinely
  satisfied here (line 612, `_apply_to_idp(uids, admin_users.deactivate_user, ...)`), and
  the recorded-call-list assertions are what actually prove the call happens once per member.
