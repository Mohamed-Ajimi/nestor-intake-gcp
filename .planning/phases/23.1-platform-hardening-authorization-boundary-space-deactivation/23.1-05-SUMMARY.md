# Phase 23.1 Plan 05: Tribunal Run-Ownership Fence Summary

`AND worker_id = :wid`, bound to the module `WORKER_ID`, added to six `run`
UPDATEs in `worker.py` — the liveness heartbeat, both terminal writes and all
three park writes — so that a worker displaced by a stale reclaim can no longer
assert liveness on, finalize, fail, park, or write an `Output` row for a run it
has lost, while `REAP_SQL` stays deliberately unfenced and is now asserted so.

```
failure                : ... WHERE id=:id AND status='running' AND worker_id = :wid   binds=['e','id','wid']
REAP_SQL contains worker_id: False
```

### The bind is `WORKER_ID`, and one test discriminates

At claim time `claimed["worker_id"] == WORKER_ID`, so no happy-path assertion can
tell the two apart. `test_the_wid_bind_is_this_process_not_the_claimed_copy`
drives `execute_run` with a `claimed` dict carrying a FOREIGN `worker_id` and
asserts the captured bind equals `worker.WORKER_ID` and does **not** equal the
foreign value. Without that test the whole fix could be silently reverted to a
predicate that is trivially true for the displaced worker.

### Ordering is forced, and reading the tests is what found it

`AND worker_id = :wid` is appended **after** `AND status='running'`, not before
(which is the natural reading order and the order `_CONSUME_CLAIM_SQL` uses).
Three pre-existing tests constrain it:

| Test | Assertion | Would have broken if the fence went first |
|---|---|---|
| `test_status_gates.py:189` | `"WHERE id=:id AND status='running'" in src` | yes |
| `test_gate_replay.py:973` | same exact substring, on the runtime string | yes |
| `test_checkpoint_resume.py:483` | `count("AND status='running'") >= count('"UPDATE run SET status=')` | no (count-based) |

Both substring failures would have reported **"the cancel guard is gone"** — a
false message that invites exactly the wrong fix (deleting the assertion) on a
change that in fact strengthens the guard.

## 3. The park decision, and why it went the way it did

**Decision: the three park writes ARE fenced.** This is a deliberate extension
beyond the literal wording of D-23.1-06 ("`_HEARTBEAT_SQL` and the terminal
write"), taken under deviation Rule 2, and it is one commit to back out
(`6722560`) if the phase owner disagrees.

**Why.** Every guard in this subsystem keys on `status='running'`:
`_HEARTBEAT_SQL`, `CLAIM_SQL`'s reclaim arm, `REAP_SQL`, `_CONSUME_CLAIM_SQL`,
and both terminal writes. A park moves the row **off** `running`. So a displaced
worker that parks a run it lost:

1. disarms the new owner's own — now fenced — terminal write, which then matches
   zero rows, so the real execution finishes and writes nothing at all; and
2. leaves the run sitting in `needs_input` asking a human to answer clarifying
   questions produced by an execution that was already abandoned.

Fencing the terminal writes while leaving the parks open therefore leaves the
same tampering primitive (T-23.1-17) reachable through a different door — and a
user-visible door at that. A partial fence that has an equivalent bypass is a
correctness gap in the mitigation being shipped, not a scope saving.

**Why it is safe.** The legitimate owner's row always carries
`worker_id = WORKER_ID` (`CLAIM_SQL` stamps it; `_CONSUME_CLAIM_SQL` re-verifies
it), so the only behaviour change is that a displaced park matches zero rows —
identical to how a cancelled run already behaves. Proven, not assumed:
`test_owner_can_still_park_a_run` runs the real `execute_run` against a real
Postgres and asserts the run reaches `needs_input` **and still carries its
clarifying questions** (a park that lost its payload would be a park the user
cannot act on). `test_displaced_worker_cannot_park_a_run` is its mirror.

No existing test asserts the park SQL text in a way the append disturbs; the
count-based `test_checkpoint_resume.py::test_worker_park_branch_keeps_the_cancel_guard`
still reads 5 guards against 5 terminal UPDATEs and stays green.

## 4. `REAP_SQL` is NOT fenced, and is now asserted unfenced

Proven twice, deliberately at two different levels so a text-only cleanup cannot
pass:

- `test_reap_sql_must_never_be_fenced_by_worker_id` — `"worker_id" not in
  REAP_SQL.text`, and the guards it *does* need (`status = 'running'`,
  `reclaim_count >= :max_reclaims`) are still present.
- `test_reap_still_fires_on_a_run_whose_worker_is_gone` — **LIVE**: seeds an
  abandoned over-ceiling run owned by a foreign worker and asserts `REAP_SQL`
  reaps it to `failed` with a non-empty sentence. This is what makes the absence
  real behaviour rather than missing text.

The reasoning is written into the test's docstring and the module docstring:
`REAP_SQL` exists to fail a run whose worker has gone silent **and** has
exhausted `MAX_RECLAIMS`. Adding `worker_id = :wid` would let the reaper fire
only on runs the reaping process already owns — i.e. never on the abandoned runs
it was built for. Those rows would then sit in `running` forever, unretryable
(the intake's retry gate excludes `running`), which is precisely the failure
`REAP_SQL`'s own comment says it prevents. A safety net becomes a permanent leak.

## 6. Deviations from plan

### 1. [Rule 1 — Bug] `test_stale_reclaim.py` seeded an ownership shape the fix makes impossible

- **Found during:** Task 1, by the recorded per-file delta (it is the only reason
  this was caught — the file is green at baseline and green after, so a
  count-only check would have shown nothing wrong at either end).
- **Issue:** `test_heartbeat_loop_writes_then_stops_on_cancel` seeded
  `worker_id="worker-under-test"`, a literal placeholder, then drove the real
  `_heartbeat_loop`. Once `_HEARTBEAT_SQL` binds the module `WORKER_ID`, that
  seed is the **displaced-worker** shape, so the loop correctly refused to write
  and the test failed — for the right reason:
  `assert beating > seeded` with both timestamps byte-identical.
- **Fix:** seed `worker_id=worker.WORKER_ID`, the id `CLAIM_SQL` actually stamps
  and therefore the only shape a live heartbeat ever sees, with a comment saying
  why the literal cannot come back. Both properties the test pins (the loop
  advances `heartbeat_at`; a cancel stops it) are untouched; the displaced case
  it accidentally described is now proven deliberately in the new file.
- **Not a weakening:** before the fix `worker_id` was irrelevant to the
  statement, so the seed was arbitrary. It is now load-bearing, and a foreign id
  there would assert that a displaced worker CAN heartbeat — the defect.
- **Files modified:** `tribunal/nestor_pulse_sdk/tests/test_stale_reclaim.py`
  (outside the plan's `files_modified`; unavoidable, and the edit is 1 value + 8
  comment lines)
- **Commit:** `2c02c26`

### 7d. CONFIRMED — the environment claim holds, and the order-dependence is the whole story

`23.1-CONTEXT.md` § 10 and the plan's `<environment>` state the tribunal suite is
not reliably runnable here (178 failed / 2273 passed / 13 errors,
order-dependent). **Confirmed at the suite level:** the whole-directory run gives
**170 failed / 2307 passed / 21 skipped / 3 xfailed / 6 errors**, and the
pre-change tree gives **170 failed / 2287 passed** with an identical failure set
(§ 9a) — the same shape the CONTEXT records. I first hypothesised this was an
incomplete-install artifact; that was wrong, and the numbers above are from a
complete install.

Two separate effects were in play and it is worth keeping them apart, because one
of them changes how a future executor should set up:

1. **A partial install looks exactly like the order-dependence, and isn't.** My
   first measurement pass ran while `pip install` was still going and produced 3
   failures in `test_async_worker`, 4 in `test_status_gates` and a collection
   ERROR in `test_gate_replay` (`ModuleNotFoundError: No module named 'fastapi'`,
   though `fastapi==0.136.3` is line 38 of `tribunal/requirements.txt`). **Every
   one went green once the install finished.** Anyone recording a baseline here
   must confirm `pip` has exited before measuring, or they will bake install
   noise into the number they later measure a delta against.
2. **The real order-dependence is unaffected by that.** With a complete install
   AND a DSN, all 11 files run ALONE are green, and the same tests run in one
   batch are not. That is why this plan measures per-file deltas, per the CONTEXT
   ruling, and why the full-suite figure below is reported for information rather
   than used as an acceptance gate.

The `role "worker_user" does not exist` family is separately explained and is a
DSN problem, not an order problem: a `postgres:15` container with `worker_user`
created (the shape `cloudbuild.test-critical.yaml` provisions) turns them green.
`test_stale_reclaim.py` went from 5 skipped to 5 passed on exactly that, which is
also what made the 13 LIVE proofs in this plan runnable at all.
