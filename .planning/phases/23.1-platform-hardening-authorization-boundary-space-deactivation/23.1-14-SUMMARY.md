## Task 1 — the three fixes (`7d86450`)

All three were TEST defects. No product code changed; `autoescape` is still on
(`app/mail/render.py:38`).

**1. `test_invite_carries_link`.** The jinja environment has `autoescape` on by design (the
T-10-01 XSS guard) and a Firebase action link carries a query string, so its `&` renders as
`&amp;`. Rendering it confirmed: the CTA emits
`href="https://auth.example/action?mode=resetPassword&amp;oobCode=XYZ123"`. The old
`assert action_link in html` compared the raw URL against escaped output and could only ever
have passed with the guard OFF.

It now asserts both halves: the escaped link IS present inside the `href` (D-09 — the invite
really does carry its action link), and the raw form is ABSENT. The second half is what makes
it meaningful — the test now fails if someone disables autoescape, where before it failed
*because* autoescape was on. A new sibling, `test_invite_autoescapes_hostile_cta_url`, covers
the property the original was reaching for: a `cta_url` of
`https://evil.example/a"><script>alert(1)</script>` renders as
`...a&#34;&gt;&lt;script&gt;...`, so no live tag and no early-closed attribute.

**2 & 3. The two migration tests — replaced, not repaired.**

`test_carries_grants` built `f"GRANT ... ON {SCHEMA}.{TABLE} TO app_superadmin"` from its own
constants and looked for that *interpolated* string in the migration's *raw source*, where it
exists only as an f-string with `{SCHEMA}.{_NEW_TABLE}` placeholders
(`0011_research_runs.py:242-244`). It could never have matched.
`test_0012_no_server_default_on_new_columns` asserted `"server_default" not in src` over a
file whose own docstring says the columns are added "with NO ``server_default``".

Both source-text assertions were **deleted**, not kept alongside the replacements. A text
assertion that "also passes" is precisely the trap this phase keeps hitting: it reads green
while meaning nothing, and it makes the next docstring edit look like a regression.

The replacements assert against the schema `alembic upgrade head` actually built:

| new test | asserts |
|---|---|
| `test_research_runs_grants_app_superadmin_crud` | `information_schema.role_table_grants` shows app_superadmin holding SELECT / INSERT / UPDATE / DELETE on `nestor.research_runs` — each checked **separately**, so a partial grant names the missing one |
| `test_research_runs_grants_runtime_sa_when_configured` | the env-guarded runtime-SA half: asserts the same four privileges when `RUNTIME_DB_USER` is set and the role exists, and otherwise SKIPS with an explicit reason |
| `test_0012_columns_have_no_server_default` | `column_default IS NULL` for all three 0012 columns |

The runtime-SA test skips in practice (`RUNTIME_DB_USER` is unset in the test container, so
0011's grant never fired). That skip is honest — there is genuinely nothing to observe — and
it prints why, which a vacuously-passing assertion would not.

### Evidence these are behavioural, not better greps

Mutation-tested against a real migrated database, then reverted (`git status` clean, no
`MUTATION` string survives):

| mutation | result |
|---|---|
| `0011`'s GRANT narrowed to `SELECT, INSERT` | **still passed** — see below |
| `0011` gains `REVOKE UPDATE, DELETE ... FROM app_superadmin`; `0012`'s `bundle_key` gains `server_default="x"` | **2 failed, 16 passed** — both new tests red |

⭐ The first mutation is the interesting one and it corrected an assumption. Narrowing 0011's
explicit GRANT changes nothing observable, because `0003_superadmin_bypass.py:96` already
issues `ALTER DEFAULT PRIVILEGES ... GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO
app_superadmin` for future tables in `nestor`. The 0011 comment's "belt-and-braces over 0003"
is literal. So the new test pins the **effective** privilege — which is the property the
security contract actually needs — and does *not* discriminate which migration granted it.
That is a real and deliberate difference from the deleted source grep, and it is stated here
rather than glossed.

**Result: `599 passed, 2 skipped, 0 failed, 19 warnings in 183.76s`** — the summary line the
widened CI gate must reproduce. (Baseline 599 tests -> 601: three source tests removed, one
mail test and four DB tests added.)

## Task 2 — the widened backend gate (`daa3935`)

The marker filter is gone; the step is renamed `pytest-full-suite` and runs
`python -m pytest tests -v -rs`. `-rs` is deliberate: it prints every skip reason, so a test
that quietly stops running appears in the log rather than being absorbed into a summary count.

**The collection assertion uses two numbers, because they catch different things:**

```
EXPECTED_DISK_FILES=66   # tests/test_*.py present  -> catches an incomplete upload
EXPECTED_FILES=65        # files pytest collects >=1 test from -> catches a file that is
                         # present but contributes nothing (broken import / module skip)
```

⭐ Deriving these by running the count, as the plan insisted, was load-bearing. `ls` gives
**66**; pytest gives **65**. Hand-counting from `ls` would have made the gate spuriously red
on its very first execution. The one-file delta is
`tests/test_tribunal_seam_denial.py`, whose module-level
`pytest.importorskip("nestor_pulse_sdk...")` cannot resolve in a backend-only install —
`nestor_pulse_sdk` is confirmed absent from `backend/pyproject.toml`. The config prints the
delta rather than absorbing it into a round number, so a *second* silent file is immediately
visible. There is no early exit for an empty collection: empty is the worst false green and
fails like any other shortfall.

Both numbers were derived inside `python:3.12-slim` itself, not in the local venv.

**T-23.1-65 measured, not assumed.** `docker run --rm python:3.12-slim bash -c ...` reports
GNU bash 5.2.37 plus `grep`/`sed`/`find`, and all three `backend/scripts/*.sh` guards exit 0
when run inside that image against this tree (`ci_no_permissive_rls.sh`,
`ci_no_raw_db_access.sh`, `ci_no_run_research.sh`). So `test_ci_guard_raw_db.py` and its three
siblings will genuinely run in CI rather than hitting their `bash`-missing skip. No install
was added; the result is recorded in the step comment.

`timeout: "1200s"` was left alone, and the config says why rather than raising it
speculatively: the suite is 102-184s.

### How far this was actually validated

The YAML parses, and step 3's script was extracted and **executed verbatim** inside
`python:3.12-slim` against a real `pgvector/pgvector:pg16` container on a docker network
mirroring the config's own: **599 passed, 2 skipped, 102.28s**. The assertion prints
`collection assertion OK: 65 of 65 collected, 66 of 66 on disk`, and with `EXPECTED_FILES`
mutated to 64 it exits 1 with the full diagnostic block. This is the closest local proxy to
the operator's build; it is **not** a Cloud Build result.

## Task 3 — frontend tsc + vitest, and no lint (`4e3a549`)

Two `node:22-slim` steps ahead of `build` (matching the Dockerfile's own build stage;
local toolchain is Node v22.14.0): `install-and-typecheck` runs `npm ci` + `npx tsc --noEmit`,
`vitest` runs `npm test`. `npm ci`, never `npm install` — the lockfile is committed. The
vitest step guards on `node_modules` and reinstalls if `/workspace` did not carry it over,
because a step that silently reinstalls costs a minute while a step that silently skips is a
green tick that tested nothing. Confirmed no `waitFor` anywhere, so `build` runs strictly last.

Both step scripts were extracted and executed verbatim in `node:22-slim` against a true-LF
tree with no `node_modules`: step 1 exit 0 (`typecheck OK`), step 2 exit 0 (10 files, 154
tests), and step 2 reused the install rather than repeating it. Again: not a Cloud Build run.

### ⭐ The inherited lint numbers were wrong by two orders of magnitude

The plan, plan 08's `DEF-23.1-02` and `23.1-CONTEXT.md` all record "61 errors + 38 warnings on
an LF checkout" with everything else dismissed as CRLF artifacts. That figure was never
measured on an LF tree: it counted the non-`prettier/prettier` messages and assumed every
`prettier/prettier` message was a line-ending artifact.

Measured on a genuine LF tree — `git -c core.autocrlf=false -c core.eol=lf archive HEAD`,
because plain `git archive` still applies `core.autocrlf` and yields CRLF — linted inside
`node:22-slim`:

| tree | errors | warnings |
|---|---|---|
| **true LF** | **6540** | **36** |
| this machine's Windows tree | 28924 | 36 |

By rule on LF, across **91 files**: `prettier/prettier` **6480** (99.1%),
`@typescript-eslint/no-explicit-any` 54, `no-empty` 4, `prefer-const` 2. Warnings:
`react-refresh/only-export-components` 32, `react-hooks/exhaustive-deps` 2, 2 with no rule id.
Worst file: `src/routes/admin.pulse.intakes.$id.tsx`, 1148 errors alone.

So there are **two** distinct problems, not one: ~6480 genuine formatting violations that have
nothing to do with line endings (the repo was never prettier-formatted), plus the CRLF
divergence that inflates that to 28864 on this machine (`core.autocrlf=true`,
`git ls-files --eol` -> `i/lf w/crlf`) and means `gcloud builds submit` from here uploads CRLF
sources. Only **60** of the 6540 errors are non-formatting.

The disposition is unchanged and now better supported: **no lint step**. A blocking lint gate
would land red and block every merge (T-23.1-63). The cleanup is a ~91-file prettier sweep
that must follow a settled line-ending policy, not a 61-error tidy-up. The reason is recorded
in two places with these measured numbers, as the plan requires: the header of
`frontend/cloudbuild.yaml`, and `deferred-items.md`.
