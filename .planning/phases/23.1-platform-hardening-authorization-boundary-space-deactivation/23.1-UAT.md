## 3.4 — ⚠ 0014 IS THE RISKY ONE. Read this before running it.

`0014` does **more than create an index**, and production almost certainly holds the rows it has
to resolve first.

1. **`CREATE UNIQUE INDEX` ABORTS on a table that already violates the constraint.** Nothing has
   constrained duplicate `running` skill-run rows since Phase 7, and
   `sweep_orphaned_skill_runs` only runs at app startup and only clears rows older than 30
   minutes. **Duplicates very probably exist in the live database.** Without the pre-flight this
   migration fails the deploy.
2. **The pre-flight closes older duplicates as `failed`.** It keeps the **newest** row of each
   `(intake_id, skill)` group running — an actually in-flight run must not be killed by its own
   migration — and stamps the others with
   `"superseded by a newer run of the same skill; closed when the single-active-run invariant was introduced"`.
   The tie-break is `(created_at, id)`, a **total** order: `created_at` alone ties for rows written
   in one transaction (`server_default now()` is fixed per transaction), which would leave both
   running and the index creation would still abort.
3. **RLS FORCE is dropped for exactly that one statement and restored in a `finally`.**
   `skill_runs` carries FORCE ROW LEVEL SECURITY, which binds the table OWNER — the role alembic
   runs as. With no `app.current_space_id` GUC set, a plain cross-space `UPDATE` matches **zero
   rows, silently**. The policies themselves are never dropped, altered or re-created, and a raise
   in between rolls the FORCE back with the transaction.
4. **`downgrade()` drops the index and NOTHING else.** The duplicate resolution is **one-way** —
   those rows' pre-migration status is gone and there is no record of which were genuinely in
   flight. Reversing 0014 does not restore them.

# § 7 — Reading discipline

Three rules. Each has cost this project something.

### 1. Read build status from `builds describe` — **never** a shell exit code.

`gcloud builds submit … | tail` returns the **PIPE's** status. A **FAILED build reports exit 0**
through a pipe. Every build status recorded in this document must come from:

```bash
gcloud builds describe BUILD_ID --format='value(status)' \
  --account=tools@dotto.be --project=project-cb01b861-cb4a-438d-b9a
```

Related: your terminal times out at ~2 minutes while the build keeps going. **Poll by build id.
NEVER resubmit.**

### 2. Prove a deploy with `status.imageDigest` off the REVISION — **never** `containers[0].image`.

`containers[0].image` is a **mutable tag**. It can read `:20260904-…` while the revision is running
whatever that tag pointed at when it was pulled. The only claim worth making is that the digest
**changed**, which is why § 0's Q-PRE-1 exists at all: without a *before*, an *after* digest proves
nothing.

### 3. Smoke on `/readyz` — **not** `/healthz`.

`/healthz` **404s from the Google upstream** on this deployment while `/readyz` returns 200. That
404 is **pre-existing** and is **not** a deploy failure. Do not chase it, and do not record it as
one.

### A fourth, general one, because it has bitten twice

**A substring match is not evidence.** `pipeline.py:4570`'s local dict named `verification_report`
would have dragged the money-risk `tribunal-worker` into a deploy surface derived by name.
`"PASSED"` contains the substring `sse`, which once made a grep for SSE tests return *every* test.
`canHaveVerificationReport` contains `VerificationReport`. **Derive by imports.** § 1b does.
