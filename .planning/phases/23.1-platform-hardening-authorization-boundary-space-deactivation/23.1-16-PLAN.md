## THE EXACT WINDOW — RE-VERIFIED HERE, AND IT IS NARROWER AND SHARPER THAN "CLAIMS GET MINTED"

Traced independently at `29bc2f1`, confirming `23.1-CONTEXT.md` D-23.1-13:

- `app/api/auth_routes.py:99` is the SOLE caller of `sync_claims_from_membership`
  (`grep -rn` over `backend/app` returns that one call site plus the definition and docstrings).
- `session.py:139-142` short-circuits with **NO DB READ AT ALL** when the token already carries
  a `role` claim, returning `ALREADY_SYNCED`. So the missing filter cannot bite for a token
  that is already synced.
- `auth_routes.py:89` catches `auth.UserDisabledError` and returns **401 before login-sync

**The two exclusions leave exactly one window, and it is the partial-cascade failure.** A
member whose row says `space_deactivated`, whose IdP disable did NOT land, presenting a
still-valid ID token with no baked-in claims, hits `/auth/session`; `_find_membership` returns
the row and fresh `role` + `space_id` claims are minted for someone the operator just cut off.

This is why Task 1's central case is that scenario and not the happy path. It is also why the
refusal tests must assert on the RECORDED `set_custom_user_claims` CALL LIST: a `SyncResult`
value alone does not prove no claim was minted, and minting is the harm.

## THE INTERACTION WITH admin_routes.py:236 — RULED HERE, NOT LEFT FOR AN EXECUTOR

`admin_routes.py:230-241` guards individual deactivation with:

    if (membership.role == "superadmin"
        and membership.status == "active"
        and repo.count_active_superadmins() <= 1):
        raise 409 "Cannot deactivate the last active superadmin"

Once plan 23.1-03's cascade marks a member `space_deactivated`, that guard no longer fires for
them. **That is CORRECT and no change is needed.** The guard exists to stop the active
superadmin count reaching zero, and `count_active_superadmins()` counts `status == "active"` —
a `space_deactivated` superadmin is ALREADY not counted, so deactivating them further cannot
drop the count. Skipping the guard is arithmetically right, not an oversight.

What it means in practice is worth stating plainly, because it is a real and desirable
semantic: individually deactivating an already-cascade-deactivated member flips
`space_deactivated` -> `deactivated`, which converts a reversible space-level suspension into
a permanent individual one. A later space reactivate will then NOT restore that member (plan
23.1-03's selective inverse restores only `space_deactivated` rows). That is "fire someone
whose space is currently off", and it works. Record this paragraph in the code comment so the
next reader does not file it as a bug.

The self-deactivation guard at `:230` (`membership.provider_user_id == identity.uid`) is
status-independent and is unaffected.

## WHAT THIS PLAN MUST NOT DO

- **Do NOT change the `SyncResult` contract.** Three states, same meanings, same HTTP mapping.
  A deactivated member must return `NO_MEMBERSHIP` and reach the caller's 403 — the SAME
  outcome as a user with no row. Do not add a fourth state, do not add a distinct error
  message, and do not log anything at the route that would let a caller tell the two apart.
- **Do NOT weaken the CR-01 `email_verified` guard** at `session.py:145-147`. The email arm is
  only reached when the token asserts `email_verified`; that stays exactly as it is, and this
  plan ADDS a status test on top of it rather than replacing it.
- **Do NOT touch the CR-02 `.scalars().first()` shape.** Both arms resolve to a single row so
  the handshake can never raise `MultipleResultsFound` and turn an auth decision into a 500.
  Adding a `WHERE` narrows the candidate set; it must not change the `.first()` resolution.
- **Do NOT add a DB call to `app/auth/dependencies.py`.** D-06 keeps it DB-free and D-23.1-03
  rejected an org-status lookup there by name. This plan changes login-sync only, which
  already opens a session.
- **Do NOT change `admin_routes.py`.** The interaction above is ruled as correct-as-is.
