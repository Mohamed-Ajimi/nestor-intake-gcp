## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → FastAPI (multipart) | Untrusted file bytes + declared category cross here; server authors the key and enforces size/type |
| Client key param → signed-url/delete | Client-supplied object key is untrusted; validated by ownership 404 + prefix assert |
| bg task → GCS (audio fetch) | download_bytes runs in the AI-06 no-DB-connection window |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-05 | Information Disclosure / EoP (IDOR/BOLA) | signed-url + delete key params | mitigate | ownership 404 (`intake_repo.get -> None -> 404`) + `key.startswith(f"{intake.space_id}/{intake_id}/")` assert (Task 2); cross-tenant suite asserts 404 (09-01) |
| T-09-06 | Tampering | path traversal via category/filename | mitigate | category restricted to CATEGORIES; key server-authored via build_object_key; client `path`/`bucket` never trusted (Task 2) |
| T-09-07 | Denial of Service | oversize / zip-bomb upload | mitigate | authoritative `read(_MAX_BYTES+1)` 25 MB cap -> 413 (Task 2); Cloud Run 32 MB front-end backstop |
| T-09-08 | Tampering / Info Disclosure | content-type spoofing | mitigate | declared-MIME + extension allowlist -> 415 (Task 2); attachment disposition (09-01) neutralizes render attacks |
| T-09-09 | Information Disclosure | dangling GCS object or DB ref after delete | mitigate | delete cleans the intake_sources ref in the SAME tx as the object delete; idempotent on already-gone object (Task 2, D-09) |
</threat_model>
