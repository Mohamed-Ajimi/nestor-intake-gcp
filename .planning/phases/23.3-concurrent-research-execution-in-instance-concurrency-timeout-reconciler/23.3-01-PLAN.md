<objective>
Put a run-level wall-clock ceiling around `runner.run()` in the Tribunal worker, so a hung
run is cancelled and failed with a worded reason instead of blocking its instance forever.

Purpose: `d6bb3aae` ran for **1472 minutes** in production (23.3-CONTEXT.md § 1). The
heartbeat is a separate `asyncio.Task` that keeps writing every 30s while `runner.run()`
is stuck, so the row never goes stale, `REAP_SQL` never touches it, and the worker stays
blocked on the `await` forever (§ 6). Stage-level timeouts already exist — 35 min per
provider, 300 s per skeptic batch, a 30 s redirect deadline, `AsyncOpenAI(timeout=3600)` —
so this is a BACKSTOP over them, not a replacement, and it is NOT a complete cure:
`asyncio` cancellation only bites at an `await`, so a synchronous or C-extension hang will
not be interrupted (§ 6, trap 8). Say that in the code; do not oversell it.

Output: a bounded `execute_run`, a worded terminal message, and three tests.
</objective>

  <action>
Add, next to the other module constants (after `MAX_RECLAIMS`):

`RUN_TIMEOUT_MINUTES = float(os.environ.get("NESTOR_WORKER_RUN_TIMEOUT_MINUTES", "120"))`

Read as float, like `POLL_INTERVAL_SECONDS` and `HEARTBEAT_INTERVAL_SECONDS` and unlike
`STALE_RUN_MINUTES`, so a test can collapse it sub-minute without a code change. Give it a
comment block that records the DERIVATION, not a preference — this is D-23.3-04:

  * the longest run that legitimately completed is `7dcf51d5` at 64.2 minutes;
  * the ceiling is 120 minutes, 1.87x that, so ordinary variance above the longest run
    ever observed does not kill a run that has already spent ~$25-45;
  * a ceiling BELOW ~64.2 min kills legitimate runs *and* burns the money they already
    spent (23.3-CONTEXT.md trap 7);
  * it bounds `d6bb3aae`'s 1472-minute pathology to 120 minutes, a 12x reduction;
  * it is unrelated to Cloud Run's `--timeout=3600`, which applies to REQUESTS; the poll
    loop is not a request, so nobody should "align" the two.

Also state, in the same block, that this is a BACKSTOP over the stage-level timeouts that
already exist (35 min per provider `degraded_parallel.py:103`, 300 s per skeptic batch
`pipeline.py:261`, a 30 s redirect deadline, `AsyncOpenAI(timeout=3600)`), and that
`asyncio` cancellation only takes effect at an `await` point — a hang inside a synchronous
call or a C extension is NOT interrupted and the worker stays blocked. Do not write a
sentence that claims the hang is cured.

In `execute_run`, wrap ONLY the `await runner.run(...)` expression:

    async with asyncio.timeout(RUN_TIMEOUT_MINUTES * 60):
        result = await runner.run(...)

Nothing else moves inside it. The post-completion branches (needs_input, needs_report_spec,
park, the success finalize) stay outside: a slow terminal DB write must not be cancelled by
a ceiling that exists to bound the ENGINE.

Add a handler `except TimeoutError:` placed AFTER `except RunCancelled:` and IMMEDIATELY
BEFORE `except Exception as exc:`. Ordering is load-bearing and must be commented: in
Python 3.11+ `asyncio.TimeoutError` IS the builtin `TimeoutError`, which derives from
`OSError` and therefore from `Exception` — so without its own branch the existing generic
handler would catch it and write `error_message = str(exc)`, which for a bare `TimeoutError`
is the EMPTY STRING. The operator would get a `failed` run carrying no reason at all.

The branch must:
  * `log.error("run_timed_out", run_id=..., ceiling_minutes=RUN_TIMEOUT_MINUTES)`;
  * open its own session, `set_tenant_context(session, claimed["tenant_id"])` first
    (T-06-02), then run the SAME fenced write the `except Exception` branch uses —
    `WHERE id=:id AND status='running' AND worker_id = :wid`, `:wid` bound to the module
    `WORKER_ID`. The fence is not optional: an unfenced write moves the row off `running`
    and disarms the real owner's own status guard (D-23.1-06);
  * carry a worded `error_message` built by a new `_timeout_message()` helper written in
    the register of `_reap_message()` — it names the ceiling in minutes, says the run was
    stopped rather than left to run up an unbounded bill, and says a person should look at
    it. No code, no exception repr.

Do NOT touch the `finally` block. `_hb.cancel()` already runs on every exit path including
this one, and hoisting the heartbeat anywhere else would make every concurrent run share
one liveness signal (23.3-CONTEXT.md trap 9).
