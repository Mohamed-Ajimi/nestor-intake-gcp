# Phase 23.3 Plan 06: Reconciler Trigger, Runbook Truth, and the Spend Deferral — Summary

The orphaned-run sweep now fires on a 5-minute in-process timer inside `nestor-api` — offloaded
with `asyncio.to_thread` so a 30-second seam call cannot stall request handling — and the two
pieces of documentation that would have silently disabled it are corrected.

## What was built

**1. The trigger (`backend/app/main.py`).**

- `RECONCILE_INTERVAL_SECONDS = float(os.environ.get("NESTOR_RECONCILE_INTERVAL_S", "300"))`.
  `0` or negative disables the timer and logs a WARNING saying it did.
- `async def _reconcile_loop()` — sleeps FIRST, then `await asyncio.to_thread(sweep_once)`,
  `except Exception: log WARNING; continue`, and logs the tally only when `claimed` is truthy.
- `lifespan` creates the task inside a `try/except` (startup must never fail because the
  reconciler could not start), holds it both in a local and on `app.state.reconcile_task`, and
  on shutdown cancels + awaits it under `contextlib.suppress(asyncio.CancelledError)` **before**
  the existing engine dispose.
- **No route added.** A Cloud Scheduler HTTP trigger remains available later; adding an endpoint
  now would create request surface for an API nobody can call (DEF-23.3-10).

**2. Six tests (`backend/tests/test_reconciler_lifespan.py`)** — ticks with zero HTTP requests;
answers `/healthz` while the sweep blocks its thread; survives a raising sweep; survives a
reconciler that cannot start; honours the kill switch **and** logs it; shuts down with the task
cancelled and no pending-task warning.

**3. `infra/DEPLOY-RUNBOOK.md`** — Step 4 corrected to `--min-instances=1` with the measured live
table; `--no-cpu-throttling` flagged as load-bearing at its point of use; a new § Phase 23.3
deploy section ordered "queue empty first, worker last"; the `:874` line disambiguated.

**4. `deferred-items.md`** — `DEF-23.3-00` plus `-09` … `-15`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug] Three log assertions passed alone and failed in the full suite. Root cause PROVEN, not tuned away.**

- **Found during:** Task 2, first full-suite run (`4 failed, 787 passed`).
- **Issue:** `logs.records` was empty in tests 3, 4 and 5 whenever any DB-backed module ran
  first, while the behavioural half of each assertion passed.
- **Diagnosis (measured, not inferred):** `backend/app/db/alembic/env.py:41` calls
  `fileConfig(config.config_file_name)`; `logging.config.fileConfig` defaults to
  `disable_existing_loggers=True`; `alembic.ini`'s `[loggers] keys = root,sqlalchemy,alembic`
  names none of this app's loggers. So the conftest's `alembic upgrade head` sets
  `logging.getLogger("nestor.health").disabled = True` **for the rest of the pytest process**,
  and a disabled logger drops records before any handler sees them. Reproduced in isolation:
  handler attached → `warning()` → 1 record → `fileConfig("alembic.ini")` → `warning()` → still
  1 record, `disabled` now `True`.
- **Fix:** `_capture` clears `lg.disabled` for the assertion and restores it afterwards, with the
  mechanism and the reproduction written into its docstring.
- **⚠ Registered as DEF-23.3-15** because the *visible* direction (a false RED) is the harmless
  one. The dangerous direction is silent: any assertion of the shape "no ERROR was logged" goes
  **vacuously GREEN** across this entire suite. Pre-existing; this plan neither caused nor fixed
  the underlying `env.py` call.
- **Files:** `backend/tests/test_reconciler_lifespan.py` · **Commit:** `b6be3b1`

**2. [Rule 1 — Bug] Test 2 was flaky under full-suite load. Fixed by removing the race, not by loosening the budget.**

- **Found during:** Task 2 verification.
- **Issue:** test 2 failed only inside the full 790-test run — first on its non-vacuity guard,
  then, after widening `BLOCK_SECONDS` 0.5→1.5 s, on the warm-up sanity check. The captured
  assertion text showed the cause: the **first** request through TestClient's portal (portal
  handoff, route match, anyio worker-thread spin-up) exceeded a full second on a loaded box, so
  the timer's blocking window had already elapsed before the measurement began.
- **Fix:** the stub is now **armed**. It returns a cheap no-op on every tick until the test sets
  an event, so the warm-up request takes as long as it takes and the blocking sweep cannot begin
  until it is finished. The race is removed rather than out-waited.
- **Why this does not weaken the gate:** re-verified after the change — a loop-blocking
  implementation still fails test 2 in isolation (`1 failed, 5 passed`) and after a DB-backed
  module (`1 failed, 8 passed`).
- **Files:** `backend/tests/test_reconciler_lifespan.py` · **Commit:** `b6be3b1`

**3. [Rule 2 — Missing critical functionality] `app.state.reconcile_task` added alongside the plan's local variable.**

The plan asked for a local strong reference. A local in the lifespan generator frame is a strong
reference for the context's lifetime, and it is kept — but it is invisible to a test, so test 6
(clean shutdown, no orphaned task) could not have been written against it. The task is also
recorded on `app.state`, which is both a strong reference and observable. `lifespan` reads the
`app.state` copy when cancelling. **Commit:** `91bcde6`

**4. [Documented deviation] Test 4 tests the guard the plan meant, not the one it wrote.**

The plan says "with `sweep_once` patched to raise at import/creation time". Patching `sweep_once`
cannot exercise task-*creation* failure — it raises inside the loop, which is test 3. Test 4
instead makes `_reconcile_loop` itself raise synchronously, which is what actually exercises the
`try/except` around `asyncio.create_task(...)`. Same threat (T-23.3-32), correct mechanism. The
deviation is written into the test's own docstring so nobody re-"fixes" it later.

### Out-of-scope discoveries — logged, NOT fixed

## ⛔ DEF-23.3-00 — the uncapped simultaneous-spend exposure (NOT fixed, by ruling)

Recorded plainly, per the operator ruling of 2026-09-07. **No cap was added, and concurrency was
not lowered as a proxy for one** — doing so would overturn the ruling while appearing to comply.

`tribunal-worker` runs `NESTOR_TRIBUNAL_UNCAPPED=1`. This phase takes simultaneous execution from
**1 run** to **M × K = 2 × 4 = 8**.

| | before 23.3 | after 23.3 |
|---|---|---|
| simultaneous runs | 1 | **8** |
| at the $24.78 measured on run `fb9484dd` | ~$25 | **~$198** |
| at the top of the measured $25–45 range | ~$45 | **~$360** |

K = `NESTOR_WORKER_RUN_CONCURRENCY` = 4 is a **memory** bound; M = `MIN_INSTANCES` = 2 is an
**availability** choice; `--max-instances=5` is **inert** on that service. The pre-existing $25
governor is unchanged — and it **has never fired**, so it is not evidence of a working ceiling.

Compensating controls, none of them a cap: rollback with `NESTOR_WORKER_RUN_CONCURRENCY=1` or
`NESTOR_RECONCILE_INTERVAL_S=0`; the runbook's queue-empty-first deploy ordering; and Task 4's
blocking checkpoint.
