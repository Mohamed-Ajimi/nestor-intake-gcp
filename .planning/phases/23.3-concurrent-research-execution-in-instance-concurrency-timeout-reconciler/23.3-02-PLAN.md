<objective>
Make the process-wide LLM concurrency budget scale with the number of runs sharing a worker
process, and pin an explicit timeout on the one provider client constructed without one.

Purpose — and this is the thing 23.3-CONTEXT.md does not say, so read it before you judge
the change out of scope. `audit/audited_llm_client.py:256` is

    _SEMAPHORE = asyncio.Semaphore(8)  # bounds ALL in-flight LLM calls per worker

a MODULE-LEVEL semaphore shared by every coroutine in the process. Today the worker runs
one run at a time, so that one run has all 8 slots. And `pipeline.py:261` sets
`_SKEPTIC_CONCURRENCY = 8` — the skeptic stage, which is ~79% of run cost, is sized to
saturate exactly those 8 slots. Put K=4 runs in one process against an unchanged
`Semaphore(8)` and each run's skeptic stage gets 2 slots instead of 8: every run runs
several times slower, and the 120-minute ceiling plan 01 adds would then start killing
legitimate runs. Scaling the semaphore to `8 * K` keeps each run's provider parallelism
byte-for-byte identical to today at any K — which is exactly what "no engine behaviour
change, output comparability preserved" requires. This is scheduling, not engine
behaviour: the same calls are made, to the same models, with the same prompts.

This plan ships with the default K=1, so at merge time NOTHING changes. Plan 03 raises K.

Output: one new 20-line module, two edits to the LLM client, one test file.
</objective>

  `_SEMAPHORE` calls it once at import, so a runtime change to the env var does NOT resize
  an already-built semaphore. That is intended: the value is deployment configuration.

`deploy-worker.sh` are what raise it.
