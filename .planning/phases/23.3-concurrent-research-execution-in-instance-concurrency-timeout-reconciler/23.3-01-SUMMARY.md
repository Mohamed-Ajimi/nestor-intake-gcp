# Phase 23.3 Plan 01: Run-level timeout backstop Summary

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] The tests were order-dependent through a process-wide cached engine**

- **Found during:** Task 2, first GREEN run (`2 failed, 3 passed`).
- **Issue:** `db.base.get_engine()` is `@functools.lru_cache(maxsize=1)` — **one engine per
  PROCESS** — while pytest-asyncio gives every test its **own event loop**. The first test to
  open a connection cached an engine whose pooled asyncpg connections belonged to a loop that
  was closed by the time the next test ran. `pool_pre_ping` then failed with
  `RuntimeError: Event loop is closed` / `AttributeError: 'NoneType' object has no attribute
  'send'`, and `execute_run`'s generic `except Exception` dutifully wrote `failed`.
  **This artifact wore the exact costume of a real regression: it made the comparability
  guard report a genuinely completed run as `'failed'`.** Had I not chased it, the honest
  reading would have been "the fix broke the success path".
- **Fix:** `_bind_worker_to(live_engine, monkeypatch)` — patches `worker.get_sessionmaker`
  (the name `worker` binds at import; patching `db.base` would not take) to the per-test
  engine. Nothing under test is bypassed: the branch, the fenced SQL and the tenant context
  all still run against real Postgres.
- **Verification:** re-measured the at-HEAD RED **with this fix in place** — still
  `4 failed, 1 passed`, same breakdown. The harness fix does not manufacture the RED.
- **Committed in:** `4b01614`.

**Total deviations:** 1 auto-fixed (Rule 3). **Impact:** none on scope. It is a test-harness
correction; no production code changed because of it.

### ⛔ What this does NOT fix — say this out loud

`asyncio` cancellation **only takes effect at an `await` point**. A hang inside a synchronous
call or a C extension never yields, is never interrupted, and blocks the worker exactly as it
does today. This ceiling ends the class of hang that parks on an await; it ends no other
class. The constant's comment block in `worker.py` says this in as many words, and the test
file's `_HangingRunner` docstring says it again at the point where someone might mistake the
stub for full coverage. **A hung run is not now impossible.**

It is also a **backstop over** stage-level timeouts that already exist — 35 min per provider,
a skeptic batch timeout, a 30 s redirect deadline, a SerpAPI timeout, `AsyncOpenAI(timeout=
3600)`. Coverage before this plan was better than "there are no timeouts", and overselling
this constant would misrepresent that.
