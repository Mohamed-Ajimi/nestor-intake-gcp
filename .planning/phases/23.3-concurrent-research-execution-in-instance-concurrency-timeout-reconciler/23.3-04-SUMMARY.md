## What was built

four columns on `nestor.research_runs`, all `nullable=True` with no `server_default` — a
metadata-only `ADD COLUMN` on a table that holds paid, in-flight rows — plus one partial
btree `ix_research_runs_orphan_candidates` on `driver_heartbeat_at` WHERE
`status IN ('queued','running','needs_report_spec')`. `downgrade()` drops the index and the
four columns and nothing else.

## Criteria that were wrong or unmeasurable — routed, not rewritten

### 1. `alembic check` cannot run in this repository at all

The plan's verification step 3 and Task 1's done-criterion both say "`alembic check` is
clean". **This criterion is unmeasurable here, and was equally unmeasurable at HEAD.** It is
not caused by this plan — `backend/alembic.ini` was not touched.

```
$ python -m alembic check
sqlalchemy.exc.ArgumentError: Could not parse SQLAlchemy URL from given URL string

$ grep -n "sqlalchemy.url" backend/alembic.ini
24:sqlalchemy.url =
```

`alembic.ini` deliberately ships an **empty** `sqlalchemy.url` (env.py and conftest inject
the DSN), so the CLI form fails on every tree, correct or not. This was already documented
in `tests/test_research_dispatch_dedup.py:545-553` — the plan's criterion contradicted a
finding already committed in this repository.

I did **not** quietly drop it. I measured what it was reaching for — ORM metadata versus the
schema `alembic upgrade head` actually built — using alembic's own `compare_metadata`
against the testcontainer, run through a throwaway probe and then deleted:

```
=== research_runs diffs: 0
=== total diffs: 0
```

Zero drift across the whole metadata, including the four new columns, their DB comments and
the new partial index. That is the substance of the criterion; the CLI wrapper for it does
not exist in this repo.

⚠ And per DEF-23.2-15 this would not have been sufficient anyway: alembic's postgresql
`compare_indexes` never inspects `postgresql_where`, so a drifted predicate passes silently.
Test 2 pins the three literals against the deployed `pg_indexes.indexdef` for that reason.

### 2. "764 + this plan's 7" became 764 + 8

The plan predicted seven tests. I shipped eight — the extra one is the reversibility proof
described under deviations. The predicted total was therefore off by one. Reported here
rather than adjusted to fit.

### 3. A criterion with no proof behind it

Task 1's done-criterion says "0017 applies and reverses". Nothing in the plan's seven listed
behaviours would have noticed a broken `downgrade()`. Rather than let a reversibility claim
ride unexercised, I added test 8 (Rule 2 below).

### Deliberate Additions

**3. [Rule 2 — Missing critical functionality] Test 8: 0017 reverses**

The plan's done-criterion claims the migration "applies and reverses" but listed no
behaviour that would catch a broken `downgrade()`. An unexercised reversal is a claim, not
a proof — precisely the "green because it ran nothing" shape this project has been bitten
by. Test 8 drives the real alembic commands against the container and asserts the downgrade
removes exactly the four columns and the one index (and *nothing else* on a table of paid
runs), then that the re-upgrade restores exactly those. 0016's sibling proof lives in
`test_research_dispatch_dedup.py`; this is its counterpart.

### Deliberate Non-Additions

**`resume_research` does not log the missing-email WARNING.** The plan specified that
warning for the trigger path only. A resume by an email-less superadmin creates the same
NULL gap, so the symmetric warning is arguably warranted — but it is unrequested behaviour
with no test pinning it, and this phase's discipline is against quietly widening scope.
**Routed to plan 05**, which is the consumer that actually has to skip such rows and is the
right place to decide whether the gap deserves a second log line.
