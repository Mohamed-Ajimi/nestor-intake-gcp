# Phase 23.3 Plan 03: In-instance worker concurrency Summary

**`worker_loop` no longer awaits a whole research run before claiming the next one: it takes one of K semaphore slots, claims, and dispatches through `asyncio.create_task`, so K runs execute concurrently in one process — proven by two runs from two different tenants being suspended inside `runner.run()` at the same instant on an `asyncio.Barrier(2)`, by their wall-clock intervals overlapping, by a run stuck on `asyncio.sleep(3600)` no longer holding the queue (the second run's terminal write lands FIRST), and by no database session ever being handed two tenant ids.** `MIN_INSTANCES` defaults to 2 and the deploy script now carries K=4, so a later operator deploy gives 2 x 4 = 8 concurrent runs. Nothing was deployed.

## ⭐ TWO CAVEATS ON K=4 THAT MUST NOT BE DROPPED

K=4 is derived from Cloud Monitoring `container/memory/utilizations` P99 for
`tribunal-worker` against its 2Gi limit: idle ~123 MiB, peak with ONE run in flight ~368 MiB
(2026-07-28), so ~245 MiB marginal per run; 123 + 4x245 = 1103 MiB = 54% of 2Gi, where K=8
projects to 2083 MiB and an OOM kill.

1. **It is a 5-minute P99 alignment, not a true high-water mark, so it UNDER-states the
   peak.** A spike shorter than the alignment window is averaged away. This is exactly why the
   answer is 4 and not 5 (66%) or 7.
2. **No sample was ever taken with more than one run in flight.** The ~245 MiB marginal is
   inferred from a SINGLE-RUN delta and assumes the per-run cost is additive and constant. It
   may not be. **K=4 is a conservative reading of single-run data, not a figure measured under
   real concurrency.** The first genuinely concurrent production run is where this number gets
   checked, and whoever watches it should watch memory, not just throughput.

Both caveats are written into `deploy-worker.sh` beside the value, not only here.

## What changed

### `runs/worker.py` (+145 / −29)

`_dispatch_one(claimed, sem)` is new: it holds the EXISTING defensive guard
(`except Exception` → `log.exception("execute_run_crashed")` → swallow) byte-for-byte, plus
`finally: sem.release()`. `worker_loop`'s body is the only other thing rewritten. Five
properties are load-bearing and each is commented at the line that carries it:

1. **Slot first, then claim.** Claiming and *then* blocking on the semaphore would park a row
   at `status='running'` with a `heartbeat_at` stamped by `CLAIM_SQL` and no heartbeat task —
   stale-reclaimed and re-executed at full cost after `STALE_RUN_MINUTES`. That is the D-E
   money defect rebuilt (T-23.3-11).
2. **The claim session is opened and CLOSED before `create_task` and never captured by the
   task.** Every dispatched run reaches the database only through its own per-block sessions
   (T-23.3-09, CONTEXT trap 3).
3. **`inflight` holds a strong reference to every task**, with
   `add_done_callback(inflight.discard)` bounding it (T-23.3-12).
4. **The slot is released in a `finally`, on every path** — success, `RunCancelled`,
   exception, and 23.3-01's `TimeoutError` (T-23.3-13).
5. **The reap still runs on the empty-queue tick only**, and the slot is handed back BEFORE
   that tick sleeps — otherwise an idle queue would retire one slot per poll and the worker
   would silently stop claiming.

## Deviations from Plan

### 1. [Rule 1 — Bug] ⭐ The plan's own slot-release gate is satisfied by a DOCSTRING

- **Found during:** Task 1, running a deliberate counterfactual.
- **Issue:** the plan's Task-1 automated verify is
  `assert 'sem.release()' in d and 'finally' in d` where `d = inspect.getsource(_dispatch_one)`,
  and my first version of the test tripwire was the same shape plus "release appears after
  `finally`". **`_dispatch_one`'s docstring contains the sentence "THE SLOT IS RELEASED IN THE
  `finally`".** So `'finally' in d` is true of the prose, and `find("finally")` returns the
  docstring's occurrence — which sits *before* the code, making the ordering assertion pass
  too.
- **Proven, not suspected.** I built the counterfactual — the release moved out of the
  `finally` onto the happy path only, `else: sem.release()` — and ran it:
  ```
  6 passed, 1 failed
  FAILED test_a_crashing_dispatch_gives_its_slot_back
  ```
  The source tripwire **PASSED on code with the defect it exists to catch.** Only the new
  behavioural test caught it.
- **Fix:** both load-bearing assertions now run against the parsed AST — an `ast.Try` whose
  `finalbody` contains a `release()` call, and no `ast.Await` of a Call to `execute_run_locked`
  anywhere in `worker_loop`. Same counterfactual afterwards: `5 passed, 2 failed` (the
  tripwire now fails too). Prose cannot satisfy a syntax tree.
- **Why this is routed rather than quietly fixed:** a criterion that a comment can satisfy is
  exactly the class of false acceptance criterion 23.1 and 23.2 kept shipping, and this one is
  in the plan text.
- **Commit:** `59680b1`

### 2. [Rule 2 — Missing critical gate] Nothing behavioural covered T-23.3-13

- **Found during:** Task 2, after the six planned tests were green.
- **Issue:** the threat register lists T-23.3-13 (a leaked slot permanently shrinking the
  worker to K-1) as `mitigate`, and the only thing checking it was a grep. None of the six
  planned tests can distinguish a `finally` release from a happy-path-only release: at K=2

- **Labelled honestly:** green at HEAD by construction, so it is not evidence for this change.
  Its at-HEAD result was measured, not assumed (the re-measurement above).
- **Commit:** `59680b1`

### 5. [Rule 3 — Blocking] The tests cannot claim under `app_user` — the worker ROLE is required

- **Found during:** Task 2, harness design.
- **Issue:** `CLAIM_SQL` is a cross-tenant UPDATE issued with NO `app.tenant_id`. Under

  does not mention this, and a test file that used the ordinary `DATABASE_URL` would have
  claimed nothing and timed out for a reason unrelated to concurrency.
- **Fix:** the file reads `DATABASE_URL_WORKER` first (exactly what the worker service mounts
  in production), falls back to `DATABASE_URL`, and a fixture PROVES the connected role can see

### 6. [Rule 2 — Missing critical safeguard] `worker_loop` claims from the WHOLE database

- **Found during:** Task 2, harness design.
- **Issue:** `CLAIM_SQL` picks the oldest claimable row anywhere, and the dev database had
  **55 claimable rows** (47 `queued` + stale `running`). The loop under test would have
  claimed, executed a stub against, and finalized somebody else's runs.
- **Fix:** a `queued_runs_quarantined` fixture holds `SELECT … FOR UPDATE` on every
  pre-existing `queued` row, so `CLAIM_SQL`'s own `FOR UPDATE SKIP LOCKED` skips them —
  non-destructive, released by a teardown rollback — and it PROVES the quarantine held (a
  second connection must find nothing claimable). `STALE_RUN_MINUTES` is parked a year out for
  the duration, which neutralises the stale-`running` claim branch and also stops `REAP_SQL`
  failing a stranger's row on an idle tick. Every test additionally asserts
  `runner.foreign == []`.

  of K slots instead of the whole instance. It is not a cure and must not be written up as one.
- **Raising concurrency raises maximum simultaneous spend.** `NESTOR_TRIBUNAL_UNCAPPED=1` is
  live, runs cost ~$25–45 each ($24.78 measured on `fb9484dd`), and at M=2/K=4 up to 8 can be
  in flight. **No cap was added** — deferred by operator ruling (CONTEXT § 9) — and the
  exposure is stated here rather than mitigated silently.
- **`--max-instances=5` remains inert** and was deliberately left at 5. Raising it still does
  nothing; the footer echo now says so.
