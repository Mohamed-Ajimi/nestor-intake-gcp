<objective>
Replace the worker's one-run-at-a-time loop with bounded in-instance concurrency, and set
the `min-instances` value that goes with it.

Purpose: `worker_loop` claims one run then `await execute_run_locked(claimed)` — the ENTIRE
run — before claiming again (23.3-CONTEXT.md § 3, `worker.py:736/740/795`). Concurrency is
therefore exactly one per instance. And raising `max-instances` does NOT help: the worker
has no real HTTP traffic (`_health_server` exists only to satisfy Cloud Run's PORT
contract), Cloud Run autoscales a service on request concurrency, so **`maxScale=5` is inert
and effective concurrency equals `minScale`** (§ 3, trap 1). Runs are I/O-bound — 35+
minutes long-polling providers — so a semaphore of K on `min-instances=M` gives M×K
concurrent runs at M× idle cost (§ 5).

What must NOT be rebuilt: `claim_one`'s `FOR UPDATE SKIP LOCKED` and the per-run 64-bit
advisory lock in `runs/execute.py` are already what makes >1 executor safe (§ 4, trap 4);
the heartbeat is already a per-run `asyncio.Task` cancelled in a `finally` and must stay
per-run (trap 9); and the failure path already does not block the queue (§ 7, trap 5).
**Only the loop is serial. That is the whole defect.**

Output: a concurrent loop, a deploy-script default, three tests that would each fail today.
</objective>

`runs/execute.py::execute_run_locked(claimed: dict) -> None` — opens its OWN session via
`get_sessionmaker()`, takes `pg_advisory_xact_lock(('x' || md5(:run_id))::bit(64)::bigint)`,
CONSUMES the `(worker_id, started_at)` fencing token, releases the lock, and only then
`await execute_run(claimed)`. It takes NO session argument and must not be given one.

`runs/worker.py::execute_run(claimed: dict) -> None` — likewise takes no session; every
write opens `async with sessionmaker() as session: async with session.begin():` and calls
`set_tenant_context(session, claimed["tenant_id"])` inside it. This per-block session
discipline is already correct for concurrency and is what Task 2's test pins.

  <action>
Rewrite the body of `worker_loop` only. `claim_one`, `execute_run`, `_heartbeat_loop`,
`REAP_SQL`, `_reap_message`, `CLAIM_SQL` and `_health_server` are NOT touched.

```
sem = asyncio.Semaphore(run_concurrency())        # from nestor_pulse_sdk.concurrency
inflight: set[asyncio.Task] = set()
while True:
    await sem.acquire()                            # SLOT FIRST, then claim
    async with sessionmaker() as session:          # unchanged claim, its own session
        async with session.begin():
            claimed = await claim_one(session)
    if claimed is None:
        sem.release()                              # give the slot straight back
        <the existing REAP block, unchanged>
        await asyncio.sleep(POLL_INTERVAL_SECONDS)
        continue
    <the existing reclaim_count warning and run_claimed log, unchanged>
    task = asyncio.create_task(_dispatch_one(claimed, sem))
    inflight.add(task)
    task.add_done_callback(inflight.discard)
```

Five things about that shape are load-bearing; comment each one, because each is a way a
later edit silently breaks it:

1. **Acquire the slot BEFORE the claim, never after.** Claiming first and then blocking on
   the semaphore would leave a row at `status='running'` with a `heartbeat_at` stamped by
   `CLAIM_SQL` and NO heartbeat task running — after `STALE_RUN_MINUTES` it would be
   stale-reclaimed and re-executed at full cost, which is the D-E money defect rebuilt.
2. **The claim session is opened and CLOSED before `create_task`.** It is never captured by
   the task. Each dispatched run reaches the database only through `execute_run_locked` and
   `execute_run`, which open their own sessions per block. A shared session across
   concurrent runs would carry one run's `SET LOCAL app.tenant_id` into another's
   transaction — a cross-tenant defect, not a performance bug (23.3-CONTEXT.md trap 3, the
   highest-severity risk in this phase).
3. **`inflight` holds a STRONG reference to every task.** `asyncio.create_task` returns the
   only strong reference; a task that is merely created and dropped can be garbage-collected
   mid-run, which here would abandon a paid run with its heartbeat still asserting liveness.
   `add_done_callback(inflight.discard)` is what keeps the set from growing.
4. **The slot is released in `_dispatch_one`'s `finally`, on EVERY path** — success,
   `RunCancelled`, exception, and plan 01's `TimeoutError`. A leaked slot silently shrinks
   the worker to K-1 forever, and the symptom (throughput quietly halves after some
   failure) is nearly undiagnosable.
5. **The reap still runs on the empty-queue tick only**, exactly as today: one statement per
   idle poll, never competing with real work.

Add `async def _dispatch_one(claimed: dict, sem: asyncio.Semaphore) -> None` next to
`worker_loop`. It contains the EXISTING defensive guard verbatim —
`try: await execute_run_locked(claimed) except Exception: try: log.exception("execute_run_crashed", run_id=...) except Exception: pass` —
plus `finally: sem.release()`. Nothing else. Keeping the guard byte-identical is what makes
"a failed run does not block the queue" (§ 7) still true, now per task.

Update `worker_loop`'s docstring: it currently says "Claims one run at a time" and "D-09
single-worker simplification", both of which become false. State the new shape, and state
that `maxScale` remains INERT — Cloud Run will never autoscale a service with no requests,
so effective instance count is `minScale` and the only two knobs that matter are
`min-instances` (M) and `NESTOR_WORKER_RUN_CONCURRENCY` (K).

Do not add a shutdown drain, a cancellation handler or a graceful-SIGTERM path. Cloud Run's
lifecycle plus the existing stale-reclaim + `MAX_RECLAIMS` ceiling already cover instance
death (§ 7), and inventing a second recovery mechanism is how the two disagree.
  </action>

| deploy script -> live service | `--set-env-vars` replaces the entire env; an omitted variable is silently dropped from the next revision |
