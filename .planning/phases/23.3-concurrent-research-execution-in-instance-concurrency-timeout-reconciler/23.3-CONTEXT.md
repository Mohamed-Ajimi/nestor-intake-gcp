## § 2 D-23.3-01 — KEEP THE PULL WORKER. Push dispatch is REJECTED, on the measurement.

Push-based dispatch was proposed in-session and then rejected when the durations came back:

* **Pub/Sub push → Cloud Run service**: a Cloud Run *service* request is capped at **60 minutes**.
  `7dcf51d5` (64.2 min) would have been killed mid-run, having already spent the money.
* **Cloud Tasks → HTTP target**: worse — a **30-minute** dispatch deadline, under half the median.
* A pull worker has **no request timeout and no ack deadline to extend**, which is the correct shape
  for a 45–65-minute job.

**Anyone proposing "just use Pub/Sub" must first answer the 64.2-minute run.** Cloud Run *Jobs*
(24 h per task) remain a legitimate future option and are NOT rejected here — they are simply not
needed for this phase, which reaches the goal without new infrastructure.

⚠ This reverses an earlier in-session suggestion of mine that push dispatch was the answer. It was
wrong, and it was wrong because I had not measured run duration. Recorded so the rejected option
does not get re-proposed as a fresh idea.

## § 3 Why runs are serial today — the exact mechanism

`tribunal/nestor_pulse_sdk/runs/worker.py`:

```
:736   while True:
:740       claimed = await claim_one(session)     # ONE run
:795       await execute_run_locked(claimed)      # the ENTIRE run, awaited
```

One run per instance, by construction. And the instance count is pinned at one:

* `minScale=1`, `maxScale=5`, `cpu-throttling=false` (measured on the live service).
* The worker has **no real HTTP traffic** — `_health_server` (`:805`) exists only to satisfy Cloud
  Run's requirement that every revision bind `$PORT`. Cloud Run autoscales a *service* on request
  concurrency, and there are no requests.
* ⭐ **Therefore `maxScale=5` is INERT and effective concurrency is EXACTLY `minScale`.** Raising
  `max-instances` does nothing at all. This is the single most misleading thing about the current
  configuration and the most likely wrong fix.

`cpu-throttling=false` is already set and is load-bearing: with throttling on, an idle Cloud Run
instance has its CPU cut between requests and the background poll loop would stall.

## § 4 Multi-poller concurrency is ALREADY SAFE — do not rebuild it

The hard parts are done and must not be re-implemented:

* `claim_one` (`:161`) claims via `FOR UPDATE SKIP LOCKED` — two pollers cannot claim the same row.
* The dispatch is wrapped in a **per-run 64-bit advisory lock** (`execute_run_locked`) precisely so
  more than one poller/instance is safe for the audit chain (ENGINE-08 / T-13-06). The module
  docstring states this in as many words.
* The heartbeat is already a **per-run** `asyncio.Task` (`:314`), cancelled on every exit path in a
  `finally` (`:715`) — success, `RunCancelled` and exception alike.
* The claim runs WITHOUT tenant context (worker sees all tenants); `execute_run()` calls
  `set_tenant_context(session, run.tenant_id)` IMMEDIATELY after. ⛔ That ordering is a documented
  anti-pattern boundary (01-RESEARCH.md line 583) — **do not set tenant context before the claim**,
  and concurrency must not disturb it: each concurrent run needs its OWN session, never a shared one.

**Only the loop is serial.** That is the whole defect.

## § 5 Runs are I/O-bound — which is why in-instance concurrency is the high-leverage change

A run spends 35+ minutes long-polling provider APIs (`PROVIDER_TIMEOUT_S`,
`degraded_parallel.py:13`), not computing. So one instance can host several concurrent runs.

* A semaphore of **K** on **`min-instances=M`** yields **M×K** concurrent runs at **M×** idle cost.
  Eight always-on instances and `M=2, K=4` both give 8 — one costs 4× the other.
* Connections are not the binding constraint: pool is SQLAlchemy defaults (`db/base.py:34` sets no
  `pool_size`, so 5 + 10 overflow = 15 per instance), and the loop deliberately holds **no DB
  connection across the dispatch** (T-16-06). K is bounded by **memory (2Gi shared)**, not the pool.
* ⚠ K must be chosen against measured memory, not taste. A run holds report text, claims and
  citations in memory; `fb9484dd` produced 444 audit blobs / ~466 MB across the whole bucket. Size K
  from an observed high-water mark, and say in the plan how it was obtained.

## § 6 The hang — real, unbounded, and observed in production

* There is **no `wait_for` and no `asyncio.timeout` anywhere around `runner.run()`**. Verified by
  grep across `nestor_pulse_sdk` excluding tests.
* ⭐ **The heartbeat makes a hang INVISIBLE to the reclaim machinery.** `_heartbeat_loop` is a
  separate task that keeps writing every 30s while `runner.run()` is stuck, so the row never goes
  stale (`STALE_RUN_MINUTES=60`), `REAP_SQL` never touches it, and the worker stays blocked on the
  `await` forever. This is by design — the heartbeat exists so a legitimately silent 35-minute
  deep-research poll is not mistaken for a dead process — and the cost is that a hang and a slow run
  are indistinguishable.
* `d6bb3aae` at **1472 minutes** is that failure, observed in production.

⚠ **Stage-level timeouts ALREADY EXIST** and the run-level bound is a BACKSTOP over them, not a
replacement: 35 min per provider (`degraded_parallel.py:249`), a skeptic timeout
(`pipeline.py:3212`), a 30 s redirect-resolver deadline, a SerpAPI timeout,
`AsyncOpenAI(api_key=…, timeout=3600)` (`audited_llm_client.py:1728`). Coverage is better than
"there are no timeouts" — say so honestly rather than overselling the fix.

⛔ **`asyncio` cancellation only takes effect at an `await` point.** A hang inside a synchronous call
or a C extension will NOT be interrupted by `wait_for`, and the worker stays blocked. The backstop
must never be documented as a complete cure.

The one client constructed with no explicit timeout is the bare `AsyncAnthropic()`
(`audited_llm_client.py:1951`). The SDK's own default applies, so it is not literally unbounded —
but it is the only construction not bounded *by intent*, and the skeptic stage it serves is ~79% of
run cost.

## § 7 A FAILED run already does NOT block the queue — do not "fix" it

`except Exception` around `execute_run_locked` (`:796`) is the LAST statement in the `while True`
body, so a raising run is caught, logged `execute_run_crashed`, and the loop claims the next run.
`execute_run_locked`'s own `finally` cancels the heartbeat and its except-path finalizes the row.
An instance crash is also covered: Cloud Run restarts it and stale reclaim rescues the row after 60
minutes, bounded by `MAX_RECLAIMS=2`, after which `REAP_SQL` fails it with a worded reason.

**Only a HANG blocks.** The failure path is correct and must be left alone.

## § 8 The durability hole is in nestor-api, NOT the worker

This scoping is the difference between a small phase and a rewrite.

**The worker is already durable**: SKIP LOCKED claim + 30 s heartbeat + stale reclaim +
`MAX_RECLAIMS=2` + worded reap. That is a genuine at-least-once execution guarantee.

**What is fragile is `run_poll_driver`** (`backend/app/research/run_task.py:643`): a `while True`
(`:725`) inside a FastAPI `BackgroundTask`, with no wall-clock cap. If that nestor-api instance
recycles — a deploy, a scale event, or Cloud Run's own lifecycle — the driver dies silently: the
engine keeps executing and spending, `research_runs` is never mirrored or finalized, and **nothing
sweeps it**. That is DEF-23.2-03.

**So the fix is a stateless RECONCILER, not a dispatch rewrite.** A sweep that finds every
non-terminal `research_runs` row and mirrors its current engine state makes the per-run poll driver
an *optimisation* (fast updates) rather than the only path to a terminal state.

⚠ **Cloud Scheduler API is NOT ENABLED on this project.** Verified 2026-09-07:
`gcloud scheduler jobs list --location=europe-west1` returns
`PERMISSION_DENIED: Cloud Scheduler API has not been used in project … before or it is disabled`.
Enabling it is an operator/IAM action the agent cannot perform ([[agent-gcloud-readonly-yes-iam-no]]).

So the trigger must be designed as an **in-process periodic sweep inside nestor-api**, which is
self-healing precisely because it is stateless: `minScale=1` guarantees an instance exists, and
unlike the per-run driver **any** instance can recover **any** orphaned run. A Cloud Scheduler
trigger stays available as belt-and-braces once an operator enables the API — design the sweep as a
callable unit so both triggers can drive it.

⛔ **nestor-api runs `maxScale=4`.** Concurrent sweeps from multiple instances must be serialised —
a Postgres advisory lock or a claim, the same pattern the worker already uses. Two instances
mirroring the same run concurrently is the defect this phase must not introduce.

Reuse, do not duplicate: `mirror_tick`, the RESEARCH terminal set (`app/research/run_status.py`),
the 401/403 and 5xx retry budgets, and the completion/park/fail finalize paths all already exist in
`run_task.py`. The reconciler is a different DRIVER over the same machinery.

## § 9 Scope fences

**IN scope:** in-instance worker concurrency; the worker `min-instances` value; a run-level timeout
backstop; an explicit timeout on the bare `AsyncAnthropic()`; the reconciler sweep and its
serialisation; the tests for all of it.

**OUT of scope, explicitly:**

* ⛔ **A concurrency/spend cap — DEFERRED BY OPERATOR RULING, 2026-09-07.**
  `NESTOR_TRIBUNAL_UNCAPPED=1` is live on `tribunal-worker`, so raising concurrency raises maximum
  simultaneous spend (≈$25–45 per run, measured $24.78 on `fb9484dd`). The operator has explicitly
  deferred sizing a ceiling until there is data. **Do not add one. Do not quietly cap concurrency as
  a proxy for it.** Record the exposure in the deferral register and leave the decision open.
* Push-based dispatch (§ 2) and Cloud Run Jobs.
* The frontend. No UI change is required to run more research concurrently.
* The engine's own stages, prompts, models and costs. This phase changes SCHEDULING only —
  **no plan may alter what a run produces.** Output comparability with prior runs must be preserved.
* Enabling the Cloud Scheduler API (operator action).

## § 10 Traps

1. **`maxScale` is inert.** Raising `max-instances` looks like the fix and does nothing (§ 3).
2. **A worker config change BOOTS the container, and the loop CLAIMS FIRST / SLEEPS LAST.**
   `--min-instances=0` is not protection; an empty queue is the only protection. This caused the
   2026-07-28 incident. **Apply worker changes with the queue verified empty.**
3. **Do not set tenant context before the claim** (§ 4), and give each concurrent run its OWN
   session — a shared session would leak tenant context ACROSS concurrent runs, which is a
   cross-tenant defect, not a performance bug. This is the single highest-severity risk in the phase.
4. **Do not re-implement SKIP LOCKED or the advisory lock** (§ 4). They are there.
5. **Do not "fix" the failure path** (§ 7). It already works; only the hang blocks.
6. **A green test proves nothing about concurrency unless it is genuinely concurrent.** A test that
   awaits two runs sequentially passes on the serial code. Prove interleaving with a barrier — the
   shape `23.2-05` used for its CAS (a row-lock barrier proving the interleaving was real, not
   "A finishes then B starts").
7. **Timeout values must be MEASURED, not chosen.** § 1 is the evidence base; a ceiling below
   ~64.2 min kills legitimate runs *and* burns the money they already spent.
8. **`asyncio.wait_for` does not interrupt synchronous hangs** (§ 6). Do not claim it does.
9. **The heartbeat must keep running for each concurrent run independently** — it is already
   per-run, but a refactor that hoists it out of `execute_run_locked` would make every concurrent
   run share one liveness signal and silently break stale reclaim.
10. **Verify the deployed reality, not the IaC.** This project has documented IaC drift; read live
    service config with `gcloud run services describe`, pinning `--account=tools@dotto.be` (four
    accounts are authenticated and the config reverts mid-session).

## § 12 What "done" means

1. Two runs from two different intakes execute **at the same time**, proven by overlapping
   start/end timestamps, not by both eventually completing.
2. A run that hangs is cancelled at the measured ceiling, finalized `failed` with a worded reason,
   and **the queue keeps moving** — proven by a second run completing while the first is stuck.
3. A `research_runs` row whose poll driver died is finalized by the reconciler — proven by killing
   the driver, not by simulating its absence.
4. Route inventory unchanged; no engine output change; `frontend/` diff EMPTY.
