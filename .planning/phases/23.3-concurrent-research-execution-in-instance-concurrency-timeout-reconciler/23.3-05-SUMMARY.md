## The cutoff: `ORPHAN_CUTOFF_MINUTES = 15`, unchanged from the plan

The number is not taste and the derivation is written into the constant's docstring so it
cannot be edited without meeting the argument:

* a live driver `continue`s round its loop **without calling `mirror_tick`** for up to
  `_MAX_METRICS_AUTH_OUTAGE_SECONDS` = 200 × 3.0 s = **600 s = 10 minutes** while it
  tolerates a 401/403 from a Cloud Run revision rollout (itself sized from the live
  2026-07-28 incident);
* the sweep's designed response to a missing heartbeat is to **take the run over**;
* so any cutoff at or below 10 minutes seizes healthy, paid runs mid-rollout. 15 minutes
  clears it by 50%.

Test 9 asserts on the numbers from BOTH modules (`outage == 600.0`,
`_MAX_METRICS_AUTH_RETRIES == 200`, `cutoff > outage`, `cutoff >= outage * 1.5`) so the pair
cannot drift apart in separate commits. Test 3 pins the behavioural half with a 9-minute row
that must NOT be claimed, plus a 30-minute positive control so it cannot pass vacuously.

`LEASE_MINUTES = 5` (> the 30 s `get_metrics` timeout, asserted in test 9) and
`SWEEP_BATCH = 10`.

## Criteria that were wrong, and how each was routed

### 1. The plan's step ordering would have made the CAS fail 100% of the time

Task 2's action says: *"3. `mirror_tick(...)` — always, terminal or not"*, and then
*"5. ... `patch_if` with `expected={"status": row["status"]}` — the status observed at claim
time."*

**Those two cannot both hold.** `mirror_tick` writes `status = metrics["status"]`. On a
terminal tick that is `"completed"`, so by the time step 5 runs, the row's status is no
longer the claim-time `"running"` and the CAS precondition can never match. Every single
terminal reconcile would have returned `skipped_lost_cas` and **the sweep would never have
finalized anything** — while every test that only checked "no double write" stayed green.

**Resolution:** `mirror_tick` is called on the NON-terminal path only. On the terminal path
the finalize IS the mirror — `finalize_completed` / `_failed` / `_parked` already write
status, stage, cost, the timestamps and the `event_seq` cursor in one statement. No value is
lost, one write is saved, and the CAS becomes meaningful: after the claim, only a live driver
can move that status. Written into the code as a comment, not just here.

### 2. `finalize_parked`'s signature in the plan's `<interfaces>` is missing an argument

The plan lists `finalize_parked(session, research_run_id, metrics, *, identity)`. The real
signature is `finalize_parked(session, research_run_id, metrics, park_reason, *, identity)` —
`park_reason` is REQUIRED and must arrive pre-composed as `"[park#<seq>] <reason>"`, because
that marker is the DEC-5 mail-idempotency record. Implemented as `reconcile._park_reason`,
which reuses `run_task._DEFAULT_PARK_REASON` and `_MAX_PARK_MESSAGE_CHARS` and applies the
same ASVS V5 defensive parse of the remote `park` descriptor.

### 3. `grep "reconcile" == 0` — see the RED section above. False at HEAD, twice.

### 4. The plan's DEF ids `-02` and `-03` are already taken

The output block asks me to record "DEF-23.3-02 / DEF-23.3-03". Wave 1's merge already
allocated `-01`..`-04` in `deferred-items.md`, and that file's own heading warns that a
collision has already happened once on it. **Continued at `-05`**: DEF-23.3-05 (the
non-CAS'd non-terminal mirror), DEF-23.3-06 (the superadmin replay identity — the plan's
"-02"), DEF-23.3-07 (a run that never reached the engine — the plan's "-03"). The code

## Test 2's barrier: why it is NOT the `pg_stat_activity` idiom the plan named

The plan says to port `test_run_state_cas.py`'s barrier: a third connection takes
`SELECT ... FOR UPDATE` on the candidate row, then `wait_until_blocked(2)` polls
`pg_stat_activity` until both claim UPDATEs are WAITING.

**That barrier cannot work against this statement, and would have produced a test that
passes on an implementation with no serialisation whatsoever.** The tribunal barrier works
because the statements under test BLOCK on a row lock. This claim uses `FOR UPDATE SKIP
LOCKED`, whose entire purpose is *not* to block: a third connection holding the candidate row
would make **both** sweeps skip it and claim nothing, `wait_until_blocked(2)` would time out,
and any "exactly one winner" assertion phrased over two empty results would be vacuous.

So the interleaving is built the other way round, and it is genuine:

1. sweep A runs in its own thread and is held **inside** its claim transaction — after the
   UPDATE has executed and taken the row lock, before COMMIT;
2. a third connection proves the lock is real, with the same self-check discipline the
   tribunal barrier uses: the row must be **visible** (`SELECT` returns it — otherwise "it is
   locked" would be indistinguishable from "RLS hid it") but **not lockable**
   (`FOR UPDATE SKIP LOCKED` returns nothing). If either half fails the test says *"setup
   failure, not a pass"* and stops;
3. sweep B's **entire** claim then executes inside that window and must claim zero;
4. A is released and commits; it must be the winner;
5. a **third** claim, issued after A's row lock is gone, must ALSO find nothing — which is
   the half only the LEASE can cover.

The perturbation table above shows both halves failing when their mechanism is removed. This
is a deviation from the plan's named technique, taken because the named technique would have
been a false green.
