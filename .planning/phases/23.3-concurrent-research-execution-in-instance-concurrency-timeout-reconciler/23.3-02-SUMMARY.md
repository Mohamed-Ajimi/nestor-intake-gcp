# Phase 23.3 Plan 02: K-scaled LLM slots + a pinned Anthropic timeout — Summary

The worker's process-wide LLM semaphore now sizes itself as `LLM_SLOTS_PER_RUN * run_concurrency()`
instead of the literal `8`, so each concurrent run keeps the same 8 in-flight provider slots it has
today at any K — and the one provider client built without an explicit timeout now carries one.
At the default `K=1` the semaphore evaluates to 8 and nothing changes: this ships as a no-op.

## What was actually wrong

`audit/audited_llm_client.py` owns a **module-level** `asyncio.Semaphore(8)` shared by every
coroutine in the worker process, acquired at five sites (`anthropic_messages`, `serpapi_search`,
`gemini_generate`, `openai_response`, `end_call`). That literal `8` was correct only by accident of
the poll loop being serial: one run at a time meant one run held the whole budget.

`pipeline/tribunal/pipeline.py:260` sets `_SKEPTIC_CONCURRENCY` (default 8), sizing the skeptic
stage — ~79% of a run's cost — to saturate exactly those 8 slots. So K runs sharing one process
against an unchanged `Semaphore(8)` would each get `8/K` slots, stretching every run's wall clock by
roughly K, straight into the run-level ceiling plan 01 adds. The two halves of this phase would have
defeated each other, and the symptom would have read as *"the timeout is too aggressive"* rather
than *"the semaphore was never scaled"*.

## What changed

**`tribunal/nestor_pulse_sdk/concurrency.py` (new, 83 lines).** A leaf module importing only `os`
and `logging` — nothing from the package — so `audit/` and `runs/` can read the same number without
an import cycle and without `audit` importing `runs`.

- `LLM_SLOTS_PER_RUN = 8`. Not a new number: it is what `_SEMAPHORE` has carried since
  PATTERNS 302-304 and what `_SKEPTIC_CONCURRENCY` is sized to saturate. Naming it makes "one run's
  budget" and "the process's budget" two different things, which is the whole point. The comment
  states in as many words that changing it changes ENGINE behaviour and is out of scope for 23.3.
- `run_concurrency()` — a function, not an import-time constant, so tests re-derive without an
  `importlib.reload` dance. Its docstring records that `_SEMAPHORE` calls it **once at import**, so a
  runtime env change does not resize an already-built semaphore; that is deployment config, not a
  runtime dial.

**`audit/audited_llm_client.py`.** `_SEMAPHORE = asyncio.Semaphore(LLM_SLOTS_PER_RUN * run_concurrency())`,
plus a comment block recording the `8/K` starvation reasoning and the interaction with plan 01's
ceiling. The **module docstring at `:17` was updated in the same commit** — leaving it asserting
`_SEMAPHORE(8)` against code that says otherwise is this repository's most-repeated defect shape.
`AsyncAnthropic(timeout=600.0)` at the single permitted construction site.

## Honesty about what the timeout buys

23.3-CONTEXT.md § 6 is already straight about this and the code comment matches it: **the SDK's own
default already applied, so this client was never literally unbounded** — it was the only
construction in the engine not bounded *by intent*. What changes is ownership: an `anthropic`
release that moves its default can no longer silently move ours. 600 s was chosen, not guessed — above
`_SKEPTIC_TIMEOUT_S = 300` so it cannot truncate a legal call, far below the 120-minute run ceiling
so it stays a per-call bound, and equal to the SDK's current default so the change is
behaviour-neutral today. Overselling this as "fixing an unbounded client" would be false.

## Cross-file pollution

A module-level semaphore reloaded under `monkeypatch.setenv` is exactly the shape that causes the
documented DEF-23.2-14 pollution. The test file carries an `autouse` fixture that deletes the env
var and reloads the client module in teardown, so it cannot leave a 32-slot semaphore behind for
whatever runs next. Verified by the full-suite run above showing no new failures anywhere.
