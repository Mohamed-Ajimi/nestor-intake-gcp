## 2. Task 1 — the loop driver

**Commits:** `d53d98c` (the atomic scope-rule swap), `e4f5389` (the loop).

### 2.1 The scope-lock edit was made ATOMIC, as required

`_EVOLVE_PROMPT` line 2297 — `"- Do NOT merge two questions into one, and do NOT
broaden one."` — was deleted **and its replacement wired in the same commit**
(`d53d98c`). The replacement is a new `{scope_rules}` placeholder filled by
`workshop_rank._scope_rules_block()`, which returns
`workshop_evolve.MANDATE_SCOPE_LOCK` + `workshop_evolve.DISCOVERY_EVIDENCE_ANCHOR`.

Three properties that matter:

- **Both halves are IMPORTED, never retyped.** The sharpening prompt and the
  generative prompt now render the same two constants, so they cannot drift into
  two different scope rules.
- **The import is function-local.** `workshop_evolve` imports `workshop_rank` at
  module level (it aliases `_flatten`, `_normalise_langs`, `_parents_of` and four
  more), so a module-level import the other way does not resolve at all.
- **The failure mode keeps the LOCK.** If the import ever fails, the fallback text
  is the mandate half in plain words — a prompt that silently loses its scope rule
  is precisely the regression the edit had to avoid.

Acceptance greps:

| grep | required | actual |
|---|---|---|
| `grep -v '^ *#' workshop_rank.py \| grep -c "Do NOT merge two questions into one"` | 0 | **0** |
| mandate scope-lock replacement present | ≥ 1 | **1** (`MANDATE_SCOPE_LOCK`) |
| `DISCOVERY_EVIDENCE_ANCHOR` present | ≥ 1 | **1** |

### 2.2 THE DECISION: `evolve_winners` vs `evolve_generative`

**Stated in the code at the top of the loop, and here.**

| step | when | job |
|---|---|---|
| `workshop_evolve.evolve_generative` | ONCE PER ROUND, inside the loop | **GENERATION** — grows the population via the five moves. Never touches the winners it was given. |
| `evolve_winners` (this module) | ONCE, after the loop, over the final chosen winners | **SHARPENING** — final wording, and D7 `langs`. |

**`langs` is why the second one survives at all.** It is written only by
`evolve_winners` via `_normalise_langs`, and plan 15.2-13 builds its angle-query
language sentence only when `langs` is non-empty. A loop that routed around it
would ship D7-less winners while every other assertion in this phase read green.

### 2.3 `born_round` is the round the candidate FIRST COMPETES IN

This is the subtlest thing in Task 1 and it is a latent always-passes-criterion
bug if got wrong.

`exit_verdict` tests criterion 3 (SATURATION) as `born_round == round_no` over the
winners **selected in that round**. Selection happens *before* evolve inside a
round, so a candidate written by round N's evolve can never appear in round N's
winner set. Stamping it `N` would make `new_entrants` permanently zero and
criterion 3 permanently TRUE — a criterion that always passes is not a criterion,
and the loop would exit the first time coverage and quality happened to align.

`_stamp_loop_candidates` therefore stamps `round_no + 1`, and says why.

### 2.4 Observed exit-round range

Driven through the REAL `run_workshop_stage_b` with scripted stubs, five seeds,
identical configuration:

```
observed exit rounds: [3, 3, 3, 3, 3, 4]      (six seeds)
winners: 17 for 3 client questions  (5 + 5 + 5 + 2 — the validated shape)
```

Asserted as a **RANGE** (`1 <= r < 10`, plus `r >= 2`), never as a constant. The
`r >= 2` half is load-bearing: without it a run that exited in round 1 would
satisfy the range assertion while proving nothing about the loop.

**A real finding while building this.** The first scripted brief exited at round 1
for every seed, and that turned out to be *correct behaviour*, not a bug: with a
KEEP-heavy population, prefer-KEEP satisfies coverage and quality immediately and
saturation passes trivially in round 1 (nothing carries a `born_round` yet). To
exercise the loop at all, one client question's candidates must be WEAK for the
first rounds so its floor slots have no KEEP to prefer. That is now written into
the test's docstring, because a future reader tuning the fixture back to
all-KEEP would silently reduce the loop test to a one-round test.

**Mutant B is the D7 non-vacuity proof the plan demanded, and getting it to bite
took a second attempt worth recording.** The obvious mutants — deleting the sweep,
or bypassing `evolve_winners` — each left `EMPTY_LANGS=0`, because the *other* one
was still writing `langs`. The mutation had genuinely applied (the harness prints
`[MUTANT APPLIED]` and refuses to be silent about a missed anchor), so this was a
vacuous test, not a failed mutation.

The case that actually bites is the one the source's own comment names: a client
question with **no candidates at all** is repaired by `enforce_scope_guard`
injecting `_verbatim_winner`, which sets `langs: []`, and that winner reaches the
tail **without passing through `evolve_winners`**. That is exactly the plan's
requirement — "a scripted winner reaching the tail WITHOUT passing through
whatever writes `langs` must make this test FAIL" — and it now does.
