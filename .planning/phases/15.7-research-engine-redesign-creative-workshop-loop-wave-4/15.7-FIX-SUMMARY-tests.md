**Confirmed out of scope and pre-existing:**

four tests in the file never call `_run`, which is why they pass.

### H2. `test_the_grouping_call_is_counted_in_the_stage_actions_and_cost` — GREEN, but green **by fixture**

`summary["actions"] == audited.call_count` (now at `:1439`) **passes**. It is not
red, so nothing was relaxed. But the brief's concern is real and I am reporting
it rather than closing it:

- `workshop_rank.py:4920` adds `admission_stats["admission_resolver_calls"]` into
  `actions`.
- `workshop_admission.py:638-640` sets `resolver_calls = 1` **only `if
  batch_urls`**, and the work it counts is `await resolve_redirects(...)` — an
  **HTTP** call, not an `audited` LLM call.
- This fixture produces `grounded_lookups: 0`, so `resolver_calls` is 0 and the
  equality holds **arithmetically by accident**.

So the test is **fragile, not wrong**: the first fixture that exercises the
grounding path makes `actions` exceed `audited.call_count` by the number of
resolver batches.

**THE SEMANTICS QUESTION, FOR YOU — I have not chosen an answer.** Should
`actions` count non-LLM calls?

- **Yes** — `actions` is the stage's work meter and the resolver is real paid-ish
  work (latency, quota, a denial-of-wallet surface T-15.7-08-03 names). Then this
  test's invariant is simply wrong and must become
  `actions == audited.call_count + resolver_calls`.
- **No** — `actions` pairs with `cost_usd`, which only ever accumulates LLM
  spend, and the resolver contributes none. Then `workshop_rank.py:4920` is the
  defect and the resolver term should come out of the sum.

These give different numbers the moment grounding fires, and it is a design call
about what the run's only spend signal is supposed to mean — not a test bug.
