# Phase 15.7 Plan 04: The Within-Run Rejected Register Summary

The workshop can now remember what it already rejected — for exactly one run, with each
entry carrying the flaw that got it barred, and with the two outcomes D-W4-1 forbids
made structurally impossible to express rather than merely left unused.

## What Was Built

One new stdlib-only module, `tribunal/nestor_pulse_sdk/pipeline/tribunal/workshop_register.py`
(631 lines), plus 25 tests appended as SECTION 6 of the already-registered
`test_workshop_critique.py`.

`grep -n "barred" workshop_rank.py workshop.py` returned nothing before this plan. There was

### Exported signatures, verbatim

Plans 15.7-06, 15.7-07 and 15.7-09 code against these.

```python
BAR_KILL_DEFECT   = "kill_defect"
BAR_WEAK_TWICE    = "weak_twice"
BAR_LOOKUP_FAILED = "lookup_failed"

DROP_CLUSTERED_ONTO_BARRED = "clustered_onto_barred"
DROP_CLUSTERED_ONTO_LIVE   = "clustered_onto_live"

def new_register() -> dict[str, Any]: ...

def bar(
    register: Any,
    *,
    text: Any,
    flaw: Any,
    cause: Any,
    round_no: Any = 0,
) -> bool: ...

def note_weak_pass(register: Any, text: Any) -> int: ...

def barred_block(
    register: Any,
    *,
    cap_entries: Any = None,
    cap_chars: Any = None,
) -> str: ...

def record_drop(
    register: Any,
    *,
    text: Any,
    clustered_onto: Any,
    cause: Any,
    round_no: Any,
) -> bool: ...

def drop_summary(register: Any, round_no: Any) -> str: ...
```

`new_register()` returns `{"barred": [], "drops": [], "weak_passes": {}}`.

A barred entry is `{key, text, flaw, cause, round}`.
A drop record is `{text, clustered_onto, cause, round}`.
Both are strings and ints only — no set, no float, no handle.

### Module constants a consumer will reach for

| Constant | Value | Why it is a bare literal and not an env knob |
|---|---|---|
| `_BARRED_TEXT_CHARS` | 200 | A barred entry only has to be RECOGNISABLE; the model is being told what not to propose, not asked to judge it |
| `_BARRED_FLAW_CHARS` | 160 | Matches the width the critique pass already keeps a flaw at, so one sentence does not get two truncations |
| `_BARRED_MAX_ENTRIES` | 24 | Bounds prompt inflation across a ten-round run |
| `_KEY_CHARS` | 600 | Identity only — two questions differing after char 200 are two questions and must not collapse onto one bar |

These are deliberately **not** environment variables. A prompt-injection bound that an
environment variable can widen is not a bound — the same reasoning the admission gate
already records for `_ADMISSION_QUOTE_CHARS`, and the opposite of the `min(5, …)` /
240-char trap class this phase exists to unpick.

## THE LOAD-BEARING QUESTION: is a tournament loser still promotable?

**Yes. Proven by driving the real guard, not by inspection.**

Test: `test_a_candidate_that_merely_came_last_is_still_promotable_after_barring`
(`test_workshop_critique.py`, SECTION 6).

It builds a register, **bars something else in the same run** (a `BAR_KILL_DEFECT` entry),
then calls the **real** `workshop_rank.enforce_scope_guard` with a client question `Q2`
that has no winner and one below-the-cut candidate (`rank: 42`) in `all_ranked`. It asserts
the also-ran was **promoted** — `scope_injected` is True, `winners` carries the candidate's
own text, `injected == ["Q2"]` — and explicitly asserts the guard did **not** fall back to
verbatim injection of the raw client question.

The two subsystems are therefore proven **compatible**, not merely proven separately. That
distinction is the point: Wave 3's two criticals lived in exactly this kind of seam, where
each plan's `must_haves` were individually satisfied.

The structural half of the guarantee is stronger than the test. **There is no cause constant
meaning "lost the tournament" and none meaning "restated another candidate."** `bar()`
refuses any cause outside the three allowed ones, returns `False`, stores nothing, and logs
a WARNING naming the rule. A caller cannot bar a loser even by mistake, because the module
cannot say it. The by-name test
`test_the_register_exposes_exactly_three_bar_causes_and_can_express_no_fourth` pins the
exact sorted set `["BAR_KILL_DEFECT", "BAR_LOOKUP_FAILED", "BAR_WEAK_TWICE"]` and also
asserts no cause name or value contains `tournament`, `loser`, `lost`, `duplicate`,
`restat` or `rank`. Its docstring states why the absence *is* the control, so nobody
"completes" the enum later.

## How a dropped invention reaches the register

This is the measured gap D-W4-1 exists to close. In the Wave-4 harness, failed-lookup
angles were never added to the barred register, so **"minimale netwerkdichtheid" was
re-proposed in rounds 2 AND 3, spending a paid grounded lookup each time.**

The path, end to end:

1. Wave 1's `workshop_admission.py` drops an invented angle and stamps it with one of its
   three machine-readable reasons — `DROP_PREMISE_NOT_REAL`, `DROP_NO_ADMITTING_SOURCE`,
   `DROP_LOOKUP_FAILED`. A dropped angle is `{text, reason, note}` (per 15.7-05-SUMMARY).
2. **All three of those map onto this module's single `BAR_LOOKUP_FAILED` cause.** The
   specific admission reason belongs in the entry's `flaw`, where a model can actually read
   it, rather than in a fourth cause constant that nothing would branch on.
3. `bar(register, text=dropped["text"], flaw=<the admission reason/note>,
   cause=BAR_LOOKUP_FAILED, round_no=<round>)` stores it for the rest of the run.
4. `barred_block()` then carries it into every subsequent generate and evolve prompt, with
   its flaw attached, so the angle is not re-proposed and does not spend a second lookup.

**The wiring of step 3 is plan 15.7-09's, not this plan's** — `files_modified` for 15.7-04
is exactly two files. Wave 1 already anticipated this handshake: `workshop_admission.py`'s
own comment above the three `DROP_*` constants reads *"Plan 15.7-09 turns a drop into a bar
… **A DROPPED INVENTION IS A BAR.**"* This plan supplies the receiving end, and the
`BAR_LOOKUP_FAILED` docstring records the "minimale netwerkdichtheid" case verbatim so the
next reader knows what the cause is *for*.

**A dropped invention is a bar. A tournament loss is not.** Both facts are in the module
docstring's treatment table.

## What the drop log records beyond a bare count

**It records what each dropped candidate clustered ONTO, and `clustered_onto` is a REQUIRED
keyword argument with no default.**

The reason is that two *opposite* failures were both measured, and they produce the
identical number:

- **The loop SPINNING** — re-proposing its own rejects. *"Round 2 proposed 3 questions
  already rejected in round 1."*
- **The filter being OVER-EAGER** — the harness's semantic dedup dropped 6 proposals as
  rewordings, mostly fairly, but it also killed SPECIALISE and COMBINE attempts and **killed
  round 1's only INVENT before its grounded lookup ever ran.** An over-eager filter
  suppresses discovery invisibly: nothing errors, the round simply produces less.

"3 drops" is the same figure in both worlds. Only *what each one clustered onto* separates
them. So `record_drop` refuses two ways: omitting `clustered_onto` is a `TypeError` (no
default in the signature), and passing an empty one returns `False` and logs a WARNING
rather than storing a blank. Both refusals are driven by
`test_record_drop_requires_clustered_onto_and_will_not_default_it_silently`.

The two drop causes are what make the distinction machine-readable:

| Cause | Meaning | Signal |
|---|---|---|
| `DROP_CLUSTERED_ONTO_BARRED` | landed on something already barred | the loop is SPINNING |
| `DROP_CLUSTERED_ONTO_LIVE` | landed on a live candidate on the table | ordinary near-copy collapse — watch the count for over-eagerness |

`drop_summary(register, round_no)` returns **three distinct plain-words sentences**, not one
template with a swapped number: nothing dropped / some drops repeated an already-rejected
question (names the loop as SPINNING and says the next round needs a new angle rather than a
new phrasing) / drops all landed on live candidates (says the near-copy filter is doing the
work and to check it is not also discarding genuinely new angles). Each is over 40
characters, names its count as a literal digit, and states the CONSEQUENCE rather than just
the event — the bar every degradation and note sentence in this engine already meets.
`test_drop_summary_tells_a_spinning_loop_from_an_over_eager_dedup` asserts the two sentences
actually differ, which a single shared template would fail.

## No table, no migration, no cross-run persistence — confirmed

- **No new table.** None created, none referenced.
- **No alembic migration.** None added. Migrations `0016` and `0017` have still never
  touched a database; this phase deliberately adds no third unpaid proof.
- **No cross-run persistence.** The register is a plain dict returned fresh by
  `new_register()` on every call. It lives for one workshop run and dies with it.
  *"Barred this run, kept for the next"* means the next **ROUND**, not the next **RUN** —
  recorded as fact (a) at the top of the module docstring so the spec's phrasing cannot be
  re-misread.
- **No disk, no database, no network.** Asserted over the source by
  `test_the_module_reaches_no_file_no_database_and_no_sibling_package`: the tokens `open(`,
  `os.path`, `sqlalchemy`, `sessionmaker` and `create_engine` appear nowhere in the file.
  The module imports only `logging`, `re` and `typing.Any`.
- **No module-level mutable default**, so one run's bars cannot leak into another's even
  inside a single worker process. Asserted twice: driven
  (`test_new_register_hands_back_a_fresh_dict_every_time`) and over the AST
  (`test_the_source_has_no_module_level_mutable_default_and_no_mutable_argument`, which also
  rejects mutable function defaults). The allowed-cause collections are **tuples**, not
  lists, because the set of causes is a fact about the design and not something to append to.
- **JSON-safe.** `json.dumps` succeeds on a fresh register and on one after 20 bars, and a
  recursive type walk asserts no `set` and no `float` is reachable. Verified by
  `test_the_register_is_json_safe_and_holds_no_set_and_no_float`.

Nothing was deployed, no migration was run, no live run was made, and **no package was
installed** — the module imports only the standard library (threat `T-15.7-04-SC`).

## Deviations from Plan

No deviation changed behaviour. Four items are worth recording.

**1. [Plan-internal contradiction — resolved] The module docstring vs. the `nestor_pulse_sdk` grep**

The plan's `<action>` requires the module docstring to record *"this module imports nothing
from `nestor_pulse_sdk`"*. The plan's own `<acceptance_criteria>` requires
`grep -v '^ *#' workshop_register.py | grep -c 'nestor_pulse_sdk'` to return **0**. A
docstring is not a `#` comment, so satisfying the first sentence literally would fail the
second check.

**Resolved by splitting them.** Docstring fact (c) states the property in words ("this module
imports nothing from the pipeline package, only the standard library") and the `#` comment
block immediately below the docstring names the package literally and explains the rule.
Both the required documentation and the required grep result are satisfied. No behaviour
change.

**2. [Rule 2 — missing critical documentation] A grep-safety note added to the module**

`grep -riE "tournament|loser|duplicate"` must find those words only in prose about what is
NOT barred. My first draft used "duplicates"/"duplication" three times in an unrelated
sense — describing why `_flatten` is re-implemented locally rather than imported. Technically
prose, but it makes the acceptance grep ambiguous for a future reviewer.

Reworded to "repeats"/"re-implementations", reserving "duplicate" exclusively for the
not-barred rule, and added an explicit note to the module for anyone running that grep. All
7 remaining hits are now unambiguously about what is NOT barred. Re-verified 25/25 after the
rewording.

**3. [Plan omission — implemented anyway] `note_weak_pass` is not in the `exports` list**

The plan's `must_haves.artifacts.exports` lists seven names and omits `note_weak_pass`, but
the `<action>` text explicitly requires it ("so the caller can apply 'WEAK after TWO evolve
passes' without holding that state itself"). Implemented as
`note_weak_pass(register, text) -> int`, returning the running count. **Consumers in
15.7-06/07/09 should treat it as part of the public surface.**

**4. [Harness, not source] Two fixes to my own test driver**

Neither touched committed code. (a) The driver initially loaded the module under a short
name, so `__name__` — and therefore the logger name — did not match `_REGISTER_LOG`, making
one `caplog` assertion fail spuriously. The refusal *was* being logged. Fixed by loading
under the real dotted name. (b) The lift list initially omitted two test-local helpers.
Recorded here so nobody reads the intermediate run as a source defect.
