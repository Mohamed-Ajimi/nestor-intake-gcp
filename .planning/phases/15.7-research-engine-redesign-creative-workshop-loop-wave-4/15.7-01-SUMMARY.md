# Phase 15.7 Plan 01: Numeric Bounds + Per-Question Grouping Summary

Closed the three numeric bounds standing between Wave 4's measured design and the code — a declamped
group ceiling, a size cap re-sized from 4 to 7, and a dispatch winner bound raised from 15 to 32 — and
made one-group-per-client-question the primary grouping path (D-W4-4a), costing zero LLM calls and
emitting a note rather than a degradation.

## The Measurement That Justifies Task 3

Driven on the real `divide()` through the real `build_groups`, both columns:

| | edited source (32) | mutant restoring `"15"` |
| --- | --- | --- |
| D-W4-5's 17 winners reaching a provider | **17** | **15** |
| which two were dropped | — | **`cross-cutting Q1+Q2` and `cross-cutting Q2+Q3`** |
| paid calls | 12 (`4 groups x 3 streams`) | 12 |
| 40 winners | truncates to 32 | truncates to 15 |

**The two the old bound silently deleted were exactly the two CROSS-CUTTING questions.** That is not a
coincidence of the fixture: cross-cutting questions are appended after the per-question floor, so they
sit at the bottom of the rank order and are the first thing a rank-ordered truncation eats. D-W4-5
names cross-question synthesis as *"where the best output came from"* and measured per-question
brackets producing **zero** cross-cutting winners. A bound of 15 would have deleted them anyway, after
the tournament had already paid to rank them, with one warning line as the only trace.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Two `test_workshop_scope_guard.py` tests the plan did not name**

- **Found during:** Task 2
- **Issue:** The plan named three `AT MOST … groups` assertions. Two further tests in the same file
  depend on the grouping LLM call having happened at all — `test_a_grouping_failure_degrades_…`
  part (a) (asserts a grouping-fallback degradation) and
  `test_the_grouping_call_is_counted_in_the_stage_actions_and_cost` (asserts a grouping prompt exists).
  Both go red on the primary path.
- **Fix:** Both pinned to `topic` mode through the same `grouping_mode()` context manager, each with
  its reason in the docstring. Recorded in the table above.
- **Files modified:** `tribunal/nestor_pulse_sdk/tests/test_workshop_scope_guard.py`
- **Commit:** `b2a10e6`

**2. [Rule 2 — Missing critical functionality] `_env_int` applied to both grouping constants**

- **Found during:** Task 1
- **Issue:** The plan required the non-integer guard only on `_D6_MAX_GROUPS`. `_D6_MAX_GROUP_SIZE`
  used the same bare `int(os.environ.get(...))`, which **raises at IMPORT time** on a typo — taking
  the whole worker process down before a run can start, with a stack trace from a module the operator
  never edited.
- **Fix:** `_env_int` applied to both. It changes no specified behaviour (the floor/ceiling arithmetic
  is unchanged) and strictly widens robustness.
- **Files modified:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/question_grouping.py`
- **Commit:** `1e7aad8`

**3. [Rule 2 — Missing critical functionality] The primary path's own failure mode**

- **Found during:** Task 2
- **Issue:** The plan's branch specification returns `(groups, notes, [])` unconditionally. If
  `fallback_groups` or `build_groups` swallowed an exception, `groups` would be empty and the run
  would report a clean, non-degraded grouping over **nothing to dispatch**.
- **Fix:** An explicit `if not groups:` arm that logs at ERROR and returns the D-12 degradation
  reason. There is nothing to fall back TO on this path — it already *is* the fallback shape — so
  degrading is the honest answer.
- **Commit:** `b2a10e6`

**4. [Rule 3 — Blocking] The over-the-bound fixture was pinned to 20 winners**

- **Found during:** Task 3
- **Issue:** `test_the_winners_bound_still_bites_on_groups_a_caller_supplied` built 20 winners against
  a bound of 15. At a bound of 32 the fixture stops exceeding the bound entirely and the test goes
  green while proving nothing — a silent vacuity, the exact failure class this phase's traps list.
- **Fix:** The fixture is now derived from the constant (`over = rd._D6_MAX_WINNERS + 5`), so it
  cannot stop biting whatever the bound becomes. The `== 32` pin is kept separately so the constant
  itself is still asserted.
- **Commit:** `3467f48`
