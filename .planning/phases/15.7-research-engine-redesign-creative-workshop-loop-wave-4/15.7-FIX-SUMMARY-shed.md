## 2. Diagnosis

### The chain

CR-09 changed `attach_discovery_riders` (`question_grouping.py:1050`) from a
**total-size cap** to a **rider budget**:

* `max_size` is still accepted, is explicitly `_ = max_size`-discarded (line 1110), and
  **no longer binds**;
* shedding is governed by `max_riders`, defaulting to `_D6_MAX_RIDERS_PER_GROUP` (= 3).

The production call site (`workshop_rank.py:4792`) passes **only** `max_size`, so the
effective budget is always the default 3.

The failing test configures its scenario with `_engine_run(..., max_group_size=len(_CANDIDATES))`,
which monkeypatches `question_grouping._D6_MAX_GROUP_SIZE` to 3 — **the parameter that
CR-09 made inert.** With one rider and a budget of 3, nothing is shed. The rider rides
along, is dispatched, and is annotated as researched — correctly. The test then fires an
assertion whose message ("a discovery question that was SHED …") is now a **misdiagnosis**:
nothing was shed.

Mechanism proof, real import of `question_grouping`, no stubs, exact production call site:

```
qg._D6_MAX_GROUP_SIZE = 3
qg.attach_discovery_riders([group_of_3_winners], [rider], max_size=qg._D6_MAX_GROUP_SIZE)
  -> members after : ['w1', 'w2', 'w3', 'DISCOVERY Q']
  -> SHED          : []            # under the OLD total-size rule this was [rider]
  -> rider_budget  : 3
```

### Why (b) is ruled out

The annotation path was audited end to end and is sound:

* `discovery_bracket.annotate_conflicts` (line 549) annotates **only** what it is handed,
  and is handed `dispatched_discovery`.
* `workshop_rank` subtracts all three shed channels from that set before it is built —
  `shed_riders` (rider budget), `gap_a_dropped`, and `coverage_shed`
  (`workshop_rank.py:4803-4817`, `4849-4861`).
* `pipeline.py:1794-1804` re-subtracts `discovery_not_researched` defensively.
* `research_division._bound_groups_to_winners` **exempts discovery members** by design
  (`research_division.py:1130-1135`), so the winners bound cannot silently drop a rider.
* `_angle_query` truncates each member to `_SUBQ_CHARS` but **drops no member**, so a
  rider that reaches `divide` is genuinely asked.

No fourth, unaccounted clip was found between the winner set and the report.

## 4. Harness — and a defect found inside it

Real imports of every engine module (`question_grouping`, `workshop_rank`,
`research_division`, `discovery_bracket`, `pipeline`, `synthesis/steps`).
**No `ast` lift. No claim in this document rests on a lift.**

Only non-stdlib **leaves** are stubbed: `sqlalchemy`, `httpx`, and FastAPI router
scaffolding. The stubs raise loudly rather than returning plausible empties. The names the
auto-stub actually resolved were printed and audited: `fastapi.APIRouter/Depends/
HTTPException/Request/status` and `func.now` — none on the engine path.

**Harness soundness was established before any source was trusted:**

* whole file: **12 passed / 1 failed**, matching Cloud Build's single failure in this file;
* the one failure is the target test, at line 2844, with the byte-identical message.

**A harness defect was found and fixed en route** — the exact trap that was warned about.
`sqlalchemy.text()` initially returned a raw `str`, but `citations/extractor.py:446-457`
calls `.bindparams(...)` on the **claim INSERT**. That raised `AttributeError`, the caller
swallowed it, and the run silently lost its claim and `research_gap` rows while still
reporting success — two extra tests failed for a reason that had nothing to do with the
code under test. Fixed by making `text()` return a `str` subclass carrying `bindparams`
(so `str(stmt)` still yields the SQL verbatim, which the fake session routes on). Had this
gone unnoticed it would have produced exactly the "degraded run reported green" artefact
this codebase keeps getting bitten by.

## 5. What changed

**One file: `tribunal/nestor_pulse_sdk/tests/test_engine_e2e_stubbed.py`. No source
change.** The honesty invariant was found intact, so per the scope rule the source was
left alone.

1. **`_engine_run` gains `max_riders`** (monkeypatches
   `question_grouping._D6_MAX_RIDERS_PER_GROUP`). The comment on the existing
   `max_group_size` knob was corrected — it said the size cap "needs to BITE" for the
   shed test, which stopped being true at CR-09.
2. **The shed test steers `max_riders=0` instead of `max_group_size=len(_CANDIDATES)`.**
   Zero, not a small number: the fixture raises exactly one discovery question, so any
   positive budget admits it and sheds nothing.
3. **Three NON-VACUITY guards added.** The central assertion is unchanged, verbatim.
   * *NON-VACUITY 1* — the discovery frame produced a question at all (reusing
     production's `discovery_question_text`, never a retyped literal).
   * *NON-VACUITY 2* — the operator feed does **not** name a dispatched discovery
     question. With guard 1 this is the positive statement that the shed happened;
     the shed is not otherwise observable, because the note reaches `workshop_notes`
     which `pipeline.py:1989` only logs.
   * *NON-VACUITY 3* — the framed text reaches **no** provider prompt. Discriminating,
     not trivially true: at the production budget the same fixture puts this exact text
     into an angle prompt.

worth knowing that nothing would catch it rotting.

## 7. Incidental findings (reported, not fixed — out of scope)

1. **`max_size` is a live trap, not just dead weight.** This regression *is* the hazard
   report for the follow-up the CR-09 author flagged. A caller that configures shedding
   through `max_size` gets silently different behaviour with no error. The test was such a
   caller. `attach_discovery_riders`' docstring argues the parameter must stay because
   removing it would be a `TypeError` in a stage that must never raise — that reasoning is
   sound, but it leaves a knob that reads as load-bearing and is not. Worth an explicit
   deprecation warning or a rename to `max_size_unused_`.

2. **Workshop notes are logged, never persisted.** `pipeline.py:1989` only
   `log.info`s `workshop_notes`, so the shed note — the operator's one record that a
   discovered question was dropped — is unobservable from the run's own artifacts. This is
   the same "stage-logging-is-inert" class already recorded for V-01. Not fixed here.
