# Phase 15.7 Plan 07: Aspect Coverage and the Barred Semantic Drop — Summary

Compound-question generation is now stopped by a **Python assertion over an explicit ask
decomposition** rather than by prompt wording, and the rejected register gained its **second
enforcement layer**: a semantic drop that clusters each round's new candidates together with the
barred ones and records what each drop clustered *onto*.

Both new keywords are **optional and default to `None`/`0`**, so every pre-loop caller is unchanged.

`stats` gained two additive keys: `generate_candidates` writes **`notes`** (a list of plain-words
repair sentences), `cluster_candidates` writes **`dropped_on_bar`** (an int). Neither widens a
return type.

## Task 1 — aspect decomposition and the COVERAGE rule (D-W4-4b)

**The generation stage now runs three steps, not one.** A decomposition call per client question
produces its DISTINCT ASKS; the asks are rendered into the generation prompt under a new COVERAGE
rule; and then — after generation — Python asserts every ask came back with at least one
sub-question.

| What | Where |
|---|---|
| `_ASPECT_PROMPT_TEMPLATE`, fenced `ASKS_START` / `ASKS_END` | new, before the candidate section |
| `_parse_aspect_lines` | regex-extracted, bounds-checked index; garbled lines ignored; never raises |
| `_asks_block` | indexed + truncated, the same control `_findings_block` documents |
| `_ASPECTS_PER_QUESTION_MAX` (5) / `_ASPECT_MAX_CHARS` (220) / `_ASPECT_MIN_CHARS` (8) | house `NESTOR_TRIBUNAL_*` idiom |
| COVERAGE RULE added **beside** the kept SCOPE RULE | `_CANDIDATE_PROMPT_TEMPLATE` |
| `_repair_uncovered_aspects` | **the control** — asserts, repairs, never raises |

**The SCOPE RULE was kept verbatim.** The coverage rule is additive and says out loud why the two
are compatible: *covering an ask the client explicitly made is not broadening*. The scope lock stays
load-bearing for D4's coverage guarantees.

**The nuance the plan asked to preserve is preserved.** The assertion is built on the client's own
distinct asks, **not** on the comparator list from orientation. An assertion over comparators would
have demanded a US sub-question nobody wanted — orientation cites the US only as a market where
supermarkets still win, and the client is Benelux/Germany-focused. France is the fair miss.

**Repair, not raise.** An uncovered ask is carried forward as its own candidate with the client's own
wording, stamped `source="aspect_repair"` and **the same `parent` as its siblings** (asserted). A
repair is a **NOTE** (`stats["notes"]`) because the output is complete; a **full decomposition
failure** is a **DEGRADATION** on the returned `reasons`. The two channels are kept apart — the D-12
alarm-fatigue rule.

**Parent attribution is untouched (T-15.7-07-01).** The new `ASK:` segment is read for coverage only
and is bounds-checked. A hostile `ASK:` costs at most one repair; it can never move a candidate onto
another client question. `_candidates_from_lines` and `_parse_candidate_lines` were kept at their
original names and shapes as thin text-only views over the new row parsers, so every pre-existing
caller and test reads exactly the contract it always did.

## Task 2 — the barred list and the semantic drop (D-W4-1)

**Layer 1 (cheap, not the guarantee):** `_barred_section(register)` renders
`workshop_register.barred_block` under its own heading with an explicit *do not propose these, and do
not reword them* sentence. Rendering is **delegated, never reimplemented** (T-15.7-07-02). With no
register the section is `""` and the prompt carries no heading — asserted both ways.

**Layer 2 (the actual guarantee):** the round's new candidates are handed to `grouping._cluster_block`
**together with the barred entries as shadow members**, and any new candidate landing in a cluster
with a shadow is dropped. This is semantic because the requirement is *"do not propose this again OR A
REWORDING OF IT"* — no string comparison can enforce a rewording ban, which is why D-W4-1 names
`cluster_candidates` rather than naming a comparison.

**Every drop records what it clustered ONTO**, via `record_drop(..., clustered_onto=...)`, because the
two measured failures point in opposite directions and a bare count cannot separate them: the loop
**spinning** (round 2 re-proposing 3 questions rejected in round 1) versus the dedup being
**over-eager** (6 dropped as rewordings, killing SPECIALISE and COMBINE attempts and round 1's only
INVENT *before the grounded lookup ever ran*). Both are written into the docstring.

**Every pre-existing property preserved and re-stated in the docstring**, each with a test:
lowest-`index` representative; the ordered `parents` union that makes clustering D4-safe; the negative
cluster id as never-drop sentinel; degrade-to-singletons on any exception. A shadow can never
represent a cluster and never contributes a parent (T-15.7-07-04); a shadow-only cluster yields no
representative, so a barred question can never re-enter the population.

## Deviations from Plan

### [Rule 3 - Blocking] `cluster_candidates` needed a `round_no` the plan did not specify

`workshop_register.record_drop` requires `round_no` (it stamps every drop). The plan's Task 2 gave
`cluster_candidates` only an optional `register`. Added `round_no: Any = 0` as a second optional
keyword. **Plan 15.7-09 must pass the loop's round number** or every drop is stamped round 0.

### [Rule 2 - Missing critical] Barred drops counted apart from near-duplicate collapse

The pre-existing `_reason_cluster_collapse` fires on `len(representatives) < len(items)`. With the bar
active, barred drops would have been reported as *near-duplicate collapse* — a working bar
misreported as a lossy clusterer, and the exact ambiguity D-W4-1 exists to remove. The collapse
reason is now computed against the population that **survived the bar**, and barred drops are logged
and counted separately (`stats["dropped_on_bar"]`).

### [Rule 2 - Missing critical] Shadows join every chunk, not just one

The plan said "append the barred entries to the population". Appending once, before chunking, means
the bar silently stops applying to every chunk but one as soon as a round exceeds
`grouping._CLUSTER_MAX_BLOCK` — a defect that reads green forever. Shadows are appended to **each**
chunk; cluster keys are already namespaced per chunk so nothing collides. Pinned by M10.

## Contradictions and open items — reported, not silently chosen

**1. The plan's line numbers were stale, as warned.** Every symbol was located by content. The plan's
`<interfaces>` numbers (950 / 1059 / 1263 / 1482 / 2130) were all wrong at this base; the orchestrator
prompt's corrected table matched.

**2. `_trim_round_robin` does NOT extend its guarantee to aspects — checked, as the plan asked, and
it does not hold.** The function buckets by `parent` and preserves within-bucket order, so its
promise is "every PARENT keeps its first candidate before any parent gets a second", not "every ASPECT
keeps one". Repairs are appended at the end of their parent's bucket, so under a cap tight enough to
bite, a repair is trimmed *before* a second model line for the same parent — weakening the very
coverage guarantee Task 1 establishes.

Not reachable on today's numbers (`_MAX_CANDIDATES` 120 vs 12 per question — the cap only bites above
ten client questions), so it is **documented in-source and flagged here rather than fixed**: closing
it means teaching `_trim_round_robin` a per-aspect bucket, and that function is read by other plans in
this wave. **Recommend plan 15.7-09 or a reconciliation plan owns this.**

**3. `workshop_evolve` is deliberately NOT imported** (plan instruction, honoured). It is *named in a
comment* explaining why, so `test_workshop_does_not_import_its_same_wave_sibling` asserts over
**import lines only**, not over any mention. Both `workshop_evolve.barred_section` and
`workshop._barred_section` now present a barred list; if their wording differs, **15.7-09 reconciles
them** — that divergence is expected, not a defect.

**4. Cost note for 15.7-09.** Decomposition adds **one Anthropic call per client question per
generation**. At 5 questions that is 5 extra calls per round. It shares the existing
`_WORKSHOP_CONCURRENCY` semaphore and its cost is rolled into `stats["cost_usd"]`. Nothing was run
live, so this is an arithmetic estimate, not a measurement.
