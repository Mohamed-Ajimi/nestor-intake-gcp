## Task-by-task

### Task 1 — the leading-column normaliser (commits `25ad4d3` test, `6a56d90` feat)

`_LEADING_COLUMN_TOKENS = frozenset({"STATEMENT", "FACT", "CLAIM"})` and
`_strip_uniform_leading_column(region) -> (lines, token | None)`, wired into `parse_fact_list`
immediately after `_extract_region` and before the per-line loop. It returns the region unchanged
unless there are ≥2 non-empty lines, every non-empty line contains a tab, and the first tab-column
of every non-empty line — stripped and uppercased — is the same token from the set. Blank lines
pass through. When it fires, a WARNING names the provider and the token; the normalised lines are
**not** counted as parse errors, because they parsed.

Tests added: the idx-8 rescue built from the DIAGNOSTICS quote
(`STATEMENT<TAB>Tamoil Nederland uses PriceCast Fuel…`), the same block with the normaliser
disabled via `monkeypatch.setattr(facts, "_LEADING_COLUMN_TOKENS", frozenset())` as the BEFORE
picture, all three tokens plus case/whitespace variants, a lone echoed header row, one header
among three good lines, six must-not-fire cases as a direct unit test of the helper, the
`_MIN_STATEMENT_CHARS` bound, and T-15.4-11 (a shifted block forges neither attribution nor its
D-13 grades).

### Task 2 — `[cite: N]` resolution (commits `a3d6da0` test, `558a489` feat)

- `_CITE_ENTRY_RE` — a numbered bibliography line, matched per line, bounded quantifiers.
- `_CITE_CELL_RE` — a SOURCE_URL cell that is *only* a cite marker, capturing its digits; spelled
  `cite[:_]` to stay in step with `audited_llm_client._CITE_MARKER_RE`.
- `build_cite_index(text) -> dict[int, str]` — line-by-line scan, first number wins, http(s) only,
  capped at `_MAX_LABEL_INDEX`, never raises.
- `_is_cite_cell` / `_resolve_cite_cell` — full-match recognition, then resolution in order and
  deduped. A partial resolution counts as resolved.
- `parse_fact_list` gained an optional `cite_index` parameter defaulted from the body exactly as
  `label_index` is. When `_parse_url_cell` returns rejected-and-not-placeholder and the raw cell is
  a cite marker, the marker is resolved: on success the URLs go into `source_urls` and
  `rejected_urls` is **not** incremented; on failure today's behaviour is kept and
  `unresolved_cite_markers` is incremented.
- `source_domain` / `quality_tier_hint` derive from the **first** resolved URL via the existing
  `display_domain(...)`, so a recovered redirect is graded like any other URL rather than left at
  tier 3.
- `FactListResult.unresolved_cite_markers: int = 0`, appended last and documented in the
  dataclass's "every field except facts and not_found is a NAMED LOSS" voice.

## Deviations from Plan

**1. [Rule 2 — missing critical functionality] A per-report WARNING for RESOLVED cite markers**

- **Found during:** Task 2.
- **Issue:** `_parse_url_cell` logs `rejecting non-http(s) SOURCE_URL '[cite: 25, 26]'` per cell,
  at WARNING, *before* the caller gets a chance to recover the citation. The plan asks for one
  WARNING when `unresolved_cite_markers` is non-zero, and for nothing on the success path. That
  would leave a production trail showing 20 rejection warnings and no statement that the sources
  were in fact recovered — an operator reading it would conclude the citations were lost. In a
  phase whose entire premise is that a silent/misleading log cost a client report, shipping that
  was not defensible.
- **Fix:** a second, single, per-report WARNING on the success path, naming the provider and the
  count and explicitly referring to the rejection warnings above it. Counted in a **local**
  variable — `FactListResult` gained only the one field the plan named.
- **Files modified:** `facts.py` (`parse_fact_list`).
- **Commit:** `558a489`.

**2. [Rule 2] The module docstring's "no second `[cite: N]` regex" claim was made honest**

- **Found during:** Task 2.
- **Issue:** `facts.py`'s header states "No second `[cite: N]` stripper —
  `strip_unresolved_cite_markers` is reused", and the phase CONTEXT calls `_CITE_MARKER_RE` "the
  ONE cite-marker regex in this codebase". `_CITE_CELL_RE` is a second cite-marker regex. Leaving
  the claim standing would have made the file's own documentation false — the exact defect class
  the CONTEXT flags at `steps.py` ~1202.
- **Fix:** the bullet now states that `_CITE_CELL_RE` strips nothing, that it *recognises and
  captures* (which the stripper's regex deliberately cannot do, since it captures no group), and
  that it is spelled `cite[:_]` to stay in step. Reuse was considered and rejected on that ground.
- **Files modified:** `facts.py` (module docstring).
- **Commit:** `558a489`.

**3. [documentation] Two `FactListResult` field docstrings were amended**

`parse_errors` now records that a uniformly-prefixed block is normalised away first and is not
counted; `rejected_urls` now records that a resolved `[cite: N]` is not counted there. Both were
made false by this change and would otherwise have misdescribed the numbers an operator reads.

**4. [scope, deliberate] The three byte-for-byte prompt-block assertions were NOT edited**

Lines 373/381/527 of `test_fact_list_parser.py` assert
`"STATEMENT<TAB>SOURCE_URL<TAB>QUALITY<TAB>CERTAINTY<TAB>EVIDENCE"` is present in
`build_fact_list_prompt_block()`. This plan does not change that function, so the assertions are
untouched and must stay green (P-1). **Observation worth recording, not acted on:** that prompt
contract has the *same shape* as the `<TAB>` pathology D-R1 is fixing in the distiller prompt — the
fact-list prompt also describes its separator with a five-character token a model can copy back as
data, and idx 8's `STATEMENT`-prefix deviation is a cousin of copying the contract into the output.
That is a `build_fact_list_prompt_block` question and belongs to a plan that owns it; naming it
here so it is not lost.

**5. [scope] STATE.md / ROADMAP.md were not updated by this executor**

Four executors are running against this one working tree in parallel (I observed sibling edits to
`source.py`, `cloudbuild.test-engine.yaml` and a new `0016_source_resolved_url.py` mid-session).
Mutating shared planning state concurrently would corrupt it. The orchestrator owns
`state.advance-plan` / `roadmap.update-plan-progress` for this wave; this plan's commits are
task-scoped and stage only its own two files.
