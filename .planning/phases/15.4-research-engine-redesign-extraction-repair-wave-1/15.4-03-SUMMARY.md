## Task 1 — the splitter

`_split_distiller_line` at `steps.py:1141`, constants at `1136`/`1139`.
Semantics exactly as specified: each literal separator tried in order, returning
`[p.strip() for p in line.split(sep, 2)]` on the first present; then the
2+-space regex, returned only when it produced more than one part; else `None`.
`_parse_distiller_response` calls it in place of the bare `if "\t" not in line`
drop. Every downstream rule is byte-identical: the `< 10` drop, the `general`
fallback, the unknown-facet `log.debug`, and `found_by` from the caller-supplied
`provider` (T-15.2-60 — asserted, see below).

**The priority order is not theoretical.** V-01's own 143-claim control blob
contains **two lines with 2+ spaces inside the claim text**. Had the space run
been tried before the tab, those two lines would have split on the wrong column.
That case has its own named test.

Registration and the count bump landed in the same commit as the file
(`EXPECTED_FILES` 31 -> 32, plus the owner comment in the `15.3-01 ->` style).

## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 1 — Bug in my own test] The `general` facet fallback is unreachable via a leading real tab**

- **Found during:** Task 1, by actually running the test file (this is the
  finding that justifies the local-execution effort).
- **Issue:** I wrote `test_an_empty_facet_falls_back_to_general` using
  `"\t{CLAIM}\t{EVIDENCE}"`. It FAILED. `_parse_distiller_response` does
  `line = line.strip()` **before** splitting — which predates this plan — so a
  leading empty facet column is eaten and every column shifts left by one. The
  `general` fallback is reachable for `<TAB>`, `|||` and `|`, but **not** for a
  real tab.
- **Fix:** the assertion now uses `<TAB>`, and a second named test
  `test_a_LEADING_REAL_TAB_is_eaten_by_the_line_strip_first` asserts the
  column-shift as **recorded behaviour** with the reason it is not being
  changed.
- **Why not fixed:** touching `line.strip()` would change how every
  already-working tab response parses — including V-01's 43 and 143 — which is
  outside D-R1(a) and would defeat the non-regression half of this plan.
  Flagged here for a future decision.
- **Commit:** `69b7f8d`

**2. [Rule 3 — Blocking] `__pycache__` was untracked and not gitignored**

- **Found during:** Task 1 staging. `py_compile` and local imports generate
  `__pycache__/` across the tree; with several executors active in this
  worktree, uncommitted bytecode is one careless `git add -A` from the repo.
- **Fix:** added `__pycache__/` and `*.py[cod]` to `.gitignore`.
- **Commit:** `69b7f8d`

**3. [Rule 2 — Correctness of a gate] A stale count inside the gate's own comments**

- **Found during:** Task 1. `cloudbuild.test-engine.yaml`'s narrative comment
  still said "30 paths … ALL 30 NOW EXIST"; the real count was 31 before my
  change and 32 after. In a config whose entire purpose is reconciling counts,
  a stale count in its own prose is exactly the class of quietly-wrong number
  this phase exists to repair.
- **Fix:** left the 30 as documented history and added a note stating that it
  is the 15.2+15.3 baseline, that later phases add on top, and that
  `EXPECTED_FILES` is the one number that must track the list.
- **Commit:** `69b7f8d`
