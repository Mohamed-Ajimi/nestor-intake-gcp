# Phase 23.4 — CONTEXT: client environment + dev→client promotion

**Written 2026-09-11 by the orchestrator from the operator conversation. Operator decisions are
marked D-23.4-NN. Facts below were READ from GCP / the repo on 2026-09-11; re-verify before acting
on any that could have moved.**

## Why this phase exists

The presentation to stakeholders went well; the client is to get access to test the app while
development continues. Today there is ONE environment (`project-cb01b861-cb4a-438d-b9a`, "Nestor
Pulse") that is simultaneously the dev box and the only deployment. Every deploy goes straight
there, a worker deploy restarts instances and interrupts paid runs, and half-finished work would
land in front of the client.

## Operator decisions (locked)

- **D-23.4-01 — Fresh project for the client.** The client environment is the NEW project
  **`nestor-pulse-prod`** (created 2026-09-11 10:17Z, `tools@dotto.be` is `roles/owner`). The
  current project `project-cb01b861-cb4a-438d-b9a` becomes the DEV environment. Do not rename or
  migrate anything out of the current project; the client starts clean (no test tenants, no old
  runs).
- **D-23.4-02 — Keys.** Resend, Gemini and OpenAI keys are SHARED between dev and client (same
  values in both projects). Anthropic gets a DIFFERENT key in the client project. Consequence
  accepted by the operator: Gemini/OpenAI spend and rate limits are shared across environments.
- **D-23.4-03 — Identity Platform already enabled** on `nestor-pulse-prod` with the Email/Password
  provider on (operator did this 2026-09-11; `identitytoolkit` and `firebase` APIs are enabled).
  Authorized domains are NOT yet added — they can only be added after the first frontend deploy
  (both Cloud Run hostnames: `nestor-frontend-<hash>-ew.a.run.app` and
  `nestor-frontend-<project-number>.europe-west1.run.app`). Templates untouched (defaults OK).
  No custom domain yet; `authDomain` = `nestor-pulse-prod.firebaseapp.com`.
- **D-23.4-04 — Promotion model.** Branch `develop` (or master, operator to confirm) deploys to
  dev; a release TAG promotes to client. Build ONCE, promote the same image DIGESTS, never rebuild
  for the client. Order per release: migrations → nestor-api → nestor-frontend → tribunal-api →
  tribunal-worker. **The worker step must refuse to deploy while any tribunal `run` row is
  `status='running'`** (the idle gate) — a worker deploy restarts instances and kills paid runs.
- **D-23.4-05 — Secret VALUES are never handled by the agent.** Terraform creates the secret
  containers; the operator adds versions via console or their own terminal. The agent hands the
  operator the exact secret NAMES after `terraform apply`. In the NEW project use ONE Anthropic
  secret shared by nestor-api and both tribunal services (the current project drifted into
  `nestor-anthropic-api-key` vs `Nestor_Claude2`); set `tribunal_claude_secret_id` etc. in the
  client tfvars to the shared names.
- **D-23.4-06 — Prove it before the client gets a link.** One small end-to-end research run on the
  client project, observed (logs + browser), before any client user is created. Every earlier
  environment change in this repo shipped unobserved; this one must not.
- **D-23.4-07 — Ship two owed fixes in the first client release**, not after: revert
  `NESTOR_WORKER_STALE_MINUTES` 90→60 in BOTH `tribunal/infrastructure/cloud-run/deploy-worker.sh`
  and `infra/variables.tf` (the heartbeat is proven to land since 2026-09-09), and make the research
  attempt cap (`backend/app/api/research_routes.py` `_MAX_ATTEMPTS=3`) exclude `cancelled` runs,
  plus make the frontend surface the `needs_investigation` 202 instead of a silent no-op.
