# Phase 23.4 Plan 02: D-23.4-07 owed fixes + deploy-script project guard — Summary

Shipped the three owed D-23.4-07 fixes — a cancelled research run no longer burns one of the
three paid attempts, an over-cap trigger now says so in three languages on both surfaces
instead of showing a green toast and doing nothing, and `NESTOR_WORKER_STALE_MINUTES` is back
to 60 with the stopgap's history written down in the past tense — and made all four tribunal
deploy scripts refuse to guess a project.

No deploy, no gcloud mutation, no provider spend, zero new dependencies.

## What was built

### Task 1 — the attempt cap stops counting cancelled runs

`trigger_research` now computes `counted = [r for r in prior if r.status not in
_CAP_EXEMPT_RUN_STATUSES]` and compares `len(counted) >= _MAX_ATTEMPTS`. `prior` itself is
left unfiltered, because the retry path below reads `prior[0]` and a cancelled *latest* run is
a legal retry trigger — filtering `prior` would have broken that silently.

The reported `attempts` figure and the `_log.warning` are computed from the same `counted`
list, and the log additionally states how many rows were exempt, so a support conversation can
reconcile the number the operator saw against the row count in the database (T-23.4-07).

`_CAP_EXEMPT_RUN_STATUSES = {"cancelled"}` is deliberately **not** folded into
`_RETRYABLE_RUN_STATUSES`. The two answer different questions — "may this run be superseded?"
versus "did this run consume a paid attempt?" — and they already disagree about `needs_input`,
which is retryable but *did* spend and so still counts.

### Task 2 — the over-cap 202 is no longer silent

The backend answers an over-cap trigger with **HTTP 202** and `{"research_run_id": null,
"status": "needs_investigation", "attempts": N}`. Because that is a 202 and not a 4xx,
`ApiResult.success` is `true`, so both call sites took the success branch: green toast, reload,
nothing changed. The reload is what made the no-op read as a refresh.

- `TriggerResearchResponse` (new, exported) gives `research_run_id` a nullable type. The old
  non-nullable declaration made the refusal *un-representable*, which is precisely what let
  the silent branch type-check.
- `classifyTriggerOutcome` is a pure module — no React, no i18n, no network — because
  `vitest.config.ts` runs `node` and includes only `src/**/*.test.ts`, so the branch is
  testable at all only if it lives outside the components that call it.
- Both `RunActions.tsx::handleFreshAttempt` and
  `admin.pulse.intakes.$id.tsx::onStartAutoResearch` switch on it. `needs_investigation`
  warns and deliberately does **not** reload.
- Six locale files; nl and fr are real translations. No hard-coded cap number — the cap is a
  server constant, and a hard-coded "3" in three languages is the class of defect phase 23
  shipped.

### Task 3 — deploy scripts that cannot guess

`build-and-push.sh` and `artifact-registry-create.sh` defaulted `PROJECT` to the **dev project
id**, so a client release landed there unless someone remembered an env var. All four scripts
now share one canonical `GOOGLE_PROJECT` with a no-default `GOOGLE_CLOUD_PROJECT` fallback;
`build-and-push.sh` exports the resolved value so its `artifact-registry-create.sh` child
cannot disagree. Optional `GCLOUD_ACCOUNT` pins `--account` on every real invocation and warns
loudly to stderr when unset.

`NESTOR_WORKER_STALE_MINUTES` went 90 → 60 as a value-only change inside the single atomic
`--set-env-vars=` line.

### Auto-fixed issues

**1. [Rule 3 — Blocking] `fail()` needed the narrowed failure shape in the switch**

- **Found during:** Task 2, first GREEN `tsc` run.
- **Issue:** `TS2345: Argument of type 'ApiResult<TriggerResearchResponse>' is not assignable
  to parameter of type '{ error: string; code?: string }'`. The old `if (!res.success)` shape
  narrowed the union for free; a `switch` on a classifier return value does not.
- **Fix:** the `"error"` case guards with `if (!res.success)` before calling `fail`, with a
  comment stating it is a type-level formality (the classifier returns `"error"` only when
  `success` is false), not a second copy of the rule. The route file needed the equivalent
  treatment for `res.code` / `res.error`, done the same way.
- **Files:** `frontend/src/components/research/RunActions.tsx`,
  `frontend/src/routes/admin.pulse.intakes.$id.tsx`. **Commit:** `61d6c36`
