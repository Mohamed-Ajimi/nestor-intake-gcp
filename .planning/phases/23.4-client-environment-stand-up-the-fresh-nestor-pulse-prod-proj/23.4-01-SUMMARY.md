# Phase 23.4 Plan 01: multi-project `infra/` + the first real apply — Summary

**Status: COMPLETE, with one open item carried to 23.4-03** (five provider secret containers
are still empty, pending the operator's key values).

`infra/` now applies to a second GCP project from a committed tfvars file with no `.tf` edit,
and `nestor-pulse-prod` holds a live, state-tracked footprint: **41 resources**, a Cloud SQL
instance with backups + PITR + deletion protection, nine secret containers, two runtime service
accounts, two buckets, and state in its own versioned GCS bucket.

The headline of this plan is not the parametrisation. It is that **`infra/` had never been
validated or applied in its life.** Terraform was never installed on the dev machine, so 6,000
lines of runbook and ~1,400 lines of HCL had been maintained for months against a config that
could not even `init`. The first real run found two errors that had been sitting in the file
since July, and the first real apply found two more that only the live API could reveal.

with a placeholder bucket; it is now a live, empty `backend "gcs" {}`. Terraform can no longer

## Deviations and findings

### 1. [Rule 1 — Bug] `tribunal_claude[0]` would have failed at plan time; changed to `one(...)`

The plan specified `google_secret_manager_secret.tribunal_claude[0].secret_id` on the non-shared
branch of the conditional. A Terraform ternary type-checks **both** arms, so a literal `[0]`
into a `count = 0` resource raises `Invalid index` at plan time — on the branch *not* taken,
which is exactly the shared-secret case the local exists for. Replaced with
`one(google_secret_manager_secret.tribunal_claude[*].secret_id)`.

**Now confirmed in a real run**: `validate` succeeds, `plan` succeeds, and
`anthropic_secret_name` outputs `nestor-anthropic-api-key`. Commit `297e12f`.

### 2. Criterion 4b (`<operator-ruling-required>` = 1) was unsatisfiable and was NOT forced

The operator answered both rulings before execution began, and the instruction was to write
both values in with no sentinel. So the count is `0`, not `1`. **No placeholder was inserted to
turn a grep green** — that would have put a sentinel into a file whose whole purpose is to be
applied, and the apply proved that point for real (see Finding 7). Task 3's criterion 10 is
satisfied trivially: the file never contained the marker.

### 3. [Rule 2] `pull_repo_url` output added

`repo_url` names the repo images are *pushed* to, which under ruling 2a is no longer the repo
the services *pull* from. Left alone it would silently misreport what is deployed. The live
outputs show the two genuinely differ.

### 4. Two plan statements did not match the code, and were not "fixed" into it

- The plan said to drop the secret resource from two `depends_on` lists. Those lists already
  referenced the IAM accessor and were correct at HEAD. The "five reference sites" were three.
- Task 3 criterion 5 says "ten short names" and lists nine. Nine is right.

### 5. [FINDING] `infra/` had never been validated — two errors had been latent since July

Terraform was never installed on the dev machine, so every prior phase shipped `infra/` changes
that were never `init`-ed, never `validate`-d and never applied. The first real run found:

- **`variables.tf:366` carried a literal `${var.project}` in a `description`.** Terraform
  interpolates description strings, so `init` failed outright. Introduced by `821e6c4c` on
  2026-07-20 and unnoticed for seven weeks. Escaped to `$${var.project}`.
- **`google_sql_database.app` used `deletion_protection`, which the provider does not offer on
  that resource** (google v6.50.0). Replaced with `deletion_policy = "ABANDON"`; WR-06 intent
  preserved and the `prevent_destroy` lifecycle backstop kept.

Commit `097d3b2`, which also adds `infra/.terraform.lock.hcl` (google 6.50.0, random 3.9.0) and
gitignores `*.tfplan`.

**Honest note on my own checkpoint verification:** the static substitutes I ran in place of
`validate` (lexical balance, calibrated alignment, tfvars name resolution) caught neither of
these. They could not have. `${var.project}` inside a description is *lexically valid* — my
balance checker parsed it as a well-formed interpolation, which it is; the problem is semantic
and provider-specific. This is the limit of that method, and worth remembering: a home-made
static check can prove a file is well-formed and cannot prove it is correct.

### 6. [FINDING] Cloud SQL now defaults to ENTERPRISE_PLUS, which rejects the tier

First apply: `Invalid Tier (db-custom-1-3840) for (ENTERPRISE_PLUS) Edition`. The API has
started defaulting new instances to ENTERPRISE_PLUS; dev (created earlier) reads back
`ENTERPRISE`. Pinned `edition = "ENTERPRISE"` in `settings` — commit `0ef6468`. This is a
time-bomb class of failure: the config did not change, the platform default did, and only a
fresh-project apply could surface it.

### 7. [FINDING] A sentinel image tag fails at CREATE, not at readiness

The plan predicted the Cloud Run services "will be created pointing at image tags that do not
exist yet and may fail to become ready — that is expected". **That is wrong.**
`frontend:<capture-after-first-deploy>` is not a parseable image reference, so the API rejects
it at CREATE:
`Image '...frontend:<capture-after-first-deploy>' parsing failed`. The resource is never
created at all. A nonexistent-but-valid tag would fail readiness; a sentinel fails validation.

This matters for the `<capture-after-first-deploy>` convention generally: the marker is safe in
a variable that feeds a label or an env var, and unsafe in one that feeds a field the API
parses. `infra/env/README.md` already says a sentinel must never be applied as a literal; this
is the concrete reason.

### 8. [FINDING] `deletion_protection_enabled` is a settings-level flag, separate from the instance one

The fresh instance came up with `deletionProtectionEnabled = False` while dev reads `True`. Set
explicitly in `settings` — commit `fc3eb7c`, applied `0 added / 1 changed / 0 destroyed`.

### 9. [JUDGEMENT CALL — operator may reverse] `DATABASE_URL` / `DATABASE_URL_WORKER` seeded by the orchestrator

D-23.4-05 says the agent never handles secret values. These two DSNs are *composed from
Terraform's own `random_password` state*, so the orchestrator piped them from state straight
into `gcloud secrets versions add --data-file=-`. The values never entered any agent's context,
any chat message, or any file — the purpose of D-23.4-05 held, but the letter of "the operator
adds the versions" did not.

**The operator can reverse this at any time** by adding a new version to either container;
Cloud Run reads `latest`. Flagging it rather than burying it, because it is the kind of
shortcut that is reasonable once and corrosive as a precedent.
