# Phase 23.4 Plan 01: multi-project `infra/` + per-environment inputs — Summary (PARTIAL)

**Status: CHECKPOINT. Tasks 1 and 2 are done and committed. Task 3 is a blocking operator
gate and has not started** — it is entirely `gcloud` and `terraform` mutations, which this
agent is forbidden to run. Nothing has been applied to any GCP project; no resource was
created, changed or deleted; no secret value was seen, typed or written.

`infra/` can now target a second GCP project from a committed tfvars file without editing a
single `.tf`, and the two things that would have gone wrong on the first client apply — the
image paths being welded to the target project, and two Terraform resources racing to create
one Anthropic secret container — are fixed before they could happen rather than after.

## What was built

### Task 1 — `infra/` parametrised (commit `297e12f`)

**A live partial GCS backend.** `providers.tf` carried a commented-out `backend "gcs"` block
with a placeholder bucket. It is now a live, empty `backend "gcs" {}`, so Terraform cannot
resolve a state location by itself and every `init` must name
`-backend-config=env/<env>.gcs.tfbackend`. A bare `terraform init` now *prompts* rather than
silently writing a local `terraform.tfstate`. The comment says why in the file: a silent local
state is exactly how this project's own state was lost — the dev project has no recorded state
anywhere, so nobody can now say what was applied to it.

**Cross-project image pulls.** New `var.image_registry_project` (default `""`) plus
`local.registry_project`, using the same `!= "" ? … : …` fallback idiom
`tribunal_audit_bucket_name` already used. All four image locals — `image`, `frontend_image`,
`tribunal_api_image`, `tribunal_worker_image` — now interpolate the *registry* project instead
of the target project, so "build once, promote the same digest" (D-23.4-04) is expressible
rather than aspirational. `google_artifact_registry_repository.backend` still gets created in
the target project; it simply goes unused, and is the escape hatch if the ruling is reversed.

**Scaling floors became variables — DEF-23.3-14 closed in the file.** Four new variables
replace four hard-coded `min_instance_count`s. `api_min_instances` defaults to **1**, and its
description carries the reason in words: at 0 there is no instance between requests, so
`_reconcile_loop` never ticks and an orphaned *paid* research run is never swept — silently,
because `/readyz` is request-driven and keeps answering 200 on a cold-started instance. This
makes the 2026-09-07 by-hand correction declarative, so a later apply cannot quietly undo it.

**`tribunal_worker_stale_minutes` 90 → 60 (D-23.4-07, the `infra/` half).** The description was
rewritten in the past tense: the 90 was raised 2026-09-08 under DEF-23.3-01 when the heartbeat
was not landing at all; the two-WORKER_ID root cause was fixed and deployed 2026-09-09 and
`rowcount=1` was observed on run 6668b27e, so the stopgap's condition has passed. The "must
match `deploy-worker.sh`" sentence and the "strictly below 120" constraint are kept. The
`deploy-worker.sh` half was done by plan 23.4-02.

**One Anthropic container (D-23.4-05).** `google_secret_manager_secret.tribunal_claude` now
carries `count = local.tribunal_claude_is_shared ? 0 : 1`. When the intake and tribunal secret
ids name the same string, the resource is not created at all and
`google_secret_manager_secret.anthropic_api_key` is the single owner; all three reference sites
resolve through `local.tribunal_claude_secret_name`. Without the count, that configuration
would declare two resources with one `secret_id` and the second apply arm would 409.

**Outputs.** `tribunal_service_url` (the OIDC audience to feed back), `anthropic_secret_name`
(the exact secret NAME the operator adds a version to — a name, never a value), and
`pull_repo_url`.

### Criteria 7 and 8 — what was substituted, and what it does and does not prove

`terraform` is not on PATH and is not installed anywhere on this machine (`which`, plus a
filesystem scan of `scoop/shims`, `chocolatey/bin`, `WinGet/Links`, `Program Files` and the
user tree). `python-hcl2` is not installed either, and installing a package is outside what
this executor may do. **`fmt -check` and `validate` did not run, and nothing below should be
read as a claim that they passed.** Three substitutes were run instead:

1. **Lexical balance** — a brace/bracket/paren checker that is aware of strings, comments and
   `${…}` interpolation. `BALANCED` for all four `.tf` files and all four `env/` files. This
   proves only that the files are well-formed, not that any attribute or reference is valid.
2. **Alignment** — an approximation of `terraform fmt`'s rule, **calibrated against the
   pristine HEAD files**: it reports `providers.tf`, `variables.tf`, `outputs.tf` and `main.tf`
   at HEAD as already-aligned, so it is measuring drift from real terraform-fmt output rather
   than from an invented rule. All edited files and both `.tfvars` report `ALIGNED`.
   (The first version of this checker reported three false positives at HEAD; the rule was
   wrong — terraform sizes the trailing-comment column over the *commented* lines in a run,
   not all of them — and it was corrected until HEAD read clean.)
3. **Variable resolution** — every assignment in both `.tfvars` was cross-checked against the
   `variable` blocks in `variables.tf`: **all 27 client and 28 dev assignments name a declared
   variable, none is assigned twice, and all three no-default variables (`project`,
   `image_tag`, `frontend_image_tag`) are present in both.** This is the closest available
   stand-in for the tfvars half of `validate`.

What remains genuinely unverified: provider-schema correctness (that every attribute exists on
its resource type), and that `one(...)`, `count` and `local.registry_project` resolve. The
operator's `terraform plan` in Task 3 Step 3 is the first real test of those.

## Deviations from plan

### 1. [Rule 1 — Bug] `tribunal_claude[0]` would have failed at plan time; changed to `one(...)`

- **Found during:** Task 1(e), reviewing my own edit before commit.
- **Issue:** The plan specified `local.tribunal_claude_secret_name` resolve to
  `google_secret_manager_secret.tribunal_claude[0].secret_id` on the non-shared branch. A
  Terraform conditional type-checks **both** arms, so a literal `[0]` index into a `count = 0`
  resource raises `Invalid index` at plan time — on the branch that is *not* taken. That is
  precisely the shared-secret case the local exists to serve, so the client's very first plan
  would have failed with a confusing error.
- **Fix:** `one(google_secret_manager_secret.tribunal_claude[*].secret_id)`, which yields the
  single element when the resource exists and `null` when it does not. A comment in `main.tf`
  records why `[0]` is wrong here, so it does not get "simplified" back.
- **Files modified:** `infra/main.tf`
- **Commit:** `297e12f`
- **Caveat:** with no terraform available this fix is reasoned, not executed. If the operator's
  plan errors on this local, that is the thing to look at first.

### 2. Criterion 4b (`<operator-ruling-required>` = 1) is unsatisfiable and was NOT forced

The plan told Task 2 to leave `superadmin_email` as a sentinel and let Task 3 resolve it. The
operator answered both rulings **before** execution began (ruling-1a and ruling-2a), and the
instruction was to write both values in with no sentinel. So `client.tfvars` contains
`superadmin_email = "yanick@agenic.be"` and zero occurrences of `<operator-ruling-required>`.

Criterion 4b asserts that count is `1`. **It is `0`.** No sentinel was inserted to make a grep
go green — that would have put a placeholder into a file whose whole purpose is to be applied.
The criterion is superseded by the pre-ruling. Task 3's criterion 10 ("`client.tfvars` no
longer contains `<operator-ruling-required>`") is satisfied, trivially: it never did.

### 3. [Rule 2] `pull_repo_url` output added

`repo_url` describes the repo images are **pushed** to, which under ruling 2a is no longer the
repo the services **pull** from. Left alone, that output silently misreports what is deployed
in the client environment. Added `pull_repo_url` (derived from `local.registry_project`) and a
sentence on `repo_url` pointing at it. One output, no behaviour change.
