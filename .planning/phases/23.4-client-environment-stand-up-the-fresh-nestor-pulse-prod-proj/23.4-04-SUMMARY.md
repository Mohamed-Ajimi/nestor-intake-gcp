# Phase 23.4 Plan 04: promotion pipeline + the idle gate — Summary (PARTIAL)

A release is now one script whose ordering rules are enforced instead of remembered: digests
resolved before anything moves, a fail-closed queue gate before the first migration and again
immediately before the worker, the worker last, and a smoke check that says out loud when it
could not run.

**This SUMMARY is PARTIAL.** All four files are written, committed, and their file-level
acceptance criteria run. The one criterion that cannot be satisfied by an agent — Task 3's
criterion 5, PROVING the gate is able to fail — requires `gcloud builds submit` against the dev
project, which the permission classifier blocks. The exact operator command block is at the end
of this file and in the checkpoint message.

No deploy, no gcloud mutation, no provider spend. Nothing outside the plan's four
`files_modified` was touched; STATE.md and ROADMAP.md are untouched by design.

## What was built

### Task 1 — `infra/queue-check.yaml`, the fail-closed idle gate

A single-step `--no-source` Cloud Build config, run as the EXISTING `nestor-run@` (which
already holds `secretAccessor` on `DATABASE_URL_WORKER`, so no IAM change and no
authorized-network change), that answers one question in its **exit status**:

| code | meaning |
|------|---------|
| 0  | no row in `tribunal.run` is `queued` or `running` — safe to deploy the worker |
| 90 | proxy/psql/secret could not answer — UNKNOWN, therefore NOT SAFE |
| 91 | `current_user` is not `worker_user` — the anti-vacuity check |
| 92 | `tribunal.run` absent from `information_schema.tables` |
| 93 | one or more claimable rows |

Exit 91 is the one that matters most and it runs *before* the queue query. A tenant-scoped role
matches no `worker_all` RLS policy, returns a falsely empty queue, and a gate that cannot see
the rows always passes — it would have waved through every deploy while looking green.

The answer is the code and not the stdout because `nestor-run@` has no `roles/logging.logWriter`:
the build goes SUCCESS and `gcloud builds log` returns an empty REMOTE BUILD OUTPUT. The rows are
still printed, for a human who has the logs.

`_INVERT=1` flips the predicate to `NOT IN ('queued','running')` so every completed run counts as
claimable and the gate must refuse. It is documented, in the file, as a self-test knob that must
never be set during a promotion.

### Task 2 — `infra/promote.sh`

Ten steps, in the order the two recorded incidents dictate:

1. resolve digests in the source registry (a tag is mutable; the digest is the release identity)
1b. **confirm the same digest exists in the target registry** — added beyond the plan, see Deviations
2. the idle gate, at the top, before anything is applied
3a/3b. `nestor-migrate` then `tribunal-migrate`, each **repinned** with `jobs update --image`
4. `nestor-api` by digest, then `status.imageDigest` read back and compared
5. the frontend **rebuilt**, not promoted (Vite inlines `VITE_*` at build time)
6. `tribunal-api` via `deploy-api.sh`
7. **the idle gate again**, immediately before the worker
8. `tribunal-worker` via `deploy-worker.sh`, LAST
9. smoke: `/readyz`, `/auth/login`, one authenticated intake read
10. the promoted tags written back into the tfvars file — the only file the script edits

Two rules here have already cost real money, so neither is prose any more. A worker deploy boots
the poll loop, which CLAIMS FIRST and SLEEPS LAST, so `--min-instances=0` is not protection and
an empty queue is the only protection (2026-07-28) — hence the gate at 2 and 7 and the worker
last. And `gcloud builds submit | tail` reports the PIPE's status, so a FAILED build exits 0 —
hence every build confirmed by `builds describe <FULL UUID>`.

`DRY_RUN=1` makes **no outbound call at all**, which is load-bearing rather than tidy: step 1's
real `artifacts docker images describe` fails on a tag that does not exist, so a dry run with a
placeholder tag would die before reaching the ordering the dry run exists to show.

### Task 3 — the two Cloud Build configs

`cloudbuild.deploy-dev.yaml` builds backend, tribunal-api and tribunal-worker at the resolved
tag and then calls `promote.sh` with `SOURCE_PROJECT` and `TARGET_PROJECT` **both** set to the
dev project. Promoting the project to itself means the dev deploy and the client release run the
same ordered code path — gate included — so the client's path is exercised on every dev deploy
rather than once per release.

`cloudbuild.promote-client.yaml` has exactly ONE step and it is not a docker build. That absence
is the D-23.4-04 guarantee and it is stated at the top of the file.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] promote.sh step 1b: the promoted digest must exist in the target registry

- **Found during:** Task 2, writing step 1.
- **Issue:** The plan resolves digests in `SOURCE_PROJECT` and then deploys the tribunal services
  through `deploy-api.sh` / `deploy-worker.sh`, which build their image URL from
  `${TARGET_PROJECT}` **and address it by TAG**. When the two projects differ, that image is not
  in the target registry unless it was copied there, and "we promoted the same digest" would have
  been an unchecked claim — the failure would have surfaced as a Cloud Run pull error halfway
  through a release, after the migrations had already run.
- **Fix:** a step 1b that verifies each resolved digest is present in the target registry and,
  when it is not, aborts **before the first migration** with the exact
  `gcloud artifacts docker images copy` command printed. When `SOURCE == TARGET` (the dev
  self-promotion path) it is trivially satisfied. Belt and braces: the digest is also read back
  off the live revision after every deploy and a mismatch aborts.
- **Files modified:** `infra/promote.sh`
- **Commit:** `dc27c85`

### 2. [Rule 1 — bug] the idle gate's exit code is not gcloud's exit code

- **Found during:** Task 2, writing the gate wrapper.
- **Issue:** `gcloud builds submit` returns `1` for ANY failed build. It does not hand back the
  build step's exit status, so the plan's "map the code to Task 1's table" would have mapped
  every refusal to the same unreadable `1` — losing exactly the distinction (93 = runs in flight,
  91 = the gate is blind) the code scheme exists to make.
- **Fix:** on failure the wrapper recovers the build UUID from the submit output, reads
  `builds describe <UUID> --format='value(status,statusDetail)'`, and parses the `exited with
  status N` code out of the detail. If the UUID or the code cannot be read, it **refuses** —
  "the check errored" is never "the check passed".
- **Files modified:** `infra/promote.sh`
- **Commit:** `dc27c85`

### 3. [Rule 1 — bug] `resolve_digest` printed into a command substitution

- **Found during:** Task 2 self-review before the dry run.
- **Issue:** the first draft called `DIGEST=$(resolve_digest backend)`, which would have
  **captured** the `would resolve digest for ...` lines instead of printing them — criterion 3a
  would have counted `0`, and the dry run's whole purpose (an offline, readable plan) would have
  silently evaporated.
- **Fix:** the function sets `RESOLVED_DIGEST` instead of echoing.
- **Commit:** `dc27c85`

### 4. [Rule 1 — bug] `eval "$(python3 ...)"` reports success on empty output

- **Found during:** Task 1 self-review.
- **Issue:** in `queue-check.yaml`, `if ! eval "$(parser)"` cannot fail: `eval` of an empty string
  exits 0, so a dead parser would fall through with `PGUSER` unset. (It would have been caught one
  step later as a connection failure — exit 90, still fail-closed — but the reported cause would
  have been wrong.)
- **Fix:** capture into `PGENV`, check status and emptiness, then `eval`; the parser also raises
  when the DSN carries no user.
- **Commit:** `2e26a70`

### 5. [Deliberate, documented] `_IMAGE_TAG` is not defaulted to the literal `$SHORT_SHA`

The plan specifies `_IMAGE_TAG` with default `$SHORT_SHA`. Cloud Build does **not** expand
substitutions inside substitution DEFAULTS, so that default would arrive as the ten-character
string `$SHORT_SHA` and every image in a by-hand build would be tagged with it. `deploy-dev` uses
`_IMAGE_TAG: ''` plus a `resolve-tag` step that falls back to the built-in `$SHORT_SHA` (which a
trigger supplies and a by-hand `builds submit` leaves empty) and **fails the build** when neither
exists.

### 6. [Deliberate, documented] the gate installs `postgresql-client` when the image lacks it

The threat model's T-23.4-SC line says the gate "uses the base image's psql". The
`cloud-sdk:slim` image is not guaranteed to ship a postgres client, and assuming it does would
make the gate exit 90 every time — a gate that always refuses is as useless as one that always
passes. The step installs `postgresql-client` from the image's own distro **only when `psql` is
absent**, and treats a failed install as exit 90 (UNKNOWN, not safe). No repository dependency is
added; this is an ephemeral build-step package, and the `cloud-sql-proxy` version IS pinned as
T-23.4-SC requires.
