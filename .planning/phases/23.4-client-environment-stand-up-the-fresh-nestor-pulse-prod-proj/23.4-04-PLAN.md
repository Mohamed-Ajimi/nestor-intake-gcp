<objective>
Turn the stand-up into a repeatable release: one script that promotes the dev digests to the
client environment in a safe order, with a gate that will not let a worker deploy kill a paid
run, and a smoke check that makes a broken promotion visible in the same minute.

Purpose: today every deploy in this project is a hand-assembled sequence recovered from a
7,000-line runbook, and the ordering rules that matter most exist only as prose warnings. Two
of them have already cost real money. A worker deploy BOOTS the poll loop, which claims first
and sleeps last, so `--min-instances=0` is not protection and an empty queue is the only
protection (the 2026-07-28 incident). And `gcloud builds submit | tail` reports the PIPE's
status, so a FAILED build exits 0. This plan makes both mechanical.

Output: a fail-closed queue gate, a promotion script, two Cloud Build configs, and a decision
checkpoint on the branch model and whether triggers are wired now. NOTHING is deployed by this
plan and no provider spend occurs.
</objective>

Reproduced here because this plan turns it into a file:

* Both obvious paths are CLOSED. `nestor-pg`'s authorized-networks list is empty, so there is
  no public-IP route without patching production networking; and `tribunal-api` rejects a plain
  Cloud Run invoker token with "invalid internal caller token" (the Phase-14 lockdown), so the
  seam cannot answer it either.
* The path that WORKS: `gcloud builds submit --no-source --config=<queue-check>.yaml
  --service-account=projects/$P/serviceAccounts/nestor-run@$P.iam.gserviceaccount.com`.

* TRAP 1 — `nestor-run@` lacks `roles/logging.logWriter`, so the build's stdout is LOST: the
  build goes SUCCESS and `gcloud builds log` returns an empty `REMOTE BUILD OUTPUT`. A green
  build is therefore NOT an empty queue. Carry the answer in the EXIT STATUS.
* TRAP 2 — connect as `worker_user`, never `app_user`. `worker_user` matches the `worker_all`
  RLS policy; `app_user` is tenant-scoped and returns a FALSELY EMPTY queue.
* The query: `SELECT id, status, started_at, heartbeat_at, reclaim_count FROM tribunal.run
  WHERE status IN ('queued','running')`.

DEPLOY SCRIPTS, as hardened by plan 23.4-02: all four require `GOOGLE_PROJECT` (fallback
`GOOGLE_CLOUD_PROJECT`) with NO default and exit non-zero when neither is set; all four accept

BUILD CONFIRMATION: `gcloud builds describe <FULL UUID> --format='value(status)'`; short ids

DIGEST PROMOTION: `gcloud artifacts docker images describe "<repo>/<name>:<tag>"

`${_PROJECT}:${_REGION}:${_INSTANCE}` on `127.0.0.1:5432`, reads the worker DSN from Secret

Exit-code contract, written as a comment block at the top of the file AND implemented, one
cause per code so a failure message identifies itself:
* `0`  — no row in `tribunal.run` has status `queued` or `running`. Safe to deploy the worker.
* `90` — the proxy did not come up or psql could not connect. UNKNOWN, therefore NOT SAFE.
* `91` — `SELECT current_user` is not `worker_user`. A tenant-scoped role returns a FALSELY
  EMPTY queue, which would read as "safe" (trap 2). This is the anti-vacuity check and it is
  the one that matters most: a gate that cannot see the rows always passes.
* `92` — `tribunal.run` is not present in `information_schema.tables`. The schema is not there,
  so the answer is meaningless.
* `93` — one or more claimable rows. NOT SAFE.
Anything non-zero means DO NOT DEPLOY. State that rule in the comment in those words: the gate
is fail-closed, and "the check errored" is never "the check passed".

Do NOT rely on stdout for the answer — `nestor-run@` has no `roles/logging.logWriter`, so the
build's REMOTE BUILD OUTPUT comes back EMPTY and a green build proves nothing. Still print the
offending ids for a human, but the machine answer is the code.

solely so the gate can be PROVEN able to fail against a project that has completed runs, which
is Task 3's checkpoint. Comment it as a self-test knob and state that it must never be set
during a promotion.

**`DRY_RUN=1` prints every command it would run and exits 0 without mutating, AND makes no
outbound gcloud call at all.** That second half is load-bearing, not a nicety: step 1 resolves
image digests with a real `gcloud artifacts docker images describe`, which fails on a tag that
does not exist, so a dry run with a placeholder tag would die before reaching the ordering the
dry run exists to show. Under `DRY_RUN=1`, digest resolution therefore prints exactly
`would resolve digest for <image>:<tag>` — one line per image, using that literal wording — and
SKIPS the gcloud call, substituting a fixed placeholder digest for the rest of the plan. Apply
the same rule to every other read the script makes: under `DRY_RUN=1` nothing reaches the
network, so the whole ordering is reviewable offline by anyone, including an agent whose
permission classifier blocks the real commands.

**Steps, in this order, each announcing itself on stdout with a stable token:**

deploys to dev; a release TAG promotes to client". The repository's only branch today is
`master` and every merge lands there.

Recommended: keep `master` as the dev branch. Introducing `develop` adds a merge step per
change for a one-developer repository, and the promotion boundary that actually protects the
client is the TAG, not the branch. Alternative: `develop` for dev, `master` reserved for
released code, which makes "what the client has" readable from the branch alone.

OAuth flow. The committed configs work either way — they can be invoked by hand with
`gcloud builds submit --config=... --substitutions=...` from a tag today, and attached to a
trigger whenever the connection exists. Recommended: commit the configs now, run promotions by

successfully at least once end to end. A trigger that fires an unproven script into the client
