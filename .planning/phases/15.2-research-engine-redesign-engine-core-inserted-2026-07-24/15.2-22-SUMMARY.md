# Phase 15.2 Plan 22: Two Dead Research Streams Summary

Both research streams that failed 100% of their sessions on run `d6bb3aae` now have their
root cause fixed offline and proven by a committed fixture: the own-researcher's replayed
assistant turn is deep-serialised so a failed `web_fetch` no longer poisons the conversation
(D-B), and a refused model id is a named, breaker-tripping configuration failure on its first
occurrence rather than seven quiet per-angle warnings (D-A), with `gpt-5.6-sol` pinned in both
the code default and the deploy script.

## What was built

**Task 1 — the D-A checkpoint.** Pre-answered before execution and NOT re-opened. OpenAI shut
both deep-research models down on 2026-07-23, four days before the run; the migration target is
`gpt-5.6-sol`, already on the account and verified live by polling a background probe to a
TERMINAL state (`queued` -> `completed`). No probe, no live call and no paid quota was spent by
this plan.

**Task 2 — the shape fix (D-B).**

- `tests/fixtures/web_fetch_error_turn.json` — two `web_fetch_20250910` assistant turns, the
  error variant and the success variant, with a `_comment` block recording where the shape came
  from and why the stubbed e2e could never produce it.
- `skeptic._to_plain()` — recursive conversion preferring the provider's own `model_dump()`
  (canonical, guaranteed to agree with the request schema), then `__dict__`, with `str()` as the
  floor. `exclude_none` because a RESPONSE model declares every optional field, so an attribute
  copy leaks them into the next REQUEST as explicit `null`s.
- `skeptic._content_to_serialisable()` — same name, same signature, still never raises. One
  unconvertible block degrades to a type-only stub instead of killing a paid loop. All four
  callers (`group_skeptic`, `own_researcher`, `workshop`, `workshop_rank`) are fixed by the
  shared helper without being touched.
- `skeptic.is_poisoned_turn_error()` — 400 + the block name only, consulting
  `reliability._CAP_MARKERS` rather than re-listing them so the 776-error class can never be
  swallowed by a drop-and-retry.

**Task 3 — the configuration fix (D-A).**

- `reliability.CONFIG_ERROR` — decided on WORDING ahead of every status rung, never transient,
  and routed through the EXISTING hard-wall breaker branch so it trips on the first occurrence.
  One rule, two causes, two distinct operator-facing reasons.
- `audited_llm_client.OPENAI_DEEP_RESEARCH_MODEL` default -> `gpt-5.6-sol`, with the incident,
  the verification method and the open caveat recorded above it.
- `audited_llm_client.log_resolved_dr_models()` — one INFO line naming both resolved ids and
  whether each came from the environment or the default, emitted once per process from the first
  client construction. Model ids only; no other env value is read or logged (T-15.2-223).
- `deploy-worker.sh` — `NESTOR_OPENAI_DR_MODEL=gpt-5.6-sol` added to the single `--set-env-vars`
  line. The variable was previously **not bound at all**, which is precisely how the dead code
  default reached production.

  verification 3 requires `test_reliability_retry.py` to still pass. Both assumed no existing
  case was already a refused model id. One was:
  `_FakeHTTPError(404, "not_found_error: unknown model")`, expected `HARD`. That message **is**
  a refused model id — semantically identical to D-A — so it now classifies as `CONFIG_ERROR`.
- **Fix:** the expectation for that ONE row was changed to `CONFIG_ERROR`, with an inline comment
  naming the plan, the date and the reason. `is_transient` for that row is unchanged (`False`

- **Why it was done rather than reported as a blocker:** the executor's file-ownership rule
  exists to avoid collisions with the two sibling agents running this wave. I read both sibling
  plans' `files_modified` — 15.2-21 (`brief_input.py`, `pipeline.py`, `test_brief_input.py`,
  `backend/app/research/brief.py`, `backend/tests/test_research_brief_input.py`) and 15.2-23

  `test_fact_list_parser.py`) — and **neither owns `test_reliability_retry.py`**, so the stated
  hazard is nil. The alternative was shipping a red gate, which this repository's history says
  is the worse outcome. **Flagging it for the orchestrator anyway: this is a one-line,
  one-commit revert (`e4baada`) if you disagree.**
- **Files modified:** `tribunal/nestor_pulse_sdk/tests/test_reliability_retry.py` (import +
  one table row).
- **Commit:** `e4baada`

### 2. [Rule 2 - Correctness] `"does not exist"` narrowed to a MODEL-scoped match

- **Issue:** the plan lists `"does not exist"` as a `_CONFIG_ERROR_MARKERS` phrase. As a bare
  substring it also matches "the requested file does not exist" and, more dangerously, an OpenAI
  background response that is past its ~10-minute retention window (the R7/DEC-2 resume path).
  Neither is a statement about this deployment's configuration, and either would open a **healthy**
  provider's circuit after a single failure — the opposite of the plan's intent.
- **Fix:** the phrase is honoured via `_MODEL_MISSING_RE = r"\bmodel\b.{0,120}?\bdoes not exist"`,
  which requires "model" and "does not exist" in the same clause. The other three phrases
  (`model_not_found`, `model not found`, `unknown model`, `has been deprecated`) are plain
  substrings as specified. `test_does_not_exist_is_scoped_to_MODELS_not_to_any_missing_thing`
  pins both directions.
- **Commit:** `e4baada`

### 3. [Rule 3 - Blocking] The deploy-script comment could not sit where the plan said

- **Issue:** the plan asks for a comment "above the line". A `#` comment cannot appear between
  backslash-continued lines of a shell command, and the backtick-comment idiom that can is
  untestable here (this plan is forbidden from executing the script).
- **Fix:** the comment block sits immediately above the `gcloud run deploy` invocation instead,
  naming the variable, the incident and the WR-01 "`--set-env-vars` replaces the whole plain env"
  rule that keeps it on that one line. `bash -n` parses clean.
- **Commit:** `e4baada`

### 4. [Rule 3 - Blocking] The plan's own grep gate would have failed on its own comment

- **Issue:** the plan's Task 3 verification runs `grep -v '^#' … | grep -c "o4-mini-deep-research"`
  and expects `0`, while also asking the new comment to "name the deprecated id". `^#` does not
  strip an INDENTED comment, so naming the id inside the `os.environ.get(...)` call would have
  made the plan's own gate red.
- **Fix:** the comment block was moved to column 0 above the assignment and the retired id is
  described rather than spelled, with a line saying exactly why. The gate now reads literally:
  count is 0 with or without the comment filter.
- **Commit:** `e4baada`

## Open Caveats — do not read these as verified

1. **`gpt-5.6-sol` adapter parity is UNVERIFIED.** It is a GPT-5.x model, not an o-series
   deep-research model. The live probe proves it is *callable* on the background Responses path
   and reaches a terminal `completed`. It does **not** prove that `openai_deep_research_raw`'s
   two-phase start/poll adapter parses its response body and `usage` fields identically to the
   retired o-series model. Cost extraction and report extraction could both differ. This can only
   be settled by the next live run, and it is recorded in the code comment as well as here.

2. **Never treat request acceptance as proof a deep-research model is alive.** The dead model also
   returned `status: queued` and only failed asynchronously with `model_not_found`. Any future
   probe must poll to a TERMINAL state. This is why the plan's original "fail loud at startup on a
   rejected model id" is impossible and was implemented as first-failure classification instead.

3. **The CONFIG_ERROR class is not yet reached by the deep-research angle path.** `run_angles`
   (`research_division.py:1270`) and `degraded_parallel.py:236` consume a provider ERROR ENVELOPE
   (`{"status": "error", "error_message": …}`) and log a warning; they never raise, so `classify`
   and the breaker are never consulted for a D-A-shaped failure. The classification is correct,
   proven and reached by every path that DOES raise (Anthropic calls, SerpApi, the own-researcher),
   but converting a deep-research error envelope into a classified failure needs an edit to
   `research_division.py`, which is 15.2-23's file this wave and outside this plan's scope. **So
   D-A's blast-radius fix is the pinned model id; the breaker half is proven in unit tests and
   awaits that seam.** Recommend it be checked during 15.2-26 reconciliation.
