# Phase 15.2 Plan 15: Cross-Provider Merge Before The Gates + D-13 Persistence Summary

**All four research streams' facts are now deduped, clustered and corroboration-ordered as ONE list before any verification gate runs, so two providers contradicting each other reach one skeptic session instead of two — and the certainty, provenance, per-source quality and couldn't-find lists that justify a fact's priority now survive the run as queryable columns.**

## Performance

- **Duration:** ~85 min, one session
- **Tasks:** 3 of 3
- **Files modified:** 8 (5 source, 3 test); 0 created; 1,698 insertions / 72 deletions

## Accomplishments

### Task 1 — The reorder (`8d3a05f`)

**The distill stage stopped shredding prose.** `pipeline.py`'s `claim_distiller(provider_reports=provider_results, …)` call is gone; the stage now calls 15.2-14's `collect_provider_facts`, which reads each stream's own D8 fact list and falls back to the distiller **per provider**. `claim_distiller` is no longer even imported by `pipeline.py` — that import *was* the distiller-as-primary-source wiring D-03 unwires. The function, its `full_extraction` fallback mode and both of its test files are untouched (D-15).

`provider_results` is rebound once to `facts_result.reports`, which covers all five downstream consumers (`_extract_sources_for_group`, `_extract_sources_for_claim` ×2, the `provider_results=` argument, `scrub_research`) with the machine-readable block already stripped.

**A new `merge` stage sits between `distill` and `gate`.** It cancel-checks, opens a running row, runs the deterministic half (`_dedupe_claims`), then the LLM half — the **existing** `group_claims`, wrapped best-effort and degrading to one singleton group per claim so a failed merge can never lose one — then counts corroboration through the **existing** `_group_corroboration`. The grouped-verify branch below is now a pure consumer of `groups` / `n_groups` / `multi`.

The closing feed row names, in a sentence: cluster count, multi-claim clusters, clusters corroborated by ≥2 streams, duplicates collapsed, and which providers fell back and why. With `NESTOR_TRIBUNAL_GROUP_VERIFY=false` it says instead — in 300+ characters an operator reads — that clustering was **skipped** and that contradictions will therefore not share a skeptic session.

**`_dedupe_claims` became the cross-stream merge point**, extended in place (no second deduper): `source_urls` unioned, a `provider_quality_by_url` map so each URL keeps the grading of the provider that supplied it, and G-11's cautious certainty (`single` wins). Every branch is guarded on the key being present, so distiller-produced claims behave byte-identically.

**`grouping.py`'s `if not _CLUSTER_ENABLED:` branch is deleted.** `_exact_keys` and `_CLUSTER_ENABLED` remain defined, importable and unchanged in body, each with a comment naming 15.2-18's V-03 as the commit that deletes them. Both docstrings that advertised the A/B path were corrected.

## Deviations from Plan

### 1. [Rule 1 — plan claim corrected] Only THREE of the four contradictions can merge with the run's real entity tags

- **Found during:** Task 3, on the first gates run (`351bec8b` — 3 failed).
- **The plan asked for:** a must-have that all four recorded contradictions "land in ONE group", using specific entity tags including `LUKOIL Nederland` vs `lukoil nl`.
- **What the code actually does:** `group_claims` blocks by `_norm(entity)` **alone**, and `_norm` collapses case, spacing and punctuation — nothing else. `_norm("LUKOIL Nederland")` is `lukoilnederland`; `_norm("lukoil nl")` is `lukoilnl`. Different blocks. The clusterer is never even asked about the pair. The same is true of the recorded run's *real* tags for the buyer contradiction: `lukoil` vs `lukoil benelux`.
- **This is not a bug.** It is `grouping.py:57-64`'s ACCEPTED LIMITATION, stated verbatim in the module before this plan started, and it is a **recall** limit rather than a correctness one — an unmerged claim is still verified, it just gets its own session. Closing it would mean changing the blocking key, i.e. modifying the clusterer, which this plan forbids by name (B-04, "reused verbatim").
- **Fix:** the fixture carries formatting variants of one entity (the case where the tagger names the same company on both sides, which is what the merge genuinely fixes), and a **new** test — `test_entity_tags_that_normalise_apart_are_the_known_recall_limit` — pins the other case with the recorded run's real tags, proving both the premise (`_norm` differs) and the consequence (two groups, zero cluster calls, no claim lost). The gap is now asserted rather than implied.
- **Operator-facing consequence, stated plainly:** this plan makes a cross-provider contradiction reach one skeptic session **when the tagger gives both sides the same entity name**. When the tagger splits the entity (`lukoil` vs `lukoil benelux`), the contradiction still ships as two independent claims. How often that happens is what the hand-run August calibration (G-05) measures; it is deliberately not a CI number.
- **Commit:** `77d6828`

### 2. [Rule 3 — blocking] `ProviderFactsResult` gained `not_found_by_provider`

- **Found during:** Task 1.
- **Issue:** Task 1 must produce `research_gaps` as `[{"provider", "text"}]`, but 15.2-14's `ProviderFactsResult.not_found` is a **flat text union** — `not_found_raw.extend(parsed.not_found)` discards the provider. `research_gap.provider` is NOT NULL and 15.2-06 groups the report section by provider, so the union alone cannot be persisted without inventing an attribution.
- **Fix:** an additive final field on the frozen dataclass, filled from the same `parsed.not_found` in the same place, deduped on the **pair** (two streams reporting the same gap is two honest rows) and capped by the same `_NOT_FOUND_TOTAL_MAX`, loudly. No existing field renamed; no positional construction broken; 15.2-14's 37 tests unaffected.
- **Note on scope:** the plan's `<file_ownership_deviation>` said `steps.py` was touched for "ONE additive change inside `_dedupe_claims`". This is a second additive change in that file. Wave 8 has one plan and `steps.py`'s previous owner (15.2-14, wave 7) merged first, so there is no ownership conflict.
- **Commit:** `8d3a05f`

### 3. [Rule 3 — blocking] The A/B test was flipped in Task 1, not Task 3

- **Found during:** Task 1 verification (build `e1e0cb05` — 1 failed).
- **Issue:** Deleting `group_claims`' `if not _CLUSTER_ENABLED:` branch necessarily breaks `test_cluster_disabled_falls_back_to_exact_key_bucketing`, which the plan schedules for rewrite in **Task 3**. Following the plan's task split literally would have shipped a red suite at the Task 1 and Task 2 commits — precisely the pattern 15.2-14's Task 1 was faulted for.
- **Fix:** Task 3's action B was folded into the Task 1 commit. Every commit in this plan is individually green.
- **Commit:** `8d3a05f`

### 4. [Rule 1 — caller fallout] `test_tribunal_pipeline.py` stand-ins updated

- **Found during:** the first full-suite run (`605b0fd6` — 3 failed), then a second round (`5e2eb197` — 1 remaining).
- **Issue:** three failures, all direct consequences of this plan's source changes, none in the plan's file list:
  1. two tests `monkeypatch.setattr(..., "pipeline.claim_distiller", …)` — an attribute that no longer exists, raising `AttributeError`. The patch target moved with the behaviour it stands in for.
  2. `fake_insert_claim()` rejected the new `certainty` kwarg.
  3. `fake_persist()` rejected the new `research_gaps` kwarg — and because Stage 7 catches persistence errors so as not to cost the operator a report, this surfaced as the *silent* symptom "persist was never called", not as a traceback in the test.
- **Fix:** a `fake_facts_result()` helper returning a real `ProviderFactsResult`, and the three stand-ins widened to accept the additive keyword arguments. `fake_persist` now **captures** `research_gaps`, so that test also pins that the merge's couldn't-find list reaches persistence.
- **Commit:** `0b0c0ef`

### 5. [Judgement call] The distill stage kept `set_stage` instead of adopting a `StageFeed`

15.2-14's hand-off suggested passing the distill `StageFeed` as `feed=` to `collect_provider_facts`. It was not taken. `set_stage` merges with `||`, which **replaces** the whole `items` key, so a `StageFeed` owner and a direct `set_stage` writer on the same stage key are last-writer-wins by construction — `stage_feed.py`'s own module docstring is about exactly that defect. Rather than mix them, the per-provider information is folded into the closing `set_stage` row and the collector's `log.info`. The plan's own wording ("keep the existing `distill` feed rows") is `set_stage`-shaped, so this is a deviation from the hand-off note, not from the plan.
