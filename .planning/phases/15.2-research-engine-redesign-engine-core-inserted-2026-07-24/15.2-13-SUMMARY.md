## The D6 distribution rule, as built

`_D6_STREAMS = ("gemini", "openai", "claude", "own")` — the single source of stream ordering, used
for dealing, for laying out a corroboration group, and (reversed) for the trim order.

1. **Normalise and bound.** Winners are read tolerantly (missing `rank` takes the list position, a
   missing `parent` attaches to the first client question, empty text is dropped with a warning),
   sorted by `(rank, original_index)`, then truncated to `_D6_MAX_WINNERS`.
2. **Corroboration set.** The first `_D6_TOP_K` winners each produce **one angle per stream** — four
   angles carrying `corroboration: True` and `corroboration_key: "wNN"`.
3. **Remainder.** Ordered by `(stakes, rank)`, then dealt round-robin over `_D6_STREAMS`: the i-th
   remaining winner goes to `_D6_STREAMS[i % 4]`. High-stakes remainders therefore get first pick of
   Gemini deep research, every stream receives work, and the deal is a pure function of the ranking,
   so it replays byte-identically (asserted over 20 repetitions).
4. **Trim.** The priority ladder below.

Every angle keeps the four original keys (`query`, `stakes`, `focus_area`, `provider`) and adds five
in-memory-only ones (`sub_question`, `rank`, `langs`, `corroboration`, `corroboration_key`). Nothing
was renamed, and none of the additive keys enters the frozen audit payload (T-15.2-64).

`focus_area` is always the **parent client-question label**, never the winner text — which is what
keeps `_propagate_stakes`, `_gate_decision_context`, `extract_focus_areas` and the report's section
structure exactly where they were (D4).

## The `_MAX_ANGLES` arithmetic, and the F5 reversal

**Why 28.** Worst normal case is `_D6_MAX_WINNERS = 15` winners with `_D6_TOP_K` at its clamp of 4:
`4 groups × 4 streams = 16`, plus `15 − 4 = 11` single-stream angles = **27**. 28 leaves one slot of
headroom, so **a normal run never trims at all**. The cap survives only as the bound on a
pathological workshop output (a 200-winner input returns ≤ 28, asserted).

**The reversal.** The old trimmer built `primaries` (everything that was *not* a redundancy copy)
and kept `primaries[:_MAX_ANGLES]`, backfilling with redundancy copies only if room remained — i.e.
it dropped the duplicates FIRST. Correct when a duplicate was optional extra coverage; exactly
backwards under D6, where those duplicates ARE the corroboration signal the merge clusters and
`_group_corroboration` counts. Trimming them first would delete the evidence base at source while
the run still reported healthy. The new ladder:

- **P0, never trimmed** — the first angle of each distinct `focus_area` (D4).
- **P3, first** — surplus single-stream angles (extra depth), weakest rank first.
- **P2, next** — corroboration copies above the floor, weakest-rank group first and in **reverse**
  stream order (`own`, `claude`, `openai`, `gemini`), so the strongest deep-research stream keeps
  the question longest.
- **P1, last resort** — copies below the floor. Only reachable on a misconfigured cap.

Every removal appends a record to `trim_out` (`kind` / `parent` / `sub_question` / `stream` /
`rank` / `degrading`) and the function emits one warning naming the totals per kind.

## Plan decisions recorded

**Stakes from rank, not from a second LLM call.** `_stakes_for_rank(rank, n)`: `rank ≤ _D6_TOP_K →
high`; `rank ≤ ceil(0.6·n) → med`; else `low`. The tournament judge already answered precisely the
stakes question — "which of these two matters more for THIS client's decision" — so a second model
asked to tag stakes would be a redundant, non-reproducible guess over an answer the engine already
holds. Deriving it is deterministic and replays byte-identically. `adaptive_intake`'s stakes tagging
is exactly the LLM call D-03 unwires.

**Which trims degrade the run.** `surplus` and floor-respecting `corroboration` trims are recorded
and logged but marked `degrading: False`: the client-validated question is still researched and the
merge still has two independent views of it, so demoting the run would be the alarm fatigue D-12
explicitly rejects. `corroboration_lost` (below two copies) and `parent_uncovered` are
`degrading: True` — falling below two copies destroys the corroboration signal itself, and that is a
real shortfall. Only the degrading ones become D-12 reasons.

**A corroboration copy is never reassigned.** When its stream is disabled, `run_angles` SKIPS the
copy if a sibling copy still has an enabled stream. Reassigning it would ask one provider the same
question twice — double spend, zero corroboration gain, and, if both copies came back with the same
text, a **false agreement signal** in the merge. The group's LAST copy always falls through to the
existing round-robin, so the skip rule can never starve a group.
