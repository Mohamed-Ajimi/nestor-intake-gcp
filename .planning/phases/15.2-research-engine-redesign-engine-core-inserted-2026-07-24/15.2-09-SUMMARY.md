# Phase 15.2 Plan 09: Status Vocabulary and the One Shared Predicate — Summary

Four inline `run.status != "completed"` comparisons — the entire access model for a
~$45 run's output — collapsed into two named, tested predicates, and `completed_degraded`
promoted from a report marker into a real terminal state across all nine vocabulary sites
(engine schema, four gates, worker write, intake poll driver, intake SSE handler, intake
download gate, SSE client, UI terminal set, UI card).

## What Was Built

**Task 1 — the vocabulary and the predicate** (`04dfb36`)

`RunStatus` went from seven literals to nine, character-matched against the
`ck_run_status` CHECK that 15.2-01 already shipped in migration 0013. Below it,
`REPORT_READABLE_STATUSES` / `BUNDLE_READABLE_STATUSES` and the two predicates
`report_readable()` / `bundle_readable()`. Their docstrings are the single audit
surface D-09 asked for: they state that `completed_degraded` gets everything
`completed` gets, that `parked` gets the bundle but not the report, and the two
invariants a future editor must not break — widening a *status* gate never widens
*tenant* scope (cross-tenant `run_id` stays **404, never 403**), and F1's
`GET /{run_id}/verification` is deliberately gate-free.

`test_fail_loud.py`'s G-10 negative test was **updated in place, not deleted**, and
renamed `test_four_terminal_states_and_completed_still_means_clean`. Its original G-10
rationale paragraph is kept verbatim with a sentence appended recording that 15.2
discharged the preconditions rather than ignoring them.

**Task 2 — the four gates, F2, and an honest terminal status** (`a9555d6`)

All four gate sites route through the predicates: the blind-critique filter (587),
the content-compare filter (691), `GET /report` (947, `report_readable`) and
`GET /research-bundle` (1046, `bundle_readable`). **Zero** `status != "completed"`
comparisons remain in `runs/api.py`.

F2 fixed: `get_run_metrics` now computes `current_stage=("done" if
report_readable(run.status) else ...)`, so a degraded run shows a finished stage list
instead of a permanently spinning stage — on exactly the runs an operator most needs
to read.

F1 honoured as a *documentation* change only: `get_run_verification` is behaviourally
byte-identical, with one added docstring paragraph stating it is deliberately
status-gate-free and naming the test that pins it.

`runs/worker.py`'s completion UPDATE now binds `status=:final_status`, computed by
15.2-02's `terminal_state()` — no second degradation rule was written. The reason list
is persisted as a **sibling** key on the funnel in the *same statement* as the status
(T-15.2-23: a run must never be able to say `completed` while its marker is missing).
`build_verification_summary()` and `RECORDED_FUNNEL_COUNTS` are untouched (Pitfall 3),
and the `WHERE id=:id AND status='running'` cancel guard survives verbatim.

New `test_status_gates.py`: 9 pure tests (no DB, no network, no LLM, no mocking library).

**Task 3 — the intake seam, the SSE bridge and the UI** (`e6e6af9`)

New `backend/app/research/run_status.py` is the intake side's one copy of the
vocabulary, imported by both consumers that previously each carried their own literal
set. A degraded run now gets its bundle (`build_completion`), its report row
(`finalize_completed`), its completion mail and its raw-output download. The
`finalize_failed` clamp was widened to carry `parked` verbatim so a parked run is not
mislabelled `failed` — which would destroy the resume affordance 15.2-19 builds.

Both SSE terminal sets (server handler and browser client) learn `completed_degraded`,
so a degraded run's stream closes instead of running to the 10-minute cap server-side
and driving the client into its `retry()` reconnect loop.

## The Frontend Delta Was 2 Files, Not 1 — and the Second Half Is the Load-Bearing One

The older docs claiming "frontend changes in exactly ONE place" were wrong, and the
correction matters more than it looks. Adding `completed_degraded` to
`ResearchRunProgress.tsx:40` **alone** makes `isTerminal` true while the
`status === "completed"` branch below still fails — which routes a degraded run past
the success card into the grey cancelled card, stripping the raw-output download, the
verification-report button and the frozen feed. That is D-09 inverted on precisely the
runs G-10 exists to protect.

Both halves are handled. The success branch condition became
`status === "completed" || status === "completed_degraded"`, and `isDegraded` varies
exactly four things — border colour (`#D97706`), icon (`AlertTriangle`), title, body.
`RawOutputControls`, the verification-report toggle, the `VerificationReport` panel and
the frozen `AgentFeed` are all left **unconditional**. The third site,
`lib/api/research.ts:210`, is the SSE client stop condition.

## The Deliberate `parked` Gap

`parked` is in `RunStatus` (CR-03 — a read of a parked run must not 500), in
`bundle_readable` (D-09 inspection), and in the `finalize_failed` clamp. It is
deliberately **absent** from every terminal set and from the UI card.

This is left open on purpose. `parked` needs the Resume button, the
`render_research_parked` mail and F-02's free-resume rule — all owned by **15.2-19**
(wave 10). Adding it to a terminal set now would ship a dead-end state: a run that
stops polling with no affordance to move it forward. Until 15.2-19 lands, a parked run
keeps its SSE stream open to the 10-minute cap and renders as in-progress.
