   ~40 lines of hand-written Python.

   regex-extract the index, bounds-check against `n`, reject a partially valid row whole, clamp the
   enum to a safe default that fails toward *keeping* a candidate, ignore garbled lines,
   **never `json.loads` raw model text**, never raise.

   model that had read the open web. Truncate everything embedded and **address every answer by
   index**; carry the ignore-instructions line. This is a security control, not formatting
   (`gates.py:362-368`, `test_gate_replay.py:76-84`).

   scope-guard injection, a total fallback — is a plain-words sentence and a WARNING log. Never a
   silent green.
7. **Tenant isolation.** No new table, no new endpoint. `run_id` / `tenant_id` are threaded to every
   `audited.*` call and to the caller-supplied `StageFeed`; nothing here opens a DB session.
8. **No local Python/Docker.** Author by construction; every verify command runs in Cloud Build.

   `T-15.2-11N` (plan 11 → the 110s band, 111-119). Bands 01-08, 101-109, 21-29, 30-39, 40-48,

- Build `covered = ordered union over winners of (w["parents"] or [w["parent"]])`. **Use `parents`,
  not `parent`** — a cluster representative can carry several, and reading only `parent` would
  declare a client question uncovered when a merged candidate genuinely covers it. Carry a comment
  saying exactly that, naming plan 15.2-10's parent-union rule as the reason it exists.
- `missing = [q for q in client_questions if q not in covered]`, in client-question order.
- For each missing label, in order: if `all_ranked` contains a candidate whose parents include that
  label, promote its **best-ranked** one (a real sub-question beats raw question text); otherwise
  synthesise `{"text": <the client question's own text, truncated to _WINNER_MAX_CHARS>,
  "parent": <label>, "parents": [label], "source": "verbatim", "scope_injected": True}`.
- **Injected and promoted winners go to the TOP of the list**, in client-question order, and the
  whole list is then re-ranked `1..N`. Carry the reasoning in a comment: 15.2-13 derives its D6
  stakes from `rank`, so appending an injected client question at the bottom would give the client's
  own validated question the *weakest* stakes and the fewest streams — scope-preserving on paper and
  quality-destroying in practice. A client-validated question the workshop failed to deepen is the
  most literal expression of client intent and cannot rank below a model-invented sub-question.
- Log every injection at **WARNING**, one line each, naming the client question label and whether it
  was a promotion or a verbatim injection. This is the "log loudly" half.
- **Notes, not degradation reasons.** Return the sentences in the `notes` list. Record the reasoning
  in the docstring: D-12 lists *"the workshop fell back to client-validated questions only"* as a
  degrading condition, not "a question was injected". A partial injection means the output is
  **complete** — the question is researched — so demoting the run would be exactly the alarm fatigue
  D-12 warns against. The full fallback in step H is what degrades.
- **Post-condition, asserted in code, not just in a test:** after the guard,
  `set(client_questions) <= covered_after`. If it somehow still is not, log at ERROR with the
  difference and inject verbatim unconditionally. The function must be idempotent — running it twice
  changes nothing.
- Never raises.
