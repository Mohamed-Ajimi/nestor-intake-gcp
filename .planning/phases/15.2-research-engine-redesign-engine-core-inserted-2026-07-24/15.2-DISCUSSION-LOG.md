## Citations vs. prose-written reports

**Orchestrator note:** before asking, the code was traced rather than assumed. Findings that
reshaped the options: `citations/numbering.py::number_citations` already exists and is tested
(Phase 15) but is not wired into the report body; `[cite: N]` markers are Gemini deep-research
artifacts resolved by `resolve_url_citations` and stripped at `pipeline.py:1307`, not our
convention; `## Sources` is already rebuilt deterministically in Python after the model was
caught truncating URLs.

### Q1 — How do generated `[n]` markers attach to statements in a prose-written report?

| Option | Description | Selected |
|--------|-------------|----------|
| Model marks anchors, machine assigns numbers | Model tags load-bearing statements with an opaque claim/source reference; Python post-pass rewrites each to its `[n]`; model never picks a number | ✓ |
| Post-hoc matching, model writes no markers | Removes the model entirely, but prose→claim matching is the clustering problem again and a wrong match cites the wrong source | |
| Cite only what the pipeline can prove | Zero fabrication risk, but leaves most load-bearing prose unmarked | |

**User's choice:** Model marks anchors, machine assigns numbers.
**Notes:** Satisfies D13's "never left to the writing model" while letting the model decide
placement — the only part it actually knows. → CONTEXT D-05.

**Notes:** Today these vanish with only a log line — that is last run's 28 stripped markers.

## New moving parts: failure + budget

**User clarification mid-area.** The first framing of the D8 question was rejected with:
*"the deep research returns a fact list? claim list?"* — a premise check. The answer traced
the two vocabularies: a **claim** is a DB row (`text`, `facet`, `position` only), produced
today by extracting assertions out of provider prose; a **fact** is what D8 asks the provider
to hand back (statement + source link + source quality + certain/found-once). They are the
same objects at different stages, and D8 changes *who produces them*. That surfaced a
structural gap not previously named — a D8 fact carries metadata the `claim` table has
nowhere to store — which became the first question instead.

### Q1 — Where does a D8 fact's extra metadata live?

| Option | Description | Selected |
|--------|-------------|----------|
| Add columns to claim, plus a small table for couldn't-find | Certainty + `found_by` on `claim`, provider-stated quality on `claim_source` (domain heuristic as fallback), small table for couldn't-find feeding D14; queryable, tenant-scoped, chain-safe | ✓ |
| One JSONB metadata column on claim | Cheapest migration and easiest to extend, but corroboration/priority logic would read JSON | |
| Keep it in memory, persist only what surfaces need | No migration, but nothing is reconstructable after the run | |

**User's choice:** Real columns plus a small couldn't-find table.
**Notes:** Rejected the in-memory option partly because the August live run is the one run
that has to prove the phase and must be re-examinable afterwards. → CONTEXT D-13.

### Q2 — What happens when a provider returns prose but no usable fact list?

| Option | Description | Selected |
|--------|-------------|----------|
| Fall back to full distillation for that provider, and record it | Research still reaches the merge; certainty/quality left null with the domain heuristic filling the tier; fallback recorded per provider and surfaced | ✓ |
| Retry that provider once with a corrective prompt, then fall back | Better odds of good input at the cost of one extra deep-research call | |
| Drop that provider's stream and mark the run degraded | Clean data model, but discards a paid call and weakens corroboration | |

**User's choice:** Fall back to full distillation, recorded.
**Notes:** Consequence flagged and captured separately — the distiller's full-extraction mode
must **survive** V-03's removal as the fallback path. → CONTEXT D-14 and D-15.

### Q3 — How does SerpAPI spend enter the C1 cost accounting?

| Option | Description | Selected |
|--------|-------------|----------|
| Recorded search count × published per-search unit price | `plan price ÷ plan quota` is published, so `count × unit` is a correct calculation not an estimate — same treatment as Anthropic web_search fees; unit price recorded for reproducibility | ✓ |
| Show searches as pending, reconcile against the invoice | Strictest C1 reading, but a prepaid plan bills a flat monthly charge so there may be no per-run figure to backfill | |
| Record search counts, no money figure | Zero risk of a wrong number, but puts a known cost class outside the total | |

**User's choice:** Count × published unit price.
**Notes:** Verified beforehand that the INTAKE-05 scope guard scans `backend/app/**` and
`frontend/src` only, not `tribunal/` — so D10's SerpAPI use inside the SDK does not trip CI.
→ CONTEXT D-16.

### Q4 — When does a per-provider breaker trip escalate into a whole-run park?
