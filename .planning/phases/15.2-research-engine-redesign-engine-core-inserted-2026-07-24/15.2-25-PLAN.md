<objective>
**D-D — there is no operator cancel path anywhere.** Operator-confirmed fix (2026-07-27, item 2):
**cancel belongs in the UI**, across all three layers.

`POST /api/runs/{run_id}/cancel` **already exists** on `tribunal-api` and is correct: it sets
`status='cancelled'`, stamps `completed_at`, is idempotent on a terminal run, and is tenant-scoped
via RLS. Every terminal write in `runs/worker.py` is guarded with `AND status='running'` precisely so
a cancel wins the race. What is missing is everything on the intake side: **no `cancel_run` in
`tribunal_client.py`, no route on `nestor-api`, no button in the UI** — `cancelled` appears in the
frontend only as a status it renders.

So when run `d6bb3aae` had to be stopped, the operator had to pause the entire worker with
`--min-instances=0`. That did not work: **pausing is not cancelling.** The in-flight process kept
going for another 16 minutes; terminating it required deploying a new revision; and that immediately
started a fresh worker which was about to re-claim the run (D-E, plan 15.2-20).

**Why the manual seam call could not substitute for this**, and why the gap is real rather than a
convenience. On 2026-07-27 `roles/iam.serviceAccountTokenCreator` on `nestor-run@` was granted to
`tools@dotto.be` to attempt exactly that. Two guards had to be satisfied and only one could be:
`gcloud auth print-identity-token --impersonate-service-account` omits the `email` claim unless
`--include-email` is passed (403 `caller is not the intake backend`); adding it satisfied
`InternalCallerProvider`, and the second guard then returned **400 missing required
`X-Nestor-Tenant-Id`**. The tenant id is recorded nowhere reachable — not in the audit blobs, not in
either service's Cloud Run logs — and obtaining it from the intake requires an Identity Platform user
token. **The seam is, by construction, callable only by the intake backend that already knows the
tenant.** That is the Phase-14 lockdown working exactly as designed, and it must not be weakened; the
answer is a route on the backend that already holds the tenant, which is this plan.

**Its first real use is clearing run `d6bb3aae-33e7-49fd-aa35-57dc529e05b3`** on intake
`4a500d44-62b5-4f73-905f-792e31d0d9cc`. That run is still `running` in the DB even though its process
is dead, and because `_RETRYABLE_RUN_STATUSES = {failed, cancelled, needs_input}` excludes `running`,
**that intake cannot be retried until the row is resolved.** Cancelling it moves it to `cancelled`,
which IS retryable — so the demo and the unblocking are the same action. That acceptance demo is
executed with the operator in plan **15.2-26**, after deploy.

**A standing action this plan creates.** Once the UI cancel ships, the `serviceAccountTokenCreator`
grant on `nestor-run@` is a standing weakening of the Phase-14 lockdown with no remaining purpose.
Plan 15.2-26 revokes it as an operator step. This plan records the dependency so the two are not
separated.

Purpose: an operator must be able to stop a run they are paying for, without deploying anything.
Output: `cancel_run` on the seam client, `POST /intakes/{intake_id}/research/cancel`, the denial trio,
a Stop button on the active card behind a confirmation, and six locale keys in three languages.
</objective>
