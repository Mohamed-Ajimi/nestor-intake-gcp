# Phase 15.2 Plan 25: Operator Cancel Path (D-D) Summary

A superadmin can now stop a research run from the intake detail page in one click plus a
confirmation, across all three layers — seam client, backend route, UI — replacing the
dangerous "pause the whole Cloud Run service" manoeuvre that does not actually stop a run.

## What was built

**`tribunal_client.cancel_run`** — a byte-for-byte sibling of `resume_run` (keyword-only args,
`_headers(...)`, `_TIMEOUT_S`, `json={}`, `raise_for_status()`, `return resp.json()`), differing
only in the path. Its docstring carries the tenant discipline verbatim and states the one
difference that matters: **there is no 409 arm**, because the engine treats cancelling a terminal
run as an idempotent no-op rather than a conflict.

**`POST /intakes/{intake_id}/research/cancel`** — superadmin-only, space-scoped, existence-hidden.
`_superadmin_gate` is declared BEFORE `get_tenant_repo` so a null-space user is 404 there rather
than 403 here; the in-body role re-check is the `get_bundle_url` double-gate register. The seam
call runs outside any held DB session and before the mirror patch. The mirror patch and the
`research.cancelled` audit row (`{"from","to"}`, no link, no token) run in ONE `tenant_session`
that commits on block exit.

**The Stop control** on the ACTIVE card only, beneath the cost line in the right-hand column —
the cost is the number that makes an operator want to stop, and that placement keeps it out of
competition with the stage feed. Secondary outline styling, not the primary ink fill: stopping is
an escape hatch, not the expected next action.

## The two things that had to be true, and are

**`cancelled` genuinely resolves the row, and is retryable.** The mirror row reads `cancelled`
after the call, and `test_cancel_superadmin_resolves_the_run_row_and_unblocks_retry` asserts
membership against the production constant itself:

- `"cancelled" in research_mod._RETRYABLE_RUN_STATUSES` — the unblocking half
- `"running" not in research_mod._RETRYABLE_RUN_STATUSES` — the reason a stuck run blocks its
  intake in the first place

Asserting against the live constant (not a copy) means a future edit to that set cannot silently
re-break retry for a cancelled run.

**The denial trio returns EXACTLY 404.** Each case runs through `_assert_exactly_404`, which pins
`!= 403` and `!= 200` by name before asserting `== 404`, with the reason spelled out in the failure
message. Each also asserts the seam was NOT called and the row was NOT touched — a run stopped
behind a 404 would be a cross-tenant write dressed up as a denial.

## Deviations from Plan

**1. [Rule 2 — missing correctness] `completed_at` is stamped on a real transition**

- **Found during:** Task 1, writing the mirror patch.
- **Issue:** The plan specified patching only `status`. But the run row is what has to be
  *resolved*, and the poll driver that normally stamps `completed_at` on a terminal is very
  plausibly dead — that is the exact condition that makes an operator reach for this button. A
  terminal run carrying `completed_at IS NULL` is half-resolved.
- **Fix:** `completed_at=func.now()` in the same patch — the identical shape
  `run_task.finalize_completed` / `finalize_failed` already use, so the timestamp comes from the DB
  clock. Deliberately **not** applied on the already-terminal no-op path, where it would clobber a
  finished run's real completion time; `test_cancel_already_terminal_run_is_a_reporting_no_op`
  asserts the whole row is byte-identical before and after.
- **Files:** `backend/app/api/research_routes.py`
- **Commit:** `46cdda9`

**2. [Plan-internal contradiction resolved] 202, not 200, for the terminal no-op**

- **Found during:** Task 1, writing Test 4.
- **Issue:** The plan's `<behavior>` said an already-terminal run "returns 200"; its `<action>`
  said "Return `202` ... matching the trigger/resume response shape". A FastAPI route declaring
  `status_code=202` cannot return 200, so the two cannot both hold.
- **Fix:** 202, per the explicit action instruction, the sibling response shape it names, and the
  `must_haves` artifact contract. The phase rule "each case pinning ONE exact status code" is
  honoured — the test asserts `== 202`, not a range. The `<behavior>` line's "200" reads as
  "a success response, not an error", which is the substantive claim and is satisfied.
- **Files:** `backend/app/api/research_routes.py`, `backend/tests/test_research_cross_tenant.py`
- **Commit:** `46cdda9`

**3. [Rule 3 — blocking] `_seed_run` gained an optional `tribunal_run_id`**

- **Found during:** Task 1, writing the WR-03 arm.
- **Issue:** `_seed_run` always derived `trib-{run_id}`, so there was no way to seed the
  NULL-engine-id run that arm requires.
- **Fix:** An optional keyword defaulting to a `_TRID_AUTO` sentinel that reproduces the previous
  behaviour exactly; passing `None` seeds NULL. Every pre-existing caller is unaffected (proven by
  the full 219-test gate staying green).
- **Files:** `backend/tests/test_research_cross_tenant.py`
- **Commit:** `46cdda9`

**4. [Rule 3 — blocking] `from sqlalchemy import func` added to `research_routes.py`**

- **Found during:** Task 1, needed for deviation 1.
- **Issue:** D-03's `ci_no_raw_db_access.sh` forbids raw DB symbols outside `app/db/`.
- **Fix:** `func` is a SQL-expression helper, not an engine/session factory, and does not match the
  guard's pattern. Verified by running the guard: the ONLY offender it reports is the pre-existing
  `run_task.py:103` (see Pre-existing issues). A comment at the import records why it is sanctioned.
- **Files:** `backend/app/api/research_routes.py`
- **Commit:** `46cdda9`

**5. [Plan latitude exercised] The confirmation is an `AlertDialog`**

- **Found during:** Task 2.
- **Issue:** The plan offered a fork — match the route's `confirm(...)` if that is the pattern, or

  imports no `AlertDialog`, and its hand-rolled overlay is the ARCHIVE dialog, not a research

- **Fix:** The affordance the route already uses **for a destructive/paid research action** is
