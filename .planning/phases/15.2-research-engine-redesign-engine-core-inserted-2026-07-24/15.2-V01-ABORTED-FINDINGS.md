## D-E — the stale reaper RE-RUNS a stuck run instead of failing it (money risk)

**CLOSED by 15.2-20 (2026-07-27)** — migration **0014** plus a heartbeat-aware claim, a reclaim
ceiling and a reap-to-failed statement, so that killing a worker stops meaning restarting its run.
Proven by five SQL-level tests **against a real Postgres**, all five PASSED by name in Cloud Build
`2e55aeaa` (35 passed, 0 skipped); the exactly-once keystone re-proved green in `64058b51`
(34 passed, 0 skipped, all four live `test_advisory_lock_exactly_once.py` tests executed).

The three parts:

1. **A real liveness signal.** `run.heartbeat_at` is bumped every `NESTOR_WORKER_HEARTBEAT_S`
   (default 30s) by a loop started immediately before the long `await runner.run(...)` and cancelled
   in a `finally` covering the success, `RunCancelled` and exception paths alike. Staleness became
   `COALESCE(heartbeat_at, started_at)`, so every pre-0014 row behaves exactly as before — no
   backfill, no behaviour change on legacy data.
2. **A ceiling.** `run.reclaim_count` is incremented only when the claim re-claims a row that was
   already `running`, and the reclaim arm requires `reclaim_count < NESTOR_WORKER_MAX_RECLAIMS`
   (default 2). Past the ceiling `REAP_SQL` flips the run to `failed` with one plain sentence rather
   than starting it again. **"A permanently stalling run re-bills every 60 minutes forever" is now
   structurally unreachable.**
3. **`started_at` is untouched** — it is the CR-01 fencing token that `_CONSUME_CLAIM_SQL` matches to
   guarantee a claim dispatches at most once (ENGINE-08, legally load-bearing for the audit chain).
   Bumping it on a timer would make every heartbeat invalidate the run's own claim token. Verified by
   an EMPTY `git diff --stat` on `runs/execute.py` and all of `pipeline/`.

**Two things this fix does NOT do, and both matter:**

- **It does not protect run `d6bb3aae` itself.** That row predates 0014, so its `heartbeat_at` is
  NULL and `COALESCE` falls back to a `started_at` of 08:09 UTC — long stale — with
  `reclaim_count` 0, under the ceiling. **The moment the deploy restores
  `NESTOR_WORKER_STALE_MINUTES=60`, that row is claimable again.** This is why the runbook cancels
  it BEFORE unpausing, and why the two must not be reordered.
- **No COMMITTED gate runs the five proofs.** They pass in the DB-less engine gate as five loud
  skips whose message says in words that a skip is not a pass; the harness that ran them for real
  was a scratch config. Until `test_stale_reclaim.py` joins `cloudbuild.test-critical.yaml`, the
  regression protection for the money defect is one build id. Filed as **D26-1** in
  `deferred-items.md` — the highest-value open item this phase leaves behind.

**The original record follows.**

`worker.py` `CLAIM_SQL`:

```sql
OR (status = 'running' AND started_at < NOW() - make_interval(mins => :stale))
```

A run stuck in `running` is **re-claimed and re-executed** once it is older than
`NESTOR_WORKER_STALE_MINUTES` (deployed value: **60**). With `started_at` ≈ 08:09 UTC this run would
have restarted at ≈ 09:09 UTC and spent again, unattended.

That is correct for a worker that genuinely *died* mid-execute — the case the comment describes —
but wrong for a run whose process is alive and simply not progressing. Combined with D-D (no way to
cancel) it is a silent, repeating spend. **Worst case: a permanently stalling run re-bills every 60
minutes forever.**

Mitigated for now by pausing the worker. Needs: an attempt counter / max-reclaims, or a distinction
between "worker died" and "run stalled", before the worker is unpaused with real runs queued.

## D-F — the engine logs ONLY failures

**CLOSED by 15.2-24 (2026-07-27).** A `stage_enter` line is emitted for every stage the engine
reports and a `stage_exit` line carries that stage's monotonic wall seconds plus its counts, at the
single `set_stage` choke point. A real stubbed run now produces, in order:
`intake → workshop → research_division → deep_research → distill → merge → gate → verify →
adjudicate → coverage → verify → conflict → synthesize → done`, closed by
`run_stages_complete: seconds=… stages=14`. Proven by 18 tests in `test_stage_logging.py`, Cloud
Build `fe1c7332` (704 passed) and `c771c88c` (713 passed), with `test_stage_schema.py` re-run
separately in `29716f9a` (179 passed) because it lives in a different gate config.

**The counts ride the exit lines**, read off values the pipeline already computed: `workshop
questions_in/winners_out`, `research_division client_questions/workshop_questions/angles/
corroborated`, `deep_research angles_dispatched/angles_ok/angles_failed/streams`, `gate
claims_in/selected_for_checking/not_checkable/gate_errors`, `verify sessions/verdicts/
claims_with_a_verdict`.

**Line safety is structural, not a blacklist.** `_stage_log_line` renders every value through
`int()` and every name through a key sanitiser, so a non-integer is **dropped whole, key and value**,
never stringified — `test_a_non_integer_count_is_dropped_not_stringified` hands it a real research
question and proves the question never appears. A whitelist assertion requires every captured record
to match `^tribunal_pipeline (stage_enter|stage_exit|run_stages_complete): (key=value )*$` with every
value `[a-z0-9_.]+`, which a prompt body, a claim text or a URL cannot satisfy.

**This is the structural fix for the withdrawn D-C.** After deploy, the last `stage_enter` line
names the stage a silent run is sitting inside — the thing that was missing when a flat CPU trace
was read as a stall. **Not yet observed against a real run:** every proof here is stubbed, and these
lines have never been read from a paid Cloud Run log. That is the next live run's job.

**The original record follows.**

All 72 log lines from 08:09 to 08:53 are either the workshop's output or angle-failure warnings.
There is **not one success or stage-transition marker**. A stall between stages is therefore
invisible in logs, and diagnosis had to fall back on Cloud Run CPU metrics.

This is the same "green for the wrong reason" family this phase spent six waves eliminating, one
layer up: nothing raised, so nothing reported. A single INFO line per stage entry/exit would have
made D-C obvious in seconds.
