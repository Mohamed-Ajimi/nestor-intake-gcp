# V-01 attempt 1 — ABORTED. Six defects found in 33 minutes.

The first live run of the phase-15.2 engine. It did not reach a terminal state; it **stalled
silently** and was aborted by pausing the worker. Per plan 18 Task 4's own instruction for a run
that does not reach `completed` / `completed_degraded` / `parked`: record the failure and the stage

## D-A — the OpenAI deep-research model is DEPRECATED (7 failures, 100% of that stream)

```
angle N (openai) did not succeed: Research failed:
ResponseError(code='model_not_found', message='The model `o4-mini-deep-research` has been deprecated')
```

`audited_llm_client.py:89` reads `NESTOR_OPENAI_DR_MODEL` and defaults to `"o4-mini-deep-research"`.
**The worker does not set that env var**, so it runs on the dead default. Every OpenAI angle failed.

**INVESTIGATED LIVE 2026-07-27 10:30 — the fix is NOT a one-line env var. Read this before
planning 15.2-22 Task 1.**

Probing the account with the `Nestor_OpenAI` key established four things:

1. **The account lists only two deep-research ids**: `o4-mini-deep-research` and its snapshot
   `o4-mini-deep-research-2025-06-26`. There is **no `o3-deep-research`** and no other
   `*-deep-research` model. So there is **no drop-in replacement to name.**
2. **Synchronous validation PASSES for both.** `POST /v1/responses` with a bad body returns
   `missing_required_parameter: input`, not a model error — so any probe that stops at request
   validation will wrongly conclude the model is fine. (I made exactly that mistake mid-session.)
3. **The deprecation fires ASYNCHRONOUSLY.** With the required `web_search_preview` tool the request
   is *accepted* — `status: queued`, id `resp_0afbcc50…` — and only then fails:
   ```json
   {"status":"failed","model":"o4-mini-deep-research-2025-06-26",
    "error":{"code":"model_not_found",
             "message":"The model `o4-mini-deep-research` has been deprecated"}}
   ```
   This is why the engine sees it per-angle, minutes in, as a research failure rather than a
   configuration error. **A startup-time model check will NOT catch this** — the plan's proposed
   "fail loud at startup on a rejected model id" cannot work against an async deprecation. It needs
   to be a *first-failure* classification instead: the first `model_not_found` on a deep-research job
   must be treated as a configuration error that fails the run loudly, not as one more dead angle.
4. **Search-capable alternatives DO exist on the account**: `gpt-5-search-api`,
   `gpt-4o-search-preview`, `gpt-4o-mini-search-preview`. These are *search* models, not
   deep-research — a different capability and response shape.

**So the operator decision in 15.2-22 Task 1 is bigger than "which id", and should be posed as:**

- **(a)** obtain entitlement to a current OpenAI deep-research model (account/billing action, outside
  the repo), then set `NESTOR_OPENAI_DR_MODEL`; or
- **(b)** re-point the OpenAI arm at `gpt-5-search-api` — needs adapter work, since it is not a
  deep-research job and does not share the two-phase start/poll shape; or
- **(c)** drop the OpenAI stream and run three streams, accepting reduced corroboration (D6
  distribution and the corroboration-safe angle cap already tolerate this).

**Also found:** the audit blob for an OpenAI call stores only `{"query": …}` — not the tools, model or
parameters actually sent. Same completeness problem as D-J, different provider. It is why the engine's
exact request could not be compared against the probe.

## D-B — the own-researcher (D10, NEW in this phase) 400s on every session (6 failures, 100%)

```
BadRequestError: 400 invalid_request_error
messages.N.content.M.web_fetch_tool_result.content.RequestWebFetchToolResultError:
Input does not match the expected shape.
```

The error is on a **prior turn's** content block being echoed back, and specifically on the
`RequestWebFetchToolResultError` — the **error variant** of a web_fetch result. So the stream works
until a fetch fails, at which point the malformed error result is replayed into the next request and
the whole call 400s. `tools.py:24` pins `web_fetch_20250910` deliberately (not `web_fetch_20260209`,
which needs the code-execution tool), so the shape must match that version's error contract.

Aggravating: `reliability.with_retry` classifies it `hard failure` and gives up
**after attempt 1/4** — so no retry is even attempted.

**Why CI missed it:** `test_engine_e2e_stubbed.py` stubs the provider, so it never reproduces
Anthropic's real server-tool *error* payload. A fixture capturing a genuine failed web_fetch result
is the regression test this needs.

## D-C — **WITHDRAWN 2026-07-27 09:20. THIS WAS A MISDIAGNOSIS.**

**The pipeline never stalled.** It was blocked on long-poll I/O the whole time, exactly as the
`audited_llm_client` docstring warns ("deep-research calls that may take up to 35 minutes"). At
**09:07:35** it logged `OpenAI deep-research: RESUMING the existing response resp_0182…` — 15.2-16's
R7 provider-resume working as designed — then gemini reports landed at 09:09:43 and
`claim_distiller` ran across every focus area at 09:11:09. The run advanced into fact collection and
merge on its own.

**What I got wrong, and why:** I treated a flat CPU trace (0.0014–0.0018 for ten minutes) as proof
of a stall. It is not. A process awaiting an HTTP response consumes no CPU, and the earlier
"activity blips" I calibrated against were simply shorter angles completing. Combined with D-F
(the engine logs only failures), silence plus idle CPU looked like death and was actually patience.
**Lesson: on this engine, neither log silence nor idle CPU is evidence of a stall. Only the run row
is.** The one authoritative check — reading `status`/`updated_at` — is the one I could not perform,
and I should have said that was the answer rather than inferring from proxies.

The section below is retained verbatim as the record of the misdiagnosis. Everything in it is
observationally true and interpretively wrong.

| Time (UTC) | Event |
|---|---|

is why the UI looked alive rather than failed — it faithfully reported a run that had stopped moving.

**Not yet distinguished** (needs the run row read directly, which the Phase-14 lockdown correctly
prevents from this workstation): a hung `await` that never returns, versus a terminal-state write
that failed silently. Stage 7 swallows persistence errors by design, so the second is plausible and
they need different fixes.

## D-L — the elapsed counter restarts from zero on every page refresh

Reported by the operator, confirmed in code.

`ResearchRunProgress.tsx:187` — `useElapsed(startedAt, active)` does:

```ts
const start = startedAt ? new Date(startedAt).getTime() : Date.now();
```

`frontend/src/lib/api/research.ts:191` declares `started_at: string | null`, and
`ResearchRunProgress.tsx:603` consumes it — **but the backend never sends it.** A repo-wide search
of `backend/app/research/` and `research_routes.py` for `started_at` returns nothing. So the field
is always null, `start` falls back to `Date.now()`, and the clock counts from *page load* instead of
from run start.

Same root cause breaks the summary card: `fmtDuration(run?.started_at, run?.completed_at)` at
`:644` returns `"—"` whenever either is missing.

**Fix:** add `started_at` (and `completed_at`) to the run-status payload the seam returns. The
frontend contract already expects them — only the producer is missing.

## Abort record — 2026-07-27 09:25-09:27 UTC (operator decision)

The run was stopped at operator request after ~13 min of log silence in the gates/merge stage.
**Note the silence was NOT proof of a stall** (see the withdrawn D-C); the run was stopped because
it is invalid regardless — it researched the wrong questions (D-G) — not because it was proven dead.

How it was stopped, and what it cost to learn:

1. `--min-instances=0` at 08:55 did **not** stop it. That only prevents claiming NEW runs; the
   in-flight process kept going for another 16 minutes. **Pausing is not cancelling.**
2. Terminating the instance required deploying a new revision (`tribunal-worker-00016-ljj`).
3. **That immediately started a fresh worker** (`worker_started poll_s=2.0`) — and because the run
   was by then ~76 min old, past `NESTOR_WORKER_STALE_MINUTES=60`, the new worker was about to
   re-claim and re-execute it. **D-E fired for real.** Blocked by setting
   `NESTOR_WORKER_STALE_MINUTES=525600` (`tribunal-worker-00017-6cv`).

**Without that guard, "cancelling" would have RESTARTED the run.** This is the single most
dangerous defect found today: on this build, killing a worker is indistinguishable from a worker
crash, and the designed recovery for a crash is to re-run — unattended, at full cost, on a loop.

**State left behind:** the process is dead, but run `d6bb3aae` is **still `running` in the DB**.
The seam therefore keeps answering `/metrics` and the UI keeps showing it as active with a resetting
clock (D-L). Because `_RETRYABLE_RUN_STATUSES = {failed, cancelled, needs_input}` excludes
`running`, **that intake cannot be retried** until the row is resolved. Resolving it needs a call the
Phase-14 lockdown blocks from this workstation — see D-D.

**Temporary config that MUST be reverted before real runs:**
`NESTOR_WORKER_STALE_MINUTES=525600` and `NESTOR_RUN_ABORTED_MARKER=d6bb3aae-20260727` on
`tribunal-worker`. Restore `60` (or whatever D-E's fix replaces it with) once the stuck row is
resolved — otherwise a genuinely crashed worker will never be recovered.

## D-D — there is NO operator cancel path

`POST /api/runs/{run_id}/cancel` exists on `tribunal-api` only, which is reachable solely by
`nestor-run@` (Phase-14 lockdown). There is **no cancel function in `tribunal_client.py`**, **no
cancel route on `nestor-api`**, and **no cancel button in the UI** — `cancelled` appears in the
frontend only as a status it renders.

So when a run stalls, the operator cannot stop it. This run had to be aborted by pausing the entire
worker (`--min-instances=0`).

## D-E — the stale reaper RE-RUNS a stuck run instead of failing it (money risk)

`worker.py` `CLAIM_SQL`:

```sql
OR (status = 'running' AND started_at < NOW() - make_interval(mins => :stale))
```

A run stuck in `running` is **re-claimed and re-executed** once it is older than
`NESTOR_WORKER_STALE_MINUTES` (deployed value: **60**). With `started_at` ≈ 08:09 UTC this run would
have restarted at ≈ 09:09 UTC and spent again, unattended.

That is correct for a worker that genuinely *died* mid-execute — the case the comment describes —
but wrong for a run whose process is alive and simply not progressing. Combined with D-D (no way to
cancel) it is a silent, repeating spend. **Worst case: a permanently stalling run re-bills every 60
minutes forever.**

Mitigated for now by pausing the worker. Needs: an attempt counter / max-reclaims, or a distinction
between "worker died" and "run stalled", before the worker is unpaused with real runs queued.
