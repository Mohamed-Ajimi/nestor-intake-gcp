## D-A — the OpenAI deep-research model is DEPRECATED (7 failures, 100% of that stream)

```
angle N (openai) did not succeed: Research failed:
ResponseError(code='model_not_found', message='The model `o4-mini-deep-research` has been deprecated')
```

`audited_llm_client.py:89` reads `NESTOR_OPENAI_DR_MODEL` and defaults to `"o4-mini-deep-research"`.
**The worker does not set that env var**, so it runs on the dead default. Every OpenAI angle failed.

**Fix:** one `--update-env-vars NESTOR_OPENAI_DR_MODEL=<current model>` — no rebuild, no redeploy of
code. Blocked only on knowing which OpenAI deep-research model the account is entitled to. Consider
also failing loudly at startup when a configured model id is rejected, rather than degrading a whole
stream silently per-angle.

## D-B — the own-researcher (D10, NEW in this phase) 400s on every session (6 failures, 100%)

```
BadRequestError: 400 invalid_request_error
messages.N.content.M.web_fetch_tool_result.content.RequestWebFetchToolResultError:
Input does not match the expected shape.
```

The error is on a **prior turn's** content block being echoed back, and specifically on the
`RequestWebFetchToolResultError` — the **error variant** of a web_fetch result. So the stream works
until a fetch fails, at which point the malformed error result is replayed into the next request and
the whole call 400s. `tools.py:24` pins `web_fetch_20250910` deliberately (not `web_fetch_20260209`,
which needs the code-execution tool), so the shape must match that version's error contract.

Aggravating: `reliability.with_retry` classifies it `hard failure` and gives up
**after attempt 1/4** — so no retry is even attempted.

**Why CI missed it:** `test_engine_e2e_stubbed.py` stubs the provider, so it never reproduces
Anthropic's real server-tool *error* payload. A fixture capturing a genuine failed web_fetch result
is the regression test this needs.

## D-C — the pipeline STALLED between stages, silently (the reason this run was aborted)

| Time (UTC) | Event |
|---|---|
| 08:41:22 | last log — `angle 24 (openai) did not succeed`, the final retry |
| 08:43 | worker CPU drops to idle floor |
| 08:43 → 08:53 | **10 min flat idle. No ERROR. No restart. No status change.** |

CPU is decisive here, because the log is silent by design (see D-F). During the provably-active
research phase CPU oscillated 0.005–0.086 with constant blips; from 08:43 it flatlined at
0.0014–0.0018 and stayed there. A deep-research long-poll still shows the wake/parse blips. This
does not.

So `run_angles` completed its retry sweep and the pipeline **never advanced to merge/gates**. The
run row sits in `running` forever. The seam kept answering `GET /metrics` with 200 every ~3s, which
is why the UI looked alive rather than failed — it faithfully reported a run that had stopped moving.

**Not yet distinguished** (needs the run row read directly, which the Phase-14 lockdown correctly
prevents from this workstation): a hung `await` that never returns, versus a terminal-state write
that failed silently. Stage 7 swallows persistence errors by design, so the second is plausible and
they need different fixes.

## D-D — there is NO operator cancel path

`POST /api/runs/{run_id}/cancel` exists on `tribunal-api` only, which is reachable solely by
`nestor-run@` (Phase-14 lockdown). There is **no cancel function in `tribunal_client.py`**, **no
cancel route on `nestor-api`**, and **no cancel button in the UI** — `cancelled` appears in the
frontend only as a status it renders.

So when a run stalls, the operator cannot stop it. This run had to be aborted by pausing the entire
worker (`--min-instances=0`).

## D-E — the stale reaper RE-RUNS a stuck run instead of failing it (money risk)

`worker.py` `CLAIM_SQL`:

```sql
OR (status = 'running' AND started_at < NOW() - make_interval(mins => :stale))
```

A run stuck in `running` is **re-claimed and re-executed** once it is older than
`NESTOR_WORKER_STALE_MINUTES` (deployed value: **60**). With `started_at` ≈ 08:09 UTC this run would
have restarted at ≈ 09:09 UTC and spent again, unattended.

That is correct for a worker that genuinely *died* mid-execute — the case the comment describes —
but wrong for a run whose process is alive and simply not progressing. Combined with D-D (no way to
cancel) it is a silent, repeating spend. **Worst case: a permanently stalling run re-bills every 60
minutes forever.**

Mitigated for now by pausing the worker. Needs: an attempt counter / max-reclaims, or a distinction
between "worker died" and "run stalled", before the worker is unpaused with real runs queued.

## D-F — the engine logs ONLY failures

All 72 log lines from 08:09 to 08:53 are either the workshop's output or angle-failure warnings.
There is **not one success or stage-transition marker**. A stall between stages is therefore

This is the same "green for the wrong reason" family this phase spent six waves eliminating, one
layer up: nothing raised, so nothing reported. A single INFO line per stage entry/exit would have
made D-C obvious in seconds.
