**D-A — the OpenAI deep-research model is deprecated.** Seven angles, seven identical failures:

    ResponseError(code='model_not_found',
                  message='The model `o4-mini-deep-research` has been deprecated')

`audited_llm_client.OPENAI_DEEP_RESEARCH_MODEL` reads `NESTOR_OPENAI_DR_MODEL` and defaults to that
dead id; **`deploy-worker.sh` does not bind the variable**, so the deployed worker runs on the dead

model this deployment is configured with does not exist". Seven identical warnings is how a
configuration error disguises itself as flaky providers.

**D-B — the own-researcher 400s on every session.** Six failures, 100% of the new D10 stream:

    BadRequestError: 400 invalid_request_error
    messages.N.content.M.web_fetch_tool_result.content.RequestWebFetchToolResultError:
    Input does not match the expected shape.

Read the path: `messages.N` is a **prior turn** being echoed back, and the offending block is
`RequestWebFetchToolResultError` — the **error variant** of a `web_fetch` result. So the stream works
until a fetch fails; then the malformed error result is replayed into the next request and every
subsequent call 400s. The culprit is `skeptic._content_to_serialisable`, which every hand-written
loop uses to append the assistant turn:

    result.append({k: v for k, v in block.__dict__.items() if not k.startswith("_")})

That is a ONE-LEVEL copy. A `web_fetch_tool_result` block's `content` is itself a provider object —
for the error variant, `RequestWebFetchToolResultError` — and it survives the copy as a live object
rather than the plain `{"type": …, "error_code": …}` dict the API's request schema accepts.
`tools.py` pins `web_fetch_20250910` deliberately (not `web_fetch_20260209`, which requires the
code-execution tool), so the shape must match THAT version's error contract.

**Why CI missed it, and what closes that:** `test_engine_e2e_stubbed.py` stubs the provider, so it
never produces Anthropic's real server-tool *error* payload. This plan's fixture is the regression
test — a genuine failed `web_fetch` assistant turn, replayed through the real serialiser and asserted
to be JSON-round-trippable with no live object left in it.

**On `reliability.with_retry` giving up after attempt 1/4** (named as aggravating in the findings):
that classification is CORRECT and stays. A 400 for a malformed request is not transient — retrying
the identical poisoned message list can only produce the identical 400, faster, which is the
776-error incident's lesson in a different costume. The right recovery is shape, not repetition. This
plan adds one bounded exception: when a 400's message names `web_fetch_tool_result`, the loop drops
the offending assistant turn and retries ONCE, so a stream that has already paid for its searches is
not thrown away over one bad page.

**The unknown.** The correct replacement OpenAI deep-research model id is NOT KNOWN and cannot be
guessed — guessing produces the same `model_not_found`, just with a different string. Task 1 is a
blocking `checkpoint:decision`.

Purpose: two of four research streams are dead. Until they are fixed, every run is a two-stream run
whose corroboration coverage is halved.
Output: a real failed-fetch fixture, a deep serialiser, one bounded poison-turn recovery, a
configuration-error classification that fails loud on first sight, a startup line naming the resolved
model ids, and the operator's chosen model id committed in both places.
