# Phase 15.2 Plan 20: Worker Liveness and Bounded Reclaim (D-E) Summary

Migration 0014 plus a heartbeat-aware claim, a reclaim ceiling and a reap-to-failed statement, so that killing a worker stops meaning restarting its run — proven by five SQL-level tests that all execute and pass against a real Postgres.

## What was built

**The defect.** `worker.py`'s `CLAIM_SQL` measured staleness by `started_at`, which is stamped once at claim time and never moves again. A live process holding a ~35-minute deep-research long-poll was therefore indistinguishable from a process that died 35 minutes ago — and the designed response to a dead process is to re-run. On 2026-07-27 terminating a stuck worker started a fresh one that was seconds from re-executing run `d6bb3aae` at full cost, unattended, on a 60-minute loop. It is held back today only by a temporary `NESTOR_WORKER_STALE_MINUTES=525600` on the deployed service, which is worse in the other direction: with it set, a genuinely crashed worker is never recovered.

**The fix, in three parts.**

1. **A real liveness signal.** `run.heartbeat_at` (migration 0014, nullable) is bumped every `NESTOR_WORKER_HEARTBEAT_S` (default 30s) by `_heartbeat_loop`, started in `execute_run` immediately before the long `await runner.run(...)` and cancelled in a `finally` that covers the success, `RunCancelled` and exception paths alike. Staleness became `COALESCE(heartbeat_at, started_at)`, so every pre-0014 row behaves exactly as it did before — no backfill, no behaviour change on legacy data.

2. **A ceiling.** `run.reclaim_count` (NOT NULL DEFAULT 0) is incremented by the claim *only* when it re-claims a row that was already `running`. The reclaim arm gained `AND reclaim_count < :max_reclaims`. Past `NESTOR_WORKER_MAX_RECLAIMS` (default 2) the run is not claimable at all, and `REAP_SQL` — run on the empty-queue tick only — flips it to `failed` with one plain sentence saying the worker stopped responding, that it had already been recovered N times, and that it was failed rather than started again so it could not keep spending. "A permanently stalling run re-bills every 60 minutes forever" is now structurally unreachable.

3. **The revert, written down.** Runbook Step 15.2.j carries the five-step procedure with the reason for every ordering constraint, and the summary checklist gained a matching entry. Nothing was deployed and no live env var was touched; `tribunal-worker` remains paused. Plan 15.2-26 runs it with the operator.

**The exactly-once keystone is untouched.** `started_at` is written by exactly two production statements in the tree — `worker.CLAIM_SQL` and `execute.py::_CONSUME_CLAIM_SQL` — and `git diff --stat` against the plan base is empty for both `runs/execute.py` and all of `pipeline/`.

**2. [Rule 3 - Blocking] the same file forced staleness by backdating `started_at` alone**
- **Found during:** Task 2

Under the new `COALESCE(heartbeat_at, started_at)` clock — and because the claim now stamps a fresh `heartbeat_at` — that no longer makes the row stale, so worker-B would never re-claim and the test would fail. - **Fix:** the stale-forcing UPDATE now backdates `heartbeat_at` as well, with a comment explaining that backdating `started_at` alone is *supposed* to be insufficient now.

### Small design choices worth naming

- **`HEARTBEAT_INTERVAL_SECONDS` is parsed as `float`, not `int`.** The plan cites the `int(os.environ.get(...))` idiom, but `POLL_INTERVAL_SECONDS` in the same file uses `float`, and a sub-second value is needed for Test 5 to assert on the row rather than on a long sleep. The loop reads the module global on every iteration precisely so the test can patch it.
- **`CLAIM_SQL`'s `RETURNING` gained `reclaim_count`, and `REAP_SQL` gained `RETURNING id`.** Both are additive and both exist to satisfy phase rule 7 ("a refused reclaim, a hit ceiling and a reap are each logged naming the cause and the run id"): the worker now logs `run_reclaimed_from_dead_worker` with the count when a recovery actually happens, and `stale_runs_reaped_to_failed` with the reaped ids.
- **The reap swallows its own exceptions** with a WARNING, matching the file's existing "a single run must never kill the worker" posture. Housekeeping must not stall the queue (Rule 2).
