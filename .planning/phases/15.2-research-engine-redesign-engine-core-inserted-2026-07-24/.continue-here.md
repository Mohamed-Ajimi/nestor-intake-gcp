## Critical Anti-Patterns

| # | Anti-pattern | severity |
|---|---|---|
| 1 | Treating log silence or idle CPU as proof that a run has stalled | blocking |
| 2 | Starting a live Tribunal run before plan 15.2-20 (D-E) has landed | blocking |
| 3 | Reverting `NESTOR_WORKER_STALE_MINUTES=525600` before D-E is fixed | blocking |

**1 — silence is not death.** The engine logs ONLY failures (D-F). A healthy deep-research long-poll
and a dead pipeline look identical: no logs, flat CPU. On 2026-07-27 I read a flat CPU trace as a
stall, wrote it up as defect D-C, and was wrong — the run resumed on its own 25 minutes later
(`OpenAI deep-research: RESUMING the existing response`). D-C is WITHDRAWN in the findings file, with
the original text kept as the record. **Only the run row is authoritative.** If you cannot read it,
say so — do not infer from proxies. Structural prevention: plan 15.2-24 adds a stage entry/exit log
line, which makes this diagnosable in seconds instead of an hour.

**2 and 3 — cancelling can RESTART a run.** `worker.py` CLAIM_SQL re-claims any run in `status
='running'` older than `NESTOR_WORKER_STALE_MINUTES`. That is correct for a worker that died and
wrong for a run that stalled — and the two are indistinguishable today. On 2026-07-27, terminating
the worker started a fresh one that was seconds from re-executing the run at full cost. It is held
back ONLY by a temporary env hack. Structural prevention: plan 15.2-20 adds `heartbeat_at` +
`reclaim_count` (migration 0014) with a reap-to-failed ceiling, AND reverts the hack in the same
plan. Never revert the hack on its own.
