<planner_corrections>
Two corrections to the draft DDL in `15.2-RESEARCH.md` § *The D-13 Additive Migration*. Both are
load-bearing; implement the corrected version.

**Correction 1 — the policy expression.** RESEARCH's draft writes the `research_gap` policy with
the bare `current_setting('app.tenant_id')::uuid`. That is the **superseded** 0002/0003/0011 form.
Migrations `0009` and `0010` exist precisely because that form crash-loops the worker: the worker
connects as `worker_user` with `app.tenant_id` unset (first claim) or reverted to the empty string
`''` (every later claim on a pooled connection), PostgreSQL still EVALUATES the tenant_isolation
branch even though `worker_all` is true, and `''::uuid` raises
`invalid input syntax for type uuid: ""`, aborting the whole statement. Use the current head form
verbatim:

`NULLIF(current_setting('app.tenant_id', true), '')::uuid`

Semantics: USING → NULL → no rows (fail-safe read); WITH CHECK → NULL → INSERT/UPDATE REJECTED
(fail-loud write). Exactly what D-13's denial requirement wants.

**Correction 2 — no `research_gap_worker_all` policy, and no explicit GRANT.** This matches the
`verification_verdict` precedent set by `0011` (which added neither) and is a deliberate decision,
not an omission:

- **No worker_all policy.** `research_gap` rows are written by the pipeline on the
  `persist_tribunal_claims` path (plan `15.2-15`), which always runs inside
  `db/rls.py::set_tenant_context`. The cross-tenant SKIP-LOCKED *claim* path (the only reason
  `worker_all` exists, migration `0008`) never touches `research_gap`.
  **Record this in the migration docstring** so `15.2-15` knows its write path must be inside a
  tenant context.
- **No explicit GRANT.** Production runs `alembic upgrade head` under the **app_user DSN**
  (`infra/DEPLOY-RUNBOOK.md` Step 13.f / line 1820), so `0008`'s
  `ALTER DEFAULT PRIVILEGES FOR ROLE app_user IN SCHEMA tribunal GRANT ... TO worker_user`
  covers `research_gap` automatically at creation time. Adding a redundant GRANT would be
  regression risk with zero benefit — the same reasoning `0012` records for re-issued policies.
</planner_corrections>
