<objective>
**D-E — the stale reaper RE-RUNS a stuck run instead of failing it.** This is the money defect, and
it fired for real on 2026-07-27: killing the worker started a fresh one that was about to re-execute
run `d6bb3aae` at full cost, unattended, because the run was past `NESTOR_WORKER_STALE_MINUTES=60`.
It is blocked today only by a temporary `NESTOR_WORKER_STALE_MINUTES=525600` (one year) on
`tribunal-worker`, which is worse than the bug in the other direction: with it set, a genuinely
crashed worker is NEVER recovered.

The defect is that the worker has **no way to tell a dead process from a slow one**. `CLAIM_SQL`'s
only liveness signal is `started_at`, which is stamped once at claim time and never moves again — so
a live process holding a 35-minute deep-research long-poll is indistinguishable from a process that
died thirty-five minutes ago. The engine's own docstring warns those calls take up to 35 minutes; the
stale threshold is 60.

The fix is a real liveness signal plus a bounded number of recoveries:

1. **`heartbeat_at`** — the executing worker bumps it on a timer while `runner.run()` is awaited. A
   live process therefore has a fresh heartbeat even during a silent long-poll; a dead one stops
   writing within one interval. Staleness becomes `COALESCE(heartbeat_at, started_at)`, so pre-0014
   rows keep exactly today's behaviour.
2. **`reclaim_count` + a ceiling** — a run that keeps dying takes at most `NESTOR_WORKER_MAX_RECLAIMS`
   recoveries. Past that it is **failed with a sentence**, not re-executed. The "permanently stalling
   run re-bills every 60 minutes forever" worst case is structurally unreachable after this plan.
3. **The revert** — `NESTOR_WORKER_STALE_MINUTES` goes back to a real value and
   `NESTOR_RUN_ABORTED_MARKER` is removed. `NESTOR_RUN_ABORTED_MARKER` is read by **no code in this
   repository** (verified: zero hits outside the findings document) — it was a human annotation on the
   revision, so reverting it is a Cloud Run env removal with no code change.

**Why `started_at` is not reused as the heartbeat.** `started_at` is the CR-01 **fencing token**:
`runs/execute.py`'s `_CONSUME_CLAIM_SQL` matches `AND started_at = :token` to guarantee a claim
dispatches at most once. Bumping it on a timer would make every heartbeat invalidate the run's own
claim token and break the exactly-once keystone (ENGINE-08, legally load-bearing for the audit
chain). A separate column is the only safe carrier. `runs/execute.py` is NOT edited by this plan.

**This plan also seeds the gap phase's CI gate.** It is the first plan in the wave order, so it owns
`tribunal/cloudbuild.test-engine.yaml` for the whole gap phase and adds the FIVE gap-phase engine
test filenames to its collected `FILES` list in one edit. Four of those files do not exist yet; the
config's `ls ... || true` idiom silently skips a missing name, so each later plan proves its own file
is BOTH collected and green, and plan 15.2-26 reconciles the final count. That is the only
arrangement that keeps one owner for the config without giving any plan an ungated test forever.

Purpose: before the worker is unpaused with real runs queued, "killing a worker" must stop meaning
"restarting the run".
Output: migration 0014 + the ORM columns, a heartbeat-aware claim, a reclaim ceiling, a reap-to-failed
statement, four SQL-level tests, the gate seeded, and the revert written into the runbook.
</objective>
