<domain>
## Phase Boundary

**What this phase delivers.** A claim row records **which sub-question it answers** and **which
corroboration group it came from** — plus its own date where the provider stated one.

Today a claim's `facet` is the *parent client question*, inherited from the angle it was dispatched
under: `_angle()` sets `"focus_area": label`, and that label is stamped onto the claim in Python,
never read from model output (`T-15.2-60`). That inheritance is correct **only while one angle maps
to exactly one client question.** Wave 3 (phase 15.6) makes an LLM group winners into ≤5 groups and
sends each group to all providers — the moment a group spans two client questions, a claim from it
has **no single parent** and `facet` becomes a lie.

So this phase is a **hard prerequisite for 15.6**, not a nice-to-have. It is deliberately small and
deliberately boring: it records information that already exists at dispatch and currently stops
before the claim row.

**The three columns** (`tribunal/nestor_pulse_sdk/db/models/claim.py`, all `nullable=True`):

| Column | Type | Purpose |
|---|---|---|
| `sub_question` | `Text` | the winner text this claim answers |
| `corroboration_key` | `Text` | the shared key (`w01`/`w02`/…) — the real join key for corroboration |
| `as_of` | `Date` | the claim's own date, where the provider stated one |

**Why `as_of` belongs here and not in a "dates" phase.** D-V01-4 was *withdrawn* because gemini and
claude read **different De Haan articles at different points in a rollout** — 7 sites in 2021 vs ~90
later. **Both were true.** Without a date the engine cannot tell a contradiction from a time series,
and neither could the human analysis. This is missing metadata, not a missing detector.

**NOT DEPLOYED, and that is deliberate.** Per the operator ruling of 2026-07-29 — *"I don't want to
measure anything unless we finish all changes"* — nothing in Waves 1–4 goes live. Wave 1 (phase 15.4)
is code-complete and gate-verified but not deployed; this wave lands on top of it in git only. **One**
deploy and **one** measuring run happen at the end of phase 15.8. Do not add a deploy step to any plan
in this phase. Do not propose one. This reverses `ENGINE-REDESIGN-SPEC.md` § 2, which still reads the
other way on its face — the override is recorded in-place there.

### The threading path — all of it already exists

Every value this phase persists is **already present in memory** and simply stops short of the claim
row. The plans should read as plumbing, not invention.

1. **`research_division.py:846` — `_angle()`** already builds each angle dict with
   `"sub_question": w["text"]` and `"corroboration_key": key` alongside `focus_area`, `provider`,
   `stakes`, `rank`, `langs`, `language`, `corroboration`.
2. **`research_division.py:1514` — `_enriched`** is where an angle's result is enriched for the
   checkpoint AND the return value (deliberately the same object, so a restored angle is
   byte-identical to a fresh one):
   ```python
   _enriched = {**result, "_angle": fa, "_stakes": stakes, "_d8_prompted": prompted}
   ```
   Wave 2 adds the new keys here, in the same underscore-prefixed style.
3. **`synthesis/steps.py:2201` — `collect_provider_facts`** reads that enriched dict and produces the
   per-claim dicts.
4. **`synthesis/steps.py:1416` — `_dedupe_claims`** collapses the streams' views of one fact.
5. **`citations/extractor.py` — `persist_tribunal_claims` → `_insert_claim` (def line 279)** writes the
   row. `_insert_claim`'s existing kwargs (`certainty`, `found_by`) are the exact precedent to follow:
   keyword-only, defaulted to `None`, so **every pre-existing call site stays valid unchanged**.

**STAMP IN PYTHON FROM THE ASSIGNMENT — NEVER PARSE IT OUT OF MODEL OUTPUT.** This is the identical
rule `_parse_distiller_response` already applies to `provider` and `enforce_scope_guard` applies to
`parent`. A model-supplied `corroboration_key` would let model text choose its own corroboration
partner. (`as_of` is the sole exception and is bounded — see D-W2-1.)

### D-W2-1 — `as_of` is parsed in Python from EVIDENCE; **the distiller prompt is NOT touched**

**Operator decision, 2026-07-29.**

The distiller contract is `FACET ||| CLAIM_TEXT ||| EVIDENCE` and **that exact contract is what Wave 1
just proved** — 141/137/43/143 against the real V-01 audit blobs, where the 43 and 143 are the
already-working responses that prove a fix rather than a trade. Adding a fourth `AS_OF` column would
reopen it and force a full fixture re-proof.

- **Do NOT add a 4th column.** `_build_distiller_prompt` (`steps.py:1185`, contract text at `:1333`,
  `:1348`, `:1352`) is **out of scope for this phase.** So is `_parse_distiller_response`'s arity.
- Extract the date **in Python from the EVIDENCE cell**, after parsing. `None` when no date is present
  — which will be the common case, and that is accepted.
- Keep the extractor a **pure, separately testable function** over a string. That is what makes it
  provable on this machine (see `<constraints>`).
- **Bound what it accepts.** A wrong date is worse than no date: it would turn a real contradiction into
  a fake time series. Prefer explicit, unambiguous forms; reject ambiguous ones rather than guessing.
  A bare 4-digit year is acceptable as a year-precision date; `03/04/2021` is **not** decidable between
  DD/MM and MM/DD and must yield `None`. State the accepted grammar in the plan and test the rejections
  as hard as the acceptances.

### D-W2-2 — Record the dispatch `corroboration_key` **as-is**; NULL where there is none

**Operator decision, 2026-07-29.**

A code-grounded fact the spec does not mention: **only the top-3 winners get a `corroboration_key`.**
`research_division.py:867-874` — the top-`k` winners are dealt to every stream with
`key = f"w{int(w['rank']):02d}"`, and the **remainder is dealt round-robin with `""`**:

```python
for w in ordered[:top_k]:
    key = f"w{int(w['rank']):02d}"
    for stream in _D6_STREAMS:
        angles.append(_angle(w, stream, True, key))
...
for i, w in enumerate(remainder):
    angles.append(_angle(w, _D6_STREAMS[i % len(_D6_STREAMS)], False, ""))
```

So in this wave the column is **NULL for roughly 12 of 15 winners**, and that is expected and correct.
It fills up in Wave 3, when every group goes to every provider.

- **Do NOT populate the empty key** to make the column look fuller. `corroboration_key` is *read* for
  dispatch decisions in four places — `research_division.py:684`, `:714`, `:1313`, and
  `pipeline/tribunal/pipeline.py:3920` (`_group_size`). Changing `""` to a real key would silently
  change reassignment behaviour and group sizes. The rejected alternative (a second, recording-only key
  alongside the dispatch key) was declined: two near-identically-named keys is a confusion trap.
- An absent key must be written as **NULL, not `""`**. Follow the `found_by` precedent documented in
  `_insert_claim`'s docstring: *"An ABSENT provenance is bound as `None`, never as `[]`"* — "no key
  recorded" and "recorded as the empty key" are different facts and the corroboration queries must be
  able to tell them apart.

### D-W2-3 — `_dedupe_claims` merge rule: **first-wins**, both fields

**Operator decision, 2026-07-29.**

`_dedupe_claims` (`steps.py:1416`) is the cross-stream merge point, and it already has a per-field rule:
`found_by` unions, `source_urls` union, `provider_quality_by_url` is first-to-introduce-owns-it, and
`certainty` takes the **cautious** value.

- `sub_question` and `corroboration_key` follow **first-wins** — the first occurrence's value survives,
  matching the `provider_quality_by_url` precedent. The row stays a scalar `Text`, as specced.
- **Guard every new branch on the key being present**, exactly as the existing branches do. The
  `claim_distiller` path carries no `source_urls`, no `provider_quality` and no `certainty`, and its
  behaviour through this function must stay **byte-identical**.
- The rejected alternative — warning on a cross-key merge — was declined for this wave. Note for the
  planner: that means a claim merged across two corroboration groups is silently attributed to the
  first. It is a known, accepted information loss, not an oversight; do not add the warning back.

### D-R3 invariants (spec § 3) — all four hold

1. **Nullable everywhere.** Legacy rows and the distiller path (which has no source and no certainty
   *by design*) must keep working. A run over pre-0017 data must not fail.
2. **A claim whose group spanned two client questions takes its `facet` from its sub-question's
   parent**, not from the group. In Wave 2 this is a **no-op by construction** — a winner's parent
   label *is* the `focus_area` already stamped, so the resolved value equals today's value. Build the
   plumbing so 15.6 has it, and **assert the no-op in a test** rather than assuming it.
3. **No behaviour change beyond recording.** Corroboration still uses today's key. No dispatch
   decision, no merge outcome, no report sentence changes in this wave. A diff that alters which claims
   reach paid verification is out of contract — that is the one variable the 15.8 measuring run must
   hold still.
4. **Stamped in Python from the assignment**, never parsed from model output (`as_of` excepted, per
   D-W2-1).

### Claude's Discretion

- Plan count and wave structure. Wave 2 is small; do not inflate it. The schema change and the
  threading are separable and can run in parallel if the column names are fixed first.
- The exact date grammar for `as_of`, within D-W2-1's "reject the ambiguous" bound.
- Whether `as_of` extraction lives in `synthesis/steps.py` beside the parser or in its own module —
  but it must be an importable pure function either way.
- Test placement, provided the gate rules in `<constraints>` are honoured.

## Hard Constraints — read before writing a plan

### Do not deploy, and do not plan a deploy
Nothing in this phase goes live. No `gcloud run deploy`, no image build, no migration **applied** to a
live database. See the boundary above.

### Alembic `0017` must be *proven*, and `0016` still has not been
**`0016` has never touched a database.** This repo has been burned by an alembic step that exited 0
without running. The proof of a migration is the literal line **`Running upgrade 0016 -> 0017`** in
output — **never exit code 0.** Since this phase does not deploy, that proof is owed at 15.8 alongside
`0016`'s; the plan must **state the proof obligation and hand it forward**, not fake it and not claim
it. Write the migration so that proof is possible; do not assert it happened.

### The engine gate YAML is a loaded gun
`tribunal/cloudbuild.test-engine.yaml`'s script is one single-quoted `bash -c '…'` block, capped by
Cloud Build at **10,000 characters** (~5,300 today). **No apostrophes anywhere inside it** — one
apostrophe closes the string and the build dies with exit 127. This cost a build in the Wave 1 session.
Commentary goes in YAML comments outside the block.

### Green must mean something — the five known ways it does not
See `[[gate-integrity-traps]]`. Specifically for this phase:
- `ls || true` silently skips a whole file — reconcile the "collecting: N" count against the files you
  intended to run.
- A test that runs as **superuser voids every RLS assertion** and passes vacuously. `claim` is
  RLS-protected and `_insert_claim` runs under `set_tenant_context`; a new-column test that does not
  set the role proves nothing.
- **grep-based gates are blind to work done in an argument list** — a gate that greps for a column name
  will pass on a comment mentioning it.
- The backend gate has previously never printed `Running upgrade X -> Y`. See above.

### Proving things on this machine
There is **no Python, no pytest, no Docker** on the dev box — but a **stdlib-only Python 3.14.4** ships
with gcloud at `C:/Users/ajimimo/google-cloud-sdk/platform/bundledpython/python.exe` (`ast`,
`py_compile`, `json`; **no** pytest, no sqlalchemy). It cannot run the suite, but it makes real proof
possible: **lift a pure function out of the committed source with `ast` and drive it.** Three Wave 1
executors used exactly this to prove things that would otherwise have been PENDING. This is precisely
why D-W2-1 requires the `as_of` extractor to be a pure function over a string.

### Judge the engine from the delivered report
Not the claim table, not the logs — the `output` row, `format='markdown'`. This wave writes columns no
report reads yet, so its own proof is the schema + the threading + the tests, and that is fine. Do not

<specifics>
## Specific Ideas

- **`_insert_claim` is the template for the whole wave.** Its docstring already states the three
  binding rules for additive nullable columns — explicit `bindparam` typing, absent-means-NULL, and
  clamping at the boundary because *"this function is the last thing between untrusted model wording
  and the database."* The new columns are caller-supplied rather than model-supplied (except `as_of`),
  so clamping is a bug bound, not an injection control — but the column must not be a place a bug can
  write unbounded data. Cap `sub_question` and `corroboration_key` lengths for the same reason
  `found_by` is capped.
- **`_enriched` is one object on purpose.** The comment at `research_division.py:1525` is explicit: the
  checkpointed value and the returned value are the same object so *"a restored angle is byte-identical
  to a freshly researched one."* Adding keys must not break that — do not build a second dict.
- **Angles carry `sub_question` already and it is already read defensively.** `research_division.py:1338`
  and `:1439` use `angle.get('sub_question') or angle.get('focus_area') or ''` because the corroboration
  path produces angles with no `sub_question` key at all. New code must use the same tolerant chain, not
  a subscript.
- **A worked assertion for the no-op invariant:** for every claim produced by a run whose groups do not
  span client questions, `resolved_facet(claim) == claim.facet`. That is invariant 2, testable today,
  and it is what 15.6 will rely on.

</specifics>
