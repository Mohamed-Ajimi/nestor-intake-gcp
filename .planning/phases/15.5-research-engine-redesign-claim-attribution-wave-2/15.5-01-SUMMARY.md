# Phase 15.5 Plan 01: Claim Attribution Schema + as_of Extractor Summary

Three nullable columns (`sub_question`, `corroboration_key`, `as_of`) on `claim` in both the ORM and
an additive alembic 0017, plus a stdlib-pure `extract_as_of` whose rejections are asserted as hard as
its acceptances — the fixed contracts that let plans 15.5-02 and 15.5-03 run in parallel.

## What Was Built

**Task 1 — the columns and the migration** (`e5e7d6f`)

`db/models/claim.py` gains three `Mapped` columns immediately after `found_by`, each with a comment
in the register of the existing `# D-13 (migration 0013):` ones: `sub_question` (Text),
`corroboration_key` (Text), `as_of` (Date). `Date` is added to the `sqlalchemy` import list and
`date` to the `datetime` import.

`alembic/versions/0017_claim_attribution.py` follows 0016 line for line: named docstring headings,
module constants, `upgrade()` containing exactly three `op.add_column` calls with no `schema=`
kwarg, `downgrade()` dropping exactly those three in exact inverse order. `revision = "0017"`,
`down_revision = "0016"`. No index, no constraint, no backfill, no security DDL.

**Task 2 — the extractor** (`b8d81ce`)

`pipeline/synthesis/claim_attribution.py` imports only `re`, `datetime` and `logging` and exports
one function, `extract_as_of(evidence: str | None) -> date | None`. It reads at most 2000 characters,
never raises, and applies the single-candidate rule. The month vocabulary is one module-level
`_MONTHS` table (English + Dutch, full + 3-letter), so the accepted words are greppable in one place.
The distiller prompt and `_parse_distiller_response` are byte-unchanged — verified by diff against
the phase base, not by memory.

**Task 3 — the test and the gate** (`c1ebe5b`)

`tests/test_claim_attribution.py`, 21 test functions in the four required sections, structured on the
`test_source_resolution.py` precedent (same `_load_migration_at` / `_executable_source` /
`_alembic_operations` helpers). Registered in `cloudbuild.test-engine.yaml` with the WANTED entry and
`EXPECTED_FILES` 32 -> 33 changed in the same edit.

## Key Implementation Details

**Why the extractor masks rather than ignores.** The rejected numeric forms are matched *in order to
consume them* — each match is blanked to spaces before the bare-year scan runs. Without that,
`03/04/2021` would be rejected as a date and then re-read as the bare year 2021, and `2021-02-30`
would return 2021-01-01 instead of `None`. The stage order (ISO full -> textual -> rejected numeric
-> bare year) is what makes both of those come out `None`, and it is the single most load-bearing
design choice in the module.

**Why no RLS test.** Written into the section-4 heading comment with both reasons, so nobody adds one
later thinking it was an oversight: (a) a PostgreSQL row-level POLICY is a TABLE-level object
evaluated against row values, so a newly added column is covered by construction — the reasoning 0013
and 0016 both record; (b) this gate provisions no database, so a role-less DB test would connect as
SUPERUSER, RLS would not apply, and every isolation assertion would pass vacuously.

**Gate edit safety.** All new commentary went into YAML comments *above* `steps:`, where it costs
zero characters against the 10,000-char cap. The script region is unchanged except for one path and
one digit: still exactly 2 apostrophes, now 5,150 characters.

## Deviations from Plan

**1. [Rule 1 - Bug] The literal proof line was wrapped in the 0017 docstring**

- **Found during:** Task 1 verification
- **Issue:** `Running upgrade 0016 -> 0017` had been line-wrapped across two lines by prose
  formatting, so the literal string was absent from the file. The acceptance criterion requires the
  literal — and a wrapped line cannot be grepped for in a deploy log, which is the only place it will
  ever be checked, so this would have quietly defeated the one assertion that matters at 15.8.
- **Fix:** Set on its own indented line, unwrapped. Added
  `test_the_migration_states_its_deploy_proof_as_owed_and_never_as_done` so a future re-wrap turns the
  gate red instead of passing silently.
- **Files modified:** `0017_claim_attribution.py`, `test_claim_attribution.py`
- **Commits:** `e5e7d6f`, `c1ebe5b`

**2. [Rule 2 - Missing critical functionality] Numeric month precision rejected in both orders**

- **Found during:** Task 2
- **Issue:** The plan names `2021-03` as a rejection. Its mirror, `03-2021`, is the same fact written
  the other way round and would have fallen through to the bare-year rule, yielding 2021-01-01 from a
  token that is not a bare year.
- **Fix:** `_PARTIAL_MY_RE` alongside `_PARTIAL_YM_RE`; both consume without collecting. Verified not
  to disturb `2020-2021`, which still returns `None` via the two-distinct-years rule.
- **Files modified:** `claim_attribution.py`
- **Commit:** `b8d81ce`

### Judgement calls, recorded rather than silently taken

- **`maart 2021` (textual month, no day) returns 2021-01-01, not `None`.** Followed the plan
  literally rather than extending the `2021-03` rejection to the textual form. The distinction is
  principled and is written into the module docstring: in `2021-03` the year is glued into a numeric
  date-shaped token and is therefore not a *bare* year, whereas in `maart 2021` it is — and the bare
  year is D-W2-1's explicit sanction. Flagged here because it is the one grammar case where a
  reasonable reviewer might have expected the opposite, and it is asserted in the test file so the
  behaviour is pinned rather than incidental.
- **The `_MONTHS` table holds only full and 3-letter names**, as specified. `sept` is deliberately
  absent; adding it would widen the accepted vocabulary beyond the plan.
