# Phase 15.5 Plan 02: Claim Attribution Threading Summary

Two values that already existed at dispatch now ride onto the claim row — plus the claim's own
date — through four call sites, one dict literal and zero new branches in the merge, with every
assertion executed on this box against the committed source and re-executed over twelve mutated
copies to prove it bites.

## What Was Built

**Task 1 — the dispatch values reach the result (`cc5088c`)**

`research_division.run_angles` reads `sub_question` and `corroboration_key` off the angle beside the
existing `fa` / `stakes` reads, with the same tolerant `.get()` the feed lines use but **ending in
`or None`, never `or ''`**, and with **no `focus_area` fallback** for the sub-question. Both
deviations from the feed-line idiom are stated in a comment beside the lines. Both keys go into the
**same `_enriched` dict literal** — the file has exactly one assignment to that name, and the
comment at its return explains why the checkpointed and returned values must stay one object.

`claim_attribution.py` gained `parent_index(winners)` and `resolved_facet(claim, parents)`. Both are
pure, both never raise, both are **deliberately not called by the pipeline**. In this wave invariant
2 is a no-op by construction — `_angle` stamps `focus_area` from `w["parent"]` and `sub_question`
from `w["text"]`, so a winner's parent label *is* the facet already on the claim — and wiring a
resolver in would add a live call path for zero gain, which invariant 3 forbids.

**Task 2 — the three keys on every claim dict (`803df47`)**

`_FACT_CLAIM_KEYS` grew to twelve. `_normalise_fact_claim` gained two keyword-only, `None`-defaulted
parameters and one `extract_as_of` call over the same evidence string it already computes.
`extract_as_of` is imported at module scope, which is safe precisely because 15.5-01 kept that
module stdlib-pure.

**Task 3 — first-wins and the byte-identical distiller path (`a3e9914`)**

`TestDedupeAttributionIsFirstWins` pins D-W2-3: the first occurrence's sub-question and key survive
a cross-stream merge, a `None` first occurrence survives a later real value, and a distiller-shaped
claim gains **no** attribution key at all. `_old_dedupe` is re-run over the distiller shape as a
second oracle. `_old_dedupe`, `MIXED_CLAIMS` and every pre-existing test are byte-unchanged —
`git diff` on that file is additions only.

## Key Implementation Details

**`_dedupe_claims` gained a docstring and not a branch.** First-wins is what the function already
does: it stores `seen[norm] = c` and mutates only the named fields it unions. Writing a branch would
have been code to preserve behaviour that needs none, on the one function whose `claim_distiller`
path must stay byte-identical. Proven, not asserted: `ast.unparse` of the function before and after
differs **only** in the docstring constant.

**The empty corroboration key is not populated, and that is the point.** `divide()` deals every
remainder angle with `""`, so the column is NULL for roughly 12 of 15 winners in this wave. That key
is *read* for dispatch decisions at `research_division.py:684`, `:714`, `:1313` and
`pipeline.py:3920`; turning `""` into a real key would silently change reassignment behaviour and
group sizes. What must not happen is `""` reaching the column, and every absence assertion in the
new tests uses `is None` rather than falsiness — the empty string is falsy too, and telling the two
apart is the entire reason D-W2-2 exists.

**The distiller-fallback branch passes literal `None`, with the reason in the code.**
`claim_distiller` builds its units as `(provider_name, chunk_text)` and `fallback_units` mixes every
fallen-back stream into one call, so the angle is gone by construction. Passing another report's
loop variable would be a fabricated attribution — worse than the NULL, because it would look like a
real corroboration partner.

**Why `as_of` on the fallback branch does not reopen T-15.2-61.** The four fields hard-written to
`None` there are free-text provider claims about their own confidence, and a page saying
"certainty: certain" is an injection aimed at a queryable column. `as_of` passes through a grammar
that can return a `date` or `None` and can express nothing else. The residual risk — a well-formed
but untrue date — is the same trust level as the claim text itself.

### Judgement calls, recorded rather than silently taken

- **The orphan-parent test resolves against a FILTERED index, not the raw one.** The plan says to
  "build `parent_index` from those same winners" and also that the resolver must "degrade to
  `claim["facet"]`". Those two cannot both hold literally: `_angle()` overrides an unknown parent to
  `labels[0]`, so the raw index says `Q9` while the stamped facet says `Q1`, and `resolved_facet`
  would return `Q9`. The test asserts **both** facts — that the raw index is faithful to the winners
  list and therefore disagrees with the facet, and that with the index restricted to real client
  questions the resolver degrades to the claim's own facet. The disagreement is named in the test as
  the trap phase 15.6 inherits rather than left to be discovered there.
- **No length cap on `sub_question` / `corroboration_key` in `steps.py`.** The CONTEXT's
  `<specifics>` calls for capping them the way `found_by` is capped, but that clamp belongs at the
  database boundary in `_insert_claim` — plan **15.5-03's** file — where the docstring already
  records the rule. Two clamps in two places would truncate differently and is the fork this phase
  forbids. Flagged here so 15.5-03 owns it knowingly.
- **`parent_index` is FIRST-WINS on a repeated winner text**, matching D-W2-3 for the columns it
  resolves. Two winners with identical text and different parents is a workshop defect, not a case
  to arbitrate in a lookup table.
- **The lookup in `resolved_facet` is exact-string, on purpose.** Both sides are the same
  engine-authored string (`divide()` copies `w["text"]` onto the angle; the index is built from the
  same `w["text"]`). This is explicitly **not** the V-01 corroboration-key mistake, which was an
  exact-string key over model-written claim text. The distinction is written into the docstring so a
  reviewer does not "fix" it into fuzzy matching.
