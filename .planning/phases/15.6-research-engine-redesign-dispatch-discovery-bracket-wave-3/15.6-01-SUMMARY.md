# Phase 15.6 Plan 01: Question Grouping — the Group Record and its Clamp Summary

An LLM now proposes how the ranked research questions group by shared groundwork, and pure Python
clamps that proposal to at most five total, disjoint groups — with every string a research provider
will ever see stamped in Python from the winners list, and four separate failure paths all landing on
one deterministic one-group-per-client-question fallback.

## What Was Built

**`tools.py` (+131 lines).** `EMIT_QUESTION_GROUPS_TOOL` and `force_emit_question_groups()`, plus the
two exported cross-question rule constants. The schema is **index-addressed, and that is the security
control**: the model returns `member_numbers` (integers) and nothing else that identifies a question.
There is no `text`, `question`, `label` or `title` property anywhere in it, and the only
`"type": "string"` property in the whole schema is `why_grouped`, which is log-only. `why_grouped` is
deliberately **not** in `required`, matching this file's existing convention twice over
(`source_url` on `EMIT_ORIENTATION_TOOL`, `superseded_note` on `EMIT_GROUP_VERDICT_TOOL`) — requiring
a field the model does not have produces a fabricated one.

The `description` is a format string with two slots, `{max_groups}` and `{cross_question_rule}`,
because the ceiling moves when the discovery bracket takes a slot.

**`question_grouping.py` (new, 1,346 lines).** The group record is documented once, in the module
docstring, as the contract plans 15.6-03/04/06 all read. Then:

- `validate_groups` — total-or-empty. 1-based to 0-based in one place, out-of-range dropped and
  counted, **first-wins** on a duplicate claim, and every winner the model forgot placed
  deterministically (into the group holding the highest-ranked winner sharing its parent, else the
  smallest group). The totality post-condition is **asserted in code**; on failure it returns
  `([], notes)` so the caller falls back rather than dispatching an incomplete set.
- `clamp_groups` — mandate-strict, **then the ceiling**, then size, then sort. Both derived rules
  yield to the operator's ceiling: a mixed or oversized group is kept and noted, never split into a
  sixth group.
- `fallback_groups` — one group per client question, deliberately **not** clamped.
- `attach_discovery_riders` — riders join their host group at no extra call, and are what **yields**
  when a group overflows. A winner is never shed.
- `warn_if_over_ceiling` — takes `n_streams` as a **parameter**.
- `group_winners` — one audited forced-tool call, four named failure paths, never raises.

**`test_question_grouping.py` (new, 1,253 lines, 62 test bodies).** Pure: no Postgres, no provider
key, no network, no mocking library. Every LLM call goes through `FakeGroupingAudited`, hand-written
in the file, which records the prompt so the rules about what reaches the model are asserted over the
exact string sent.

## Deviations from Plan

### 1. [Rule 1 — Bug] An acceptance criterion that is arithmetically unsatisfiable

- **Found during:** Task 2 verification.
- **Issue:** The criterion reads `clamp_groups(assignment=[[0..5],[6],[7]], ... max_groups=2 ...)
  returns exactly 2 groups ...; max_groups=3 returns 3 groups with none over 4`. With three groups
  already at a ceiling of three, the pinned size step (`only while len(assignment) < max_groups`)
  cannot split, so the six-member group must stay. Reaching "3 groups, none over 4" would require
  splitting past the ceiling and then merging back — precisely what the ruled precedence forbids.
- **Resolution:** Implemented the **pinned algorithm and the CONTEXT's ruling** (D-W3-1: "the ceiling
  wins — accept the oversized group and log loudly"), which the plan states three separate times, and
  tested the ruled behaviour: 3 groups, one oversized, a note, and a `log.warning` naming the group
  id, its size, the cap and the ceiling. Added a companion test proving the size split **does** fire
  when the ceiling leaves room (`max_groups=4` → 4 groups, none over 4), so the guard is not
  vacuously satisfied.
- **Files:** `question_grouping.py`, `test_question_grouping.py`
- **Commits:** 1ff17c1, bdb28c9

### 2. [Rule 1 — Bug] The plan's size-cap yield case cannot occur on production numbers

- **Found during:** Task 4, executing the committed bodies.
- **Issue:** Task 4 asks for "With `max_groups=5`, `max_size=4` and 15 winners the LLM put in ONE
  group, the result is 5 groups, one of which exceeds 4". But `ceil(15/4) = 4`, one **under** the
  ceiling — the cap is fully satisfiable and nothing has to yield. The written assertion fails
  against correct code.
- **Resolution:** Replaced with two tests that state the true arithmetic:
  `test_fifteen_winners_in_one_group_do_fit_the_size_cap_within_the_ceiling` (4 groups, none over 4,
  and **no** yield note), and
  `test_the_size_cap_yields_to_the_ceiling_when_the_two_are_genuinely_infeasible` (same 15 winners at
  `max_groups=3`, where 4 groups are needed and 3 are allowed → 3 groups, one oversized, note).
- **Files:** `test_question_grouping.py`
- **Commit:** bdb28c9

### 3. [Rule 1 — Bug] Three test defects found by EXECUTING the bodies, not by reading them

- **A self-referential check that could never go green.** `assert "DATABASE_URL" not in source` in a
  test whose own source contains that literal. Replaced with an import-root allowlist and a comment
  saying why a text grep is the wrong instrument here.
- **Two assertions that did not discriminate the rule they named.** The rider-shedding test ranked
  its riders last, so "shed the weakest member" and "shed the weakest RIDER" shed the same thing —
  the mutation came back BLIND. Re-ranked so the group's weakest member is a **winner**. The orphan
  test proposed a single group, so parent-preference and fewest-members agreed; rebuilt so the
  parent's group is the **bigger** one and the two rules disagree.
- **Files:** `test_question_grouping.py`
- **Commit:** bdb28c9

### 4. [Rule 2 — Missing critical functionality] Interface gap: carrying `why` through the clamp

- **Issue:** `validate_groups` returns `(assignment, notes)` and `clamp_groups` merges, splits and
  re-sorts groups, so nothing in the pinned signatures carries the model's `why_grouped` from the
  reader to `build_groups`. A positional list would silently mis-attribute a sentence to the wrong
  group after any clamp.
- **Resolution:** `whys` is a dict keyed by **winner index** (a group inherits the sentence of its
  best-ranked member), which survives every merge, split and re-sort. A positional list is still
  accepted for direct callers and tests. No pinned signature changed.
- **Files:** `question_grouping.py`
- **Commit:** a0a1ef3

### 5. [Rule 3 — Blocking] Two harness defects that produced false results

Both are worth recording because each would have produced a confident wrong answer.

- **`subprocess.run(text=True)` mangles every em-dash.** Git output decoded with the Windows locale
  codec (cp1252) turns `—` into U+FFFD, so six unchanged definitions in `tools.py` compared **unequal**
  under `ast.unparse` — a false red that looked exactly like accidentally editing a forbidden
  constant. Only the six definitions containing an em-dash failed, which is what identified it. Fixed
  by decoding UTF-8 explicitly.
- **`importlib.reload` silently un-mutates a mutant.** Two committed tests reload the module to
  re-read env knobs. `reload` does not re-exec the module's current source — it **re-finds the spec
  through the parent package's `__path__`** and re-execs whatever file it finds. With `__path__`
  pointing at the real tree, the reload replaced the mutant with the clean file, and because tests run
  in sorted order **every test after the first reload then ran against unmutated code**. This alone
  produced **17 false BLINDs** on the battery's first run. Fixed by writing the mutant to its own
  directory placed ahead of the real one on `__path__` — which is what would happen under pytest if
  the mutation were applied to the working tree.

### The 4 BLIND mutations — reported as gaps, not as passes

All four are **defence in depth**: a second, independent control produces the same observable, so
removing one changes no output. Each is evidenced, not assumed.

1. **Ceiling-before-size ordering reversed — provably unobservable.** I did not take the tests' word
   for this. I swapped the two blocks and compared both orderings over **110,880 configurations**
   (every set partition of up to 7 winners, 1–3 parents, ceilings 1/2/3/5, caps 1–4, both flag
   values): **zero differences**. The reason is structural — the size step is itself gated by
   `len(work) < ceiling`, and the ceiling step drives the count down **to** the ceiling, so a size
   split can only happen when the count is already below it, in which case the ceiling step is a
   no-op. The documented ordering is still correct and still worth keeping for the precedence it
   expresses, but **no test can pin it** because it is not behaviour.
2. **Discovery counter (`d2`) — masked by the guard that follows it.** `build_groups` both writes the
   literal `"d1"` and truncates to one group when asked for more. Mutating the literal alone is
   invisible because the truncation removes the second group anyway. Mutation 29 removes the **guard**
   instead and does turn the named test red, so the pair is covered — but the literal is not
   independently observable.
3. **No-tool_use-block guard removed** and 4. **empty-assignment guard removed** — both land on a
   downstream guard that produces an identical result (fallback + exactly one D-12 degradation).
   Removing either changes the `log.warning` wording but not the return value, and the tests assert
   the return value. Asserting on log text would pin the message rather than the behaviour, which is
   a worse test; I left them uncovered and named rather than writing one.

Three mutations turned a **different** named test red than predicted (2, 15, 44). Each is still
caught, by a test whose name describes the rule at least as well; recorded above with the actual
target rather than the predicted one.

## Notes for the Next Plan

- **The group record is the contract.** `client_parents` — not `parents` — is what decides whether a
  group is mixed, and what plan 15.6-04's coverage assertion must count (D-W3-5's refinement: count
  MANDATE MEMBERS, not mandate groups). A group holding one client question plus a rider is the
  intended shape and must not warn.
- **`warn_if_over_ceiling(n_groups, n_streams)` takes the stream count as an argument.** Do not pass
  it `_D6_STREAMS` by importing it here; pass the number.
- **`group_winners` returns `(groups, notes, degradation_reasons)`.** The third element is a D-12
  degradation list, empty on the happy path — do not treat notes as degradations.
- **`EMIT_QUESTION_GROUPS_TOOL["description"]` is a format string.** Any other caller must fill both
  slots and must copy the dict rather than mutate the constant.
