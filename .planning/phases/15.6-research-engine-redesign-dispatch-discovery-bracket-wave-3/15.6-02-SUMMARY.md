## Decisions Made

1. **A blank or missing `parent` is CROSS-CUTTING, never a rider.** The plan defined a rider as "any
   question whose `parent` is NOT `DISCOVERY_PARENT`", which would have made an unparented question a
   rider of nothing in particular. A rider with no named host attaches to whichever mandate group the
   caller reaches for, and its claims then file under **that** client question's facet — an arbitrary
   client question absorbing a finding that is not about it. Earning its own group is the safe
   failure. `allocate_discovery` cannot produce this shape; a hand-built or resumed list can.
   Pinned by `test_a_question_with_no_named_host_is_cross_cutting_never_a_rider`.

2. **`rank = 0` is a placeholder, and the downstream consequence is now written down.**
   `research_division._normalise_winners` coerces any rank below 1 to the entry's **1-based list
   position**, so leaving `0` in place is safe *only* if the caller appends discovery after every
   mandate winner. The plan said "stamped by the caller"; the module now says what happens if the
   caller forgets, and `test_the_zero_rank_is_a_placeholder_the_caller_must_stamp` pins it as a
   property (`!= 0` and `>= 1`) rather than as an exact number, so a re-ranking change in the
   sibling-owned module cannot turn this file red on a merge.

3. **No `from __future__ import annotations`.** The plan's acceptance criterion is that an AST scan of
   module-level imports finds only `logging`, `os` and `typing`; a `__future__` import would appear in
   that scan. The builtin generics used (`list[dict]`, `dict[str, int]`, `tuple[...]`) need no future
   import on the gate's Python 3.11. A comment in the module asks the next reader not to add one.

4. **Notes are bounded at 10 named lines plus an aggregate.** A brief with fifty unsourced flags would
   otherwise produce fifty notes, and a flood is how the V-01 losses stayed invisible in the first
   place. The aggregate note still carries the total, so only the enumeration is capped.

5. **`_conflict_key` is used on BOTH sides of `annotate_conflicts`** — over the incoming conflict and
   over the dispatched question's `provenance` — so the match is exact by construction. Its three
   fields are deliberately the same three `workshop._collect_conflicts` de-duplicates on, so two
   conflicts this module calls identical are exactly the two that module already collapsed to one.

6. **The bare `int(os.environ.get(...))` on both dials follows the house pattern** of every `_D6_*` /
   `_D7_*` constant in `research_division.py`. A malformed value therefore raises at import time,
   loudly, rather than being coerced to a default nobody chose. The never-raises guarantee is about
   the functions, and the module says so.

## Deviations from Plan

- **Found during:** Task 1 (`partition_discovery`)
- **Issue:** The plan's literal definition made an unparented question a rider, which would let a
  discovery claim file under an arbitrary client question's facet.
- **Fix:** `not parent or parent == DISCOVERY_PARENT` → cross-cutting; documented in the docstring.

**2. [Rule 2 — Missing Critical] Bounded note output**
- **Found during:** Task 1 (`allocate_discovery`)
- **Issue:** The plan requires every drop be NAMED in a note; unbounded, that is a log flood on a
  conflict-heavy brief, and the flood is itself a failure mode this phase exists to fix.
- **Fix:** `_DISCOVERY_MAX_NOTES = 10` individual lines plus an aggregate line carrying the full
  count for both the unsourced and the capped tally.
- **Files:** `discovery_bracket.py`
- **Verification:** driven — `test_a_conflict_without_a_source_can_never_consume_a_slot` asserts the
  named note; `test_six_conflicts_on_one_parent_stop_at_the_per_parent_cap` asserts the cap note.
- **Committed in:** `1729a7f`

**3. [Rule 2 — Missing Critical] `_normalise_winners` assertions weakened from exact rank to property**
- **Found during:** Task 2
- **Issue:** The plan asked that a discovery question "round-trip with its text, parent and rank
  intact". A `rank` of 0 does **not** round-trip — `_normalise_winners` coerces it to the list
  position. Asserting the coerced number exactly would pin a rule inside a module plan 15.6-03 is
  editing this same phase, which is the phase-15.5 exact-set trap in a new costume.
- **Fix:** the round-trip test stamps a realistic rank (16) and asserts that survives; a separate test
  asserts only the PROPERTY that an unstamped 0 comes back `!= 0` and `>= 1`.
- **Files:** `test_discovery_bracket.py`
- **Verification:** both tests green under the harness; neither references `_D6_STREAMS`, `_D6_TOP_K`
  or any angle set.

## Issues Encountered

**The stale-base trap fired again — 3 of 3 in phase 15.5, and now here.** This worktree was cut from
`a3a0c96`, **486 commits behind** the phase base `34bf790` (and 0 ahead). `git rev-list --count
BASE..HEAD` returning 0 says only "not ahead" — the merge-base is what exposed it. Corrected with

read**. Had this gone unnoticed, `research_division._SUBQ_CHARS`, `_normalise_winners` and
`workshop._parse_orientation` would all have been read at 486-commit-old shapes.

**Two driver assertions were wrong before the source was.** The first Task-1 driver run reported 2
failures: an assumption "truncated to 601" and a URL not in final position. Both were artefacts of the
driver, not the module — the frame's own sentence *"**A** source read during orientation says
instead:"* added the 601st `A` to a naive `count("A")`, and `str.strip()` does not remove a leading
period. Fixed in the driver (count the *run*, `lstrip(". ")`), never in the module. Recorded because
"the test was wrong" is the explanation most likely to be a lie, and here it is checkable: the frame
text is unchanged between the two runs.
