## 0. What this phase is, and why it is not "more 23.1"

Phase 23.1 answered **"who may call which verb."** It gated 8 operator intake verbs, 7 AI
routes and 11-of-11 research routes, and it pinned ten client routes OPEN so the gate could
not creep.

This phase answers the question 23.1 never asked: **"given a caller who is legitimately
allowed to call this verb, what may they see and what may they change?"**

That is a different axis. Every finding below sits *inside* a route that 23.1 correctly
decided must stay open to `role=user`. None of them is a regression from 23.1 — all seven
predate it, and 23.1's scope never looked for them.

> **The recurring failure this project keeps paying for**: a boundary gets audited along
> ONE dimension, and the table produced by that pass is then treated as the whole map.
> 23.1's CONTEXT section 1 surveyed one file and hid the ~$45 ungated trigger. This
> CONTEXT's section 1 is therefore a MEASURED enumeration of every router, produced by
> reading each router's construction — not a hand-written list. See section 11 for how to
> extend it safely.

## 2. F-01 — Admin-only content reaches clients, through FOUR paths not one

`backend/app/data/pulse_intake_v1.json:881` carries `"admin_only": true` at **SECTION**
level on `strategic_perspective`, whose own description reads *"Visible only to admin, not
to the client and not in the handoff PDF."* The section holds exactly four fields:
`bias_radar`, `blind_spots_upstream`, `blind_spots_downstream`, `blind_spots_perspectief`.

Enforcement today is **client-side only**: `IntakeForm.tsx:164` (`if (s.admin_only) return
false`) and `intake.$id.results.tsx:163`.

### The propagation chain — the audit found hops 1 and 2, and stopped

| # | Hop | Evidence | Client-reachable? |
|---|---|---|---|
| 1 | `list_answers` returns every row | `intake_routes.py:558-564` | **yes** |
| 2 | `output_parsed` carries `bias_radar` + `blind_spots` verbatim | `ai/skills/apply.py:17` | **yes** via `:1234` |
| 3 | **Context-pack generation reads ALL answers into the LLM prompt** | `ai/skills/context_pack.py:150-159` then `_format_intake_markdown` | **yes** via `GET /context-pack` |
| 4 | Embeddings index `ResearchArtifact.text_content` (= the pack) | `ai/skills/embeddings.py:89-100` | no — `/search` is gated |
| 5 | The research brief carries `context_pack_text` into Tribunal | `research_routes.py`, `assemble_brief(..., context_pack_text=...)` | no — research reads gated |

**Filtering only `list_answers` leaves hop 3 wide open**, and hop 3 is the worst of them:
once admin-only prose is laundered through the LLM into pack text, no output filter can
reliably remove it.

**D-23.2-01 — filter the INPUT, not the prose.** The context-pack generator must drop
admin-only answers *before* building `user_message`. Output-side scrubbing of generated
prose is not acceptable and must not be attempted.

**D-23.2-02 — one derivation, one helper.** Add `admin_only_field_keys()` to
`app/intake_canonical.py`, deriving the key set from the canonical schema's section-level
`admin_only`. Every consumer imports it. Do NOT hand-write the four keys anywhere: a fifth
admin-only field added to the JSON later must close automatically.

**D-23.2-03 — the projection is by ROLE, not by route.** `role == "superadmin"` sees
everything (the AIReviewPanel depends on it). `role == "user"` gets the filtered
projection. Apply at: `list_answers`, `get_skill_run_full` (`output_parsed` subset),
`list_templates` (drop admin-only sections), and the context-pack input.

**D-23.2-04 — `list_templates` is in scope.** It hands every authenticated caller the
canonical schema including the admin-only section's labels and help text
(`intake_routes.py:482-500`). That is schema disclosure, not answer disclosure — lower
severity, but it tells a client exactly which keys to ask for, and both frontend consumers
already discard the section. Filter it for `role=user`.

## 3. F-02 — Answer writes ignore lifecycle, schema membership and field permission

`upsert_answers` (`intake_routes.py:568-598`) verifies intake ownership and **nothing
else**. No status check, no schema-membership check, no admin-only check, no type/constraint
validation. A client can write an unknown field to a `delivered` intake.

### THE TRAP THAT WILL BREAK PRODUCTION IF YOU MISS IT

The intended client policy is **not** "only `draft` is writable."

* `intake.$id.tsx:106` — `editable: intake.status === "draft"`
* `intake.$id.tsx:110-114` — `phase: (status === "reviewed" || status === "validated_by_client") ? "validation" : "intake"`
* `IntakeForm.tsx:501` — `disabled={!editable && !(isValidationPhase && f.type === "proposal_list")}`

So in **`reviewed` AND `validated_by_client`**, the form is otherwise read-only but
**`proposal_list` fields stay writable** — that is the client's "keep Nestor's proposal"
tick, shipped deliberately on 2026-08-31 and live today. A naive "writable only in `draft`"
server rule silently kills it, and no existing test would go red.

**D-23.2-05 — the server-side write policy, exactly:**

| Intake status | Client (`role=user`) may write |
|---|---|
| `draft` | any field that is in the canonical schema AND not admin-only |
| `reviewed`, `validated_by_client` | **only** fields whose canonical `type` is `proposal_list` |
| `submitted`, `decomposed`, `in_research`, `delivered` | nothing — 409 |

Superadmin is unaffected — the AI-review apply path writes as superadmin
(`intake_routes.py:590-595`, a live-UAT regression fixed on 2026-07-13; do not re-break it).

**D-23.2-06 — rejection codes.** Unknown `field_key` gives 422. An admin-only `field_key`
from a `role=user` gives 404 on the field (existence-hidden, consistent with D-07). Wrong
lifecycle status gives 409. A batch is all-or-nothing: validate every item before writing
any.

**D-23.2-07 — value validation is IN scope but bounded.** Enforce the canonical field's
`type` and its `required`/`options` where the schema states them, plus a length bound. Do
NOT invent constraints the schema does not carry.

## 4. F-03 — Clients can delete operator deliverables

`delete_objects` (`storage_routes.py:273-312`) validates only that each key starts with
`{space_id}/{intake_id}/`. Reports are written to
`{space_id}/{intake_id}/reports/{uuid}-{name}.pdf` (`intake_routes.py:1468`) — **inside**
that prefix. `GET /intakes/{id}/report` hands the client that exact `storage_path`
deliberately, for the download flow (`:1699` docstring).

The fix needs no migration, because the key already encodes a category:
`build_object_key` (`storage/keys.py:90-104`) produces
`{space}/{intake}/{category}/{uuid}-{name}` and
`CATEGORIES = frozenset({"attachments", "audio", "artifacts", "reports"})` (`keys.py:35`).

**D-23.2-08 — deletion is authorized by CATEGORY, not by prefix.** A `role=user` may delete
only `attachments` and `audio` (the two a client can upload). `artifacts` and `reports` are
operator-produced and deny with 404 (existence-hidden). Superadmin may delete any category.
Parse the category as the third path segment and reject a key that does not parse — never
substring-match `"reports"` anywhere in the key.

## 5. F-04 + F-07 — Deactivation and reactivation are not fail-closed, and share ONE fix

Both cascades write the DB first and call the IdP second, committing the DB either way:

* deactivate — `admin_routes.py:598-640`
* reactivate — `admin_routes.py:675-706`

Consequences, both confirmed:

* **F-04**: `get_current_identity` (`auth/dependencies.py:78-107`) reads `role`/`space_id`
  purely from token claims with **zero DB reads**, and `login_sync`
  (`auth/session.py:205-207`) returns `ALREADY_SYNCED` before touching the DB whenever the
  token already carries a role. So when the IdP disable fails, the DB says
  `space_deactivated` while a valid token keeps working.
* **F-07**: reactivate flips rows to `active` *before* the IdP call and commits. A retry
  selects only `space_deactivated` rows, finds none, and returns 200 having done nothing —
  while the account stays disabled. Deactivate does not have this bug: its `targets`
  deliberately include already-`space_deactivated` rows for exactly this retry
  (`:598-601`).

**D-23.2-09 — invert the ordering on BOTH verbs: IdP first, DB commit second.** On partial
IdP failure the DB is not flipped for the failed members, so the DB never over-claims, the
502 is honest, and a retry re-attempts exactly the members that failed. A crash between the
IdP call and the DB commit leaves members denied with `active` rows — fail-CLOSED, the safe
direction. The audit row must still be written and committed (that was the reason for the
current ordering; preserve the intent, not the sequence).

**D-23.2-10 — `invite_user` and any individual reactivate must reject a deactivated target
space.** `invite_user` (`admin_routes.py:148-200`) checks the space EXISTS but never that it
is active, so today you can invite an active member into a deactivated space.

**D-23.2-11 — the per-request membership check is DEFERRED, deliberately.** Consulting
membership/space status on every request would close the residual token-vs-DB divergence in
general, not just on IdP failure. It is NOT in this phase: it changes the authorization
model from claims-based to session-based, touches every test fixture that builds an
`Identity` without a membership row, and deserves its own phase. **State the residual risk
plainly in the phase summary**: after D-23.2-09 the DB can no longer over-claim, but a token
minted before an *individual* deactivation still authenticates until it expires. That window
is bounded by ID-token TTL (about 1h) and `check_revoked=True` already closes it whenever
the IdP revoke succeeded.

## 6. F-05 — Concurrent research triggers duplicate a ~$45 run

`trigger_research` (`research_routes.py:260-410`) reads status and prior attempts on
`repo.session`, then opens a **separate** `tenant_session` that patches status
unconditionally and inserts a run row. `research_runs` carries three plain indexes and
**none is unique** (`db/models/research_runs.py:143-148`).

Two concurrent authorized requests therefore both read the same `prior`, both compute
`attempt = 1`, and both insert and dispatch. This is not an authorization bypass — 23.1's
gate holds and only a superadmin reaches it — but it is uncapped duplicate spend on a path
running with `NESTOR_TRIBUNAL_UNCAPPED=1`.

**D-23.2-12 — three changes, all required; any one alone is insufficient:**

1. **Migration 0016** — partial unique index on `research_runs (intake_id)
   WHERE status IN ('queued','running')`. Mirror 0014's shape exactly, including the
   FORCE-RLS bracket and the duplicate pre-flight resolution (see section 11).
2. **CAS the status flip** with the existing `patch_if` (`db/repository.py:120`), expecting
   the `old_status` that was read. `rowcount == 0` gives 409.
3. **Compute `attempt` inside the write transaction**, not from the earlier read.

`patch_if` was built and tested in 23.1 for exactly this class of bug — reuse it, do not
write a second CAS primitive.

**D-23.2-13 — the same read-then-write shape exists in Tribunal** at
`tribunal/nestor_pulse_sdk/runs/api.py:517` (`submit_report_spec`) and `:550` (`resume_run`).
`resume_run`'s docstring asserts *"two concurrent clicks cannot both succeed"* — the code
does a plain read-then-write under READ COMMITTED and does not guarantee that. Fix both, and
**fix the docstring**: a comment claiming a guarantee the code does not provide is worse than
no comment.

## 7. F-06 — An email outage erases a successful, paid research run

`write_fn` in `research/run_task.py:800-850` calls `finalize_completed(session, ...)` and
then `resend.send(...)` **inside the same** `tenant_session` block. `run_with_session_release`
(`db/ai_session.py:150-199`) routes any exception to `on_error`, which finalizes the run to
EXACTLY `failed`. So a mail outage rolls back the completion and mislabels a run that
succeeded — encouraging an unnecessary ~$45 rerun.

**D-23.2-14 — apply the pattern this codebase already uses.** `submit_intake`
(`intake_routes.py:1333-1341`) already does this correctly: it sends
`_send_admin_validated` **after** the status flip and audit, with the comment *"a mail
failure must NEVER fail the validate."* Move the research completion mail out of the write
transaction to after it commits, and swallow-and-log a send failure. This is not a new
design; it is the existing house rule applied to the one place that breaks it.

**D-23.2-15 — the transactional outbox is DEFERRED.** The audit recommends one. The defect
here is a correctness *inversion* (success recorded as failure); the outbox is a *durability*
improvement (guaranteed eventual delivery). Fixing the inversion fully closes the finding.
Record the outbox as a deferral with this reasoning, not as an unfinished task.

## 11. Traps, measured this session

1. **Prove a gate by walking the dependency graph.** `_flatten_routes` in
   `test_client_surface_open.py` exists because FastAPI 0.141 does not flatten
   `include_router` at include time — include-level dependencies (which is how `ai_router`
   is gated) never appear in a leaf's `route.dependant`. A grep for `superadmin_gate` in
   `ai_routes.py` finds the router-level line and tells you nothing about any individual
   route.
2. **The substring trap, again.** `downloadContextPackPDF` contains `ContextPackPDF`;
   `"research"` contains `"search"`. Match imports, not substrings.
3. **Signature order is load-bearing.** In `trigger_research` the gate must stay ABOVE
   `get_tenant_repo` or a null-space caller gets a 403 existence oracle instead of a 404
   (`research_routes.py:263-270`). Any new dependency added to a gated route goes AFTER the
   gate.
4. **Migration 0014 is the template for 0016**, including the parts that are easy to skip:
   `NO FORCE ROW LEVEL SECURITY`, then the duplicate-resolution UPDATE, then `FORCE`
   restored in a `finally:`, then `create_index`. `SET row_security = off` **errors** on a
   FORCE-RLS table rather than bypassing it. Production may hold duplicate rows; a migration
   that assumes it does not will abort the deploy.
5. **A test whose seed encodes the defect will assert the defect.** In 23.1,
   `test_ai_context_pack.py` seeded `'reviewed'` and had to move to `'validated_by_client'`
   — 8 insertions, 1 deletion, **zero assertions touched**. Expect the same shape here:
   fixtures that seed `delivered` intakes and then write answers are asserting F-02.
6. **`git commit` with no pathspec commits the whole index.** Use
   `git commit -- <paths>` and verify with `git show --stat`, never a summary.
7. **The worktree stale-base trap has a known root cause now**: agent worktrees are cut from
   `origin/master`, which sat at `a3a0c96` from 2026-07-24 until the 23.1 push. It is now
   `922fd91`. **Re-test isolation before assuming it is broken** — but keep the abort gate
   (`merge-base != BASE`, never `rev-list --count == 0`, which reads green while stale).
