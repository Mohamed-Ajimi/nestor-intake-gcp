`23.2-CONTEXT.md` § 7 (F-06): `write_fn` in `research/run_task.py:807-943` calls
`finalize_completed(session, ...)` and then `resend.send(...)` **inside the same**
`tenant_session` block. `run_with_session_release` (`db/ai_session.py:150-199`) routes ANY
exception from `write_fn` to `on_error`, which finalizes the run to EXACTLY `failed`. So a mail
outage rolls back the completion and mislabels a run that succeeded — encouraging an unnecessary
~$45 rerun.

Purpose: this is a correctness inversion on the most expensive path in the product. The operator
sees `failed` on a run that produced a report, a verified chain and an uploaded bundle.

Output: the mail moves out of the write transaction; the run's real terminal status is committed
first; a send failure is swallowed and logged.

## THIS IS NOT A NEW DESIGN — IT IS THE HOUSE RULE, APPLIED HERE

`submit_intake` (`intake_routes.py:1333-1346`) already does exactly this: it sends
`_send_admin_validated` AFTER the status flip and audit, wrapped in `try/except`, with the
comment *"a mail failure must NEVER fail the validate"*. `run_task.write_fn` is the one place in
the codebase that breaks the rule. Cite `intake_routes.py:1333-1346` in your comment.

## THE SHAPE

`write_fn` currently returns `None` on every branch and calls `resend.send` three times
(`:847` completed, `:913` parked, `:938` failed). Change it to:

1. Do every DB write exactly as today (`finalize_completed` / `finalize_parked` /
   `finalize_failed`, the park `already_notified` pre-read, everything).
2. **Build** each mail's `(to, subject, html)` instead of sending it, and append to a local list.
   Building the html is pure rendering — `render_research_complete` / `render_research_parked` /
   `render_research_failed` do no I/O — so it is safe inside the transaction and keeps the
   `ctx`/`metrics` data close to where it is derived.
3. `return pending` — a `list[dict]` with keys `to`, `subject`, `html`.
4. In `run_poll_driver`, after `run_with_session_release(...)` returns and therefore AFTER the
   write transaction has committed, iterate and send. Wrap EACH send in its own `try/except`,
   log a failure at WARNING with the `research_run_id` and the subject, and continue to the
   next.

`run_with_session_release` returns `write_fn`'s return value (`ai_session.py:172`), so no change
to that module is needed. Assign it: `pending = run_with_session_release(...) or []` — `or []`
because `on_error` returns `None` and the error path must not blow up on iteration.

`on_error` (`:944-963`) already wraps its own send in `try/except` and already runs after
`finalize_failed` on its own session. **Leave it exactly as it is.** Moving it out would gain
nothing (its finalize is the failure status already) and would change the one path that is
currently correct.

## THE PARK IDEMPOTENCY PRE-READ STAYS INSIDE THE TRANSACTION

The `already_notified` logic reads the PRIOR row BEFORE `finalize_parked` overwrites it
(`:876-895`). That read must stay where it is, on the write session, before the finalize. Only
the `resend.send` call moves. If you hoist the read out, it reads the row AFTER the finalize and
`already_notified` is always True — a silent mail drop with every test still green.
