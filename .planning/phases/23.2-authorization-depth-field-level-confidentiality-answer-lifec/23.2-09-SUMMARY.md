# Phase 23.2 Plan 09: Answer-Write Policy (Lifecycle + Field Permission + Value Validation) Summary

Server-side answer-write policy for `PATCH /intakes/{id}/answers` — a pure, schema-derived
lifecycle/membership/permission/value gate that closes F-02 without breaking the live
validation-phase proposal tick or the `radio` + `allow_text` object shape.

## What changed

### `backend/app/intake_write_policy.py` (new, 366 lines)

A framework-free policy: `check_answer_batch(items, *, intake_status, role)` raises
`AnswerWriteViolation(code, detail)` or returns `None`. No web framework, no database, no
session — proven by `test_the_policy_module_is_pure`, which greps the module source.

| Step | Rule | Code |
|---|---|---|
| 0 | ownership | **in the route**, 404, unchanged, still first |
| 1 | lifecycle allow-list (`draft` open, `reviewed`/`validated_by_client` proposal-only, everything else refused) | 409 |
| — | batch size > 100 | 422 |
| 2 | schema membership against `canonical_field_keys()` | 422 |
| 3 | admin-only key from a client, detail does not echo the key | 404 |
| 4 | validation phase + a non-`proposal_list` field | 409 |
| 5 | type / `options` / `max_items` / `max_files` / bounds | 422 |

Steps 2–5 run **phase by phase across the whole batch**, so the code a caller sees does not
depend on the order they sent the items in. Superadmin returns at step 0.

Bounds (documented as DoS bounds, **not** product limits): `_MAX_VALUE_CHARS = 20_000`,
`_MAX_JSON_CHARS = 100_000`, `_MAX_BATCH_ITEMS = 100`. Refused, never truncated —
`test_bounds_are_not_silently_truncated` asserts the caller's items are not mutated.

The over-long-string bound is applied **recursively** to every string nested anywhere inside
`value_json`, which is strictly stronger than the plan's "each string inside a `value_json`
list".

## `required` / `min_length` / `min_items` are NOT enforced — a deliberate departure

D-23.2-07 as written says "enforce the canonical field's `type` and its `required`/`options`".
The `required` half is **not** implemented, and must not be, on this verb. Evidence:

* `IntakeForm.tsx:214-217` — `saveCurrentSection` saves only the **dirty** fields of the
  current section.
* `IntakeForm.tsx:26-30` — `toAnswerInput` sends `{value: null, value_json: null}` for a
  null/undefined value, so **clearing a field is a normal save**.
* `IntakeForm.tsx:33-40` — `validateField` enforces `required` in the **browser**, and
  `doSubmit` (`:301-310`) is where it runs, i.e. at SUBMIT time.

Enforcing a minimum on `PATCH .../answers` would therefore 422 the live client form mid-typing,
on every intake. The policy accepts an empty value for any writable field
(`test_empty_is_always_accepted_even_for_a_required_min_length_field`, parametrised over the
cleared and empty-string shapes). `min_length` and `min_items` follow the same reasoning.

**Follow-up, not done here:** if minimum-constraint enforcement is wanted, its home is
`POST /intakes/{id}/submit` — the transition the browser already gates. CONTEXT § 3 already says
this; recorded so the decision is not re-litigated as a bug.

## Findings — criteria that were false, stale, or would have damaged correct code

### 1. ⛔ The `proposal_list` "live feature" is currently **unreachable from the client**

CONTEXT § 3 and this plan both assert the validation-phase proposal tick is "live today". It is
**rendered** but never **persisted**:

* `IntakeForm.tsx:210` — `saveCurrentSection` opens with `if (!editable) return true;`
* `IntakeForm.tsx:103` — `editable = payload.editable`
* `intake.$id.tsx:106` — `editable: intake.status === "draft"`

So while the status is `reviewed` / `validated_by_client`, `editable` is `false` and the batch
PATCH is **skipped entirely** — including from `doSubmit` (`:305`), which calls
`saveCurrentSection` and gates on its return value. `saveAnswers` has exactly three callers
(`IntakeForm.tsx:217`, `AIReviewPanel.tsx:109/415`, `admin.pulse.intakes.$id.tsx:951`) and the
last two are superadmin admin paths. **No client write reaches `PATCH /answers` in the
validation phase today.**

Consequence for this plan: the server exception is still the **right** rule — CONTEXT is the
authority, the intent is unambiguous, and the frontend fix is one line — but the claim "a
draft-only server rule silently kills a live feature" is not measurable at HEAD, because the
frontend kills it first. Shipping draft-only would merely have required a second server change
later.

Frontend is an explicit scope fence for this plan, so **nothing was changed**. Deferred below.

### 2. ⛔ `client_name` is TRIGGER-SEEDED — the plan's "swap to a canonical `text` key" has a trap

The plan says "-> a canonical `text` key, e.g. `geo_scope`". Deriving the key instead of
hard-coding it (alphabetically first canonical `text` field) selects **`client_name`**, and
migration `0008_prefill_after_insert.py`'s `seed_intake_client_name_answer` AFTER-INSERT trigger
copies the organization's name into a `client_name` answer row on **every** intake insert.

Three of my route tests failed on exactly this: every "a refused write left NOTHING behind"
assertion reads a row the trigger created before the request ran. Had the probe been chosen
without a negative assertion to expose it, those tests would have been **silently vacuous**.

`client_name` is now excluded from probe *selection* in the new test file, with the migration
cited; the anti-vacuity sweep still walks it, because as far as the policy is concerned it is an
ordinary writable `text` field.

### 3. The D-23.2-05 status table is incomplete — it names 7 of 8 statuses

`nestor.intake_status` (`app/db/models/intake.py:41-53`) carries **eight** values. The decision
table names `draft`, `reviewed`, `validated_by_client`, `submitted`, `decomposed`,
`in_research`, `delivered` — and omits **`archived`**. Implemented as an ALLOW-list, so
`archived` (and any status a later migration adds) refuses by default rather than falling
through a deny-list into "writable". `test_unrecognised_status_denies_by_default` pins it.

### 4. Verification item 4's repo-wide figure is stale by one line: **7**, not 6

The plan says `grep -rn "extra_questions_proposed\|bias_radar" backend/app --include=*.py`
returns **6 lines** at `922fd91`. Re-run with the plan's **exact** pattern at my base
`433fb60`: **7 lines**. The extra one is `app/ai/skills/structure_answers.py:11`, introduced by
sibling plan 23.2-08 (`a8a55cb`, wave 2) after `922fd91`.

Not a false criterion and nothing breaks — the plan explicitly instructs *not* to gate
repo-wide, precisely because the count is non-zero and legitimate. It is a stale number, by the
exact mechanism CONTEXT § 11 trap 9 warns about (a change here is invisible to a plan that
quotes it). The file-scoped gates the plan *does* enforce both return 0 and are green.

### 5. Verification item 4's file-scoped gate also forbids naming keys in **prose**

`grep -c "...\|output_form" backend/app/intake_write_policy.py == 0` cannot distinguish a code
literal from a comment. My first draft named `output_size` / `output_form` in two docstrings as
*evidence* for the `allow_text` trap and scored 2. Rewritten to describe them structurally
("two of the three canonical radios carry an `allow_text` option"); the gate now returns 0. This
is arguably the right outcome under D-23.2-02 — a key named in a comment is the first step
towards a key written into a rule — but the criterion is stricter than its stated intent, and
the plan's own module-docstring instructions do not warn about it.

### 6. Verification item 7 (tsc / vitest / i18n) is **decoration for this plan**

`git diff 433fb60..HEAD -- frontend/` is empty: no frontend file was touched, and no backend
change can alter a TypeScript compile. The gate therefore measures the base commit, not this
plan's work. Run anyway and green (tsc 0, 10 files / **154** tests, i18n PASS) — which also
reconciles the plan's "vitest 154" with the briefing's "10 vitest files": the same measurement
at two granularities, both correct.

### 7. Two precedence points D-23.2-06 left open, decided and documented

* **Batch size** is checked *after* the lifecycle 409, so a client on a frozen intake gets 409
  regardless of what the batch looks like. The bound protects the DB write and nothing expensive
  happens between the two checks.
* **Steps 2–5 run phase-by-phase across the batch**, not item-by-item, so a two-item batch
  produces the same code whichever order the items arrive in
  (`test_batch_verdict_is_independent_of_item_order`). The plan required order-independence but
  did not specify how; item-by-item evaluation would have satisfied its single test case while
  still being order-dependent in general.

### 8. Naming collision worth flagging: `AnswerWriteViolation.code` is an **int**

`app/api/errors.py::CodedError.code` is a curated user-facing **string** enum. The plan's
specified signature for `AnswerWriteViolation` uses `code: int` (an HTTP status). Implemented as
specified, with the distinction spelled out in the class docstring so nobody wires one into the
other's handler. Policy details must stay generic — an admin-only refusal in particular must not
carry a translatable code that names what it is hiding.
