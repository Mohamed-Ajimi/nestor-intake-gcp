`23.2-CONTEXT.md` § 4 (F-03): `delete_objects`
(`storage_routes.py:273-312`) validates only that each key starts with

`{space_id}/{intake_id}/reports/{uuid}-{name}.pdf` (`intake_routes.py:1468`) — **inside** that
prefix. `GET /intakes/{id}/report` hands the client that exact `storage_path` deliberately, for
the download flow. So a client can delete the operator's delivered report by replaying a path
the API just gave them.

No migration is needed: the key already encodes the category.
`build_object_key` (`storage/keys.py:90-104`) produces
`{space}/{intake}/{category}/{uuid4}-{sanitized_name}` and
`CATEGORIES = frozenset({"attachments", "audio", "artifacts", "reports"})` (`keys.py:35`).

Purpose: the client is handed operator-produced paths by design, and today possession of a path
is authorization to destroy the object behind it.

Output: `category_of()` on `storage/keys.py`; a per-key category authorization in
`delete_objects` that runs BEFORE any seam call; and the tests that pin both the denial and the
still-allowed client flow.

## THE RULE, EXACTLY (D-23.2-08)

| Caller | May delete |
|---|---|
| `role != "superadmin"` | `attachments` and `audio` ONLY — the two a client can upload |
| `role == "superadmin"` | any category |

A denied key is **404** (existence-hidden), the same code and the same message the existing
prefix mismatch already raises. Not 403 — a 403 here tells the caller "that object exists and
is not yours", which is the existence oracle D-07 spends the whole codebase avoiding.

A key whose third path segment is not in `CATEGORIES` is **also 404** for everyone. It cannot
have been authored by `build_object_key`, so it is either forged or from a shape the server no
longer produces; either way the safe answer is "not found".

## ⚠ NEVER SUBSTRING-MATCH THE CATEGORY

`23.2-CONTEXT.md` § 11 trap 2, and it bites here concretely. `sanitize_filename` keeps
`[A-Za-z0-9._-]`, so a client-chosen filename can legally contain the word `reports` — a key
like `{space}/{intake}/attachments/{uuid}-quarterly_reports.pdf` is a perfectly ordinary client
attachment. `"reports" in key` denies it. Conversely
`{space}/{intake}/reports/{uuid}-summary.pdf` must be denied, and a rule looking for
`"/reports/"` happens to work today but breaks the moment a category is renamed.

**Parse, then compare.** Split the key on `/`, require at least 4 segments, take index 2, and
test membership in `CATEGORIES`. The test suite must include the
`{uuid}-quarterly_reports.pdf` attachment case explicitly — it is the exact substring trap.

## D-23.2-17 — THE UPLOAD SIDE, FIXED HERE AND NOT DEFERRED

`upload_file` (`storage_routes.py:135-162`) takes `category` straight from the form and validates
it only against `CATEGORIES`, with **no role check**. So a `role=user` can upload into `reports/`
— writing objects into the operator's deliverable prefix on a tenant-billed bucket and, once
D-23.2-08 lands, creating objects they can no longer delete.

Fixing one direction and deferring the other would MANUFACTURE that asymmetry, which is why this
is a fix and not a deferral: same hole, same file, same plan, one constant.

**The rule:** `role != "superadmin"` may upload only `attachments` and `audio`. Superadmin may
upload any category.

**The code is 422, not 404** — and the difference from the delete side is deliberate. On delete,
the caller supplies an object KEY and a 404 hides whether that object exists (D-07). On upload,
`category` is a form VALUE from a fixed four-item vocabulary that the route's own existing error
message already spells out (`Unknown storage category {category!r}`, `:162`), so there is nothing
to hide; 422 matches that neighbouring refusal and tells the caller the truth. State this
reasoning in the code comment — the next reader will otherwise "harmonise" the two codes.

**ONE SHARED CONSTANT.** Put `CLIENT_WRITABLE_CATEGORIES = frozenset({"attachments", "audio"})`
in `storage/keys.py` next to `CATEGORIES`, and import it into BOTH routes. Do NOT define a second
set in `storage_routes.py`, and do NOT let the upload rule and the delete rule be expressed as
two independent literals — the whole point of D-23.2-17 is that they cannot drift apart. A
private `_CLIENT_DELETABLE_CATEGORIES` in `storage_routes.py`, or a second set beside it for the
upload side, is the shape this decision exists to forbid: one constant, one name, in `keys.py`,
imported by both. Verification step 3b machine-checks it.

**Order inside `upload_file` is load-bearing.** The existing gate order is documented in the
handler's docstring: (2a) unknown category -> 422, (2b) extension -> 415, (1) SIZE -> 413, (3)
OWNERSHIP -> 404. Put the role check **immediately after the existing unknown-category 422 at
`:159-164`** — i.e. still in the type-check band, BEFORE `file.file.read(...)`. A refusal must
not read the body: `read(_MAX_BYTES + 1)` pulls up to 25 MB off the wire, and refusing after that
means an unauthorized caller can still make the server ingest 25 MB per request. Assert that in a
test by checking the seam saw nothing AND that the refusal happens for an oversized-but-forbidden
upload.

Do NOT move the ownership check, do NOT reorder the size/type gates relative to each other, and
do NOT change `CATEGORIES` (still four).

    repos: tuple = Depends(get_intake_and_source_repos),
