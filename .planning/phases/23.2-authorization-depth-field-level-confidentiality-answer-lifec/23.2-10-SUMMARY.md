# Phase 23.2 Plan 10: Single In-Flight Research Run per Intake (F-05) Summary

The database now refuses a second in-flight research run for the same intake, the status flip
is a compare-and-swap, and `attempt` is counted inside the write transaction — so two
concurrent triggers can no longer both dispatch a ~$45 Tribunal run.

## What changed

Three mechanisms, all required, none redundant — implemented exactly as D-23.2-12 specifies.

**1. Migration 0016 (`0016_research_runs_single_inflight.py`), INTAKE line, `down_revision = "0015"`.**
A partial unique index `uq_research_runs_one_inflight_per_intake` on `research_runs (intake_id)`
`WHERE status IN ('queued', 'running', 'needs_report_spec')`, preceded by a duplicate
pre-flight in 0014's shape: `NO FORCE ROW LEVEL SECURITY` → the resolution `UPDATE` → `FORCE`
restored in a `finally:` → `create_index`. The pre-flight keeps the newest in-flight row per
intake, tie-broken on `(created_at, id)` because `created_at` is `server_default now()` and
`now()` is fixed per transaction. Superseded rows close as `cancelled` with a readable
`error_message`. `downgrade()` drops the index and nothing else, and says plainly that the
duplicate resolution is not un-done.

The three predicate literals are built from one `_INFLIGHT` tuple via `_inflight_predicate()`
rather than by string-substituting a template — a `.replace("status", "r.status")` on a
predicate containing a column named `status` is precisely the substring shape CONTEXT § 11
trap 2 warns about.

**2. The ORM declaration** in `ResearchRun.__table_args__`, name byte-identical, `unique=True`,
`postgresql_where=text("status IN ('queued', 'running', 'needs_report_spec')")`.

**3. `trigger_research`** — inside the existing `tenant_session` block (located by enclosing
function; the phrase occurs five times in the file):
- `patch_if(intake_id, {"status": old_status}, status=new_status)`; `rowcount == 0` → 409,
  raised **before** the audit call and **before** the run insert.
- `attempt = len(tx_runs.list_for_intake(intake_id)) + 1`, computed in-tx; the pre-block
  `attempt = len(prior) + 1` is deleted, so exactly one place computes it.
- `except IntegrityError` around the `create` / `create_in_space` pair only → a readable 409.
- The docstring gains the three-part idempotency paragraph, stating explicitly that the CAS
  does **not** cover the `in_research → in_research` retry path and that the index is the only
  arbiter there.

The two refusals carry deliberately different sentences — "The intake changed while this
request was being prepared" (CAS) versus "Research is already running for this intake"
(index) — so a test can prove which mechanism fired rather than just that *a* 409 happened.

### Was the in-tx `attempt` interleaving PROVEN or only read?

**Proven.** `_interleave_before_the_write` wraps `read_brief_inputs`, which the handler calls
*after* its read of `prior` and *before* it opens the write `tenant_session` — so the hook
lands squarely inside the read-then-write window F-05 lives in. No sleeps, no threads, no
flakiness. The handler reads zero prior runs (a read-time count therefore yields 1), the hook
inserts one terminal run, and the inserted row must carry `attempt = 2`. The same mechanism
makes the CAS-stale and duplicate-insert races deterministic.

### `needs_report_spec` — an honest note

Including `needs_report_spec` in the predicate is **defence-in-depth against a design change,
not the closing of a window that is open today.** On the intake seam path the state is
documented as unreachable: `app/research/brief.py` never appends the `[INTERACTIVE_REPORT]`
marker and the seam never calls `/report-spec`, so a seam run cannot reach it. It is in the
predicate because it is *not* in `_RETRYABLE_RUN_STATUSES` — a run sitting there is alive —
and leaving it out would make the DB backstop disagree with the app rule it exists to enforce.
Do not read this phase as having fixed a live `needs_report_spec` hole. The correspondence
test is what keeps the two rules aligned if the seam ever does opt in.

## False, vacuous, or already-green criteria — reported with the measured value

**1. "Parametrise over those five and assert `checked == 5`" is internally inconsistent.**
A `pytest.mark.parametrize` runs each case as a separate test; a cross-case counter cannot be
asserted from inside one. Implemented instead as a single test that loops the five terminals
and asserts `checked == 5` — which is what the criterion is actually *for* (proving the sweep
is complete, so a case that silently stopped being generated would fail). Stated in the test's
docstring.

**2. The signature-order criterion was already green at HEAD, and is now asserted three times.**
`test_the_gate_still_precedes_the_repo_in_the_signature` passed on the RED run, before any
handler change — necessarily so, since the plan forbids touching the signature and adds no
`Depends`. It is a tripwire, not a gate. It is also the *third* copy of the property:
`test_research_trigger_gate.py::test_ordering_mutation_produces_the_403_existence_oracle`
already asserts the same precondition **and** demonstrates the oracle by mutating the order,
and `test_trigger_null_space_404` covers the behaviour. Kept because it is cheap, flagged
because it is decoration.

**3. `test_ordinary_retrigger_after_a_dead_run_still_stamps_attempt_2` was green at HEAD too.**
It is a counterweight (proving the partial index does not swallow a legitimate retry), not a
proof of anything this plan built. Noted in its docstring.

**4. The plan's account of `alembic check` is half right, and the correct reason is stronger
than the one it gives.**
- Right: the **CLI** form fails on every tree. `alembic.ini`'s `sqlalchemy.url` is empty and
  `env.py` falls back to an unset `DATABASE_URL`, so it raises `ArgumentError: Could not parse
  SQLAlchemy URL`. It is not a gate.
- Incomplete: the repository **already runs `alembic check` inside pytest**, bound to the
  testcontainer DSN — `test_ai_dedup.py::test_alembic_check_reports_no_drift` — and it passes
  against 0016. So "alembic check is unavailable here" is not true of the in-pytest form.
- The real reason the pytest drift test is needed: alembic 1.18.4's postgresql
  `compare_indexes` (`alembic/ddl/postgresql.py`) compares the **unique flag and the index
  expressions only** — it never inspects `postgresql_where`. A predicate that drifted between
  the ORM and the migration would pass `alembic check` **silently**. That is the hole
  `test_orm_declaration_matches_the_deployed_index` closes, and the docstring says so.

**5. Every line citation in this plan was accurate at the base commit** — a change from this
phase's pattern, worth recording. Verified at `8222c5e`: `_RETRYABLE_RUN_STATUSES` at `:151`,
`_MAX_ATTEMPTS` at `:155`, the decorator at `:260` / `def` at `:261`, `attempt = len(prior) + 1`
