<objective>
Close **D-23.2-16**. `23.2-CONTEXT.md` § 8 (F-08).

`ai/skills/structure_answers.py:137-141` sources valid keys from `intake.template_id`, then
`IntakeTemplateRepository`. **The normal creation path never sets `template_id`** —
`frontend/src/lib/api/intakes.ts:43` sends only `client_name` — so `template_keys` is `[]`.
Line 227 then reads:

```python
if valid_keys and field_key not in valid_keys:
    continue
```

An empty list **disables filtering entirely**, and the model's invented keys are written straight
into `intake_answers` via `upsert_extracted`.

Meanwhile `GET /intakes/templates` serves the canonical in-repo schema to everyone (D-CANON,
`intake_routes.py:482-500`); per-space template rows are no longer read on the client path at
all. So the code consults a source the product stopped using, gets nothing, and turns its own
guard off.

Purpose: rows keyed on invented field keys are invisible to the form (no field renders them),
survive every later read, and end up in the context-pack prompt as `**{invented_key}**: {value}`.

Output: `valid_keys` from `canonical_field_keys()`, and the `if valid_keys and` fallback deleted
so an empty set denies.

## THE FILTER IS CANONICAL-SCHEMA-KNOWN, NOT CLIENT-VISIBLE

D-23.2-16 is explicit: admin-only keys are LEGITIMATE targets here. This skill runs on the
superadmin-gated `ai_router` and its whole job is to structure an operator interview — writing
`bias_radar` from a transcript is exactly what it is for.

So use `canonical_field_keys()` (today 29 keys, admin included), **not**
`canonical_field_keys() - admin_only_field_keys()`. Getting this backwards silently breaks the
operator's own tool while every test stays green, which is why plan 23.2-01's docstrings state
what each set is NOT.

## THE PROMPT MUST STILL CARRY THE KEYS

`read_fn` builds `user_message` as `"# Template velden"` + `json.dumps(template_keys)` +
`"# Transcript"` + the transcript. Today, on the normal path, that JSON block is `[]` — the model
is asked to extract fields from a list of no fields, and then invents. Feeding it the real 29
keys is a quality improvement that falls out of the same change: keep the block, fill it from the
canonical list.

Emit the keys as a SORTED list so the prompt is deterministic across processes (a `frozenset`'s
iteration order is not stable between runs, and a non-deterministic prompt makes a paid call
irreproducible and its audit trail useless).

## WHAT THIS PLAN MUST NOT DO

- **Do NOT filter to client-visible keys.** See above — admin-only keys are in scope here.
- **Do NOT keep a fallback** of any shape (`or template_keys`, `if not valid_keys: valid_keys =
  ...`, a settings flag). D-23.2-16 says delete the `if valid_keys and`; an empty set must deny.
  After this change `valid_keys` is never empty anyway (29 keys), and that is the point: the
  guard cannot be turned off by data.
- **Do NOT delete `IntakeTemplateRepository`, the `intake_templates` table, or the Phase-5 admin
  clone/edit endpoints.** `intake_canonical.py`'s module docstring says they stay in place for a
  possible future per-client-customization track. You are removing ONE call site.
- **Do NOT change `_split_value`, `_coerce_uuid`, `upsert_extracted`, the `extracted_by='llm'`
  marker, the superadmin `upsert_batch_in_space` branch, or the run finalize.**
- **Do NOT change `STRUCTURE_ANSWERS_SYSTEM_PROMPT`** (the system prompt) or the model.
- **Do NOT touch `_flatten_template_keys` beyond removing its call site**, unless it becomes
  entirely unreferenced — in which case delete it and say so, rather than leaving dead code.
  Check with a grep across `backend/` before deciding.
