# Phase 23.2 Plan 08: Filter structure-answers Output to the Canonical Schema Summary

`structure_answers` now validates every model-produced `field_key` against
`canonical_field_keys()` (29 keys, admin-only included) instead of a per-space template row
that the normal creation path never attaches, and the `if valid_keys and` short-circuit that
turned an empty allow-list into "permit everything" is gone — an empty set now denies.

## What changed

| `read_fn`: `template_keys = []`, then `if intake.template_id is not None: … _flatten_template_keys(tpl.schema)` | `valid_keys = sorted(canonical_field_keys())` — no DB lookup, no `template_id` read |

## The docstring that encoded the defect — old vs new

CONTEXT § 11 flagged this specifically, and it is the third instance of the class in this phase
(plan 05 deleted a false concurrency guarantee, plan 04 a false in-transaction mail claim).

**Deleted** (`_flatten_template_keys`, `:95-101`):

> Flatten `schema.sections[].fields[].key` into a list of valid field keys.
>
> Mirrors `flattenFields` (structure-answers.ts:33-35). **Returns `[]` when the intake has no
> template / schema — in which case the write phase accepts the LLM's field_keys as-is** (an
> interview intake without a strict template still structures its transcript).

The bolded sentence describes F-08 as a designed feature, complete with a rationale. The whole
function is gone, so the sentence is gone with it.

**Added** (module docstring):

> Legal field keys (D-23.2-16): the allow-list is the CANONICAL in-repo schema
> (`app.intake_canonical.canonical_field_keys` — today 29 keys), NOT the intake's per-space
> `intake_templates` row. Admin-only keys are INCLUDED: this skill runs on the
> superadmin-gated `ai_router` and structuring an operator interview into `bias_radar` is
> exactly its job, so the filter is schema MEMBERSHIP, never the client-visible subset. A
> `field_key` the canonical form does not define is DROPPED, never written.
>
> Until phase 23.2 the keys came from `intake.template_id` -> `IntakeTemplateRepository`, and
> the write phase read `if valid_keys and field_key not in valid_keys` — so an EMPTY key list
> PERMITTED every key the model invented. The normal creation path never sets `template_id`
> (`frontend/src/lib/api/intakes.ts` posts only `client_name`), so that list was always empty
> and the guard had never once run in production (F-08). The `and` is gone: an empty set now
> DENIES, and the set is never empty anyway.

`run_structure_answers`'s docstring was updated in the same shape, and the removed branch is
explained inline at the guard itself.

## Seam 3 — kept deliberately opposite to plan 23.2-07

Plan 07 filters admin-only keys **out** of the context-pack prompt (that output reaches a
client). This plan keeps them **in**: `structure_answers` runs as an operator and writing
`bias_radar` and the three `blind_spots_*` fields is its purpose. The implementation imports
`canonical_field_keys()` and never touches `admin_only_field_keys()` or
`client_visible_schema()`.

The test enforces the distinction rather than trusting the comment: it asserts
`"bias_radar" in admin_only_field_keys()` (so the case cannot silently stop being about an
admin-only key) and then asserts that key's row IS written with its real value. Swapping in the
confidentiality set would go red on that assertion and on nothing else — no client-facing test
in the suite covers this write path.

## False / unsatisfiable acceptance criteria — reported, not obeyed

**1. Verification step 2 — `grep -n "if valid_keys and" …` returns 0 lines. FALSE as written.
Real value after the fix: 2 lines.**

**2. Verification step 3 — `grep -n "template_id" …` returns 0 lines. FALSE as written. Real
value after the fix: 3 lines.**

All five surviving matches (`:15`, `:16`, `:18`, `:224`, `:226`) are **prose** — the module
docstring and the inline comment that name the removed construct in order to explain why it was
dangerous. These two criteria are in direct conflict with the plan's own instruction (and
CONTEXT § 11's) to *"comment it with D-23.2-16 and the reason the `and` was dangerous"*: a
naive substring grep cannot distinguish a live guard from its own obituary. Satisfying them
literally would mean deleting the explanation and re-creating exactly the condition under which
the next reader restores the bug.

Replaced with the stronger form — the same needles counted in **executable code only**,
tokenizing and dropping COMMENT tokens plus every bare-string statement (a `grep -v '^ *#'`
would have missed the docstring entirely, a known trap):

```
'if valid_keys and':        0 occurrence(s) in executable code
'template_id':              0 occurrence(s) in executable code
'IntakeTemplateRepository': 0 occurrence(s) in executable code
'_flatten_template_keys':   0 occurrence(s) in executable code
'canonical_field_keys':     2 occurrence(s) in executable code
```

**3. Task 1 behaviour — "assert the count of `extracted_by='llm'` rows is EXACTLY 2".
Arithmetically wrong given the plan's own array. Real value: 3.**

The same behaviour block specifies a four-entry array — `decision_or_goal`,
`audience_description`, `bias_radar`, `totally_invented_key` — of which three are canonical and
must all be written. The anti-vacuity count is therefore 3, not 2. The test asserts
`len(rows) == 3` **and** the exact key set `{decision_or_goal, audience_description,
bias_radar}`, which is strictly stronger than a bare count: a fix that dropped everything, or
one that dropped only the admin-only key, fails it.

**4. Environment baseline — "MEASURED BASELINE at `922fd91`: 608 passed". Stale for this base.
Real value at `7af9bcc`: 648 passed, 2 skipped.** Recorded, not contorted; the plan itself asks
the executor to measure their own.

No criterion was already-green-at-HEAD, and none required damaging correct code.
