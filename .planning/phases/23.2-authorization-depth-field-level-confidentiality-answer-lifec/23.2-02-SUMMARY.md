# Phase 23.2 Plan 02: Storage Category Authorization Summary

Closed **both directions** of F-03 — a `role=user` could delete the operator's delivered
report by replaying a path the API had just handed them, and could also upload into that
same `reports/` prefix — by authorizing on the **parsed** key category rather than the key
prefix, from **one** shared constant read by both routes.

Executed at `dcd79db` (abort gate: `git merge-base HEAD dcd79db` == `dcd79db`, phase
directory holds 11 plans + CONTEXT). Branch `worktree-agent-acae35fca86cd3b4f`.

## What changed

**`backend/app/storage/keys.py`** (additive only, 49 insertions / 0 deletions)

- `CLIENT_WRITABLE_CATEGORIES = frozenset({"attachments", "audio"})`, placed directly under
  `CATEGORIES`. Documented as **the one set both storage routes import**, so the write rule
  and the delete rule cannot drift into a category that is uploadable-but-undeletable.
- `category_of(key)` — the inverse of `build_object_key`. Splits on `/`, requires ≥ 4
  segments, returns `parts[2]` if it is in `CATEGORIES` else `None`. Never raises; a
  non-`str` returns `None`. The docstring carries the
  `attachments/{uuid}-quarterly_reports.pdf` counter-example explicitly so it cannot be
  "simplified" into an `in` check.
- `CATEGORIES` unchanged (still four) — pinned by a `checked == 4` assertion.

**`backend/app/api/storage_routes.py`**

- Import extended to pull `CLIENT_WRITABLE_CATEGORIES` and `category_of` from
  `app.storage.keys`. **No category constant is defined in this module** —
  `grep -c "frozenset" backend/app/api/storage_routes.py` returns **0**.
- `upload_file`: new gate `(2c) ROLE` placed **immediately after** the existing
  unknown-category 422 and **before** the extension check and the body read. Measured
  placement in the current file: role check at **`:206`**, `file.file.read(_MAX_BYTES + 1)`
  at **`:223`**. The numbered gate-order docstring was extended rather than left stale, and
  the code comment states why the code is 422 and not the delete side's 404.
- `delete_objects`: `category_of` + `CLIENT_WRITABLE_CATEGORIES` added **inside the existing
  pre-validation loop** (`:370-382`), immediately after the prefix assert on the same key.
  The deletion loop (`:385-390`) is untouched. Denials reuse
  `HTTPException(status.HTTP_404_NOT_FOUND, "Object not found")` byte-for-byte from the
  prefix branch. Docstring extended with the category rule, the existence-hiding rationale,
  the all-or-nothing placement and the parse-not-substring counter-example.
- Deny-by-default polarity in both places: `identity.role != "superadmin"`, never
  `== "user"`.

**Not touched**, as fenced: `create_signed_url`, `_normalize_intake_id`, the prefix assert,
the ownership check, the size/type gate order, `CATEGORIES`, the route's reachability
(`DELETE .../storage/objects` remains open to `role=user` — this changes what it *accepts*,
never who may call it), the entire `frontend/`, and both run-research guard tests.

### One false claim in the plan, reported rather than worked around

**[FALSE — `<interfaces>` and CONTEXT § 4] "`intake_routes.py:1468` — where a report key is
built: `build_object_key(str(intake.space_id), intake_id, "reports", body.file_name)`."**

Measured at `dcd79db`: `grep -rn "build_object_key" backend/app/` returns **zero call sites
in `intake_routes.py`**. The only occurrence of the token in that file is the word inside a
docstring at `:1442`. Line `:1468` is
`prefix = f"{intake.space_id}/{intake.id}/reports/"` — a prefix **assert** inside
`_assert_report_key`, a guard, not a builder. The only `build_object_key` call sites in the
backend are `storage_routes.py:194` (this plan's `upload_file`), `research_routes.py:750`
and `research/run_task.py:617`.

**This does not weaken the fix — it strengthens the case for D-23.2-17.** A `reports/` key
is authored by `upload_file` itself, driven by `FinalReportBlock.tsx:111`; the delivery verb
then merely **links** whatever staged path it is given, and `_assert_report_key` accepts any
path under `{space}/{intake}/reports/`. So the upload-side role check is the only thing
standing between a `role=user` and a path the report-delivery guard would accept as a valid
report. Deferring the upload direction would have been worse than the plan supposed.

The substantive premise is TRUE and independently verified: a report lives at
`{space}/{intake}/reports/{uuid}-{name}.pdf`, inside the prefix `delete_objects` accepted
(`intake_routes.py:1430` comment and the `:1468` prefix assert).

### One assertion weaker than it reads (self-reported)

The plan's must-have "a denied upload writes NOTHING: no GCS object, **no `intake_sources`
row**" is true but **non-discriminating for exactly these two categories**: `upload_file`
only ever creates a source row when `category == "audio"`, so `reports` and `artifacts`
never wrote one even at HEAD. The `_source_count(...) == 0` assertion in
`test_upload_operator_categories_denied_for_user` is therefore green by construction; the
422 and `_no_seam_calls(fake_gcs)` are what actually gate. Kept as a genuine no-side-effect
guard, flagged rather than dressed up.
