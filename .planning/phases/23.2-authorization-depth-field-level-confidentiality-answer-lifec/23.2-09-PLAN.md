### ⚠ `required` CANNOT BE ENFORCED AT WRITE TIME — A MEASURED CONFLICT

`IntakeForm.tsx:214-217` saves only the DIRTY fields of a section, mapping every value through
`toAnswerInput` (`:26-30`), which sends `{value: null, value_json: null}` for a null/undefined
value. Clearing a required field, or saving a section before a required field is filled, is a
NORMAL save-as-you-go operation and it happens on every intake. `validateField` (`:33-40`)
enforces `required` in the browser at SUBMIT time, not at save time.

Enforcing `required` on `PATCH /answers` would 422 the live client form mid-typing.

**Therefore**: an EMPTY value (both `value` and `value_json` null or empty string) is ALWAYS
accepted for a writable field. `required` is a submit-time property and this policy does not
enforce it. `min_length` is treated the same way, for the same reason — `company_intro` carries
`min_length` and a client types into it one character at a time.

This is a deliberate, stated departure from a literal reading of D-23.2-07. **Record it in the
SUMMARY under a heading of its own**, with the `IntakeForm.tsx:214-217` / `:26-30` / `:33-40`
evidence. If the operator wants `required` enforced, its home is the `/submit` verb, not this
one — name that as the follow-up rather than doing it here.

### ⚠ THE `radio` + `allow_text` TRAP — MEASURED, AND IT BREAKS A LIVE FIELD

`output_form`'s third option carries `allow_text: true`, and `FieldRenderer.tsx:302-306` stores
that choice as an **object** — `onChange({ choice: opt.value, text: current.text ?? "" })` —
i.e. in `value_json`, not as a plain string in `value`. A naive "radio ⇒ `value` must be a
string in `options`" rule REJECTS the live "Anders / Other" path, and no existing test catches
it.

The radio rule is therefore: accept EITHER

* `value` is a string equal to one of the option `value`s and `value_json` is null; OR
* `value_json` is a dict whose `choice` is one of the option `value`s **whose option carries
  `allow_text` truthy**, and whose `text` (if present) is a string within the length bound.

Your matrix must contain `{"field_key": "output_form", "value_json": {"choice": "other", "text":
"iets anders"}}` -> **accepted**, and `{"field_key": "output_form", "value": "not_an_option"}` ->
**422**.

### The rest of the type rules

Derive the field via `canonical_field(field_key)`; today's type distribution is
`longtext` 11, `text` 5, `radio` 3, `list` 3, and one each of `date`, `download`, `email`,
`file`, `files`, `tel`, `proposal_list`.

* `text` / `longtext` / `email` / `tel` / `date` — `value` must be a `str`, `value_json` must be
  null. **No format regex**: the schema states no pattern, and D-23.2-07 forbids inventing one.
* `radio` — as above.
* `list` / `proposal_list` — `value_json` must be a JSON array; `value` must be null. Enforce
  `max_items` when the schema states it (`questions`, `competitors_list`, `stakeholders_list`);
  do NOT enforce `min_items` (same save-as-you-go reasoning as `required`).
* `files` — `value_json` must be a JSON array; enforce `max_files` when stated.
* `file` — `value_json` must be a JSON object.
* `download` — display-only (`nda_download`). Accept anything within the length bound; the
  schema states no input contract for it and inventing one is out of scope.

### The length bounds

Three module constants, documented as DoS bounds and NOT as business rules — the schema carries
no maximum for any of them:

* `_MAX_VALUE_CHARS = 20_000` — `len(value)`, and each string inside a `value_json` list.
* `_MAX_JSON_CHARS = 100_000` — `len(json.dumps(value_json))`.
* `_MAX_BATCH_ITEMS = 100` — the largest section holds 6 fields; 100 is generous headroom.

An over-bound item is `422`. Do not silently truncate.
