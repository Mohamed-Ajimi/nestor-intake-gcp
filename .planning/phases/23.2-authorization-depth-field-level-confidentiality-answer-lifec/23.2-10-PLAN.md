## ⚠ ALL THREE CHANGES ARE REQUIRED. NONE ALONE IS SUFFICIENT.

D-23.2-12 says so, and here is the concrete reason, which you must not "simplify" away:

## THE INDEX — AND ITS PREDICATE IS DERIVED, NOT GUESSED

`uq_research_runs_one_inflight_per_intake` — UNIQUE on `(intake_id)` WHERE
**`status IN ('queued', 'running', 'needs_report_spec')`**.

⚠ **Three literals, not two.** An earlier draft of D-23.2-12 said `('queued','running')`; that
is subtly wrong and the correction is load-bearing.

**The measured status vocabulary.** `mirror_tick` (`research/run_task.py:281-283`) writes
`metrics.get("status")` **VERBATIM** from the Tribunal engine — it is not a mapped or
constrained enum, and there is no CHECK constraint on the column. The nine statuses that can
land are: `queued`, `running`, `cancelled`, `needs_input`, `failed`, `completed`,
`needs_report_spec`, plus `completed_degraded` and `parked` from `research/run_status.py:54,60`.

**The predicate is the COMPLEMENT of `_RETRYABLE_RUN_STATUSES ∪ RESEARCH_TERMINAL`:**

* `_RETRYABLE_RUN_STATUSES = {"failed", "cancelled", "needs_input"}` (`research_routes.py:151`)
* `RESEARCH_TERMINAL = {"completed", "completed_degraded", "failed", "cancelled", "parked"}`
  (`research/run_status.py:60`)
* union = `{completed, completed_degraded, failed, cancelled, parked, needs_input}`
* complement over the nine = **`{queued, running, needs_report_spec}`**

That is not a coincidence to be re-derived by hand each time: the index exists to back up the
app rule at `research_routes.py:326-333`, which refuses a new trigger on an `in_research` intake
unless the latest run is in `_RETRYABLE_RUN_STATUSES`. **`needs_report_spec` is NOT retryable** —
the run is alive and awaiting an operator's report spec, and `POST /report-spec` re-queues that
SAME run. A `('queued','running')` index would let a concurrent trigger through in exactly that
state, making the database backstop disagree with the app rule it exists to enforce.

**Honest note on reachability, to be carried into the docstring and the SUMMARY:** on the intake
seam path `needs_report_spec` is documented as UNREACHABLE today — `research/brief.py:6-12` says
the seam never appends the `[INTERACTIVE_REPORT]` marker and never calls `/report-spec`, so "a
seam run therefore can never reach `needs_report_spec`", and `run_task.py:39-41` calls it a
"residual response-Literal gap". So including it is **defense-in-depth against a design change,
not a fix for a live hole**. Say that plainly rather than implying the state is reachable today;
the correspondence test below is what keeps the two rules aligned if the seam ever does opt in.

**⚠ USE A POSITIVE `IN (...)` LIST. NEVER A `NOT IN (terminal)` FORMULATION.** Because
`mirror_tick` writes engine statuses verbatim, an unknown FUTURE status would match a negative
predicate and block that intake's triggers **permanently**. A positive list fails OPEN on an
unknown status, which is the right direction here because the app-level 409 still sits in front
of it.

* **Why `(intake_id)` and not `(space_id, intake_id)`.** `intake_id` is a UUID primary key of a
  space-owned table, so it is already globally unambiguous. Adding `space_id` WIDENS the key and
  thereby WEAKENS the invariant — two spaces could each hold an in-flight run for the same
  intake id, an impossible state the narrow key rules out. 0014's docstring makes this argument
  for `skill_runs`; make it again here.
* **Why partial.** Terminal rows are unconstrained, so the full run history and every legitimate
  retrigger stay legal. A plain `UNIQUE (intake_id)` would forbid the retry path outright.
* There is **no CHECK constraint** on `research_runs.status` (verified at `922fd91`: no
  `CheckConstraint` in the model and no `ck_` in 0011), so the pre-flight may write any status
  literal; choose one that is honest.

## MIGRATION 0016 MUST MIRROR 0014'S SHAPE — INCLUDING THE PARTS THAT ARE EASY TO SKIP

`23.2-CONTEXT.md` § 11 trap 4. `backend/app/db/alembic/versions/0014_skill_runs_single_running.py`
is the template. Read it in full and reproduce, in this order:

1. `ALTER TABLE nestor.research_runs NO FORCE ROW LEVEL SECURITY`
2. `try:` the duplicate-resolution UPDATE
3. `finally:` `ALTER TABLE nestor.research_runs FORCE ROW LEVEL SECURITY`
4. `op.create_index(..., unique=True, postgresql_where=sa.text("status IN ('queued','running','needs_report_spec')"))`

**Why the FORCE bracket, in one sentence you must keep in the docstring**: `research_runs` carries
ENABLE + FORCE ROW LEVEL SECURITY (0011, `:168-169`), FORCE binds the table OWNER — which is the
role alembic runs as — and with no `app.current_space_id` GUC set the policy evaluates to NULL,
so a plain cross-space UPDATE matches ZERO rows **silently**, leaving every duplicate in place for
`CREATE UNIQUE INDEX` to abort on. **`SET row_security = off` is NOT the fix — on a FORCE-RLS
table it ERRORS rather than bypassing.** The `finally:` restores FORCE even if the UPDATE raises,
and the whole migration is transactional so a rollback restores it too.

**The tie-break is `(created_at, id)`, not `created_at` alone.** `created_at` carries
`server_default now()`, and `now()` is fixed for a whole transaction, so two rows written in one
transaction share a timestamp to the microsecond. Ordering on `created_at` alone leaves BOTH
running and the index creation still aborts. The tuple makes the order total.

**Production may hold duplicate `queued`/`running` rows.** Nothing has constrained them since
Phase 11. A migration that assumes otherwise aborts the deploy. The resolution keeps the NEWEST
row of each `intake_id` group in flight and closes every older one with an honest status and a
readable `error_message` in the register of `run_task`'s own finalize messages. Keeping the newest
matters: an actually in-flight run must not be killed by its own migration.

`downgrade()` drops the index and NOTHING else. Do not attempt to un-resolve the duplicates —
that data is gone and pretending otherwise fabricates state. Say so in the downgrade comment, as
0014 does.

Following 0012/0013/0014's precedent: an index added to an already-granted, already-policied
table needs NO re-grant and NO re-policy. State that in the docstring; create no policy, grant
nothing, revoke nothing.
