# Phase 23.2 Plan 04: Mail Outage Must Not Erase a Paid Research Run — Summary

A Resend transport error inside `write_fn`'s `tenant_session` block rolled back a
completed research run's finalize and re-labelled it `failed`; the three terminal sends
now return as a pending list and are dispatched by `run_poll_driver` after the write
transaction commits, each swallowed-and-logged.

## What changed

**`backend/app/research/run_task.py`** (89 insertions, 19 deletions — commit `1f33962`)

- `write_fn` signature `-> None` becomes `-> list[dict[str, Any]]`, opens with
  `pending: list[dict[str, Any]] = []` and returns it from a single fall-through
  `return` at the end. Its new docstring names the mechanism (an exception here routes
  to `on_error`, which finalizes to EXACTLY `failed`) and cites the house precedent,
  `app/api/intake_routes.py:1333-1346` — *"a mail failure must NEVER fail the validate"*.
- The three `resend.send(...)` calls at `:847` (completed), `:913` (parked) and `:938`
  (failed) became `pending.append({"to": ..., "subject": ..., "html": ...})`. The
  surrounding conditions are byte-identical: `if to:` on completed and failed,
  `if to and not already_notified:` on parked, and the `elif already_notified:` WARNING
  is untouched.
- The park `already_notified` pre-read (`ResearchRunRepository(session, identity).get(...)`
  before `finalize_parked`) stayed exactly where it was, on the write session. Hoisting it
  out would have made it read the row after the finalize, so `already_notified` would be
  permanently True — a silent mail drop with every test still green.
- `run_poll_driver`'s bottom now reads
  `pending = run_with_session_release(...) or []`, then loops with one `try/except` per
  mail, logging `terminal mail FAILED (run already finalized, not retried):
  research_run_id=%s subject=%s` at WARNING with `exc_info=True`. The
  `run_poll_driver DONE` line stays BELOW the loop.
- The `run_poll_driver` docstring's WRITE bullet was corrected — it asserted the mail is
  sent inside the WRITE phase, which is now false. A docstring that outlives its engine is
  the exact "UI copy outlived its engine" failure mode; a new `MAIL (post-commit)` bullet
  replaces it.

**Untouched, deliberately:** `app/db/ai_session.py` (`git diff` EMPTY — it already returns
`write_fn`'s value), `on_error`, every recipient (`[ctx["acting_email"]]`), all three
subjects, all three templates, the finalize functions, `mirror_tick`, `build_completion`,
the poll loop, the cost governor.

**`backend/tests/test_research_run_task.py`** (278 insertions, **0 deletions** — commit
`5dd8b6c`). The six pre-existing mail tests are unmodified; the diff is purely additive.

## The pre-fix observation — F-06 is real in this tree

Measured at `dcd79db` with a throwaway probe (created, run, deleted — never committed),
driving each terminal with a `resend.send` that records then raises `RuntimeError("Resend 503")`:

```
PROBE[completed] attempts=['Je onderzoek is klaar', 'Je onderzoek is mislukt']
                 finalize=[('completed', 'fake report'), ('failed', 'Resend 503')]  patch_run=[]
PROBE[parked]    attempts=['Je onderzoek staat op pauze', 'Je onderzoek is mislukt']
                 finalize=[('failed', 'Resend 503')]  patch_run=['parked']
PROBE[failed]    attempts=['Je onderzoek is mislukt', 'Je onderzoek is mislukt']
                 finalize=[('failed', 'research run ended with status failed'), ('failed', 'Resend 503')]
```

Read it plainly:

- **completed** — `finalize_completed` ran, then the mail raised, then `on_error` ran
  `finalize_failed` with the **mail transport's own error string** as the run's
  `error_message`. In production the first finalize is rolled back with the transaction, so
  the operator's row reads `failed / Resend 503` on a run that produced a report, a verified
  chain and an uploaded bundle.
- **parked** — the same escape. `finalize_parked` wrote `parked`, the mail raised, and
  `finalize_failed` followed. This is the worse of the three: the run's paid work is
  checkpointed and a `failed` label destroys the resume affordance 15.2-19 shipped.
- **failed** — `finalize_failed` ran **twice**, the second time overwriting a real engine
  error message (`research run ended with status failed`) with `Resend 503`. Harmless for
  the status, actively misleading for the diagnosis.

After the fix the same three branches produce exactly one send attempt, one finalize each,
and no `on_error` involvement.

## ⛔ Acceptance criteria that were false, vacuous or already green

**1. Task 1's ORDERING criterion was already GREEN at HEAD — REPLACED.**

The plan asked for a fake `resend.send` that records `len(finalize_calls)` at call time and
asserts `>= 1`. That passes at `dcd79db` **unchanged**: pre-fix, `write_fn` already calls
`finalize_completed` before `resend.send` at `:847`, in the same block. The criterion proved
nothing about the fix — decoration, not a gate.

Replaced (per the orchestrator's instruction, and confirmed by measurement) with the pair
that the pre-fix code **cannot** satisfy, observed at the instant `write_fn` returns:

- `write_fn` returns a **non-empty** `list` of pending mails — at HEAD it returns `None`;
- `len(fake_resend["calls"]) == 0` at that moment — at HEAD it is already **1**.

Measured RED at HEAD: `AssertionError: ... Sends already made: 1. assert 1 == 0`. Green
after the fix. The test docstring records the replacement and why, so the next reader does
not reinstate the weaker form.

**2. Two of the four new tests are green at HEAD by construction — labelled as such, not
presented as proofs.**

- `test_no_double_send_on_the_completed_path` — a regression guard. Its only job is to fail a
  refactor that returns the pending mail AND leaves the original in-transaction send in
  place, which every other test in the block would pass. Its docstring says so.
- `test_on_error_path_logs_done_not_crashed` — a mutation gate on `or []` (T-23.2-04-04).
  There is no loop at HEAD, so it cannot be red there; it is red against the most likely
  wrong way to write the fix. Its docstring says so.

Both are honest guards, not gates on this change. Flagging them rather than letting the
count of "new tests" imply four proofs.

**3. The four-vs-three `resend.send` grep — the plan was right, the grep is the liar.**

Confirmed by reading the boundary, not by counting. At HEAD `write_fn` spanned `807-943` and
`on_error` began at `944`, so `:958` was on the error path — already `try/except Exception:
pass`, already on a fresh session after `finalize_failed`, **correct as it stands**. It was
not touched and is not a miss. Post-fix the boundaries moved (`write_fn` now `811-983`,
`on_error` `985-1005`, the driver's `try` at `1007`) and the grep returns **two**: `:999`
inside `on_error`, unchanged, and `:1025` in the post-commit loop.

**4. One methodological deviation from the plan's test shape.** The plan asked to
`@parametrize` the three terminals and assert `checked == 3`. A parametrized test cannot
assert its own cardinality — each param is a separate run, and a module-level accumulator
goes green under `-k`. Written instead as ONE body over an explicit loop, which makes "all
three branches were exercised" a real assertion and survives `-k` filtering. Same intent,
stronger guarantee.

## D-23.2-15 — the transactional outbox stays DEFERRED (DEF-23.2-02)

The defect fixed here is a correctness **inversion** (a success recorded as a failure). The
outbox is a **durability** improvement (guaranteed eventual delivery). Fixing the inversion
fully closes F-06. After this change a mail can still be lost if the process dies between the
commit and the send; the run is then correctly labelled and the operator's notification is
missing — a strictly better failure than the one being removed, and it is logged at WARNING
with the run id and the subject. No outbox, no retry queue, no `notifications` table, no
background retry was built.
