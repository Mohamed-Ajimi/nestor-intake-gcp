## MEASURED FACTS ABOUT THE SCHEMA (verified at `922fd91`)

Read them; do not re-derive them by hand in code.

* The schema has **14** sections and **29** fields in total.
* Sections carry `id`, **not** `key`. (`section["key"]` is `None` for all 14 — a walker that
  reads `section["key"]` silently produces nothing.)
* Exactly **one** section has `admin_only` truthy: `id == "strategic_perspective"`, holding
  exactly **4** fields — `bias_radar`, `blind_spots_upstream`, `blind_spots_downstream`,
  `blind_spots_perspectief`.
* Exactly **one** field has `type == "proposal_list"`: `extra_questions_proposed`. Plan
  23.2-09 depends on this being derivable, so `canonical_field()` must expose `type`.
* Field-level property names present across the whole schema:
  `accept, display_filename, examples, help, item, key, label, max_files, max_items,
  max_size_mb, min_items, min_length, options, placeholder, required, rows, soft_required,
  soft_required_message, storage_bucket, storage_path, storage_path_prefix, type`.
  There is **no** field-level `admin_only` anywhere — the flag lives only on the section.

## THE CONTRACT (downstream plans are written against exactly this)

```python
def admin_only_field_keys() -> frozenset[str]: ...
def canonical_field_keys() -> frozenset[str]: ...
def canonical_field(field_key: str) -> dict | None: ...
def client_visible_schema() -> dict: ...
```

* `admin_only_field_keys()` — every `field["key"]` under every section whose `admin_only` is
  truthy. Today: 4 keys.
* `canonical_field_keys()` — every `field["key"]` in the schema, admin-only included. Today:
  29 keys. This is the SCHEMA-MEMBERSHIP set (plan 23.2-09's 422 gate, plan 23.2-08's
  `valid_keys`), NOT the client-visible set.
* `canonical_field(field_key)` — the raw field dict (so a caller can read `type`, `options`,
  `max_items`, `min_length`, ...), or `None` for an unknown key.
* `client_visible_schema()` — the full schema with every `admin_only` section dropped from
  `sections`. Today: 13 sections. Every other key of the schema dict (`title`, `submit`,
  `version`, `subtitle`, `product_slug`, `save_as_you_go`, `schema_version`,
  `estimated_minutes`, `field_types_reference`) is preserved verbatim.

Derive all four at import from the already-loaded `CANONICAL_TEMPLATE_SCHEMA` and store them
in module-level constants; the functions are thin accessors. The JSON is read once at import
today (`intake_canonical.py:34`) and re-reading it per request would be a per-request file
read on the hot path.

`client_visible_schema()` must hand back a structure a caller cannot use to mutate
`CANONICAL_TEMPLATE_SCHEMA`. Build it with `copy.deepcopy` **once at import**, then return that
constant. (One deep copy at import, never per request.)

## WHAT THIS PLAN MUST NOT DO

- **Do NOT hand-write any field key** — not in the module, not as a fallback, not "for
  clarity". The whole decision is that the derivation is the only source.
- **Do NOT read `section["key"]`.** Sections carry `id`. A walker keyed on `key` returns an
  empty set and every downstream filter silently becomes a no-op — the exact failure shape
  D-23.2-02 exists to prevent.
- **Do NOT add a field-level `admin_only` reader.** No field carries the flag today; inventing
  support for one is scope the schema does not ask for. (Reading it if present is fine as a
  one-line `or`; building a policy around it is not.)
- **Do NOT change any consumer.** This plan adds the module surface and nothing else. No route,
  no skill, no test outside the new file changes here.
- **Do NOT touch `CANONICAL_TEMPLATE_ID`, `CANONICAL_TEMPLATE_NAME` or
  `CANONICAL_TEMPLATE_SCHEMA`.** Downstream code and `tests/test_intake_routes.py:563` import
  them by name.
