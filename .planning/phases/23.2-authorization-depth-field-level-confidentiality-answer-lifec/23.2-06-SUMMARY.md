# Phase 23.2 Plan 06: Role-Based Response Projection (F-01 hops 1, 2, 4a) Summary

Server-side field-level confidentiality on the three client-readable intake routes: the four
`admin_only` answer keys, the two admin-only `output_parsed` members and the admin-only template
section are now withheld from any caller whose role is not exactly `superadmin` — all three
routes still answering EXACTLY 200.

## What changed

`app/data/pulse_intake_v1.json` marks the `strategic_perspective` **section** `admin_only`, and
that section's own description reads *"Visible only to admin, not to the client and not in the
handoff PDF."* Until this plan the flag was honoured **only in the browser**
(`IntakeForm.tsx:164`, `intake.$id.results.tsx:163`). Three routes handed the operator's private
bias-radar and blind-spot analysis **of a client, to that client**.

### `backend/app/api/intake_routes.py`

Two NAMED private helpers added beside `_answer_view`:

| Helper | Rule | Why named |
|---|---|---|
| `_visible_answer_rows(rows, *, role)` | drop rows whose `field_key` ∈ `admin_only_field_keys()` | **Plan 23.2-09 imports this and defines nothing.** `upsert_answers` returns the SAME `list_for_intake` list, so an inline filter here would let a client read back through a PATCH exactly what the GET withheld. One owner, one definition. |
| `_visible_output_parsed(parsed, *, role)` | drop top-level `K` if `K ∈ admin` **or** any admin key `A` satisfies `A.startswith(K + "_")` | The nested blind-spots parent is **not itself a field key**, so a plain membership test leaks the whole object. The `startswith` clause is the entire reason the helper exists. |

Both derive from `app.intake_canonical`. Polarity is `!= "superadmin"` in all three places —
deny by default, so a future role is withheld-from by omission rather than leaked to.

Handlers: each gained `identity: Identity = Depends(get_current_identity)` as its **last**
parameter (no role gate exists on any of the three, so CONTEXT § 11 trap 3 does not apply).
`get_skill_run_full`'s 404 arms are untouched. `list_templates` stays DB-free and **serialises**
the shared `client_visible_schema()` object — it never mutates it.

### Derived drop rule — verified arithmetic

Against today's 4 admin keys and the 7 `output_parsed` keys the rule drops **exactly 2**
(`bias_radar`, `blind_spots`) and keeps **exactly 5**. Pinned as a **set equality** in the test,
which fails on an under-drop (the disclosure) *and* on an over-drop (a broken client proposal
tick, `IntakeForm.tsx:16`).

## Deviations from plan

### 1. [FALSE ACCEPTANCE CRITERION] The "JSON list `output_parsed` → 200" behaviour is unreachable

**Plan text (Task 1 `<behavior>`):** *"`output_parsed` is a JSON list (a legacy/odd row) -> 200,
value returned unchanged, no 500."*

**Measured:** `SkillRunFullView.output_parsed` is declared `dict | None`
(`intake_routes.py:209`). Constructing the response model with a list raises **before any
projection runs**:

```
ValidationError: 1 validation error for SkillRunFullView
output_parsed
  Input should be a valid dictionary [type=dict_type, input_value=[1, 2], input_type=list]
```

This is a **pre-existing** handler behaviour at `7af9bcc`, entirely independent of
D-23.2-03. Making the route answer 200 there would require **widening a pinned client route's
response contract** — which neither D-23.2-03 nor D-23.2-04 authorises, which no threat in the
register asks for, and which is exactly the "contorting the code to satisfy a criterion" the
plan's own closing section forbids. **I did not widen it.**

**What I did instead:** the true, in-scope half of the criterion — *"a projection must never 500
on odd data"* — is about the helper, and it is pinned where it is true, as a direct unit test:
`test_visible_output_parsed_helper_is_total_on_non_dict_values` asserts
`_visible_output_parsed(x, role=...) is x` for a list, a str, an int and a bool, both roles, plus
`None`. The helper is total; the response model is a separate, older contract. The reasoning is
written into that test's docstring so the next reader does not re-litigate it.

### 2. [SELF-CONTRADICTORY CRITERION] Verification gate 4 vs. the Task 2 action instruction

**Task 2 `<action>` says:** *"Put the rule in ONE private helper in `intake_routes.py` with a
docstring **naming the `blind_spots` case** as its reason for existing."*

**Verification gate 4 says:** `grep -c "bias_radar\|blind_spots" backend/app/api/intake_routes.py`
returns **0**.

These cannot both hold literally — a docstring naming the case makes the grep non-zero. My first
implementation followed the action instruction and the gate measured **2** (both hits in the
docstring, neither in code).

**Resolution:** I honoured the *purpose* of both. The gate exists so no key literal drives
policy; the action exists so the nested case is explained. The docstring now names the case
structurally ("its parent key is NOT itself a field key, but its three members map one-for-one
onto three admin field keys that share that parent as their prefix") and points at
`app/ai/prompts.py:139-145` and `AIReviewPanel.tsx:127-129` for the names, rather than repeating
them. Gate 4 now measures **0** and the explanation is intact. Flagging it so plan 23.2-11 knows
the two instructions conflict as written.
