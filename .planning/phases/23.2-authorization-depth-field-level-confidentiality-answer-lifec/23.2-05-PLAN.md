## THE SHAPE (both handlers, identically)

Keep the `select(...).scalar_one_or_none()` read and BOTH existing guards. They classify the
refusal (404 vs 409) and — for `resume_run` — the source gate at
`tests/test_checkpoint_resume.py:429` asserts `"scalar_one_or_none" in src`,
`"HTTPException(404" in src`, `"409" in src` and `"403" not in src`. Deleting the read to
"simplify into one UPDATE" breaks that gate and turns a cross-tenant 404 into a cross-tenant
409, which is an existence oracle.

Then REPLACE the attribute assignment with a conditional UPDATE:

```python
result = await session.execute(
    sa_update(Run)
    .where(Run.id == run_id, Run.status == <expected literal>)
    .values(status="queued", worker_id=None, ...)
    .execution_options(synchronize_session="fetch"),
)
if result.rowcount == 0:
    raise HTTPException(409, "<the same message the read-check raises>")
```

Four points, each of which has bitten this repo before:

1. **`synchronize_session="fetch"`.** The default `"evaluate"` compares the `run_id` value
   against the loaded instance's attribute in Python and does not reliably sync, leaving the
   already-loaded `run` STALE — so `RunResponse.model_validate(run, ...)` would return the
   PRE-flip status and the caller would see `parked` on a successful resume. The backend line
   learned this the hard way; `db/repository.py:104-118` documents the identical trap.
   Alternatively re-`select` the row after the UPDATE and validate THAT. Either is acceptable;
   returning the stale instance is not.
2. **The tenant scope is not weakened.** The UPDATE runs on the same session, which carries the
   `SET LOCAL app.tenant_id` from `get_db_session` (`auth/deps.py:149-177`), so FORCE-RLS
   applies to it exactly as it applies to the SELECT. Adding a `status` predicate can only
   narrow the match.
3. **`rowcount == 0` is indistinguishable** between "the precondition no longer holds", "the row
   is gone" and "the row belongs to another tenant" — all three are 0 by design. Raise the SAME
   409 the read-check raises; do NOT re-read to tell them apart, and do NOT let a re-read become
   the precondition.
4. **The message must match the read-check's, byte for byte.** Two different 409 strings let a
   caller distinguish "you lost the race" from "it was never parked" — a small oracle, and free
   to avoid.

## `submit_report_spec` — THE OUTPUT ROW MUST NOT SURVIVE A LOST RACE

`submit_report_spec` inserts an `Output(format="report_spec")` BEFORE the flip. Do the CAS
FIRST, then insert the Output only if `rowcount == 1`. That is the simplest correct order.

If you keep the insert first: `get_db_session` yields inside `async with session.begin()`
(`auth/deps.py:173-177`), so an HTTPException raised from the handler propagates through the
generator and the transaction ROLLS BACK — the Output would not persist. That is true today, but
it is an implicit dependency on a dependency's internals. Prefer the explicit order, and assert
the outcome either way: **after a lost race there is exactly ONE `report_spec` Output for the
run, not two.**
