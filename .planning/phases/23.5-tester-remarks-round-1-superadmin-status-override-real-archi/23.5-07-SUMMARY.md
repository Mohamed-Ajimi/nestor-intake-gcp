## The import derivation — and what it changed

The surface was derived by walking each deployed entrypoint's transitive imports with a static
AST walker that counts **module-level and function-level** imports (the DEF-23.3-01 worker bug
was a lazy import, so a module-level-only walk is not conservative enough).

| service | entrypoint | reaches `runtime_flags` | carries the env |
|---|---|---|---|
| `tribunal-worker` | `python -m nestor_pulse_sdk.runs.worker_main` | yes — `runs/worker.py` → `runs/adapter.py` → `pipeline/tribunal/pipeline.py`; also `pipeline/orchestrator.py` → `citations/extractor.py` | **YES** |
| `tribunal-api` | `uvicorn nestor_pulse_sdk.server:app` | yes — module-level via `citations/__init__.py` → `citations/extractor.py`, **and at request time** via `runs/api.py` → `verification/report.py` → `citations/numbering.py` | **YES** |
| `nestor-api` | `backend/app/main.py` | no | no |
| `nestor-frontend` | Nitro SSR | no (not Python) | no |

**`tribunal-api` is the one a careless derivation gets wrong.** `runs/api.py:1156` lazily
imports `verification/report.py`, which calls `citations/numbering.py::number_citations(...)`,
which reads `citations_v2()`, `primary_anchor()` and `render_resolved()` **at call time** to
choose the claim→source ordering. With the flag on the worker and off the API,
`GET /api/runs/{run_id}/verification` would renumber the report the worker wrote and one `[n]`
would mean two different sources depending on which service you asked.

`nestor-api` was excluded on evidence, not assumption: `grep -rn nestor_pulse backend/app/`
returns only comments, docstrings and alembic prose. The two services talk over HTTP.

**Count check:** `grep -c 'NESTOR_CITATIONS_V2' infra/main.tf` == **2** == the number of
services the derivation named.

## ⛔ The correction that matters most: DEV IS NOT TERRAFORM-MANAGED

The plan's Task 2 step 7 says `terraform -chdir=infra apply -var-file=env/dev.tfvars`.
**That must not be run.** `infra/env/dev.tfvars` says so in its own header and
`infra/env/dev.gcs.tfbackend` says it twice: the dev project has **no Terraform state
anywhere** — its resources were created by hand across phases 2–23, the state bucket does not
exist, and a plan from an empty state shows every resource as a CREATE.
`google_sql_database_instance.main` carries `deletion_protection`, so such an apply would
half-apply and leave dev in an unknown state.

**Measured confirmation that an apply would also be destructive on its own terms:** the live
dev `tribunal-worker` and `tribunal-api` both carry `SERPAPI_API_KEY` from the `Nestor_SERP`
secret, which `infra/main.tf` does not declare at all. A converging apply would strip it.

On dev the flags are set **in place** with `gcloud run services update --update-env-vars`,
which is additive (it leaves the other seven `NESTOR_*` names and every `secret_key_ref` alone)
and sticky (a later `services update --image`, which is what `promote.sh` does, preserves it).
The worker goes last, behind a green `infra/queue-check.yaml`, because a worker revision boots
the poll loop and the loop claims first and sleeps last. The exact commands are in the runbook.

- **Files created:** `infra/release-client.sh`. **Commit:** `66f79b2`. Documented in the runbook
