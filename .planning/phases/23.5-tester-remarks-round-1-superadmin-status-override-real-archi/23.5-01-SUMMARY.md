# Phase 23.5 Plan 01: Superadmin Status Override Summary

A superadmin can now set an intake to any of the seven allowed statuses — backwards
(`delivered` → `reviewed`) and sideways (anything → `archived`) included — through a new
audited `POST /intakes/{id}/status` verb wired to the intake detail page's existing select;
`in_research` is refused 409 server-side and rendered unselectable client-side because it is
the one status that costs money.

## What was built

**Backend — `backend/app/api/intake_routes.py`**

- `StatusOverride(BaseModel)` with a single `status: str`, placed beside `IntakePatch`.
  `IntakePatch` is untouched and still declares exactly one field (`client_name`), so
  `patch_intake`'s refusal to carry a status — the TENANT-02 / INTAKE-05 shape — never had
  to be relaxed.
- `_OVERRIDE_STATUSES: frozenset[str]` (the 7 allowed) and `_OVERRIDE_FORBIDDEN:
  frozenset[str]` (`{"in_research"}`), added below `_DELIVER_TRANSITIONS` with the reason
  for the exclusion written out: `research_routes._RESEARCH_TRANSITIONS` is the sole lawful
  writer of `in_research` because entering it queues a paid Tribunal run, and an override
  able to set it would leave an intake claiming research is in flight with no run behind it.
- `override_status` on `@intake_router.post("/{intake_id}/status")`. Signature order is
  `intake_id, body, Depends(superadmin_gate), Depends(get_tenant_repo)` — gate before repo,
  so a null-space caller gets the gate's 404 rather than the repo's 403. Precedence is
  404 (not in scope) → 409 (forbidden status) → 422 (unknown status), and both refusals run
  before `repo.patch`, so a refused call leaves the row untouched. One `audit_log` row per
  accepted call, `metadata={"from", "to", "override": True}`, written on `repo.session` in
  the same transaction.

**Backend tests**

- `backend/tests/test_status_override.py` (new): the 7×7 transition matrix asserted on the
  RE-READ ROW (not the response body alone), the `in_research` 409 + unchanged row + zero
  audit rows, four unknown-status 422 cases, own-space `user` 404 with no side effect,
  null-space `user` 404 (the ordering proof), cross-tenant 404 with the foreign row
  re-read as its owner, missing-intake 404, and the single `{from, to, override}` audit row.
  Plus three tests that need no DB: the allow-list is derived from the ORM enum, the
  forbidden set has exactly one member, and `IntakePatch` still carries no status field.
- `backend/tests/test_operator_verb_gate.py`: the route appended to `_GATED_VERBS`, so both
  structural audits (shared-gate presence, gate-before-repo ordering) now cover it.
- `backend/tests/test_client_surface_open.py`: the route pinned in `_PINNED_INTAKE_ROUTES`
  as an operator verb.

**Frontend**

- `overrideIntakeStatus(id, status)` in `src/lib/api/intakes.ts`, in the Transitions block
  under `reviewIntake`.
- `NAMED_TRANSITIONS` in `admin.pulse.intakes.$id.tsx` with exactly the three natural
  forward edges, mirroring `_SUBMIT_TRANSITIONS` / `_REVIEW_TRANSITIONS`. `handleStatusChange`
  routes a hit to the named verb (so completeness and the `admin_validated` mail still fire)
  and every miss to the override. The `statusUnavailable` dead end is gone from the function.
- The `in_research` option renders `disabled` unless it is the current status.
- `statusOverridden` / `statusOverrideFailed` / `statusInResearchBlocked` added to
  `intakeDetail.toast` in en, nl and fr, key-identical.
- `src/lib/intake-phase.test.ts` extended with 256 generated cases (8 statuses × 4 artifact
  combinations × 4 skill-run shapes × 2 `hasResearchArtifacts` values) asserting
  `derivePhase` returns a member of the 12-value `Phase` union and never throws, plus named
  cases for the `delivered` → `reviewed` rewind and for `archived` with artifacts present.

## Side effect worth naming: remark 3's archive button now works

`onArchive` → `confirmArchive` → `handleStatusChange("archived")` has existed on this page
all along and silently failed with the "status unavailable" toast, because nothing could
reach `archived`. With `archived` in `_OVERRIDE_STATUSES` and the dead end removed, that
button now performs the archive. Plan 23.5-03 still owns the list filter, the delete verb
and the research-run 409 (D-23.5-02); only the button's wiring is fixed here.

- **Fix:** `test_override_forbidden_set_has_exactly_one_member` pins the invariant the

- **Files modified:** `backend/tests/test_status_override.py`
- **Commit:** `7d192b7`

### Plan corrections

**4. The plan's named phase-machine case had an incomplete input**

The plan asked for: status `reviewed` + `final_report_artifact_id` set +
`results_link_sent_at` set → must return `awaiting_client_validation`. Read against
`intake-phase.ts`, the `reviewed` branch keys **only** on `validation_link_sent_at`, so that
exact input returns `awaiting_validation_send`, not `awaiting_client_validation`.

The realistic shape is the one the plan was reaching for: an intake that genuinely reached
`delivered` passed through the validation step, so it carries `validation_link_sent_at` too.
Both cases are now pinned explicitly — with the stamp → `awaiting_client_validation`,
without it → `awaiting_validation_send` — and each carries a comment saying which real
situation produces it. Nothing in `intake-phase.ts` was changed.

**5. There is no meaningful "superadmin cross-tenant 404" arm**

The plan's behaviour list asked for "a superadmin targeting an intake in another space
returns 404". A superadmin's repo is the `app_superadmin` engine with the 0003 bypass policy
(`get_tenant_repo`, D-05) — cross-tenant reach **is** the operator's designed authority, and
every other operator verb behaves that way. Asserting a 404 there would have pinned the
opposite of the platform's contract. Implemented instead as two honest arms:
`test_override_cross_tenant_404_foreign_row_untouched` (a `user` in space A against space
B's intake, foreign row re-read as its owner and asserted unchanged) and
`test_override_missing_intake_404` (a superadmin against an id that does not exist, which
exercises the `repo.get -> None` branch on the authorized path). The reasoning is recorded
in the test module's docstring, not just here.

### Finding recorded rather than coded (as instructed)

**No role check was added to `admin.pulse.intakes.$id.tsx`.** Verified at
`frontend/src/routes/admin.tsx:27-46`: `AdminLayout` reads `isSuperadmin` from `useAuth()`
and renders the access-denied wall in place for anyone else, so a client user cannot reach
the intake detail page at all. The backend `superadmin_gate` is the authority regardless. A
second check in the route would be redundant UX gating that could drift out of step with the
wall above it.
