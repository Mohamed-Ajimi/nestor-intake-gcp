# Phase 23.5 Plan 08: Gap Closure — In-Flight-Only Delete + Bulk Actions Summary

The hard-delete wall moved from "this intake has ever had research" to "research is
running on it RIGHT NOW", the `intake.deleted` audit row now carries the pointers to the
deliberately-retained tribunal runs the cascade orphans, and a superadmin can tick several
intakes on the list and archive or delete them in one action behind a single typed
`DELETE`.

## What was built

### Task 1 — the wall becomes in-flight-only (D-23.5-06)

**`backend/app/research/run_status.py`**

`RESEARCH_IN_FLIGHT = frozenset({"queued", "running", "needs_report_spec"})` plus
`is_research_in_flight()`, with the derivation written into the module docstring as a fifth
numbered point in the register of the four already there. The point argues rather than
asserts:

- the set is the COMPLEMENT of `_RETRYABLE_RUN_STATUSES` ∪ `RESEARCH_TERMINAL` over the
  nine measured statuses — the same derivation migration 0016 writes out for its partial
  unique index;
- `needs_report_spec` is the member that is easy to miss and it IS in flight (a run sitting
  there is alive, awaiting an operator's report spec, and `POST /report-spec` re-queues
  that SAME run);
- `needs_input` is the mirror trap — it is RETRYABLE, so it is NOT in flight;
- the set is POSITIVE by design, so an unknown future engine status counts as NOT in
  flight, which fails toward **allowing** the delete. That is the correct direction here
  for the same reason 0016 gives: a negated predicate leaves an intake blocked permanently
  with no operator remedy, and D-23.5-06's whole point is that the operator must be able to
  delete;
- do NOT import the set from the alembic revision — migration modules are historical
  records of what ran, not importable app code.

This module was the right home because it is dependency-free and already owns the intake
side's copy of the Tribunal status vocabulary. Putting the set in `intake_routes.py` would
have given the repository a FOURTH copy of a vocabulary that already exists in three
places.

**`backend/app/api/intake_routes.py`**

- `_has_research_runs` → `_research_runs_for_intake` (ALL rows, one scoped read on the
  handler's existing session) + `_inflight_research_runs` (the filter). `delete_intake`
  reads the list ONCE and derives both the 409 and the audit metadata from that single
  snapshot — two separate reads could disagree and the audit row would then describe a
  state that never existed.
- `_DELETE_BLOCKED_REASON = "research_in_flight"` as the ONE machine token, used by both
  `DeletableView.reason` and the 409 path. The frontend keys its localized copy off it and
  a second spelled-out literal at either site is exactly how the two drift.
- `_DELETE_BLOCKED_DETAIL` reworded from `"Intake has research runs and cannot be deleted"`
  — a statement about HISTORY, now simply false as a reason — to
  `"Research is in flight for this intake and it cannot be deleted"`.
- The audit metadata gains `"research_runs"` (the count the cascade destroyed) and
  `"tribunal_run_ids"` (their non-null pointers, nulls dropped). The code says why:
  `tribunal_run_id` is a plain `String` with no FK, the tribunal rows live in their own
  schema and are deliberately RETAINED, so once the cascade takes the nestor-side row this
  audit row is the only thing left that can point at the retained record.
- The section header comment QUOTES D-23.5-02's superseded rule, then explains why its
  premise was wrong: the audit chain it meant to protect lives in the `tribunal` schema
  (no FK into `nestor`) and in the audit bucket (whose keys this handler never enumerates).
  All of it survives the delete, so refusing for a stopped run protected nothing. An
  IN-FLIGHT run is the real hazard — a worker is writing to rows this DELETE would cascade
  away and `reconcile.py` is scanning for exactly those statuses.
- The wall stays exactly where plan 02 put it: before key collection and before the audit
  write, so a refused delete remains a true no-op.

**`backend/tests/test_intake_delete.py`** — extended, not rewritten. 16 tests → 33.

- The eligibility and 409 arms are parametrized over the IMPORTED sets
  (`RESEARCH_IN_FLIGHT` vs `RESEARCH_TERMINAL | _RETRYABLE_RUN_STATUSES`), so the suite
  pins the contract and not a re-typed copy of it.
- `test_delete_succeeds_with_a_terminal_run_and_takes_the_research_rows` — 204 and the
  `research_runs` rows are gone, with a **pre-assertion** so it cannot pass vacuously.
- `test_delete_is_409_when_a_terminal_and_an_in_flight_run_coexist` — the wall is "ANY row
  in flight", never "the newest row". Both rows seeded so ordering cannot make it pass by
  luck.
- `test_delete_audit_row_records_the_destroyed_runs_and_their_tribunal_ids` — one run with
  a tribunal id and one without, so the handler must list the non-null pointers and drop
  the rest rather than emitting a `null` into the trail.
- Two no-DB pins: the three-way set partition over the nine measured statuses (a tenth
  status turns this red and FORCES the classification), and `RESEARCH_IN_FLIGHT` against
  `ResearchRun.__table__`'s `uq_research_runs_one_inflight_per_intake` predicate — read off
  the MODEL, because a grep of the source file matches a comment just as happily as code.
- `_insert_research_run` gained `tribunal_run_id`; `_scenario`'s `with_research_run` now
  threads a status sequence rather than only a bool, so the both-runs case has one seeding
  path instead of two.

### Task 2 — multi-select with bulk Archive / Delete (D-23.5-07)

**`frontend/src/lib/intake-bulk.ts`** (new, pure): `toggleSelected`, `headerState`,
`toggleAllVisible`, `pruneSelection`, `partitionForArchive`, over `ReadonlySet<string>` /
`readonly string[]`, all returning NEW values. The module docstring records WHY it is
extracted — the route has no component test harness in this repo (no RTL, no jsdom, no
route test anywhere under `src/routes/`), so anything inline in the TSX is covered by `tsc`
and nothing else, and the thing on the other end of the selection is an irreversible delete
— and names the select-all-visible semantics explicitly: it operates on the FILTERED rows,
because a header control that reached rows off screen would destroy intakes the operator
never looked at.

**`frontend/src/lib/intake-bulk.test.ts`** (new, 22 tests): each case says what it defends.
The not-mutated cases (React bails out on a reference-identical state value, so a mutating
toggle leaves the bulk bar showing the previous count — the count next to the delete
button), the empty-visible-list header state, the "completes, never inverts" rule for
`toggleAllVisible`, and both directions of the selected-but-not-visible case.

**`frontend/src/routes/admin.pulse.intakes.index.tsx`**

- A leading checkbox column. The header checkbox is driven by
  `headerState(selected, filtered.map(r => r.id))`, with `indeterminate` set through a ref
  callback — a `some` state that renders identically to `none` invites a click that selects
  rows the operator did not mean to, one button away from a delete. The raw
  `<input type="checkbox" className="h-3.5 w-3.5 accent-ink">` idiom matches the
  show-archived toggle rather than introducing the shadcn `Checkbox`.
- The row checkbox cell carries `onClick={(e) => e.stopPropagation()}` — the row's own
  `onClick` navigates, so without it a tick becomes a navigation.
- The table went 4 → 5 columns: both `colSpan={4}` → `colSpan={5}` and the skeleton's
  per-row `Array.from({ length: 4 })` → `{ length: 5 }` (the outer `{ length: 3 }` row loop
  is untouched).
- A `pruneSelection` effect on `intakes`, so a deleted or refetched-away row cannot stay in
  the count.
- The bulk bar (count, Archive, Delete, Clear; all disabled while `bulkBusy`) renders only
  when something is selected.
- **Bulk Archive**: `partitionForArchive` first, `archiveNone` toast and stop when
  `toArchive` is empty; otherwise a SEQUENTIAL `for ... of` with `await` over
  `overrideIntakeStatus(id, "archived")` (each call writes an audit row server-side, so a
  parallel storm is a burst against the same transaction path for no benefit on a hand-made
  selection). Rows flip in place and leave through the existing `showArchived` filter; one
  summary toast; selection cleared.
- **Bulk Delete**: ONE dialog in the detail page's hand-rolled overlay shape
  (`role="alertdialog"`, red border) naming the count AND listing the selected project
  names, requiring the literal confirm word read from `intakeDetail.delete.confirmWord` —
  not copied into `intakesList.bulk`, because the word is one contract with the backend and
  a second copy is how the two dialogs drift. The match is checked on `disabled` and again
  inside the handler. On confirm, sequentially: `getIntakeDeletable(id)` → failed read
  counts `failed`, `deletable === false` counts `blocked`, otherwise `deleteIntake(id)`
  counts `done`/`failed`. The eligibility read is never skipped: the backend would 409
  anyway, but that read is what lets the summary distinguish "refused because research is
  in flight" from "failed", which is the entire point of reporting three counts.
- **No fourth role check.** The page sits behind `AdminLayout`'s superadmin wall
  (`admin.tsx:38`, `useAuth().isSuperadmin`) and all three endpoints re-derive authority
  server-side per call.

**Locales** — `intakesList.bulk.*` (13 keys) added key-identical across en/nl/fr with
`{{n}}` (never `{{count}}`, which i18next reads as the plural selector), and
`intakeDetail.delete.blockedResearch` rewritten in all three languages.

  and the `deleteIntake` doc rewritten to the in-flight rule, with an explicit "⛔ the token

- **Files modified:** `frontend/src/lib/api/intakes.ts`
- **Commit:** `6592494`

### Plan corrections

**2. The RED for task 1 is a collection ERROR, not a set of test failures**

The plan asked for the in-flight set to be imported into the test rather than re-typed. Done
— but that means at HEAD the module cannot import at all, so the file fails to COLLECT and
pytest reports one error instead of N failures. That is deliberate and it is the stronger
red: the tolerant alternative (`getattr(run_status, "RESEARCH_IN_FLIGHT", frozenset())`)
would leave the parametrized arms with an EMPTY id list and pass **vacuously** — a green
suite proving nothing, which is this project's most-recorded gate failure.

To keep an honest behavioural RED on record, the constant was stubbed into
`run_status.py` as a throwaway, the suite run (**16 failed, 17 passed**), and the stub
reverted with `git checkout --` before the test commit. The RED commit contains the test
file only.

**3. `delete_intake` filters inline rather than calling `_inflight_research_runs`**

Both helpers exist and are used (`_inflight_research_runs` serves the eligibility read;
`_research_runs_for_intake` serves the delete path). The delete path applies the predicate
inline over its already-read list instead of calling the filter helper, because calling it
would issue a SECOND scoped read — the exact thing the plan's "read once, same snapshot"
instruction exists to prevent. The `ast` acceptance gate (both `FunctionDef`s present) is
green either way.
