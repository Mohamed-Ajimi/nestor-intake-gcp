<objective>
Make the research notification mails name the CLIENT as well as the PROJECT (D-23.5-08), and
make opening an intake in the admin switch the top-bar client dropdown to that intake's client
(D-23.5-09).

Purpose: gap closure. The client tested the 2026-09-24 prod release and reported two things.
The research-completed mail says "Het onderzoek voor **Rocketship** is afgerond." — that is the
PROJECT name only, so a reader with several clients cannot tell whose research finished. And
following that mail's "Open onderzoek in admin →" link opens the intake while the top bar still
shows whichever client was selected last, so the page and the dropdown disagree about who the
operator is looking at.

Output: one new context value (the space name) threaded into seven mail call sites across two
modules, nine one-line template edits, one shared subject helper, one pure frontend predicate
with its own unit tests, and three routes wired to it.

<operator_rulings>
Both rulings are dated **2026-09-24**, after the client tested the prod release that shipped
plans 01-08. They ADD to phase 23.5; they contradict nothing already built.

**D-23.5-08 — the research mails name the CLIENT and the PROJECT.**
Today the body names the project alone. It must name both, e.g.
`Het onderzoek voor <client> — <project> is afgerond.` The subject gains
` — <client> / <project>` after its existing sentence. Note the two separators differ and that
is deliberate: the subject already uses an em dash to attach the qualifier, so the client and
project are separated inside it by a slash.

**D-23.5-09 — opening an intake sets the active client.**
When the intake detail page has loaded an intake whose `space_id` differs from the current
`activeSpaceId`, the active client becomes the intake's — **including when "All clients"
(null) is selected**. The operator's words: it should ALWAYS match and preload. The same for
the admin-shell sub-routes that render a single intake's run. Client-facing routes
(`intake.$id.tsx` and its children) are NOT touched.
</operator_rulings>

<naming_trap>
**Read this before writing a single line.** This plan threads a value called `client_name`
through modules where `client_name` already means something else, and plan 23.5-03 exists
because exactly this confusion shipped false copy once.

| name | what it actually is |
|---|---|
| `intakes.client_name` (DB column) | the operator's free-text label for ONE intake. Since plan 03 the UI calls it the **PROJECT name**. The column was deliberately NOT renamed (D-23.5-03, label-only). |
| `ctx["project_title"]` | `intake.client_name or "dit intake"` — so this is the **project**. |
| `ctx["client_name"]` (NEW, this plan) | `organizations.name` for the intake's space — the **real client / tenant**. |
| `render_admin_validated(client_name=...)` | already means the client in that template's markup (plan 03 reworded the sentence around it). The new render kwarg matches this meaning, not the column's. |

The operator named the new key `client_name`, so that is the key. Write the table above, in
prose, at the definition site in `load_trigger_context` and at the render-layer signature. A
later reader who assumes `ctx["client_name"]` is the column will put the project name in the
client slot and ship the phase-23 shape again: a label asserting the opposite of its own value,
with every gate green.
