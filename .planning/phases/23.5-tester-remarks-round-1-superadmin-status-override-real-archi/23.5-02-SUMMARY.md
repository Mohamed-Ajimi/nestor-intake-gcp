# Phase 23.5 Plan 02: Archive + Guarded Hard Delete Summary

A superadmin can now destroy an intake that has never had a research run — its answers,
skill runs, uploads, transcripts, artifacts and its own GCS objects go with it, recorded in
an `intake.deleted` audit row that outlives the cascade — while an intake with ANY
`research_runs` row is refused with 409 and left byte-for-byte alone; archived intakes drop
out of the default list behind a `show archived` toggle, and the delete is offered only when
the backend says so and only behind a typed `DELETE` confirmation.

## What was built

**Backend — `backend/app/db/repository.py`**

- `TenantRepository.delete(row_id) -> int`, the generic scoped DELETE, copying
  `IntakeSourceRepository.delete_by_storage_path`'s idiom exactly (`self._scope(delete(...))`,
  `synchronize_session=False`, return `rowcount`). The docstring records that `rowcount == 0`
  is the existence-hidden outcome (absent OR foreign — deliberately indistinguishable, D-07)
  and that the DB's eleven `ON DELETE CASCADE` foreign keys, **not** this method, remove the
  children. That choice is argued rather than assumed: RI cascades are exempt from row
  security, run inside the same statement, and cannot half-finish; an application-side loop
  over eleven tables could.
- `ResearchArtifactRepository.list_for_intake` — deliberately WITHOUT the
  `source == "context-pack-generator"` filter its two neighbours carry. Those are display
  readers (T-7-09-05); this one feeds the delete path and must see the delivered report
  artifact too, or the report PDF is orphaned in the bucket with no row left pointing at it.

**Backend — `backend/app/api/intake_routes.py`**

- `_DELETE_BLOCKED_DETAIL` (module constant) and `DeletableView` (`deletable: bool`,
  `reason: str | None`, where `reason` is a stable machine token, never prose).
- `GET /{intake_id}/deletable` → `intake_deletable`. Superadmin-gated despite being a pure
  read: ungated it answers "this intake exists, and it has had research" to anyone holding
  an id (T-23.5-02-I). The out-of-scope answer is the same existence-hidden 404, never
  `{"deletable": false}`. Its docstring states it is ADVISORY — `delete_intake` re-checks
  the wall in its own transaction, so a run queued between the two is still refused.
- `DELETE /{intake_id}` → `delete_intake`, 204. The seven-step sequence is in the docstring
  because the ORDER is the security property:
  1. `repo.get` → None → 404 (ownership first, so a miss leaks nothing about research);
  2. any `research_runs` row → 409 `_DELETE_BLOCKED_DETAIL` (D-23.5-02) — **before** key
     collection and **before** the audit write, so a refusal is a true no-op;
  3. keys collected from `intake_sources` + `research_artifacts`, read out of the DATABASE;
  4. every key prefix-asserted against `{space_id}/{intake_id}/`; a failure is dropped,
     counted and `_log.warning`'d, never a reason to refuse the delete;
  5. the `intake.deleted` audit row on `repo.session` BEFORE the delete;
  6. `repo.delete(intake_id)`, `rowcount == 0` → 404;
  7. object cleanup LAST, as a `BackgroundTasks` task, i.e. after the transaction commits.
- Two helpers carry the reasoning: `_collect_intake_object_keys` (the DB-enumeration +
  prefix wall, de-duplicating, skipping NULL `storage_path`) and `_delete_objects_best_effort`
  (try/except per key, explicitly documented as "never call with an unvalidated list").

**Backend tests**

- `backend/tests/test_intake_delete.py` (new, 16 tests): the cascade over five child tables
  with a pre-assertion so it cannot pass vacuously; the 409 with four separate
  nothing-moved assertions (children, the run row, the GCS recorder, the audit table); both
  sides of the eligibility read; the surviving audit row including its `objects` /
  `objects_skipped` metadata; the GCS **set equality**; role=`user` 404 on both routes with
  a survival check; the null-space ordering proof parametrized over both routes;
  cross-tenant 404; missing-id 404 on both routes. Plus two no-DB schema pins: `audit_log`
  has no FK to `nestor.intakes`, and every cascade child really declares `ondelete="CASCADE"`.
- `test_operator_verb_gate.py`: both routes appended to `_GATED_VERBS`; the ordering audit's
  guard counter `9 → 11`.
- `test_client_surface_open.py`: both routes pinned as operator verbs.

**Frontend**

- `getIntakeDeletable` / `deleteIntake` in `src/lib/api/intakes.ts`, with the contract
  written down that a FAILED eligibility read means "do not offer the affordance", never
  "deletion is blocked".
- `admin.pulse.intakes.$id.tsx`: `deletable` is a THREE-state (`null | true | false`) fetched
  once per intake. `null` — unanswered, failed, or the non-superadmin 404 — renders no
  control at all, so "we could not ask" can never look like "yes". `false` renders the button
  **disabled with the reason** rather than hidden. The confirm dialog requires typing the
  literal `DELETE`; the match is checked both on the button's `disabled` and again inside
  `confirmDelete`, because a disabled attribute is an affordance, not a guard. On success it
  navigates to `/admin/pulse/intakes` — the page's subject no longer exists.
  **`confirmArchive` is unchanged**: plan 23.5-01 already made it work.
- `admin.pulse.intakes.index.tsx`: `showArchived` state, the filter condition, and a toolbar
  checkbox. An explicit `status=archived` selection shows archived rows regardless of the
  toggle, encoded as its own named condition (`archivedExplicitlySelected`) rather than left
  as a side effect of filter ordering; the checkbox renders checked-and-disabled in that
  state so it does not look live while being inert.
- `intakesList.showArchived` + the eight `intakeDetail.delete.*` keys in en/nl/fr,
  key-identical, with `confirmWord: "DELETE"` in all three (the contract is the word, not its
  translation).

### Plan corrections

**5. The 204 cannot report a skipped-object count**

The plan's `<behavior>` list says the out-of-prefix key "is reported in the response count as
skipped", while its `<action>` specifies `status_code=204`. Those contradict: a 204 carries no
body. Inventing a 200-with-body for a destruction verb would be the worse fix — a caller could
not tell "deleted" from "reported".

Implemented instead as **audit metadata**: the `intake.deleted` row carries
`{"status", "objects", "objects_skipped"}`, and each dropped key is `_log.warning`'d with its
value and the prefix it failed. That is strictly better than a response field — it is durable,
it is greppable in Cloud Logging, and it survives the request. `test_delete_writes_an_audit_row_that_survives_the_cascade`
asserts all three metadata fields.

**6. There is no meaningful "superadmin cross-tenant 404" arm** (carried forward from 23.5-01)

The plan's behaviour list asked for "a superadmin targeting another space's intake gets 404".
A superadmin's repo is the `app_superadmin` engine with the 0003 bypass policy
(`get_tenant_repo`, D-05) — cross-tenant reach **is** the operator's designed authority, and
every other operator verb behaves that way. Asserting 404 there would pin the opposite of the
platform's contract. Implemented as two honest arms instead:
`test_delete_cross_tenant_404_and_the_foreign_intake_survives` (a `user` in space A against
space B's intake, B's row re-read as its owner) and
`test_delete_missing_intake_is_404_not_500` / `test_deletable_missing_intake_is_404_not_500`
(a superadmin against an id that does not exist, exercising `repo.get -> None` on the
authorized path). The reasoning is in the test module's docstring, not only here.

**7. Object cleanup runs as a `BackgroundTasks` task**

The plan says step 7 happens "AFTER the handler's transaction". `get_tenant_repo` commits when
its `maker.begin()` generator exits, i.e. during dependency teardown — so a `gcs.delete_object`
inside the handler body would run BEFORE the commit and could destroy objects belonging to an
intake whose delete then rolled back. `BackgroundTasks` is the mechanism that actually gives
after-commit semantics here. The usual objection to `BackgroundTasks` in this repo (it loses
work silently on instance death) does not bite: this work is explicitly best-effort, the keys
are recorded in the audit row's count and in the warning log, and an orphaned object is
recoverable while a half-deleted intake is not.
