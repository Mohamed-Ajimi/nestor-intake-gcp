# Phase 23.5 Plan 03: Naming — Project vs Client Summary

The operator UI now says PROJECT where it means the free-text label an operator types
(`intakes.client_name`) and CLIENT where it means the tenant, in Dutch, French and English,
with zero key churn and exactly one added key; the AI skills' markdown context header names
the project instead of telling the model the project name is the client's name; and the one
mail string that actually mislabelled its value has been reworded while the four subject
constants were each read and deliberately left alone.

**The blocking human read (Task 3) is NOT done.** By operator decision on 2026-09-22 it moved
to plan 23.5-07's dev walkthrough. See "Task 3 outcome" below — it is deferred, not skipped,
and the tables in this document are the read list.

## What was built

### Task 1 — locale values + the create guard (`44cd7eb`)

Six locale JSON files changed by VALUE only. No key was renamed, so 3-way parity is preserved
by construction and CHECK A could not go red for this plan's reasons. Exactly ONE key was
added — `intakesNew.noClientSelected` — and it was written into all three `admin.json` files
in the same edit, so parity never went red even mid-plan.

Three groups of change:

- **Project name.** The `intakesNew.*` block stops calling the free-text field a client name.
  The placeholder stops being a company example (`e.g. Acme Inc.`) and becomes a project
  example. `intakesList` and `clientDetail` gain a Project column, and the two search
  placeholders now say they search client *or project*.
- **Space becomes client.** Every operator-facing `space`/`ruimte`/`espace` string in
  `admin.json` (`nav`, `spaces.*`, `spaceForm.*`, `invite.*`, `users.*`, `templates.*`) and
  the three in `intake.json`. `spaceSwitcher.*` needed no change — it already read as client
  at HEAD.
- **The create guard.** `admin.pulse.intakes.new.tsx` reads `activeSpaceId` from
  `useActiveSpace()` and `isSuperadmin` from `useAuth()`, and renders the submit button
  `disabled` with an inline amber hint when a superadmin has no active client. The condition
  mirrors `create_intake`'s 422 exactly rather than the current shape of the wall above it:
  `AdminLayout` already blocks non-superadmins, which makes the role half redundant *today*,
  and that is written into the comment so the redundancy is not mistaken for a bug. The check
  is repeated inside `submit()` because a disabled attribute is an affordance, not a guard —
  the same rule plan 23.5-02 applied to its typed-`DELETE` confirmation.

The `clientName` state variable keeps its name and the `client_name` API field is untouched.
The comment above it now says so explicitly, so the next reader does not "fix" the mismatch.

### Task 2 — the AI context header + the mail audit (`7352e80`)

`apply.py` and `context_pack.py` now emit `**Projectnaam**:` instead of the client-name label,
and `apply.py`'s empty-value fallback `(onbekende klant)` becomes `(naamloos project)`.
`extract_insights.py`'s `# Klantcontext` / `Klant: {x}` become `# Projectcontext` /
`Projectnaam: {x}`.

The reasoning, now written into all three files: `client_name` is `intakes.client_name` — the
operator's free-text label for one intake. The client ORGANISATION reaches the model
separately, as the client's own answer `client_info.client_name`
(`app/data/pulse_intake_v1.json:101`, byte-unchanged), which arrives as an ordinary
`field_key` line. The old header was therefore telling the model that the project name was the
client's name.

### The one real find

`admin_validated.html.j2:9` read:

```jinja
<strong>{{ client_name }}</strong> heeft de intake gevalideerd voor project "{{ project_title }}".
```

`_send_admin_validated` (`intake_routes.py:1676-1679`) passes `intake.client_name` to **both**
`client_name` and `project_title`. So the ops mail actually said:

> **Acme herpositionering** heeft de intake gevalideerd voor project "Acme herpositionering".

— the same string twice, the first occurrence labelled as the party that validated. That is
exactly the plan's "the surrounding words LABEL the value as the client" branch. The actor is
now named in prose and the value rendered once, in the slot where it is true.
`render_admin_validated`'s signature keeps its `client_name` parameter (jinja ignores unused
context), so no caller and no test had to change, and a template comment records that the
parameter is unrendered-not-lost and where to put it back when a real client/space name
becomes available here.
