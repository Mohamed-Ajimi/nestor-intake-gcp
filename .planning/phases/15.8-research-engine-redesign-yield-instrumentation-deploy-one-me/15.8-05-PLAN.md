<design_decisions>
These are DECIDED HERE. A downstream plan that re-opens one is re-litigating settled work.

**1. Why new tables and not `run_events` (D-W5-1, operator).**
`runs/run_events.py::_normalise_meta` passes `meta` through the `_META_FIELDS`
**allowlist** and drops every unknown key **with a warning but out of the row**. Yield keys
are not in that tuple, so they would vanish. That is the inert-instrumentation class this
project has been burned by three times (V-01 stage logging, D-W4-11 workshop notes, the
out-of-vocabulary `kind` trap). Its `text` is also scrubbed *and clamped to 400 chars*, and
it is a **per-run feed**. **Cross-run is the entire point of D-R8:** *"if round 7+ never
produces a new entrant across several runs, drop the cap and keep the money"* is a query
over many runs, not one. `audit_log` was rejected too: it is the hash-chained Art. 12 record
whose `verify_chain` is re-gated on every deploy against a legal deadline.

**2. `client_question` NULLABLE + `parent_kind` as a REAL column (D-W5-2).**
A cross-cutting `d1` group has **no single parent** (there is never a `d2`), so it records
`client_question = NULL, parent_kind = 'cross_cutting'` — inventing a parent would fabricate
provenance in a row whose whole purpose is to be trusted later. A discovery rider parented
to a client-question label (D-W3-5.2) joins that label's mandate group, so it records **its
own** `client_question` with `parent_kind = 'discovery_rider'`. An ordinary mandate
assignment records `parent_kind = 'client_question'`.
**`parent_kind` must NOT be inferrable from `client_question IS NULL`.** The two encode
different things and a future reader will conflate them.

**3. The nullability rule for the whole schema, stated once so it is not re-derived.**
NOT NULL: `id`, `tenant_id`, `run_id`, `provider`, `parent_kind`, `created_at` (and
`round_no` on the round table). Those are identity and scoping.
NULLABLE: **every measured value**, without exception. Three reasons, all load-bearing:
(a) `client_question` is ruled nullable; (b) `claims_surviving_verification` is genuinely
unknown at INSERT time; (c) **a NOT NULL on a telemetry counter turns a missing measurement
into a FAILED INSERT inside a $45 run.** A NULL means "not recorded"; a 0 means "measured
zero". They must stay distinguishable — a coercion that turns garbage into 0 fabricates a
measurement, which is exactly what this table exists to stop.

**4. A BAD DISCRIMINATOR CLAMPS TO A SENTINEL AND THE ROW IS STILL WRITTEN. It is never
dropped, and there is no CHECK constraint. (Team-lead ruling, 2026-08-04 — this OVERRULES
the drop rule an earlier draft of this plan took from `run_event.kind`. Extended to
`provider` in the same ruling.)**

The `run_events` precedent does drop, but **read its stated reason: *"An out-of-vocabulary
kind renders as a blank line in the feed, which is worse than an absent one -- so drop the
row."* That rationale is DISPLAY-SPECIFIC and does not transfer.** A blank line in a UI feed
is noise. A dropped `assignment_yield` row is a **LOST MEASUREMENT** — `cost_usd`,
`claims_kept`, `resolvable_sources` and `duration_s` all discarded because one discriminator
column was wrong.

And consider who writes `parent_kind`: it is **ENGINE-AUTHORED, not model-authored.** An
out-of-vocabulary value means an **engine bug** — which is precisely the run whose telemetry
you most want to keep. Dropping it makes the one condition that most needs measuring the one
condition that erases itself.

**The decisive argument is about money, and it comes from 15.8-08.** `SUM(cost_usd)` SKIPS
NULL rows across four `COALESCE(...)` sites in `runs/worker.py`, so **missing cost data does
not announce itself — the total simply LOOKS complete.** A dropped assignment row is
therefore not merely a lost yield measurement, it is a **silent understatement of what the
run spent**, in the only run this project gets. A row carrying `provider = 'unknown'` still
carries its dollars.

This is also the fourth instance of one class in two days — V-01's inert stage logging, the
workshop notes that only reached `log.info`, the out-of-vocabulary `kind` trap, and this.
**A `log.warning` is not persistence.** That is the V-01 lesson stated exactly.

So: clamp to `PARENT_KIND_UNKNOWN = "unknown"` / `PROVIDER_UNKNOWN = "unknown"`, WRITE THE
ROW with every other column intact, and log loudly at WARNING with the refused value. No
CHECK constraint on either column (a CHECK would turn the same event into a failed
transaction in a paid run, which is worse still). **Never raise into the run** — that
constraint is unchanged. **Neither sentinel belongs to any vocabulary tuple**, so the ruled
vocabularies stay queryable and `= 'unknown'` becomes the engine-bug query.

Net effect: **no field value causes the emitter to discard a row.** The only rows lost are
ones a raising database write loses, and that path already logs.

**5. `claims_surviving_verification`: INSERT at research-resolve, UPDATE after verification.**
Settled here, not discovered by 15.8-09. The research half (cost, duration, claims kept,
sources, the parse/retry flags) is DURABLE and paid for the moment research resolves; the
survival count only exists later. Writing one row late would lose the paid half on a run
that is parked between the two stages.

**The UPDATE is keyed on the NATURAL KEY `(run_id, provider, group_id, client_question)`,
not on a row id returned by the INSERT.** A parked run resumes in a **different process**,
where an in-memory row id is gone; the natural key survives a restart and the row id does
not. Nullable members of the key are compared with `IS NOT DISTINCT FROM`, so a NULL
`group_id` or `client_question` matches its own row instead of matching nothing.

**⚠ 5a. THE KEY-SYMMETRY RULE — item 4's clamp COLLIDES with this key, and getting it wrong
produces a confident WRONG diagnosis. (Team-lead catch, 2026-08-04; extended here to two
more columns.)**

Three of the four key members are NORMALISED on the INSERT path: `provider` is clamped to a
sentinel, `group_id` has `''` turned into `NULL` and is length-clamped, and
`client_question` is SCRUBBED AND CLAMPED. If the completer builds its key from RAW values
while the INSERT stored normalised ones, **the UPDATE matches nothing** — and this module's
own warning reads an affected-row count of 0 as *"the INSERT half never landed"*. A bad
value would therefore produce a **specific, confident and completely wrong diagnosis of a
different failure**, in the one run there is.

The team lead caught this on `provider`. **It is at least as likely on `client_question`:**
`scrub_pii` rewrites any question containing an email or a phone number, and the clamp
rewrites any question over `MAX_QUESTION_CHARS`. Neither is exotic. `group_id` has the same
shape via the empty-string rule.

**THE RULE: one normaliser, called on BOTH paths, applied BEFORE the key is assembled.**
Not "the emitter normalises and the completer trusts". A single `_natural_key(run_id,
provider, group_id, client_question)` helper returns the four bound values, and **both
`record_assignment` and `complete_assignment` call it.** Callers pass RAW values on both
paths; the module owns the symmetry, because a caller cannot.
Asserted by a ROUND-TRIP test, not by inspection — see Task 3. **That test is worth more
than the insert-side test: the insert-side failure is loud, and this one is silent.**

**Known imprecision, logged and never silent:** `divide()`'s focus-area fallback path
doubles a high-stakes angle with a second copy to `_HIGH_REDUNDANCY_PROVIDER = "claude"`,
which can produce two rows sharing the natural key. The live group-dispatch path sends each
group to each of `_D6_STREAMS` exactly once and cannot. The completer therefore reports the
**affected row count** and WARNS when it is not exactly 1 (`0` = the INSERT half never
landed; `>1` = the doubled fallback, where a SUM over the column would double-count).
**That 0-means-the-INSERT-never-landed reading is only trustworthy BECAUSE of rule 5a** —
say so in a comment beside the warning, so nobody later "simplifies" the shared helper away
and leaves a warning that lies.

**6. The emitter writes DIRECTLY. No queue, no drain task, no batching.**
`run_events` buffers because a run emits *thousands* of feed lines from inside per-poll
provider code. This table takes **at most ~45 assignment rows and ~10 round rows per run**,
each written once, at a stage boundary, after a paid call has already resolved. A queue
here would need a drain task and a `close_run` hook — and a row lost at close is precisely
the inert-instrumentation failure this whole schema decision was made to avoid. **Durability
of these rows matters more than the microseconds.** What IS copied from `run_events` is the
discipline: own session, `session.begin()`, `set_tenant_context` first, swallow-and-warn,
never retry.

**7. Every sqlalchemy / db import in `runs/yield_records.py` is FUNCTION-LOCAL**, exactly as
`run_events.py` does it. Module level imports only stdlib plus `pii.scrub_pii` (itself
stdlib-only). This is not tidiness: it is what lets `tests/test_yield_records.py` import the
real module on a machine with no sqlalchemy, which is the only way to defeat the `ast`-lift
trap. ⛔ **The `ast`-lift harness SUPPLIES module globals and therefore MANUFACTURES any
name a module forgot to import.** It hid a missing import used at four sites through nine
plans, `py_compile`, and "38 lifted tests green". Do not use it in this plan's tests.
</design_decisions>

**⚠ `barred_drops` and D-W5-6 — record this in the model docstring so no writer gets it
wrong.** `workshop_register.record_drop` appends BOTH drop causes to one `register["drops"]`
list, and `workshop_rank.py` reads that list by BARE LENGTH in three places, all named for
the barred cause only. Today only the barred cause can be written, so a bare length is
*accidentally* correct. Once 15.8-04 lands a production `DROP_CLUSTERED_ONTO_LIVE` writer, a
bare length starts counting ordinary near-copy merges — so **the "loop is SPINNING" metric
would silently absorb the OPPOSITE failure it exists to distinguish.** D-W5-6 rules that
15.8-10 swaps all three reads to the cause-filtered `count_drops` before persisting into this
column. **This column means the barred cause and nothing else.** An inflated `barred_drops`
in the ONE measuring run is not recoverable.
