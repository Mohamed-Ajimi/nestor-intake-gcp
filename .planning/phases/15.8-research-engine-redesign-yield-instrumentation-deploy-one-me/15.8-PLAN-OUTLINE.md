## Wave ordering rationale

**Wave 1 (8 plans) — every file-disjoint fix and every contract, in parallel.** The four defect plans
(01–04) partition the six affected production files with zero overlap. 05 is interface-first: it
defines the column sets and the emitter that waves 2 consume, so no downstream plan has to go looking
for a contract. 06 and 08 are operator-gated and sit here purely for lead time — 06's answer is needed
by 10 in wave 2, and 08 gates wave 5. 07 is a self-contained config file nothing else touches.

**Wave 2 (2 plans) — the two writers, each inheriting a file from wave 1.** 09 takes
`research_division.py` + `pipeline.py` from 02; 10 takes `workshop_rank.py` from 03. They are in a
later wave for exactly that reason and for no other. The two are disjoint from each other.

**Wave 3 (2 plans) — the two passes that must see the finished tree.** 11 reviews test files that do
not all exist until wave 2 lands. 12 documents what actually shipped, which is not knowable earlier.

**Wave 4 (1 plan) — the gate.** It must run on the fully merged tree, and it is the sole editor of
`cloudbuild.test-engine.yaml` (below). Nothing runs beside it.

**Wave 5 → Wave 6 — BUILD is separated from MEASURE by wave, on purpose.** 14 and 15 are the only
plans that touch live services or spend real money; both are `autonomous: false`; both depend on
everything before them. They are two plans rather than one because the deploy can succeed and the run
can still be aborted at the pre-flight (empty queue, wrong ANTHROPIC secret, a stale image), and
because § 15.2.k's ordering makes the deploy a finished procedure with its own read-backs before a
single cent of the run is spent.

**Merging is a serial operation in this repo, not a batched one.** Eight wave-1 plans means eight
merges; each one must re-check `merge-base != BASE` (`rev-list --count BASE..HEAD == 0` reads green
while stale — 15/15 in this repo, most recently 2/2 in phase 15.7 at 595–601 commits behind), and
`git worktree list` should be swept at session start because a stale worktree from a halted run has
sat on disk before. `.planning/` is gitignored — every planning artifact needs `git add -f`.

**Code review runs PER WAVE, not batched.** Wave 3 of the redesign shipped 42/42 verification and 1283
green tests with two criticals living in the SEAMS between plans. Waves 1 and 2 here each need their
own review pass before the gate; 11 covers test files specifically, not production seams.
