# ⛔ STOP PROCEDURE — READ THIS FIRST, BEFORE ANY OTHER SECTION

**Written 2026-08-05 by plan 15.8-15, BEFORE the run was triggered.** It is deliberately the first

### 1. ONLY RESOLVING THE ROW STOPS A RUN.

**Only resolving the ROW stops a run** — `cancel_research`'s own docstring is the authority, and this
is the sentence every other point on this list depends on.

The **Stop** button on the **ACTIVE** run card →
`POST /intakes/{intake_id}/research/cancel` → the engine's `POST /runs/{run_id}/cancel`, which sets
`status='cancelled'`.

It is **idempotent**: cancelling an already-terminal run is a no-op that reports itself, returning
that run's own unchanged status. `202` carries `{research_run_id, status}`. **There is no `409` arm
and no attempt cap** — stopping a run is not an attempt at anything. A `404` means non-superadmin
caller, cross-tenant/missing intake, no run, or a run carrying no `tribunal_run_id`; existence is
always hidden, never `403`. A `502` is a seam or transport failure.

The intake row is **not** touched and stays `in_research` — that is correct and not a bug.
Resolving the run row to `cancelled` is by itself what makes `trigger_research`'s retry path
reachable again (`cancelled` is in `_RETRYABLE_RUN_STATUSES`; `running` is not, which is exactly why
a run stuck at `running` blocks its intake).

*Source: `backend/app/api/research_routes.py::cancel_research` (line 530) — its docstring is the
authority.*

### 2. PAUSING THE SERVICE IS **NOT** CANCELLING.

On **2026-07-27** the in-flight process kept going for **16 more minutes** after the service was
paused; terminating it required **deploying a new revision**; and the fresh worker that came up was
**seconds from RE-CLAIMING the run at full cost**.

`--min-instances=0` is **not** a protection either: `runs/worker.py`'s `while True:` loop **CLAIMS
FIRST and SLEEPS LAST** — `claim_one(session)` runs at the top of every iteration (`worker.py:665`)
and `await asyncio.sleep(POLL_INTERVAL_SECONDS)` is only reached on the **empty-queue** branch
(`worker.py:700`). **An empty queue is the only protection.**

*Source: `cancel_research` docstring (D-E) + `tribunal/nestor_pulse_sdk/runs/worker.py:661-701`.*

### 3. CANCELLATION IS **COOPERATIVE** — EXPECT A DELAY, NOT AN INSTANT HALT.

`runs/adapter.py` polls the cancel flag **at most once every `_CANCEL_CHECK_INTERVAL = 10.0`
seconds**, and only **between streamed events**. ADK cannot be force-killed mid-tool-call, so **cancel
latency is bounded by the gap between streamed events plus that 10-second window.** During a
deep-research call that gap can be long. A run that has not stopped after ten seconds is **not** a
failed cancel.

*Source: `tribunal/nestor_pulse_sdk/runs/adapter.py:132-144`.*

#### The cost-floor reading discipline — copied forward so Task 2 does not rediscover it

**State it once and NEVER present a floor as a total.**

- `compute()` returns **`None`** for a **missing key** and **`Decimal("0")`** for a key **present
  with null rates**. Different things — and `Decimal("0")` is **falsy**, so a truthiness check cannot
  tell them apart.
- **The openai branch of `end_call` NEVER sets `run.cost_pending`** (`dr_cost_pending` is set at
  exactly one site, inside the `handle.provider == "google"` branch). `cost_pending` is **not** the
  protection here.
- `SUM(cost_usd)` **skips NULLs**.

**THE RUN TOTAL IS A FLOOR FOR THREE MECHANICALLY DISTINCT REASONS** — they compound, and they are
not one issue restated:

1. **NULL `cost_usd` rows** silently skipped by `SUM` (V-01's `$53.48` is itself a floor for exactly
   this reason and must be compared as one);
2. **WR-02** — a failed or timed-out angle emits **no `assignment_yield` row at all**, so `SUM`
   misses it with **no column to explain the gap**;
3. **the 272K long-context meter** — above 272,000 input tokens `gpt-5.6-sol` re-bills the entire
   request at 2× input / 1.5× output, and `_rate()` has no notion of a tier, so the flat rates
   **under-report by 2×/1.5× above the boundary**. Operator ruled 2026-08-04: **record it, do NOT fix
   it.**
