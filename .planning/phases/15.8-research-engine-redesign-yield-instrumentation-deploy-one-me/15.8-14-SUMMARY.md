## Findings

### FINDING-A — the phase gate had never run on the tree being deployed

Plan Task 1(d) says *"the gate is already paid — read 15.8-13's record, do not re-run it."* **That
criterion is stale twice over and following it literally would have shipped an ungated tree.**

1. **15.8-13's recorded gate was RED** — build `b1397467` **FAILURE**, `1 failed / 1753 passed`; its
   own summary says *"the PHASE GATE is NOT GREEN."* Read literally, Task 1(d) says ABORT.
2. The later green, build `409ecddc` (created `2026-08-04T13:40:32Z`), **predates two 15.8-08 commits
   that are in HEAD** — `3597e87` and `5c04421`, both at ~22:51 +02:00, touching
   `audit/cost_prices.json`, `audit/gcs_blob.py` (production) and `tests/test_cost_serpapi.py`
   (already in the gate's 43-path list). **15.8-08's own summary says so:** *"STILL OWED TO CLOUD
   BUILD (15.8-13): the full 43-file gate"* — a debt handed to a plan that had already finished and
   could not pay it.

**Both gates were therefore re-run on HEAD before any spend**, which is also what § Step 15.8.b
instructs at deploy time:

| Gate | Build | Status | Counts |
|---|---|---|---|
| engine | `3a7a580a-2e36-4a9c-9a35-956e165ea361` | **SUCCESS** | `collecting: 43 of 43` · `1812 passed, 13 skipped` |
| gates | `f1322c33-1f10-4aef-b530-e396b24787d3` | **SUCCESS** | `collecting: 13 of 13` · `187 passed, 2 deselected` |

**The reconciliation vindicates the re-run:** 1777 → **1812** is exactly **+35**, which is 15.8-08
extending `test_cost_serpapi.py` from 16 to 51 tests. **Those 35 tests had never executed in Cloud
Build.** `skipped` held at exactly 13, so nothing went silently un-run.

### FINDING-B — my own matcher nearly reported a healthy chain as broken

The first deployed-data chain assertions matched `chain_status`, which is **`nestor-api`'s wrapper
shape**. `tribunal-api`'s `verify_chain_endpoint` returns **`{"ok": bool, "broken_at": int|null}`**.
Three builds failed on that mismatch and **read exactly like a red chain**.

What separated them was adding arms that discriminate *key absent* from *value wrong* before
reporting either. Exit 78 (no `ok` key) said "wrong shape"; only exit 77 would have said "red chain."
**Only one of those is a STOP, and it was not the one that happened.** Recorded because this phase's
dominant failure mode is calling a defect correct behaviour — the mirror image, calling correct
behaviour a defect, costs a false alarm and an aborted deploy.

### FINDING-C — the INTAKE head read is not executable by any deploy-time credential

§ 15.8.e and § 15.8.i(e) instruct `SELECT version_num FROM public.alembic_version`, expecting `0013`.
Localised by build `ddffd9bb` (**exit 72**): a `SELECT 1` proves the connection, the *no-such-relation*
and *wrong-schema* arms did **not** fire — the table **exists in `public`** — and **SELECT is refused
for `app_user`**, and separately for `worker_user` (exit 89, builds `da1e5546` / `4ef45cf9`). **A GRANT
gap, not a moved head.**

**Operator ruling 2026-08-05: record NOT OBTAINED.** Supporting evidence that it cannot have moved —
labelled **INFERENCE, not a read** — is that `nestor-migrate` was never executed and no backend
revision was added.

### FINDING-D — four instructions in this deploy path cannot be executed as written

One defect class in four coats. **An instruction no available credential can run reads as a check and
is not one.**

| # | Instruction | State |
|---|---|---|
| 1 | § 15.8.e/§ 15.8.i(e) `SELECT … FROM public.alembic_version` | refused for both DB users |
| 2 | § 15.2.k step 2's queue recipe | **prose only** — described three times, materialised nowhere |
| 3 | `gcloud beta run jobs executions logs read` | dies on a CLI self-update; `gcloud logging read` with the execution-name filter is the working form |
| 4 | § 15.8.f's superadmin **Re-verify** affordance | unreachable — a hard load of `/admin/pulse/runs/<id>` bounces to `/auth/login` then home |

Defect 4 is booked as a **UAT item**: `admin.tsx`'s `beforeLoad` redirects when `authReady()` yields
no user and `LoginPage` auto-navigates to `/admin`, **discarding the destination**.
`admin.pulse.runs.$runId.tsx` is deliberately flat and standalone *"a bookmarked link will not have
one"* — **so a route designed to be bookmarkable is unreachable by bookmark.**

### FINDING-E — the wrong-account deploy hazard

`gcloud` demanded reauthentication mid-deploy, and the login that cleared it **authenticated a
different account and switched the project**. The project was corrected, a live API call then
succeeded, and minutes later the state had **silently reverted** — the browser login finalised
asynchronously and overwrote the fix.

`builds submit`, `run deploy`, `run jobs execute` and the deploy scripts all inherit the **ambient**
account and project and **none complains about a wrong one**. Every subsequent gcloud operation in
this plan asserted both immediately before running. The guard is in the record.

## Deviations from the plan

**1. [Rule 3 — blocking] Task 1(d) was not followed; both gates were re-run.** Reasoning in
FINDING-A. This did not re-litigate 15.8-13 — it executed § 15.8.b on the tree actually being built.

**2. The plan's `user_setup` premise is FALSE, and it is corrected in place.** It claims *"the agent
has no gcloud credentials, cannot submit a Cloud Build, cannot execute a Cloud Run Job and cannot read
Cloud SQL."* `gcloud` is authenticated as `tools@dotto.be` on the project; twenty builds were
submitted from this session. ⛔ **The correction changes WHO CAN RUN a command and nothing about WHO
MAY CLEAR A GATE.** Both halves are in the record.

**3. Every step of Tasks 2 and 3 was executed by the agent, not the operator** — the plan's
`how-to-verify` addresses the operator throughout. Authorised in session. **The two blocking
`checkpoint:human-verify` gates were honoured**: the executor halted and returned at each, and never
self-approved either.

**4. `gcloud run jobs execute` was DENIED by the permission layer. It was not retried and not routed
around.** The executor halted; the operator ran it directly. This is the same discipline 15.8-13
applied to its `git revert` denial.

**5. The chain proof was taken by a direct call, not the UI Re-verify button** (unreachable —
FINDING-D). Same endpoint, same caller identity (`nestor-run@`, path-less audience), tenant **read
from `tribunal.run`** rather than guessed. **It does not exercise `nestor-api`'s proxy hop or the UI
button** — stated rather than implied. The WR-07 acting-user identity was **chosen by the operator,
in session, from the three real Identity Platform accounts, and is their own superadmin account.**
The executor declined to invent an identity and routed the question instead.

**6. `roles/logging.logWriter` was NOT granted to `nestor-run@`**, though it would have made every
read-back printable. It is 15.8-15's assigned blocking pre-flight gate (Q-PRE-4) and this plan does
not own it. Values were pinned by **paired runs** through the boolean-only channel instead.

**7. The queue/read-back configs were written to a scratchpad, not committed.** This plan's file fence
is `infra/DEPLOY-RUNBOOK.md`. Booked as FINDING-D #2 rather than silently expanded into.

**8. 15.8-12's § 15.8 procedure text was NOT edited.** Verified: steps a–i and k each still appear
exactly once, and every deleted line in the diff is inside Step 15.8.j's own skeleton. Where executing
the procedure revealed a wrong step, it is recorded as a deviation in the record — not edited into
agreement.

**9. Two of the plan's own `<automated>` verifies are unsatisfiable as written.** Task 4 greps the
**whole file** for `placeholder`, which appears **5 times in other phases' prose** (lines 529, 668,
1697, 3623, 3626) and always would have. The plan's own acceptance criterion scopes the same check to
**the § 15.8 section**, where it returns **0**. The section-scoped form is the correct one and is what
was verified. Task 2/3's verifies also grep for `chain_status`, which the record correctly does not
assert of `tribunal-api` (FINDING-B).
