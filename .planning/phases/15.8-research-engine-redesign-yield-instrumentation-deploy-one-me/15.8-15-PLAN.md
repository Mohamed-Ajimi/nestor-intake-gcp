## The exact commands, named so `<action>` can reference them without inlining code

**How to reach the database at all.** `nestor-pg` has an EMPTY authorized-networks list and the
Phase-14 lockdown rejects a plain invoker token on `tribunal-api` (`invalid internal caller token`).

with the Cloud SQL proxy inside the step — `nestor-run@` already holds `secretAccessor` on
`DATABASE_URL_WORKER`. `--no-source` is REQUIRED (that SA cannot read the build source bucket).
Connect as **`worker_user`**, not `app_user`.

⚠ **Q-PRE-4 — THE READ PATH MUST BE SETTLED BEFORE THE RUN, NOT AFTER.** As recorded 2026-07-28,
`nestor-run@` lacks `roles/logging.logWriter`, so **build stdout is LOST** and that recipe can only
carry a boolean in its exit status. That is survivable for a gate and useless for reading a table of
numbers. `assignment_yield` and `workshop_round_yield` have **no read endpoint, no seam verb and no
UI surface** — nothing in 15.8-05/09/10 adds one. So if this is not settled first, Wave 5's own
verification criterion becomes unreadable after $45 has been spent.

Recommended: grant `roles/logging.logWriter` to `nestor-run@` on the project (one reversible IAM
grant, no networking change, no new secret access) and read the query output from the build log.
Verify by read-back, then re-run a trivial `SELECT 1` build and confirm the output is visible
**before** triggering the run.

### Pre-flight

- **Q-PRE-1 — revisions.** For each of `tribunal-worker`, `tribunal-api`, `nestor-api`,
  `nestor-frontend`: `gcloud run services describe <svc> --region europe-west1 --project="$GOOGLE_PROJECT"`
  reading `status.latestReadyRevisionName`, `status.traffic` (must be 100% to that revision) and the
  container image **digest**. Compare each, character by character, against 15.8-14's deploy record.
- **Q-PRE-2 — the queue must be EMPTY.**
  `SELECT status, count(*) FROM run WHERE status IN ('queued','running') GROUP BY status;`
  as `worker_user` (`run` carries the `worker_all` policy, so this needs no tenant binding).
  **Expect zero rows.** `--min-instances=0` does NOT stop a worker booting — `runs/worker.py`'s
  `while True:` **claims FIRST and sleeps LAST**. An empty queue is the only protection.
- **Q-PRE-3 — worker env.**
  `gcloud run services describe tribunal-worker --region europe-west1 --project="$GOOGLE_PROJECT" --format='value(spec.template.spec.containers[0].env)' | tr ',' '\n' | grep -E 'NESTOR_WORKER|ANTHROPIC|SERP'`
  Record `NESTOR_WORKER_STALE_MINUTES` verbatim and which secret `ANTHROPIC_API_KEY` binds.

### The delivered report — the ONLY thing the engine is judged from

- **Q-RPT-1 (preferred, credential-free).** As superadmin in the live app, open the intake and use
  the **raw-output download** (Phase 17). `build_bundle_zip` packages the report markdown, the
  scrubbed `cleaned_reports` and the sources. This is the delivered artefact.
- **Q-RPT-2 (fallback, DB).**
  `SELECT length(body), body FROM output WHERE run_id = :run_id AND format = 'markdown' ORDER BY created_at DESC LIMIT 1;`
  RLS-scoped — bind `app.tenant_id` first, as Q-YIELD-0 does.
- ⚠ **NOT** the `claim` table and **NOT** the logs. Three of V-01's own findings-doc claims were
  wrong because they judged the verification stage from intermediate artifacts.

### The yield tables

- **Q-YIELD-0 — the tenant binding.** In ONE transaction:
  `SELECT tenant_id FROM run WHERE id = :run_id;` (visible via `worker_all`), then
  `SET LOCAL app.tenant_id = '<that uuid>';`, then the two queries below. Mirroring 0015, these
  tables get a tenant-isolation policy and **no** `worker_all` policy, so an UNBOUND query raises
  `unrecognized configuration parameter` — it fails loudly rather than returning zero rows. Do not
  read an error as an empty table.
- **Q-YIELD-1 — assignment_yield.**
  `SELECT provider, group_id, parent_kind, client_question, stakes, fact_list_parsed, retry_used, claims_kept, claims_surviving_verification, resolvable_sources, cost_usd, duration_s FROM assignment_yield WHERE run_id = :run_id ORDER BY group_id, provider;`
  plus `SELECT parent_kind, count(*) FROM assignment_yield WHERE run_id = :run_id GROUP BY parent_kind;`
- **Q-YIELD-2 — workshop_round_yield, `new_entrants_top_n` FIRST.**
  `SELECT round_no, new_entrants_top_n, candidates_in, new_candidates, keep_count, weak_count, kill_count, barred_drops, round_cost_usd FROM workshop_round_yield WHERE run_id = :run_id ORDER BY round_no;`

### Cost

- **Q-COST-1 — the total.** `SELECT COALESCE(SUM(cost_usd),0) FROM audit_log WHERE run_id = :run_id;`
- **Q-COST-2 — the floor marker, MANDATORY beside Q-COST-1.**
  `SELECT count(*) FROM audit_log WHERE run_id = :run_id AND cost_usd IS NULL;`
  A cost total recorded without this count is not a cost measurement.
- **Q-COST-3 — concentration.**
  `SELECT provider, model, count(*), SUM(cost_usd) FROM audit_log WHERE run_id = :run_id GROUP BY provider, model ORDER BY 4 DESC NULLS LAST;`

### Corroboration and claims

- **Q-CLAIM-1.**
  `SELECT count(*) AS claims, count(corroboration_key) AS with_key, count(*) - count(corroboration_key) AS null_key FROM claim WHERE run_id = :run_id;`
- **Q-CLAIM-2 — distinct keys, the V-01 killer.**
  `SELECT corroboration_key, count(*) FROM claim WHERE run_id = :run_id GROUP BY corroboration_key ORDER BY 2 DESC;`
- **Q-CLAIM-3 — coffee.** Count claims whose text matches the coffee topic (`ILIKE '%koffie%' OR ILIKE '%coffee%'`). V-01's value is **0**.

### The loop's narrative

- **Q-LOOP-1.** `SELECT seq, stage, kind, text FROM run_event WHERE run_id = :run_id ORDER BY seq;`
  (same tenant binding as Q-YIELD-0). Every workshop note is persisted under D-W4-11 and renders as
  `Question workshop — …`. This is the loop's story in the operator's own feed, and it is also
  readable in the live run page without any DB access.
