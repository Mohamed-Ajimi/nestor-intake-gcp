
**The mechanism.** `assignment_identity` stringifies *any* non-`None` `corroboration_key`. For the
hostile parameter `{"corroboration_key": object(), "focus_area": object()}` that produces
`'<object object at 0x7feaa1b680d0>'` — a **non-deterministic memory address written into a
provenance column** of `assignment_yield`. The identical shape exists one branch later at line 1199
for `client_question` (`focus_area` → `str(...)`), and **the test does not assert that half**, so the
sibling defect is live and ungated.

**Why this is the production code and not the test.** Three independent reasons, all from the
module's own stated contract:

1. `assignment_identity`'s own docstring says recording a label the run did not establish "would
   **FABRICATE PROVENANCE** in a row whose entire purpose is to be trusted later, by a reader who
   cannot re-run the $45 run to check it (D-W5-2)". A memory address is the strongest possible form
   of that: it differs on every process.
2. Rule (1) in the same docstring reads *"`group_id` is the angle's `corroboration_key`, **stripped**"*
   — stripping presupposes a string.
3. `_one_angle` stamps `_corroboration_key` as `angle.get("corroboration_key") or None`, i.e. the
   **object itself**, un-stringified. So the yield row would record `'<object object at …>'` while the
   claim row records the object — the exact disagreement that
   `test_group_id_can_never_disagree_with_the_existing_corroboration_stamp` (green today, on string
   inputs only) exists to forbid.

**The candidate fix, one line, stated but NOT applied:** accept `raw_group` only when
`isinstance(raw_group, str)`; same for `raw_label` at :1199. It is safe against
`test_group_id_can_never_disagree_with_the_existing_corroboration_stamp`, whose parametrisation is
strings / absent / `""` only.

**Why I did not fix it.** Three reasons, and the third is the real one:
- my dispatch fences this plan to `cloudbuild.test-engine.yaml` plus this SUMMARY;
- this plan's own Task 2 action says a failure is *"a real defect in the merged tree — read the
  traceback and **report it**"*, and the SCOPE BOUNDARY rule limits auto-fix to defects **caused by**
  this task, which this is not (my change *revealed* it);
- a `str`-only fix creates a **latent disagreement with `_one_angle`'s un-stringified stamp** for any
  non-`str` key. That is a cross-plan contract decision about a DB column, sitting one plan before a
  deploy and a $45 run. It is a routing decision, not a one-liner an executor should take alone —
  and this phase's dominant failure mode was an executor calling a defect "correct behaviour" in its
