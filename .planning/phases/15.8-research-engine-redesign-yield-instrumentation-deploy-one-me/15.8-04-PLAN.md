<objective>
Close the two open `workshop_register` / `workshop` gaps carried out of 15.7's verification, so that
**both halves of D-W4-1's drop signal are recordable in production** and the barred list actually
suppresses what the model is about to re-propose.

Two symbols, in two files this plan owns exclusively:

1. `workshop_register.barred_block` renders `entries[:limit]` with `_BARRED_MAX_ENTRIES = 24`. It shows
   the **OLDEST** 24 bars and hides the **NEWEST**. The bars a model has just earned are exactly the
   ones it is about to re-propose, so the block is at its least useful precisely when it starts to
   matter. It bites the moment a run passes 24 bars, which a 10-round loop over a ~36-candidate
   population reaches.
2. `DROP_CLUSTERED_ONTO_LIVE` has **no production writer**. `workshop_register.py` defines it, only
   `test_workshop_critique.py` writes it, and `drop_summary`'s third branch is therefore **dead code**.
   D-W4-1 requires the drop log to separate two OPPOSITE measured failures — the loop **SPINNING**
   (re-proposing its own rejects) and an over-eager dedup **strangling discovery invisibly**. Only the
   first is recordable today.

Purpose: 15.8-15 is the ONE measuring run. A drop log that can only express one of the two failures it
was built to tell apart produces a number nobody can act on, and there is no second run to correct it.

Output: a newest-first bounded barred block, a production live-drop writer, a cause-filtered
`count_drops` counter, and tests that go red when each fix is reverted.
</objective>

<branch_decision>
## The alternative is REJECTED, explicitly, not omitted

15.7-VERIFICATION.md offered two ways to close the `DROP_CLUSTERED_ONTO_LIVE` gap:

- **(a) Write the second drop cause in production.** ← **TAKEN.**
- **(b) Delete the constant and record that half of D-W4-1's drop signal was descoped.**

(b) is rejected because D-W4-1 does not treat the two causes as a nice-to-have pair. It names them as
two *opposite measured failures* and states, in the register's own module docstring and in
`record_drop`'s, that **"3 drops" is the same number in both worlds** and only what each clustered
ONTO separates them. Deleting the constant would leave the engine able to detect a spinning loop and
structurally unable to detect the failure the Wave-4 harness actually measured more of — the dedup
killing SPECIALISE and COMBINE attempts, and killing round 1's only INVENT before the grounded lookup
ever ran. Wave 5 exists to measure; descoping half a measurement in the phase whose whole purpose is
one trustworthy measurement is the wrong trade.

Writing it is also cheap: the site already exists, adjacent to the working
`record_drop(..., cause=DROP_CLUSTERED_ONTO_BARRED)` call, and the emitter, the cause constant and the
summary sentence are all already built and tested.
</branch_decision>

<cross_plan_hazard>
## ⚠ THE ONE CONSEQUENCE THIS PLAN CANNOT FIX ITSELF — READ BEFORE TASK 2

`workshop_register.record_drop` appends **both causes to ONE list**, `register["drops"]`. That is the
module's deliberate design (one drop log, a `cause` field, `drop_summary` filtering by cause) and this
plan does not change it.

**But `workshop_rank.py` reads that list by BARE LENGTH in two places, and both are named for the
barred cause alone:**

- `workshop_rank.py`, in the loop body around the `workshop.cluster_candidates` call:
  `drops_before = len(register.get("drops") or [])` … then
  `dropped_this_round = len(register.get("drops") or []) - drops_before`, passed to
  `workshop_loop.round_metrics(dropped_as_reproposal=dropped_this_round)`.
- `workshop_rank.py`, in the stage-B `counts` block:
  `"dropped_as_reproposal": len(register.get("drops") or [])`.

Today only the barred cause can ever be written, so a bare length is **accidentally** correct. The
moment this plan lands a production live-drop writer, `dropped_as_reproposal` silently starts counting
ordinary near-copy merges — i.e. the "loop is SPINNING" metric absorbs the exact opposite failure it
exists to distinguish. **15.8-10 persists `round_metrics` into `workshop_round_yield.barred_drops`,
and 15.8-15 reads that table as the ONE measurement.**

**`workshop_rank.py` is NOT this plan's file** (15.8-03 in wave 1, 15.8-10 in wave 2 — see the
outline's Shared-file conflicts table). So this plan does the two things it *can* do, and neither is a
silent deferral:

1. **Ships the counter the readers need** — `workshop_register.count_drops(register, *, cause=None,
   round_no=None)`, in this plan's own file, purely additive.
2. **States the hazard in `record_drop`'s docstring**, which is the module `workshop_rank` already
   imports, naming both reader sites and the replacement call.

The reader swap itself has been raised with the team lead for assignment to 15.8-10. **This plan must
not assume it happened**, and must not edit `workshop_rank.py` to do it.
