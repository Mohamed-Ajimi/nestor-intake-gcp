<objective>
Close the two open `workshop_register` / `workshop` gaps carried out of 15.7's verification, so that
**both halves of D-W4-1's drop signal are recordable in production** and the barred list actually
suppresses what the model is about to re-propose.

**Three symbols**, in two files this plan owns exclusively. The third was found while writing this
plan rather than planned into it, and was ruled in scope afterwards as **D-W5-7** — the reconciliation
pass should see it as an addition:

1. `workshop_register.barred_block` renders `entries[:limit]` with `_BARRED_MAX_ENTRIES = 24`. It shows
   the **OLDEST** 24 bars and hides the **NEWEST**. The bars a model has just earned are exactly the
   ones it is about to re-propose, so the block is at its least useful precisely when it starts to
   matter. It bites the moment a run passes 24 bars, which a 10-round loop over a ~36-candidate
   population reaches.
2. `DROP_CLUSTERED_ONTO_LIVE` has **no production writer**. `workshop_register.py` defines it, only
   `test_workshop_critique.py` writes it, and `drop_summary`'s third branch is therefore **dead code**.
   D-W4-1 requires the drop log to separate two OPPOSITE measured failures — the loop **SPINNING**
   (re-proposing its own rejects) and an over-eager dedup **strangling discovery invisibly**. Only the
   first is recordable today.
3. **`cluster_candidates`' EXCEPTION path does `stats["calls"] = 0` — an ASSIGN** — while the success
   path in the same function does `int(stats.get("calls") or 0) + calls`. Same function, opposite
   branches, and only one was fixed during 15.7. One raised clusterer in one round therefore **zeroes
   every earlier round's accumulated count**, and the function's own comment states that
   `stats["calls"]` reaches the run's call total. **D-W5-7.**

Purpose: 15.8-15 is the ONE measuring run. A drop log that can only express one of the two failures it
was built to tell apart produces a number nobody can act on, and there is no second run to correct it.
Defects 2 and 3 are the same consequence class reached from opposite directions — **a number that is
wrong in the only run there will ever be**: one inflates a drop metric, the other deflates the spend
signal.

Output: a newest-first bounded barred block, a production live-drop writer, a cause-filtered
`count_drops` counter, an accumulating exception path, and tests that go red when each fix is
reverted.
</objective>

## The alternative is REJECTED, explicitly, not omitted

15.7-VERIFICATION.md offered two ways to close the `DROP_CLUSTERED_ONTO_LIVE` gap:

- **(a) Write the second drop cause in production.** ← **TAKEN.**
- **(b) Delete the constant and record that half of D-W4-1's drop signal was descoped.**

(b) is rejected because D-W4-1 does not treat the two causes as a nice-to-have pair. It names them as
two *opposite measured failures* and states, in the register's own module docstring and in
`record_drop`'s, that **"3 drops" is the same number in both worlds** and only what each clustered

structurally unable to detect the failure the Wave-4 harness actually measured more of — the dedup

one trustworthy measurement is the wrong trade.

Writing it is also cheap: the site already exists, adjacent to the working
`record_drop(..., cause=DROP_CLUSTERED_ONTO_BARRED)` call, and the emitter, the cause constant and the
summary sentence are all already built and tested.
</branch_decision>
