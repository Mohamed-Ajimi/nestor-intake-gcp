## THE ONE THING TO READ IF YOU READ NOTHING ELSE

**The review's preferred fix for CR-01 does not work, and the reason matters more than the fix.**

The review proposed capturing `_claims_predupe = list(claims)` before `pipeline.py:2641` and deriving
the two per-provider columns from it. Two independent facts defeat that, both verified against
running production code rather than reasoned about:

1. **`_dedupe_claims` mutates the surviving dict IN PLACE.** A shallow list copy therefore holds the
   *same object* and shows the merged `found_by` and the unioned `source_urls` afterwards. Probe:

   ```
   SURVIVOR is the SAME OBJECT as the pre-dedupe entry: True True
   pre-dedupe snapshot entry 0 found_by AFTER dedupe: ['gemini', 'openai']
   pre-dedupe snapshot entry 0 source_urls AFTER dedupe: ['http://g-a', 'http://g-b', 'http://g-c', 'http://o-a']
   ```

2. **The merge has already happened before `pipeline.py` ever sees a claim.**
   `synthesis/steps.py:2723` runs `_dedupe_claims(d8_claims + fallback_claims)` inside
   `collect_provider_facts` and returns the *result* as `ProviderFactsResult.claims`;
   `pipeline.py:2478` binds that. The `_dedupe_claims` call at the merge stage is the near-no-op its
   own comment says it is. **There is no pre-merge claim list in `pipeline.py` at any depth of copy.**

So the preferred fix requires `pipeline/synthesis/steps.py` to carry the pre-merge list out — a file
outside the stated scope (`pipeline.py` + its tests). Per the brief's explicit pre-authorisation I
took **the `None` fallback rather than expanding scope**, and both facts are now pinned by tests so
the next person does not re-attempt the same repair.

**Consequence for the run, stated plainly: two of eleven `assignment_yield` columns will be NULL.**
Nine carry a measurement. Recorded in `15.8-15-PLAN.md` and `15.8-UAT.md` as NOT MEASURED, with an
instruction not to record it as a defect and not to quote a per-provider figure.

**Open decision for the lead:** authorising a `synthesis/steps.py` change to restore
`fact_list_parsed` and `resolvable_sources` before the run is the only way this run produces those
two columns at all. That is a scope call, not an executor call.

## What was done

### CR-01 (CRITICAL) — two yield columns were cross-contaminated between providers

`_dedupe_claims` unions `source_urls` and appends the incoming provider to `found_by` while keeping
the first occurrence's `fact_source`; `_claim_matches_assignment` then attributes that one merged
dict to *every* provider in `found_by`. So `resolvable_sources` counted the union of every
corroborating provider's URLs on **each** of their rows, and `fact_list_parsed` reported the first
provider's parse outcome for all of them. Reproduced on production code: an openai angle citing ONE
url and falling back to the distiller read `resolvable_sources=3, fact_list_parsed=True`.

The error is *systematically flattening* — it is worst exactly when corroboration works, destroying
the per-provider discrimination D-R8 exists to measure.

- Both columns now bind `None`. `claims_kept` is untouched: its two ruled imprecisions and its shared
  denominator with `claims_surviving_verification` stand.
- The docstring now records, at query time, why the columns are NULL and where the pre-merge list
  would have to come from.
- `resolvable_sources`/`fact_list_parsed` remain in `_ROW_KEYS` and in the emitter's keyword set —
  the field contract is unchanged, only the values are.

**Files:** `pipeline.py`, `tests/test_pipeline_assignment_yield.py` · **Commit:** `c6c917d`

### WR-03 — a hostile `bracket` cost two columns that were already computed correctly

The `str()` at `research_division.py:1207` is genuinely harmless (compared to a constant, never
written to a column) — **that judgement is confirmed and was not changed**. The *scoping* was the
defect: one outer `except` for the whole function, so a raise there discarded the `group_id` and
`client_question` computed two statements earlier. Probe on the real function returned
`{'group_id': None, 'client_question': None}` where the correct answer was `{'g1', 'Q1'}`.

Fixed with the non-string-is-absent rule the same function already applies to `corroboration_key` and
`focus_area`. Unreachable today only because `_group_angle` stringifies first — the
agree-by-accident-of-construction reasoning 15.6's CR-01 disproved.

**Files:** `research_division.py`, `tests/test_research_division_yield.py` · **Commit:** `094209d`

### WR-04 — the confident zero in the counter that justifies the whole loop

`_count_of` floors at `_safe_int(value, 0)`, so a NULL was **unwritable** in all eight
`workshop_round_yield` counters and the NULL-vs-0 doctrine that `workshop_round_yield.py` and
migration 0018 both assert was unreachable. The only production call site compounded it with
`verdict.get("new_entrants") or 0` — exactly the confident zero `round_metrics`' no-default design
exists to refuse, for the counter spec § 6 calls *the loop's entire justification*.

- New `_count_or_none`: `None` or unreadable → `None`, **never `0`**. It deliberately **keeps** the
  list-length convenience, so a caller who passes the collection instead of its length still gets the
  length — turning that into a NULL would trade a fabricated number for a lost one.
- The four D-W5-17 counters use it; **the other ten stay on `_count_of`** (they feed
  `_stage_b_result`'s prose-adjacent `loop_rounds`, are not D-W5-17 columns, and no NULL doctrine
  applies). A test pins that scope so a wider application goes red.
- The call site drops the `or 0`. `weak_winners` next door **deliberately keeps** its `or 0` — it is
  winner-scoped, not a D-W5-17 column — and now serves as the AST check's positive control.

**Said plainly rather than overclaimed:** `exit_verdict` has a single return statement and always
carries an `int` `new_entrants` today, so nothing is currently mis-recorded. This is defence in
depth — what changes is that a *future* absence becomes visible instead of becoming a zero.

**Files:** `workshop_loop.py`, `workshop_rank.py`, and both test files · **Commit:** `2529fc2`

## Deviations from the brief

**1. CR-01 took the stated fallback, not the preferred fix.** Pre-authorised by the brief
("Take the fallback rather than expanding scope, and say so"). The reason is stronger than the brief
anticipated: the preferred fix is not merely *wider* than the seam, it is **inert as written** —
`list(claims)` shares the dicts — and even a deep copy would capture already-merged claims because
the merge runs in `collect_provider_facts`. Both facts are pinned by tests.

**2. WR-04 used `_count_or_none` instead of raw pass-through.** The review suggested `round_metrics`
return the raw value for the four counters. Raw pass-through would have discarded `_count_of`'s
list-length safety net, so a caller passing a list would write NULL instead of the count — trading a
fabricated number for a lost one. `_count_or_none` satisfies the stated invariant (an absent or
unknown value is distinguishable from a measured zero) and keeps the net. Flagged rather than
silently substituted.

**3. WR-05's sentinel symbol differs from the review's suggestion.** The review proposed
`grep -q "D-W5-8" .../15.8-06-DECISION-RECORD.md`, but that file is already 15.8-06's sentinel row —
reusing it would leave 15.8-08 with no sentinel of its own. Used `_scrub_urls_in_value` from 15.8-08's
own `must_haves.artifacts` instead: a code symbol in a tracked file, which is strictly stronger.

No architectural changes. No file was touched outside those listed.
