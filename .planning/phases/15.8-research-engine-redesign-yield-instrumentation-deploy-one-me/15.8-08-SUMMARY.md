## Task 3 — URL credential redaction on both halves (commit `5c04421`)

**Both defects confirmed live in source before fixing:**

1. `_redact_dict` matches **key names only** — `{"url": "...?api_key=LIVE"}` passed through
   untouched. SerpApi authenticates by query parameter.
2. `safe_response` was a bare `deepcopy` — **no redaction at all** on the half that
   `write_failure` fills with `{"error": str(error)}`, reachable because `serpapi.search`
   does not wrap its `httpx` call.

Added `_scrub_urls_in_value` (regex-based, non-raising, depth-capped, walks
`str`/`bytes`/`dict`/`list`) plus `_CREDENTIAL_QUERY_PARAMS`; the regex is **derived from
the constant** so the vocabulary has one source of truth. Both mechanisms now run on both
halves. Module docstring updated to match.

Acceptance verify, verbatim:
```
'https://serpapi.com/search.json?q=x&api_key=[REDACTED]'
'https://example.com/a?utm_source=x&q=coffee'
OK
```

**Byte-level storage round trip** (the assertion that matters): tests drive the real
`upload_audit_body` through its `NESTOR_AUDIT_LOCAL_DIR` fallback and read the written bytes
back, so what is asserted is what reaches storage — not a helper's return value.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] Bytes values were not scrubbed
**Found during:** Task 3 edge probing.
**Issue:** the first draft passed `bytes` through untouched. `upload_audit_body` serialises
with `json.dumps(..., default=str)`, which **stringifies bytes into the stored blob** — so a
credential in a bytes value would have reached a 7-year-retained object.
**Fix:** scrub bytes, preserve the type, re-encode only when something changed, and leave
undecodable binary strictly untouched rather than corrupting evidence with a lossy decode.
**Commit:** `5c04421`.

### 2. [Rule 1 — bug in my own test] `param_name` extraction was wrong for multi-param URLs
Replaced with a stronger invariant: `scrubbed.replace("[REDACTED]", SECRET) == url`, which
catches over-redaction **and** any query-string rewriting.

### 3. [Rule 1 — my own gate would have been vacuous] The `REDACTION: PASS` self-satisfying grep
**The most important catch in this plan.** My first draft of `15.8-PRECONDITIONS.md` spelled
the literal string `REDACTION: PASS` inside the *instructions for producing it*. The runbook
clears the gate with `grep -q` for that exact string — so **the blocking credential gate
would have read GREEN while the scan had never been run.** The token is now never spelled
contiguously in the file, with an explicit in-place note saying why so nobody "tidies" it.
Verified: `grep -c "REDACTION: PASS"` → **0**.

### 4. [Deviation from an acceptance criterion — CONTEXT wins] `Nestor_Claude_Temp` appears 3×, not once
The plan's criterion says "exactly once". Satisfying it literally would require deleting the
warning that **the SerpApi rotation is NOT covered by the `Nestor_Claude_Temp` deferral** —
a substantive safety statement the phase brief explicitly requires. It appears once as the
CLOSED-BY-DECISION record and twice as that cross-reference. **It never appears as an open
item**, which is the criterion's actual intent.

### 5. [MY OWN WRONG PREMISE] I claimed the agent had no credentials for the audit bucket

**Row 5 and 5b are the ones worth carrying.** Row 5 found that `auth_token`, `x_api_key`,
`secret` and `password` could be deleted from the credential vocabulary with **nothing going

fails to go red is evidence about the mutation or the test, never automatically about the
