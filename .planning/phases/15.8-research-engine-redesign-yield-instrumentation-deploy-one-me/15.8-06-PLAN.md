## ITEM 1 — `catch_up_matches` counts newcomers in its own median

**Where it lives.** `pipeline/tribunal/workshop_loop.py::catch_up_matches` — a pure function over a
sequence of match counts. Its whole body, after cleaning, is: sort the values, return
`int(values[(len(values) - 1) // 2])` — the LOW median, as an `int`, deliberately not
`statistics.median` (which returns a float on an even-length list, and this value indexes a
schedule). Newcomers, whose `matches` is `0`, are IN `values`.

**Its one production caller.** `pipeline/tribunal/workshop_rank.py::run_tournament`, in the block
commented "THE CATCH-UP STAGE (D-W4-3), BEFORE the Swiss rounds":

    median = workshop_loop.catch_up_matches([e["matches"] for e in entries])
    catch_up = _catch_up_pairs(entries, median, seen)

**Where the no-op happens.** `workshop_rank.py::_catch_up_pairs` opens with `if median <= 0: return []`.

**So the schedule is a NO-OP exactly when the low median is 0, which happens exactly when at least
half the field has zero matches — i.e. when newcomers are ≥ half the field.**

**The arithmetic at the validated configuration, worked rather than assumed:**

- 3 client questions × 12 candidates = **36 candidates**.
- `workshop_loop.tournament_rounds(36)`: `_TOURNAMENT_ROUNDS_MIN = 6`, `_ceil_log2(36) = 6`, bounded
  above by `_TOURNAMENT_ROUNDS_MAX = 10` and by `total - 1` → **6 rounds**. Every incumbent therefore
  carries `matches = 6` after round 1.
- `workshop_evolve._NEW_PER_ROUND = 6`, and INVENT candidates are removed from the pool before
  stamping — so **at most 6 newcomers** enter a field of ~36.
- Round 2's sorted match counts are `[0]*6 + [6]*36` (42 values). The low median is
  `values[(42 - 1) // 2] = values[20] = 6`. Every newcomer gets a deficit of 6 and plays it.
  **THE SCHEDULE FIRES.**
- The no-op regime needs 6 newcomers against ≤ 6 incumbents — a total field of about 12. The
  measured population range is **23–41**. It is never approached.
- And it gets **further** away as a run proceeds, not closer: `_CATCH_UP_MAX_MATCHES`' own comment in
  `workshop_rank.py` records that with carried standings the median GROWS every loop round (measured:
  18 after three loop rounds over a field of 30).

**The honest defect that IS there.** Both `catch_up_matches`' and `_catch_up_pairs`' docstrings phrase
the guarantee unconditionally — *"a new candidate simply plays the matches it missed"*. There is a
regime in which it plays none and nothing in the code says so. Worse, it is **silent**:
`run_tournament`'s catch-up `log.info` is inside `if catch_up:`, so a no-op logs nothing at all.

**The two committed assertions that flip if the median excludes newcomers** — both in
`tests/test_workshop_loop.py`:

- `test_catch_up_matches_returns_the_low_median` — asserts `catch_up_matches([12, 12, 11, 0, 0]) == 11`.
  Excluding zeros gives `[11, 12, 12]` → **12**.
- `test_catch_up_matches_takes_the_low_side_of_an_even_field` — asserts `catch_up_matches([0, 1, 2, 3]) == 1`.
  Excluding zeros gives `[1, 2, 3]` → **2**.

The other four `catch_up_matches` tests, and
`test_workshop_tournament.py::test_a_catch_up_match_is_played_and_never_replayed` (which asserts only
`median > 0`), are unaffected under either ruling.

**⚠ VERIFICATION CORRECTED THE REVIEW HERE, AND THE CORRECTION IS THE POINT.** The review flagged
this as a defect. The verifier worked the arithmetic instead of accepting the warning and concluded
**D-W4-3 IS honestly delivered**. Nothing in this plan may reverse the two assertions above; the
operator may.

## ITEM 2 — `actions` sums `admission_resolver_calls`

**Where it lives.** `pipeline/tribunal/workshop_rank.py::run_workshop_stage_b` builds a local `calls`
as the sum of ten counters — `critique_stats["calls"]`, `tourney_stats["calls"]`,
`evolve_stats["calls"]`, `generative_stats["calls"]`, `meta_stats["meta_calls"]`,
`group_stats["calls"]`, `admission_stats["admission_calls"]`,
`admission_stats["admission_resolver_calls"]`, `admission_stats["classify_calls"]`,
`cluster_stats["calls"]` — under a comment block headed "THE ADMISSION GATE AND THE CLUSTERER (CR-07)".

`calls` is used at **exactly one site**:

    await _stage_b_feed_finish(feed, final, actions=calls, items_read=len(ranked), cost_usd=cost)

which forwards it to `runs/stage_feed.py::StageFeed.set_summary(actions=...)` → `summary["actions"]`.

**⚠ THE CORRECTION THE OPERATOR MOST NEEDS, AND IT MUST LEAD THE ITEM.** `15.8-CONTEXT.md` and
`15.7-VERIFICATION.md` both describe `actions` as *"the run's ONLY spend signal"*. **In the code it is
not a spend signal at all.** Dollars travel on the SAME call as a separate `cost_usd=` argument, built
from `admission_cost_usd`, `meta_cost_usd`, `group_stats["cost"]` and the four `cost_usd` stats.
`actions` is the workshop stage's only **CALL-COUNT** rollup. The redirect resolver records **no
cost**, so the dollar figure is uncontaminated — only the count is. Say this first; the rest of the
item only makes sense after it.

**What `admission_resolver_calls` actually counts.** In
`pipeline/tribunal/workshop_admission.py::admit_invented_angles`, phase 2:
`resolver_calls = 0`, then `if batch_urls: resolver_calls = 1`. **One per invocation, for the whole
batch** — that batching is deliberate (D-V01-11 collapsed 642 per-item requests into one). It counts
`citations/redirect_resolver.py::resolve_redirects`, an outbound HTTP redirect resolution gated by
`NESTOR_REDIRECT_RESOLVE_ENABLED`, with no provider billing.

**The magnitude, bounded.** `admit_invented_angles` is called at most once per loop round (in
`run_workshop_stage_b`'s loop, under `if invented:`). With `_LOOP_MIN_ROUNDS = 4` and
`_LOOP_MAX_ROUNDS = 10`, the overstatement is bounded by **4–10 actions**, against a total in the
dozens to low hundreds.

**Why the resolver is in the sum at all.** The CR-07 comment directly above it: *"All five of these
numbers were produced and NONE was read, so the grounded lookups — the loop's only web-grounded paid
component, and the one T-15.7-08-03 names as the denial-of-wallet risk — reported $0.00 and 0 calls."*
Removing the resolver line reverses part of a deliberate recent fix, and the record must say so.
(It survives the removal: `admission_calls`, `classify_calls`, `cluster_stats["calls"]`,
`admission_cost_usd` and `grounded_lookups` all remain read.)

**Adjacent fact, NOT a decision here:** the same sum already contains `classify_calls` and
`cluster_stats["calls"]`, whose own adjacent comment records that they *"record calls but no cost of
their own"*. `actions` mixes billing statuses in more than one place; the resolver is not unique.

**⚠ A SECOND, ALREADY-RULED DEFECT LIVES IN THE SAME TEN-TERM SUM — MENTION IT, DO NOT ABSORB IT.**
`15.8-CONTEXT.md`'s **D-W5-7** records that `workshop.py`'s `cluster_candidates` does
`stats["calls"] = 0` — an **assign**, not an accumulate — on its `except Exception` path, so one
raised clusterer in one round zeroes every prior round's accumulated count. That number is
`cluster_stats["calls"]`, **the tenth term of the very sum Item 2 is about**. The two are separate
defects pointing opposite ways: Item 2 asks whether the count should include work that was never paid
to a model; D-W5-7 is the same count silently losing work that was. D-W5-7 is already ruled and
belongs to **15.8-04**. Its only role in this record is to make Item 2's stakes concrete: two distinct
ways this one number can misreport the only run that will ever be measured were both found on
2026-08-04. **Do not re-rule it, do not fold it into an option, and do not let it widen Item 2.**

**⛔ A TRAP TO STATE, SO NO OPTION IS PROPOSED ON A FALSE PREMISE.** The obvious cheap home for a
split counter — `_stage_b_result`'s `counts` dict, which already carries `grounded_lookups` and
`admitted_angles` from the same stats dict — **has no consumer anywhere.** Grep for `.get("counts")`
across `tribunal/nestor_pulse_sdk` returns one unrelated hit in `pipeline.py`'s stage-logging state.
Adding a key there would be **inert instrumentation** — the exact class this project has been burned
by three times (V-01 stage logging, D-W4-11 workshop notes, the out-of-vocabulary `kind` trap), and
the exact reason D-W5-1 rejected `run_events`. Do not offer it as a cheap option.

**⚠ AND A SCHEDULING CONSTRAINT ON ONE OPTION.** Persisting the split as a real column on

schema and the `0018` migration, is a SIBLING PLAN IN THE SAME WAVE.** That option is not free: it
requires 15.8-05's plan to be amended before wave 1 executes. Present it with that cost attached.
