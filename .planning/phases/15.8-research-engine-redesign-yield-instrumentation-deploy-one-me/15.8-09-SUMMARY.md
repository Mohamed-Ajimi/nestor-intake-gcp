## READER-SIDE RULES FOR `assignment_yield` (for 15.8-15)

1. **DEDUPE ON THE NATURAL KEY `(run_id, provider, group_id, client_question)` BEFORE ANY
   SUM.** A resumed run's restored angle and `divide()`'s doubled high-stakes fallback copy
   each write **two rows on one key**. There is no UNIQUE constraint by ruling — a uniqueness
   violation inside a paid run is worse — and the rows are deliberately not collapsed in code,
   because collapsing would hide the condition the completer's not-exactly-one warning exists
   to surface.
2. **A SUM of `claims_kept` across providers EXCEEDS the claim count BY DESIGN.** A claim found
   by two providers is attributed to both, because it really did come out of both assignments.
   Separately, `_dedupe_claims` is first-wins on `corroboration_key`, so a statement found in
   two groups counts against the first group only and summing across assignments does **not**
   equal `len(claims)`.
3. **`fact_list_parsed IS NULL` means the assignment produced NO CLAIMS** — not that its fact
   list failed. `FALSE` means it had claims and every one was a `distiller_fallback`.
4. **`verified_at IS NULL` with `claims_surviving_verification IS NULL` means the run never
   reached verification.** `verified_at` SET with a `0` means verification **ran and kept
   nothing** — that is a measurement, and it is what distinguishes a bad provider from a broken
   pipeline.
5. `parent_kind = 'unknown'` is the **engine-bug** query (D-W5-10 sentinel, deliberately not a
   member of `PARENT_KINDS`). `parent_kind IN PARENT_KINDS` returns exactly the three ruled
   shapes.
6. **Never derive `parent_kind` from `client_question IS NULL`.** Both a mandate group with an
   empty label and a cross-cutting group write a NULL question, and they are different facts.

## What was red

Engine build `b1397467` — FAILURE. `collecting: 43 of 43`, **1 failed / 1753 passed / 13 skipped**.

test_research_division_yield.py::test_hostile_input_returns_the_conservative_shape_rather_than_raising[hostile5]

## The defect, and why it was TWO sites and not one

`assignment_identity` built BOTH of its provenance columns by `str()`-ing whatever the angle
carried. `str()` never raises, so a non-string was silently coerced instead of rejected:

| Site | Line | Column it writes | Covered by a test before this fix? |
|---|---|---|---|
| A | ~1178 | `assignment_yield.group_id` | Yes — `hostile5`, which is what went red |
| B | ~1200 | `assignment_yield.client_question` | **NO — a live, ungated hole** |

`str()` on a plain object yields `'<object object at 0x7f...>'` — **a memory address, different
on every process** — written into a provenance column of the table 15.8-15 reads as THE ONE
MEASUREMENT of a ~$45 run that cannot be repeated to check it. Such a row does not fail loudly:
it looks attributed, joins to nothing, and is believed. On Site B it is worse in kind, because
`client_question` is the column the yield table GROUPS BY — one fabricated address becomes its
own phantom client question holding a real slice of the run's spend.

Both sites were fixed. Fixing only the one the gate happened to catch would have left the
identical construction live one screen below it.

## The fix

One line per site: accept only `isinstance(raw, str)`; anything else is treated as ABSENT.

```python
group_id        = (raw_group.strip() if isinstance(raw_group, str) else "") or None
client_question = (raw_label.strip() if isinstance(raw_label, str) else "") or None
```

`.strip()` and the `or None` collapse are kept for genuine strings, so **migration 0017's
absent-is-NULL rule is preserved exactly** — "no key recorded" stays distinguishable from
"recorded as the empty key". For every `str` and for `None` the behaviour is byte-identical to
before; only non-strings change, and they change from fabricated to NULL. The docstring/comments
at both sites now state WHY, and the D-W5-2 reasoning already written there was re-read and
still holds.

## The "latent cross-plan contract" concern (raised by 15.8-13) DOES NOT SURVIVE INSPECTION

Verified in code rather than assumed:

1. **There is exactly ONE producer** of an angle's `corroboration_key` —
   `research_division.py:1655`, `"corroboration_key": str(group.get("group_id") or "")` —
   **already stringified at the write site.** Every other occurrence in `research_division.py`
   and `pipeline.py` is a read.
2. **`_one_angle`'s `_corroboration_key` stamp reads that same field** (`corr_key =
   angle.get("corroboration_key") or None`, ~:2354). Both consumers therefore read one
   stringified producer, so a `str`-only filter **cannot** create a disagreement with a stamp
   that never sees a non-string.
3. `focus_area` is the same story: every producer normalises through `str(...).strip()` or
   `(fa.get("focus_area") or "").strip()`, so a non-string cannot reach Site B either.

**Therefore the defect is unreachable in production today** — which is exactly why it was cheap
to fix properly rather than argue about. `test_group_id_can_never_disagree_with_the_existing_corroboration_stamp`
was re-checked rather than assumed safe: all five of its fixtures pass strings or omit the key,
so it is untouched by the change, and it stayed green through every run below.
