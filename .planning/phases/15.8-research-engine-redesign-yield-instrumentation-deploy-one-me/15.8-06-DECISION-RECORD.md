## ITEM 1 — `catch_up_matches` counts newcomers in its own median

### The correction comes first, because it changes the question

15.6's review flagged this as a defect. **Verification then worked the arithmetic and disagreed.**
`D-W4-3` — the catch-up schedule, this redesign's headline Wave-4 fix — **IS honestly delivered.**

So the question is *not* "fix a broken schedule". It is: **accept a documented boundary that the
validated configuration never reaches, or remove the boundary at a real price?**

### How it works, in one paragraph

A newcomer entering the tournament has played no matches, so it has no wins, so the standing sorts it
to the bottom. `catch_up_matches` fixes that by letting a newcomer *play the matches it missed* first.
It returns the field's **low median** match count. Newcomers, whose match count is `0`, are counted in
that median. Its one production caller is `run_tournament`, and the schedule is skipped entirely by
`_catch_up_pairs`, which opens with `if median <= 0: return []`.

**So the schedule is a no-op exactly when the low median is 0 — which happens exactly when newcomers
are at least half the field.**

### The arithmetic at the validated configuration, worked rather than assumed

| Step | Value | Source |
|---|---|---|
| Candidates | 3 client questions × 12 = **36** | Wave-4 validated config |
| Swiss rounds | `tournament_rounds(36)` → floor `max(6, ceil_log2(36)=6)`, capped by 10 and by `total-1` = **6** | `_TOURNAMENT_ROUNDS_MIN = 6`, `_TOURNAMENT_ROUNDS_MAX = 10` |
| Incumbent match count after round 1 | **6** each | — |
| Newcomers per round | at most **6** | `workshop_evolve._NEW_PER_ROUND = 6` |
| Round 2 sorted counts | `[0]*6 + [6]*36` → 42 values | — |
| Low median | `values[(42-1)//2] = values[20]` = **6** | — |
| Result | every newcomer gets a deficit of 6 and plays it — **THE SCHEDULE FIRES** | — |

The no-op regime would need 6 newcomers against **6 or fewer** incumbents — a total field of about 12.
The measured population range is **23–41**. It is never approached.

And it moves **further** away as a run proceeds, not closer. `_CATCH_UP_MAX_MATCHES`' own comment
records that with carried standings the median **grows** every loop round — measured at **18** after
three loop rounds over a field of 30.

### The defect that IS real

Two things, and neither is the schedule being wrong:

1. **Both docstrings promise unconditionally.** `catch_up_matches` says *"A new candidate simply plays
   the matches it missed"*; `_catch_up_pairs` repeats it. There is a regime in which it plays none, and
   nothing in the code says so.
2. **A no-op is completely silent.** `run_tournament`'s catch-up `log.info` sits *inside* `if catch_up:`
   — so when the schedule does nothing, it logs nothing at all.

### The two committed assertions that flip under option (b)

Both in `tribunal/nestor_pulse_sdk/tests/test_workshop_loop.py`. **Named here so that a ruling which
reverses them is a ruling made knowingly:**

- **`test_catch_up_matches_returns_the_low_median`** — asserts `catch_up_matches([12, 12, 11, 0, 0]) == 11`.
  Excluding zeros gives `[11, 12, 12]` → **12**.
- **`test_catch_up_matches_takes_the_low_side_of_an_even_field`** — its second assertion is
  `catch_up_matches([0, 1, 2, 3]) == 1`. Excluding zeros gives `[1, 2, 3]` → **2**.
  (Its first assertion, `[10, 12] == 10`, has no zeros and is unaffected.)

**Precision added at execution time, because it bounds the blast radius honestly:** a *third* test,
`test_catch_up_matches_returns_a_real_int_and_never_a_bool`, feeds the **same** `[12, 12, 11, 0, 0]`
input — but asserts only that the result is an `int` and not a `bool`, never its value. **It survives
either ruling.** The remaining three `catch_up_matches` tests (empty/unusable, hostile input,
negatives) and `test_workshop_tournament.py::test_a_catch_up_match_is_played_and_never_replayed`
(which asserts only `median > 0`) are likewise unaffected. So the count is **exactly two test
functions, two assertion lines** — not three, and not the whole battery.

### Options — Item 1

**(a) ACCEPT AND DOCUMENT, WITH A WARNING — `1a` — RECOMMENDED**
The function and both committed assertions stay byte-unchanged. Both docstrings gain the boundary
condition, replacing their unconditional phrasing. A `log.warning` is added at the one site that holds
both facts — `_catch_up_pairs`' `median <= 0` guard, which already has `entries` in scope — firing when
the median is 0 while some entry still has `matches == 0`.
*Gain:* no behaviour change at the validated configuration; a silent failure becomes a visible one;
15.8-15 gets a named line to grep for in the run log.
*Price:* the regime still exists. A future configuration (a much smaller pool, or a raised
`_NEW_PER_ROUND`) would enter it with only a log line to say so.

**(b) EXCLUDE NEWCOMERS FROM THE MEDIAN — `1b`**
Compute the median over entries with `matches > 0`, falling back to 0 when there are none.
*Gain:* removes the regime entirely; the schedule can never be a no-op.
*Price:* three separate costs. It **reverses the two committed assertions named above**. It **raises
the catch-up budget** — in the `[12, 12, 11, 0, 0]` case from 11 to 12 — so more paid flash matches,
and `_CATCH_UP_MAX_MATCHES = 120` (the `T-15.7-08-03` denial-of-wallet ceiling) moves closer to
binding. And it **changes a schedule that a ten-experiment harness validated**, days before the only
run that will measure it.

**(c) LEAVE IT ENTIRELY — `1c`**
Change nothing, record nothing.
*Gain:* zero work.
*Price:* two docstrings keep an unconditional promise the code does not make. That is precisely the
*"reads as a solved problem"* failure this module's own docstrings warn against twice, in capitals —
the same words used to condemn D-R11's inert median seed.

## ITEM 2 — `actions` sums `admission_resolver_calls`

### The correction comes first here too, and it is a bigger one

**`actions` is NOT the run's spend signal.** Both `15.8-CONTEXT.md` and `15.7-VERIFICATION.md`
describe it that way. In the code it is nothing of the kind.

`run_workshop_stage_b` finishes the stage with a single call:

    await _stage_b_feed_finish(feed, final, actions=calls, items_read=len(ranked), cost_usd=cost)

**Dollars ride separately, as `cost_usd`,** built from `admission_cost_usd`, `meta_cost_usd`,
`group_stats["cost"]` and four `cost_usd` stats. `actions` is the workshop stage's only **CALL-COUNT**
rollup — a sum of ten counters. The redirect resolver records **no cost at all**, so **the dollar
figure is uncontaminated.** Only the count is. Everything below is about a count, not about money.

### What `admission_resolver_calls` actually counts

In `workshop_admission.admit_invented_angles`, phase 2:

    resolver_calls = 0
    if batch_urls:
        resolver_calls = 1
        try:
            resolved = await resolve_redirects(batch_urls) or {}

**One per invocation, for the whole batch.** That batching is deliberate — D-V01-11 collapsed 642
per-item requests into one. It counts `citations/redirect_resolver.resolve_redirects`, an outbound
HTTP redirect resolution, with no provider billing.

### D-W5-14's sharpening — folded in here as that decision instructs

**`resolver_calls = 1` is assigned BEFORE the `await`, and regardless of the kill switch.**
`resolve_redirects` returns early when `NESTOR_REDIRECT_RESOLVE_ENABLED` is off — logging *"0 requests
issued"* — but the counter is already 1. Two consequences:

- **The counter's semantics are INVOCATION — not work, and not spend.** With the switch off it counts
  an operation that issues **zero HTTP requests**. Production defaults the switch **on**, so it usually
  does resolve; the semantics are still invocation.
- **This strengthens the case for removing it from the sum.** The term is not merely non-LLM work — it
  is work that **may be a complete no-op**, sitting inside the number a reader uses to judge what the
  run did.

**Also settled by D-W5-14, so you are not asked to weigh it:** the autouse `_no_live_redirect_resolution`
fixture in `tests/conftest.py` does **not** make `test_discovery_bracket.py`'s
`assert stats["admission_resolver_calls"] == 1` vacuous — because the counter is set before the call.
**No test needs changing under any option here.**

### The magnitude, bounded

`admit_invented_angles` runs at most once per loop round (under `if invented:`), and the loop runs
`_LOOP_MIN_ROUNDS = 4` to `_LOOP_MAX_ROUNDS = 10` rounds. So the overstatement is bounded by
**4–10 actions**, against a total in the dozens to low hundreds.

### Why it is in the sum at all

The CR-07 comment sits directly above the line: *"All five of these numbers were produced and NONE was
read, so the grounded lookups — the loop's only web-grounded paid component, and the one T-15.7-08-03
names as the denial-of-wallet risk — reported $0.00 and 0 calls."* Removing the resolver line reverses
**one line** of a deliberate recent fix.

**CR-07's concern survives the removal:** `admission_calls`, `classify_calls`, `cluster_stats["calls"]`,
`admission_cost_usd` and `grounded_lookups` all remain read. The grounded-lookup spend — the actual
denial-of-wallet risk CR-07 was written about — is untouched.

*Adjacent fact, not a decision:* the same sum already contains `classify_calls` and
`cluster_stats["calls"]`, whose own comment records that they *"record calls but no cost of their own"*.
`actions` mixes billing statuses in more than one place. The resolver is not unique in that.

### Why this matters more than the size of the number suggests

The **tenth term of this same sum**, `cluster_stats["calls"]`, carries a separate defect found the same
day: **D-W5-7**. `workshop.py`'s `cluster_candidates` does `stats["calls"] = 0` — an **assign**, not an
accumulate — on its `except Exception` path, so one raised clusterer in one round **zeroes every prior
round's accumulated count.**

This is not adjacency. **It is the same integer damaged from opposite directions:** Item 2 asks whether
the count should include work nobody ever paid a model for; D-W5-7 is that same count silently *losing*
work someone did. Two distinct ways this one number can misreport **the only run that will ever be
measured**, both found on 2026-08-04.

**D-W5-7 is already ruled and belongs to 15.8-04.** It is named here only to make Item 2's stakes
concrete. It is not on the table, it is not being re-ruled, and no option below may be widened to
cover it.

### A trap stated so you can see why no cheaper option 3 was offered

The obvious cheap home for a split counter is `_stage_b_result`'s `counts` dict, which already carries
`grounded_lookups` and `admitted_angles` from the same stats dict. **It has no consumer anywhere.**
Grepping `.get("counts")` across `tribunal/nestor_pulse_sdk` returns exactly **one** hit, and it is
unrelated — `pipeline.py`'s stage-logging state. A key added there would be **inert instrumentation**:
the exact class this project has been burned by three times (V-01's stage logging, D-W4-11's workshop
notes, the out-of-vocabulary `kind` trap), and the exact reason D-W5-1 rejected `run_events`.

### Options — Item 2

**(1) KEEP THE SUM AS IT IS — `2-keep`**
Leave the code alone; have 15.8-15's write-up state the definition.
*Gain:* no code change at all immediately before the run.
*Price:* the resolver count is **persisted nowhere** — it lives in the in-memory `admission_stats` dict
and in `workshop_admission`'s exit `log.info` (*"N batch resolution call(s)"*) — so subtracting it
later means reading a log line, not a field. A prose caveat is easy to lose. And per D-W5-14, the term
being kept may represent zero actual work.

**(2) REMOVE `admission_resolver_calls` FROM THE SUM — `2-remove` — RECOMMENDED, and D-W5-14
strengthens it**
One line out of the `calls` expression in `run_workshop_stage_b` — a file 15.8-10 already owns and is
already editing.
*Gain:* `actions` then means exactly one thing: **calls that went to a model.** Nothing is deleted —
the resolver keeps its own `admission_stats` key and its own log line. No schema change, no new
surface, nothing inert, **and no test change.**
*Price:* it reverses one line of the CR-07 fix (the quote is above, as is the argument that CR-07's
concern survives it), and the 15.8 `actions` figure is not directly comparable to a pre-15.8 one
without noting that the definition changed.

**(3) PERSIST THE SPLIT as a `workshop_round_yield` column — `2-persist`**
*Gain:* queryable across runs — **but only conditionally.** **D-W5-18** found that the yield tables
have **no read surface at all** (no endpoint, no seam verb, no UI), and ruled a blocking pre-flight
gate `Q-PRE-4` into 15.8-15 to grant `roles/logging.logWriter` to `nestor-run@` so they can be read.
So this option's headline benefit **depends on Q-PRE-4 landing**, not automatically.
*Price — both halves stated plainly:* **15.8-05 owns that schema and the `0018` migration, and is a
sibling plan in the SAME WAVE**, so its plan must be amended before wave 1 executes; **and D-W5-11 has
already ruled that "the columns stand exactly as D-W5-1 specified"**, resolving a `round_metrics`
mismatch by extending the emitter rather than the table — so this option also means **reopening
D-W5-11.**
It stays on the table. It must not be presented as cheap.
