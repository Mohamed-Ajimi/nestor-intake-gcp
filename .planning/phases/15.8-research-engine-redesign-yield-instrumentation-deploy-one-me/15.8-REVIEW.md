## Summary

Reviewed the thirteen-plan yield-instrumentation phase at the seams between plans, on the
premise that the green gate (engine 1765/0/13, gates 187/2 deselected) cannot see what it
does not construct. Verification was done against the **real modules** in a local venv
(gcloud's bundled Python + a targeted dependency subset; `tribunal/requirements.txt` pins
`litellm==1.86.1`, which will not resolve on that interpreter, so the full pin set was not
used). 289 of the phase's own tests pass locally. Two probe scripts against production code
confirmed the critical finding rather than hypothesising it.

**The headline:** the producer/consumer seam between `pipeline/synthesis/steps.py::_dedupe_claims`
(pre-existing) and `pipeline.py::_assignment_yield_rows` (plan 15.8-09) silently falsifies
`resolvable_sources` and `fact_list_parsed` — two of the eleven measured columns, and the two
that most directly answer D-R8's question "which provider actually yields surviving claims per
dollar". Every test fixture for those columns uses a single-provider `found_by`, which is not
the shape the redesigned engine produces: dispatch-by-topic sends every group to all three
streams precisely so that claims merge across providers. That merge is what breaks the columns,
and it is the normal case, not an edge case.

The rest is a spread of documentation-versus-behaviour gaps in exactly the places this phase
declared it would not tolerate them, plus one runbook artefact that serves two gates with two
different meanings.

**Checked and found clean, stated so the next reader does not re-derive it:**
- *Key symmetry.* `record_assignment` and `complete_assignment` both build their key through
  `_natural_key`; the pipeline passes raw values on both paths. No asymmetry.
- *Exact-string joins.* Both new `workshop_rank` joins normalise through `_text_key` on both
  sides. The `_claim_matches_assignment` group-id join compares `_corroboration_key` against
  `claim["corroboration_key"]`, which is stamped from the *same* value by
  `steps.py:2476` — an identity, not a string coincidence. The `facet` fallback join is safe
  because `divide()` writes `focus_area` already `.strip()`-ed at every one of its four
  producers (`research_division.py:1652, 1851, 1881, 1904, 1918`).
- *Drop-cause counters.* All three bare-length reads were swapped to `count_drops(cause=
  DROP_CLUSTERED_ONTO_BARRED)` (`workshop_rank.py:4833, 4844, 5401`). `barred_drops` is bound
  from `dropped_as_reproposal` and cannot conflate with `barred`.
- *Credential exposure.* Nothing in scope routes a URL, a query string or any secret-bearing
  value into a log line, an audit body or a DB column. `resolvable_sources` counts URLs and
  stores only the count. No new prompt in scope carries unbounded model-authored text:
  `barred_block` clamps per entry and now windows to the newest `limit`, and `drop_summary`
  interpolates integers only.
- *`str()` sibling at `bracket_text`.* The judgement that it never reaches a column is
  **correct**. Its failure scoping is not — see WR-03.
- *Migration 0018.* Column order matches the ORM, RLS ENABLE+FORCE+policy with `WITH CHECK`
  on both tables, downgrade is the exact inverse, no hashed `audit_log` column touched.
- *Termination.* `clamp_groups` step 0 cannot run away (appended groups are single-parent and
  hit the `len(buckets) <= 1` continue); `ceiling` is `max(1, ...)` there, so step 1's
  `weakest_first[1]` cannot IndexError.

## Critical Issues

### CR-01: `resolvable_sources` and `fact_list_parsed` are cross-contaminated between providers, silently, in the ONE measuring run

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:4464-4560` (`_assignment_yield_rows`), consuming `tribunal/nestor_pulse_sdk/pipeline/synthesis/steps.py:1543-1600` (`_dedupe_claims`)

**Issue:**

`pipeline.py:2641` runs `claims = _dedupe_claims(claims)` and `pipeline.py:2667` then builds the
yield rows from that **post-dedupe** list. `_dedupe_claims` keeps the first occurrence's dict
whole and, on a merge, (a) appends the incoming provider to `found_by` and (b) **unions
`source_urls`** (`steps.py:1587-1594`). It does *not* touch `fact_source`, which stays the first
occurrence's.

`_claim_matches_assignment` then attributes that single merged dict to **every** provider in
`found_by`. So for a claim two streams both found:

- `resolvable_sources` counts the **union of both providers' URLs** for *both* rows — not
  "how much citable ground a provider actually covered", which is the column's stated purpose
  in the docstring at `pipeline.py:4535-4537`.
- `fact_list_parsed` reports the **first** provider's parse outcome for *both* rows. A stream
  that fell back to the distiller reads `True` because a corroborating stream's D8 block parsed.

Confirmed against production code, not inferred. Probe (real `_dedupe_claims` +
real `_assignment_yield_rows`): gemini cites 3 URLs via its fact list; openai cites 1 URL and
fell back to the distiller; the two claim texts differ only by a trailing full stop, so they
merge:

```
after dedupe: 1 ['gemini','openai'] ['http://g-a','http://g-b','http://g-c','http://o-a'] fact_list
gemini claims_kept= 1 resolvable_sources= 4 fact_list_parsed= True
openai claims_kept= 1 resolvable_sources= 4 fact_list_parsed= True
```

openai's row records 4 resolvable sources (it cited 1) and `fact_list_parsed=True` (it fell
back). Both wrong, both plausible, neither detectable from the table.

**Why the gate is green.** Every fixture in `tests/test_pipeline_assignment_yield.py` for these
two columns (`:220`, `:230`, `:237`, `:253`) uses a single-provider `found_by`. No test in the
phase constructs a merged claim — which is the shape D-R4/D-W3-1 dispatch exists to produce
(every group to all three streams). The columns are tested against a shape the engine does not
emit.

**Why this is CRITICAL rather than an imprecision.** `_assignment_yield_rows`' docstring lists
two accepted imprecisions and both concern `claims_kept` only; it then asserts the
`fact_list_parsed` derivation "is exact except that it is `None` ... when the assignment produced
NO claims". It is not exact. And the contamination is *systematically flattening*: the higher
the cross-stream duplicate rate — i.e. the better corroboration works, which is the whole point
of the redesign — the more every provider's `resolvable_sources` converges on the same union,
destroying exactly the per-provider discrimination D-R8 exists to measure. There is no second
run to correct it.

**Fix:** attribute per-provider fields from the **pre-dedupe** claim list, which is still in
scope at the seam (`_n_stream_claims` is captured from it eleven lines up). Pass both lists and
derive `resolvable_sources` / `fact_list_parsed` from the provider's own claims while leaving
`claims_kept` on the post-dedupe list, so the two documented `claims_kept` imprecisions and the
shared denominator with `claims_surviving_verification` are untouched:

```python
# pipeline.py, at the INSERT seam — capture BEFORE the dedupe rebind at :2641
_claims_predupe = list(claims)
claims = _dedupe_claims(claims)
...
_yield_rows = _assignment_yield_rows(provider_results, claims, _claims_predupe)
```

```python
def _assignment_yield_rows(provider_results, claims, claims_predupe=None):
    ...
    own = [
        c for c in (claims_predupe if claims_predupe is not None else claim_list)
        if _claim_matches_assignment(
            c, provider=provider, group_id=group_id, client_question=client_question
        )
        # a pre-dedupe claim carries exactly ONE producer, so this is that provider's
        # own evidence and nobody else's
    ]
    fact_list_parsed = (
        any(c.get("fact_source") == "fact_list" for c in own) if own else None
    )
    urls = {
        u.strip() for c in own for u in (c.get("source_urls") or [])
        if isinstance(u, str) and u.strip()
    }
    # `claims_kept` stays on the POST-dedupe list — its two imprecisions are ruled,
    # and it must share a denominator basis with claims_surviving_verification.
```

If changing the seam signature is judged too wide this close to the deploy, the minimum
acceptable alternative is to **stop writing the two columns** (bind them `None`) rather than
write a number that reads as a measurement — a NULL is the honest record of "not recorded",
which is the rule the rest of this module already follows. Do not ship them as they are: an
absent measurement is recoverable, a fabricated one is not.

Add a regression test whose claim carries `found_by` with two providers and asserts the two
rows report **different** `resolvable_sources`.

### WR-01: `_dispatch_was_uniform` measures what was DISPATCHED, while its docstring and the feed comment claim what CAME BACK

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:4346-4394`, call site `:2208`, comment `:2188-2191`

**Issue:** Both the docstring ("UNIFORM means every group kept every COPY: it went out on all
three streams and **came back on all three**") and the feed comment repeat the return half. The
function is called at `pipeline.py:2208` with `angles`, bound at `:2093` from `divide(...)`, and
`run_angles` is not called until `:2379`. It cannot observe a return. What it actually measures
is *post-trim dispatch* — which is a real improvement over `_corroborated` and does close WR-06's
trim blindness, but it is a strictly weaker claim than the one written down.

Consequence: a run where all three streams are dispatched and one stream goes dark still prints
"every one of those N group(s) went to all 3 research streams" into the run record that plan
15.8-15 reads as THE measurement of the five-wave redesign. This is the same defect class that
15.8-06 ruling `1a` just corrected in `catch_up_matches` — a docstring promising more than the
code delivers — reintroduced two files over.

**Fix:** correct the claim rather than the code (the code is right for what it can see):

```python
"""Did every group go out on every stream? PURE, never raises. (WR-06.)

MEASURES DISPATCH, NOT RETURN. This runs BEFORE `run_angles`, so it sees the
post-trim angle list and nothing about which streams answered. A group dispatched
uniformly whose third stream then failed still reads UNIFORM here. Say "went to"
in the feed sentence and never "came back from".
"""
```
and drop "and came back on all three" from `pipeline.py:2189`.

### WR-02: a failed or timed-out angle contributes no `assignment_yield` row, so its spend is absent from the table entirely

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/research_division.py:2419-2450`, consumed at `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:2667`

**Issue:** `_one_angle` returns `(provider, _enriched)` only on the success path; a timeout or
runner error falls through and the angle never reaches `all_results`, so `provider_results`
carries no entry and `_assignment_yield_rows` emits no row. A deep-research call that ran for
thirty minutes and then timed out was billed and leaves **no trace at all** in `assignment_yield`.

Three modules (`assignment_yield.py:72-75`, `yield_records.py:41-44`,
`0018_yield_instrumentation.py:93-95`) warn at length that `SUM(cost_usd)` skips NULLs silently.
The larger silent omission is not a NULL cell — it is a missing row, and a missing row is
invisible to every diagnostic those three paragraphs describe. A reader comparing
`SUM(assignment_yield.cost_usd)` with `run.cost_usd_total` will find a gap with no column to
explain it.

**Fix:** either emit a row for a failed angle with `claims_kept = NULL`, `cost_usd` from the
partial result where one exists, and a `parent_kind` that still classifies it — or, if that is
too wide now, state the omission in `_assignment_yield_rows`' docstring beside the two
`claims_kept` imprecisions, so 15.8-15 prices it instead of discovering it:

```
⚠ FAILED ANGLES HAVE NO ROW. `run_angles` returns only successful assignments, so a
timed-out or errored angle — which may well have been billed — contributes nothing here.
SUM(cost_usd) over this table is therefore a LOWER BOUND on research spend, not the total.
Reconcile against run.cost_usd_total before quoting a cost-per-claim figure.
```

### WR-03: `assignment_identity`'s single outer `except` discards a group_id and a client_question it had already computed correctly

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/research_division.py:1170-1260`

**Issue:** The team-lead asked for the `bracket_text = str(bracket).strip() ...` judgement
(`:1207`) to be verified rather than accepted. **The judgement is correct**: `bracket_text` is
only ever compared to `question_grouping.GROUP_BRACKET_DISCOVERY` and never written to a column,
so the memory-address hazard that closed the `assignment_identity` gate defect does not apply.

The *failure scoping* around it is wrong. A raise anywhere in the body — including from
`str(bracket)` — is caught by the one handler at `:1247`, which returns
`{group_id: None, client_question: None, parent_kind: "client_question"}`. So a hostile
`__str__` on `bracket` costs the **group id and the client question that were already correctly
computed two statements earlier**, not just the bracket. Confirmed by probe against the real
function:

```
A:    {'group_id': None, 'client_question': None, 'parent_kind': 'client_question'}
A-ok: {'group_id': 'g1', 'client_question': 'Q1', 'parent_kind': 'client_question'}
```

Reachability today is nil — `_group_angle` writes `"bracket": str(group.get("bracket") or "")`
at `research_division.py:1671`, so the value arriving here is already a `str`. That is precisely
the "both sides happen to agree by accident of construction" justification that CR-01 in phase
15.6 proved is not enforcement, and this function's own docstring is built around losing as
little as possible.

**Fix:** one line, matching the non-string-is-absent rule the same function already applies to
`corroboration_key` and `focus_area`:

```python
bracket_text = bracket.strip() if isinstance(bracket, str) else ""
```

### WR-04: `workshop_round_yield`'s eight counter columns can never hold NULL, so the doctrine those columns were designed around is unreachable

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/workshop_loop.py:890-940` (`round_metrics`, via `_count_of` at `:~200`), consumed by `tribunal/nestor_pulse_sdk/pipeline/tribunal/workshop_rank.py:1964-1990`

**Issue:** `db/models/workshop_round_yield.py:69-74` and `0018_yield_instrumentation.py:50-56`
both state the rule: "NULL means *not recorded*; 0 means *measured zero*; the two must stay
distinguishable", and make every counter nullable for exactly that reason.
`_persist_round_yield` honours it (`record.get(...)` with no coercion) and `yield_records`
honours it (`_coerce_int` returns `None`, "NEVER 0", `yield_records.py:206-220`).

But the only producer defeats both. `round_metrics` passes every counter through
`workshop_loop._count_of`, which returns `0` for `None` (`len(None)` → `TypeError` →
`_safe_int(None, 0)`). So `keep_count`, `weak_count`, `kill_count`, `new_entrants_top_n`,
`barred_drops`, `candidates_in`, `new_candidates` and `round_no` are always a real int. A NULL
is unwritable, and any future wiring failure in the round path reads as a **confident zero** —
the fabricated-measurement outcome the table was built to prevent.

The call site compounds it: `workshop_rank.py:4888` binds
`new_entrants_top_n=verdict.get("new_entrants") or 0`. `round_metrics` deliberately gives its
four new kwargs no defaults so a forgotten wiring is a `TypeError` (`workshop_loop.py:860-866`);
the `or 0` at the only call site supplies the confident zero that design exists to refuse, for
the counter the loop's entire justification rests on.

**Fix:** either state the limit where a reader of the table will meet it (a paragraph in
`workshop_round_yield.py` saying these columns are `NOT NULL in practice`, and that a 0 in
`new_entrants_top_n` cannot be distinguished from an absent measurement), or make the round path
honour the doctrine — pass the raw values and let `yield_records._coerce_int` decide:

```python
new_entrants_top_n=verdict.get("new_entrants"),   # None stays None; the emitter coerces
```
with `round_metrics` returning the raw value for the four D-W5-17 counters rather than
`_count_of(...)`. Do not leave the two documents asserting a distinction the code cannot make.
