## Deviations from Plan

### 1. [Rule 1 — Bug] `test_a_winners_own_why_is_carried_onto_the_group_it_ended_up_in` was green ONLY because of WR-01

- **Found during:** Task 1, immediately after the fix.
- **Issue:** The test used `winners(4, parents=2)`, whose interleaving makes BOTH proposed
  groups mixed. It passed only because the WR-01 defect blocked the split: at
  `max_groups=2` with two proposed groups `room` was 0, and no merge was needed either — so
  **nothing was reshaped at all**. A test named for surviving reshaping never exercised any.
  With the split now unconditional, the two mixed groups are correctly regrouped BY CLIENT
  QUESTION into `[[0,2],[1,3]]`, which cuts across both of the model's groups, and two
  distinct sentences genuinely cannot both survive that.
- **Investigated, not assumed:** traced through `_whys_by_index` and `_why_for` on the real
  module. The `why` machinery is index-keyed precisely so it survives splits/merges/re-sorts,
  and its documented rule is that a group inherits its BEST-RANKED member's sentence.
  Winners 0 and 1 both came from the model's first proposed group, so both new groups
  inherit `"alpha groundwork"`. **The mechanism is behaving exactly as its docstring says.**
- **Fix:** repaired the test's PREMISE (single-parent proposal, so the assignment is left
  intact and the carrying itself is what is asserted), and added
  `test_a_reshaped_group_inherits_its_best_ranked_members_sentence` to pin the reshaping
  consequence explicitly rather than leave it as a future surprise. Both carry docstrings
  explaining the repair. This is the 8th test.
- **Files:** `tribunal/nestor_pulse_sdk/tests/test_question_grouping.py`
- **Commit:** `57843dc`

### 2. [Rule 2 — Missing safeguard] Two acceptance-criteria greps were self-invalidating

- **Issue:** The criteria `grep -v '^ *#' … | grep -c 'room = ceiling - len(work)'` and
  `… 'max_groups or 1'` strip only `#` comments, **not docstrings**. My first drafts quoted
  each defect literally in the rewritten docstrings, so both greps returned 1 — the guard
  reading green on its own explanation.
- **Fix:** reworded both docstrings to describe the defect without reproducing the literal,
  and stated in each why the literal is deliberately absent, so a later editor does not
  helpfully re-add it. Both greps now return 0 and the guards stay sharp against an actual
  reintroduction.

### 3. [Rule 3 — Blocking] The mutation harness read a stale `.pyc` and reported a phantom failure

- **Issue:** After the matrix, the restored, `git status`-clean tree reported
  `failed 1` — the zero-ceiling test, with logs showing the topic path making a call, i.e.
  **M3's behaviour from a tree that no longer contained M3.** The `__pycache__` bytecode from
  the last mutant was being read as valid.
- **Fix:** the harness now purges `__pycache__` on every restore and runs with
  `PYTHONDONTWRITEBYTECODE=1`. Re-running the full matrix gave **byte-identical mutant
  results** (so no mutant reading was ever contaminated — only the final restore reading was)
  and a genuinely green restored tree.
- **Worth carrying:** this is the fifth distinct harness bug in this workstream, and it
  matches the standing lesson — **the harness lies before the code does.** A `git status`
  clean tree is NOT sufficient evidence that a Python run measured the current source.
