# Phase 15.1 Plan 16: Render the Superseded Verdict Class Summary

Gave the G-06 `superseded` verdict class its own titled section on the superadmin verification
report and made its G-07 caveat render from `superseded_note` when no reconciliation note exists —
closing a silent-drop that plan 15.1-14's writer would otherwise have activated.

## What Was Built

**The gap.** `report.py` classes verdicts through an `if/elif` chain: a `superseded` verdict goes
EXCLUSIVELY into `verdicts.superseded` and never falls through to `support`/`refute`/`insufficient`.
The frontend did not type that field and rendered no section for it. The top-level `report.superseded`
list is a different thing (reconciliation-derived scoped findings) and only accepts rows that carry a
`canonical` value — which a single-member superseded group never has. So a claim the skeptic marked
"was true, has since changed" would have been rendered nowhere: not the row, not the caveat.

**Task 1 — three coordinated edits:**

1. `research.ts` — declared `superseded_note?: string | null` on `VerificationVerdictItem` (after
   `reconciliation`) and `superseded?: VerificationVerdictItem[]` on `VerificationReport["verdicts"]`
   (after `insufficient`). Both carry comments naming G-07/G-06 and pointing at the backend's own
   deliberate name-collision note, so the two `superseded` keys are not "tidied" into one later.
2. `VerificationReport.tsx` — `VerdictItemRow` now derives `reconNote` and `supersededNote`
   separately and renders the amber block from `reconNote || supersededNote`. Markup and styling are
   byte-identical to before; only the source of `note` changed. Docstring updated to record the
   fallback and its reason. A new `VerdictSection` for `report.verdicts?.superseded` sits between the
   `insufficient` section and the top-level `superseded` section, under its own heading, with a
   comment explaining the distinction.
3. i18n — `supersededVerdictsTitle` added to all three locales beside the existing `supersededTitle`:
   - en: "Superseded verdicts (true, since changed)"
   - nl: "Achterhaalde oordelen (klopte, sindsdien gewijzigd)"
   - fr: "Verdicts dépassés (vrai, depuis modifié)"

   Each reads distinctly next to the existing scoped-findings heading ("Superseded / scoped findings"
   / "Achterhaalde / afgebakende bevindingen" / "Constats dépassés / limités").

**Task 2 — the three gates.** Verification-only; it required no code change, because Task 1's edits
passed all three gates on the first run. No commit (nothing to stage).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `npm install` failed ERESOLVE; used `npm ci` against the committed lockfile**

- **Found during:** Task 2
- **Issue:** The plan (and CLAUDE.md, and the project memory note) state that this repo commits **no
  lockfile** and instruct installing with `npm install` if `node_modules` is absent. `node_modules`
  was indeed absent (it is gitignored, so a fresh worktree has none). `npm install` failed hard with
  `ERESOLVE`: freshly resolving `@hookform/resolvers@^5.2.2` pulls 5.5.0, whose optional peer
  `valibot@^1.0.0` conflicts with the `valibot@0.39.0` required by `@typeschema/valibot@0.14.0`.
  This is precisely the no-lockfile dependency-drift trap that broke production on 2026-07-21.
- **Root cause of the wrong premise:** the "no lockfile" rule is **stale**. It refers to *bun*
  (`bunfig.toml: saveTextLockfile = false`). An npm `package-lock.json` HAS since been committed:
  `git ls-files` shows `frontend/package-lock.json` (562 KB, tracked), and `frontend/Dockerfile:42-45`
  reads *"Install from the COMMITTED lockfile for a reproducible build (npm ci, not npm install)"*
  followed by `RUN npm ci`.
- **Fix:** installed with `npm ci --no-audit --no-fund`. This is strictly safer than what the plan
  asked for and satisfies every constraint it was protecting: it installs the EXACT locked versions,
  re-resolves nothing, never writes a lockfile, and cannot bump a dependency. It is also *exactly*
  what plan 15.1-15's frontend image build runs — so Gate 3 now mirrors that build rather than
  approximating it. Result: `added 868 packages in 33s`.
- **Files modified:** none (`node_modules` is gitignored; `package.json` and `package-lock.json`
  both verified byte-unchanged via `git diff --name-only -- frontend/package.json frontend/package-lock.json` → empty).
- **Commit:** n/a — no tracked file changed.

**2. [Rule 3 - Blocking] Reverted a build-generated `routeTree.gen.ts` line-ending artifact**

- **Found during:** Task 2 (after `npm run build`)
- **Issue:** The TanStack router plugin rewrites `frontend/src/routeTree.gen.ts` during the build,
  leaving it flagged as modified in `git status`. The plan and the environment constraints both
  forbid regenerating it.
- **Fix:** `git diff --stat` showed **no content change** — the flag was purely an LF→CRLF
  line-ending artifact of the regeneration. Restored with the sanctioned per-file
  `git checkout -- frontend/src/routeTree.gen.ts`. No blanket reset or `git clean` was used.
- **Files modified:** none (restored).
- **Commit:** n/a — never staged.
