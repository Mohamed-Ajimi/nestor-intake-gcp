# Phase 15.1 Plan 08: Persist the Verification Funnel Summary

`run.verification_summary` had no production writer — migration 0011 created it, the ORM
declared it, `report.py` read it, and only the test fixture loader ever wrote it. It now gets
written by the live pipeline, in the same SQL statement that marks the run `completed`, so a run
cannot report success while its honesty marker is missing.

## What Was Built

### Task 1 — the funnel on the result contract + the feed's closing sentence (commit `5f59a0b`)

**The carrier.** `_write_final_report`'s return dict gained a top-level
`"verification_summary": verification_report["funnel"]`, following the `rejected_claims`
precedent exactly — a plain result key the worker picks up defensively. The zero-claim early
return carries the same key bound to the same all-zero `_build_funnel(...)` object, so the
worker's persistence path never has to branch on which path produced its input (RESEARCH
Pitfall 10). The module docstring's documented return shape was updated to match.

There is now **one funnel object per run**, built once and referenced three times — the
synthesis bundle, the verification report, and the result key. It cannot drift between the feed,
the operator report and the persisted column because they are literally the same dict.

**The closing feed line (G-10).** `_verify_closing_item(funnel)` builds the verify stage's final
D15 row. When bucket 3 is non-empty it leads with the degradation in a full sentence:

> VERIFICATION DEGRADED — 226 of 424 selected claims were never checked (crash, usage cap,
> budget exhaustion or gate error). Their passages ship unexamined: only a refutation removes
> one. Do not read this run's verification as green. — 198 of 424 selected claims checked ·
> 706 not checkable · 32 stable facts skipped · 176 skeptic sessions

On a healthy run it is a plain completion line with the same counts. **`status` is `"failed"`** —
see Deviation 2 for why that value and not a new one.

`verify_sessions` is carried and printed, never asserted and never derived from the cluster count
(G-13); `grep -c "assert.*verify_sessions"` in `pipeline.py` returns 0.

### Task 2 — the single-transaction completion write (commit `29efa64`)

The worker's existing completion `UPDATE` was **extended**, not supplemented:

```sql
UPDATE run SET status='completed', completed_at=NOW(),
  verification_summary = CAST(:vsummary AS JSONB),      -- only when a funnel exists
  cost_usd_total = COALESCE((SELECT SUM(cost_usd) FROM audit_log WHERE run_id = :id), 0)
WHERE id=:id AND status='running'
```

- **One statement, one transaction** (T-15.1-36). Status and marker are the same write; there is
  no window in which a row reads `completed` with a NULL funnel because a second statement had
  not landed yet.
- **The cancel guard is byte-identical.** `WHERE id=:id AND status='running'` and the
  `completed.rowcount` gating on the two output inserts are untouched, so a user cancel still
  makes the whole thing a no-op and the cancelled verdict sticks (T-15.1-37).
- **`set_tenant_context` is still the first statement inside `session.begin()`** (line 206,
  carrying its T-06-02 comment) — not moved, not removed, not duplicated. Every tenant-scoped
  write to `run` depends on that GUC (ASVS V4 / T-15.1-35).
- **No funnel means NULL, not zeros** (T-15.1-38). `_has_summary` is `isinstance(dict) and
  bool(...)`; when false the original statement executes unchanged. `report.py` renders NULL as
  "this run has no gate data", whereas a zeroed funnel would certify a clean bucket 3 that
  nobody measured — worse than no funnel at all.
- **`run_verification_degraded`** structlog warning fires before the transaction when
  `should_have_been_checked > 0`, carrying run id, the bucket-3 count, `selected_verify` and
  `checked`. The UI can be closed; the log cannot.

No run status added, `RunStatus` untouched, no migration (`ls alembic/versions | grep ^0012` = 0).

## Deviations from Plan

### 1. [Rule 3 - Blocking] Worktree was 100 commits stale — fast-forwarded to master

**Found during:** setup, before Task 1.
**Issue:** the branch sat at `a3a0c96`, 100 commits behind `master` (`9d74aa4`), with zero unique
commits. Plan 15.1-07's gate stage — the direct base for this plan, in the same file — was
absent, as were `_build_funnel`, `apply_gates` and `test_gate_selector.py`.
**Fix:** `git merge --ff-only master`, lossless (`git rev-list --count master..HEAD` = 0). The
three dependency checks then passed. **This is now 6 of 8 agents cut stale in this phase.**

### 2. [Rule 1 - Bug] The reconciliation + funnel build moved up, because a late `set_stage("verify")` rewinds `current_stage`

**Found during:** Task 1.
**Issue:** the plan says to emit the closing verify row "after the verify stage completes", and
15.1-07 left the ground-truth bucket-3 reconciliation down in the synthesis block (old lines
974-991) — which is **after** `set_stage(..., "synthesize", ...)`. `set_stage` writes
`current_stage = :stage` as well as merging the detail, so emitting a `"verify"` row from there
would have rewound `run.current_stage` from `synthesize` back to `verify` mid-synthesis. The D15
feed and `runs/api.py` both read `current_stage`; the operator would have watched the run walk
backwards. Waiting until the funnel was known and reporting nothing was not an option either —
that is the silent outcome G-10 exists to prevent.
**Fix:** the reconciliation and the single `_build_funnel()` call now sit immediately after the
coverage-gate loop's final adjudication, followed by the closing `set_stage("verify", ...)`. That
is the correct place on the merits: the coverage re-entry is the **last** thing that can turn an
unchecked claim into a checked one, so the number is final there, and nothing between that point
and synthesis adds a verdict (conflict resolution only moves claims between `survivors` and
`dropped`). The old site now carries a comment pointing at the new one. Behaviour of the number
itself is unchanged — same expression, same inputs.
**Files modified:** `pipeline.py` · **Commit:** `5f59a0b`

### 3. [Decision] The degraded feed row uses `status="failed"`

The plan required picking a status the feed already renders. `ResearchRunProgress.tsx` handles
exactly five: `done`, `running`, `retry`, `failed`, `pending` — `failed` gets a red
`AlertTriangle` and the `statusFailed` label; everything else falls through to neutral styling.
`retry` (amber) would be a lie — nothing is retrying. `done` is the quiet failure this phase
exists to kill. `failed` is the honest one: part of the verification stage **did** fail, even
though the run completes. This is a stage-item status in `stage_detail` JSONB, which is purely
presentational — nothing in the backend reads item statuses, and the run's own status is set by
the worker — so it cannot be confused with a failed run (G-10 holds: status stays `completed`).

### 4. [Minor] The funnel clause is concatenated into the statement, not always-bound

The plan's acceptance grep wants the literal `verification_summary = CAST(:vsummary AS JSONB)` in
the UPDATE, and its action says to execute "the original statement unchanged" when no funnel
exists. A single always-present clause binding `None` would write SQL NULL — same result — but it
would also bind a parameter on the ADK path, and "unchanged" is the stronger guarantee for a
statement this load-bearing. So the clause is a constant string concatenated in when
`_has_summary` is true. **No value is ever interpolated into SQL** — the funnel travels as the
`:vsummary` bind parameter, JSON-serialised with `json.dumps(..., ensure_ascii=False)`. The
concatenated fragment is a compile-time literal.

### 5. [Minor] `import json as _json` hoisted

`_json` was imported inside the transaction body (for `rejected_claims`); it is now imported a
few lines earlier, next to the funnel read, since both need it. The later site carries a comment
saying so.

### 6. [Scope boundary] No new test file

The write path deserves a test asserting the funnel lands in the column. `files_modified` lists
two files and the orchestrator's success criteria say "only `pipeline.py` and `worker.py`
touched", so none was added. **Follow-up for 15.1-09/10 or the phase verifier:** a Postgres-backed
test that runs `execute_run` with a `verification_summary` in the result and asserts the column is
populated *and* that a cancelled run leaves it NULL. Today's coverage is indirect — the full
suite's worker tests prove the statement still executes and still gates on `rowcount`, and the
critical build proves the SQL is valid against real Postgres, but nothing yet reads the column
back on a live worker run.

## Notes for Downstream Plans

- **`run.verification_summary` is now populated for real runs.** `report.py` needs no change —
  it already reads the column and shapes `accounting` from it. What was fixture-only is live.
- **A NULL column still means "pre-15.1 or non-Tribunal run"**, not "clean". Any consumer that
  reads NULL as zeros re-introduces the P1 defect this phase closes.
- **The funnel is one object with three readers.** If you add a key, add it in `_build_funnel` —
  the feed line, the verification report and the persisted column all pick it up for free. Keys
  are **additive only**; `test_hash_chain_replay.py` and `test_verification_report_endpoint.py`
  compare `RECORDED_FUNNEL_COUNTS` by full dict equality.
- **15.2's R6** now has a persisted marker to promote. When `RunStatus` gains
  `completed-degraded`, the value to branch on is `verification_summary->>'verification_degraded'`
  on the run row — it is written in the same statement as the status, so the two can never
  disagree. All four `status == "completed"` endpoint gates must move together (G-10).
- **Do not issue a `set_stage("verify", ...)` from anywhere after the synthesis block.** It
  rewinds `run.current_stage`. Deviation 2 explains the trap; it applies to every stage key.
