# Phase 15.1: Code Review Report

**Reviewed:** 2026-07-25
**Depth:** standard
**Files Reviewed:** 23
**Status:** issues_found

## Summary

The gate machinery itself (`gates.py`) is the strongest part of this phase. The
fail-toward-more-checking inversion is implemented consistently, `_parse_gate_lines` is
bounds-checked and never touches `json.loads`, the 240-char truncation + index-addressing
prompt-injection control is present in both new prompt builders, the cap-400 no-retry rule is
correct, and the funnel arithmetic is computed from per-claim decisions rather than running
counters. `test_gate_replay.py` is a genuinely adversarial gate: it drives the real batching,
semaphore, parser and funnel with a fake that answers only the model, asserts exact call counts
(not `> 0`), and asserts the fake is not a real client. Claim conservation holds on every path I
traced through `apply_gates`, `group_claims` and `_cluster_keys`.

The defects cluster in the **publishing** half of the phase, not the gating half. Two of them
are blocking:

1. `superseded_note` (G-07) is produced, schema-declared, and then consumed by nothing — not
   synthesis, not the database, not the report shaper. A `superseded` claim survives adjudication
   by design, so its passage ships in the prose with no caveat anywhere. This is exactly the KPAnG
   failure G-06/G-07 were written to close, and `test_superseded_verdict.py` is written so that it
   passes on the non-functional feature.
2. No production code path writes a `verification_verdict` row. On a real 15.1 run the operator's
   `/verification` payload will report `accounting.checked = N` alongside
   `unverified.count = total_claims` and four empty verdict lists — two sibling numbers in one
   payload contradicting each other.

Beyond those, the coverage gate and the phase's own bucket-3 site (c) are unreachable dead code,
the operator-facing degradation sentence mislabels a per-claim count as batches, the new `gate`
stage is not declared in the engine stage schema the API ships, the funnel invariants are bare
`assert`s, the CI gate config cannot fail on a missing test file, and two documented operator
tunables can crash or hang the worker at zero.

## Critical Issues

### CR-01: `superseded_note` (G-07) is dead data end to end — the caveat reaches no consumer

**Files:**
`tribunal/nestor_pulse_sdk/pipeline/tribunal/group_skeptic.py:137-149`,
`tribunal/nestor_pulse_sdk/verification/report.py:61-69`,
`tribunal/nestor_pulse_sdk/db/models/verification_verdict.py:59-63`,
`tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:968-974`,
`tribunal/nestor_pulse_sdk/runs/schemas.py:235-237`

**Issue:** G-07's stated contract is that the caveat "travels as pipeline DATA so synthesis
presents it rather than the writing model phrasing it from memory"
(`group_skeptic.py:142-145`). It does not travel anywhere:

- `_parse_group_verdict` writes `superseded_note` into the verdict dict (`group_skeptic.py:146`).
  Those dicts land in `verdicts_by_claim` (`pipeline.py:703`).
- `synthesize_report` is called with `mission_brief`, `cleaned_reports`, `contested_notes` and
  `report_spec` only (`pipeline.py:1223-1230`). `contested_notes` is built from
  `group_reconciliations` and `conflict_detector` output (`pipeline.py:968-1001`) — never from
  `superseded_note`. Grep confirms `superseded_note` has zero occurrences in
  `pipeline/synthesis/`.
- `verification_verdict` has no `superseded_note` column, and the phase deliberately ships no
  migration, so it cannot be persisted.
- `_verdict_dto` (`report.py:61-69`) returns five keys and `superseded_note` is not one of them,
  so `VerificationVerdictItem.superseded_note` (`schemas.py:237`) is unconditionally `None` on
  the wire despite the comment claiming it was "declared so it survives the round trip".

Meanwhile `adjudicate()` counts only `refute` (`adjudicate.py:98`), so a `superseded` claim
survives, is never in `dropped`, is never passed to `scrub_research`, and its passage ships in
the delivered prose. Concrete failure scenario: the skeptic finds a 2026-07-22-style KPAnG claim
was true until 1 April 2026, emits `superseded` + a note quoting the source; the report body
still asserts the obsolete fact as current, and no surface — feed, report, appendix — carries the
"applied until 1 April 2026" caveat.

`test_superseded_verdict.py:159-186` is the test that should have caught this. Its assertion is
`parsed["verdicts_by_index"][0]["superseded_note"] == note`, i.e. that the parser returns what
the parser was given. That assertion holds whether or not any consumer exists.

**Fix:** Either wire it, or withdraw the claim. To wire it, the minimum is to carry the note into
the notes the synthesiser already receives:

```python
# pipeline.py, inside _flush_groups, alongside the existing recon handling
for i, c in enumerate(grp["claims"]):
    v = vbi.get(i)
    if v is None:
        continue
    verdicts_by_claim[id(c)].append(v)
    if v.get("verdict") == "superseded" and (v.get("superseded_note") or "").strip():
        superseded_notes.append(
            f"[SUPERSEDED] {(c.get('text') or '')[:120]}: {v['superseded_note'].strip()}"
        )
# ...then, where contested_notes is assembled:
contested_notes.extend(superseded_notes)
```

and add `superseded_note` to `_verdict_dto` (`report.py:63-69`). Persistence needs a column, so
if the no-migration constraint holds this phase, record the API/DB half explicitly as deferred in
`15.1-UAT.md § Known gaps` rather than leaving a declared-but-always-null schema field.

### CR-02: nothing in production writes `verification_verdict`, so the operator report contradicts itself on a real run

**Files:**
`tribunal/nestor_pulse_sdk/verification/report.py:307-341`,
`tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:1035-1048`,
`tribunal/nestor_pulse_sdk/citations/extractor.py:282-352`

**Issue:** `build_verification_report` reads `verification_verdict` rows (`report.py:382-388`),
but the only writer of that table anywhere in the repo is the test fixture loader
(`tests/fixtures/run_4cbb5311/loader.py:421-434`). The production persistence path,
`persist_tribunal_claims` (`citations/extractor.py:282`), inserts `claim`, `source` and
`claim_source` rows only — grep for `VerificationVerdict(` outside `tests/` returns nothing but
the ORM definition.

Consequence for the first real 15.1 run:

| report key | value on a real run | value it should have |
|---|---|---|
| `verdicts.support` / `.refute` / `.insufficient` / `.superseded` | `[]` | populated |
| `refuted` / `superseded` / `reconciled` | `[]` | populated |
| `counts.verdicts_total` | `0` | one per checked claim |
| `unverified.claims_with_verdict` | `0` | ≈ `accounting.checked` |
| `unverified.count` | `total_claims` | `total_claims − checked` |
| `accounting.checked` | e.g. `380` | `380` |

`unverified.count == total_claims` and `accounting.checked == 380` are published side by side in
one payload. `report.py:314-316` explicitly justifies keeping `unverified` as a sibling "so the
operator surface binds to it and keeps working untouched" — so the shipped frontend will render
"every claim unverified" next to the new honest-accounting block.

This is why the G-06 verdict class is unobservable in production: 15.1 built the class, the
pydantic field, and `test_verification_buckets.test_new_keys_survive_the_pydantic_boundary` over
a table that never receives a row. All 15.1 tests drive `shape_verification_report` with
hand-built `SimpleNamespace` rows or the fixture, so none of them can surface the gap.

**Fix:** Add a verdict write in the same transaction as `persist_tribunal_claims`, keyed to the
claim row it just inserted (which also fixes the `claim_id IS NULL` problem `report.py:87-91`
works around):

```python
# citations/extractor.py, after claim_ids.append(claim_id)
for v in (verdicts_by_claim.get(id(claim)) or []):
    session.add(VerificationVerdict(
        tenant_id=tenant_id, run_id=run_id, claim_id=claim_id,
        verdict=v.get("verdict") or "insufficient",
        confidence=None if v.get("confidence") is None else str(v["confidence"]),
        evidence_refs=v.get("evidence_refs"),
        reconciliation=v.get("reconciliation"),
    ))
```

If that is out of this phase's scope, the `unverified` block must be suppressed (or explicitly
annotated "no verdict rows persisted for this run") whenever `counts.verdicts_total == 0` and
`accounting` is non-None, so the two numbers cannot be read as disagreeing facts.

### WR-01: the coverage gate — and the phase's own bucket-3 site (c) — is unreachable dead code

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:570, 845-890`

**Issue:** `verdicts_by_claim` is seeded with **every** claim at line 570
(`{id(c): [] for c in claims}`). `adjudications` is then built as
`{id(c): True for c in claims if id(c) in verdicts_by_claim}` (lines 848-852), which is therefore
`True` for every claim unconditionally. `check_coverage` fails a claim only when
`id(claim) not in adjudications` (`coverage_gate.py:61`), so `coverage["pass"]` is **always**
`True`, `coverage["uncovered"]` is **always** empty, the `while` at line 861 never executes, and
the newly-added bucket-3 site (c) at lines 886-888 can never fire. `reentry_count` is permanently
0, so `_verification_appendix`'s re-run line never renders either.

The inline comment at lines 846-847 states the opposite of the behaviour: "A claim is
'adjudicated' when it had skeptic verdicts run (n_skeptics > 0)".

Failure scenario: a high-stakes claim whose group skeptic crashed gets no verdict; the coverage
gate is supposed to be the last-chance re-entry that gives it three more skeptics. It never runs.
The claim is caught by the ground-truth reconciliation at line 916 and booked in bucket 3, so the
funnel stays honest — but the recovery mechanism this phase's own comments rely on ("the coverage
gate re-entry, which is the last thing that can turn an unchecked claim into a checked one",
line 909-911) does not exist.

**Fix:**

```python
adjudications: dict[int, Any] = {
    id(c): True for c in claims if verdicts_by_claim.get(id(c))
}
```

and correct the comment at 845-847.

### WR-04: the closing verify write rewinds `current_stage` backwards from `coverage`

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:857, 938-941`

**Issue:** `set_stage(..., "coverage")` runs at line 857. `set_stage(..., "verify", detail=...)`

### WR-05: `_status_of` accepts any integer on `.code`/`.status`, suppressing legitimate retries

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/gates.py:261-273, 334-338`

**Issue:** `_status_of` returns the first `int` found on `status_code`, `status` or `code` with no
range validation. Many provider/transport exceptions carry a non-HTTP `code` — gRPC status codes
(`14` = UNAVAILABLE, `4` = DEADLINE_EXCEEDED, `8` = RESOURCE_EXHAUSTED) being the obvious case
for a Google SDK. `_is_transient` then hits:

```python
status = _status_of(exc)
if status is not None:
    if status == 429: return True
    return 500 <= status < 600      # 14 -> False
```

and returns `False` **without ever reaching the `_TRANSIENT_MARKERS` message sniff below**. A
`ServiceUnavailable` whose message literally says "service unavailable" is classified hard and
gets exactly one attempt. The failure direction is safe (under-retry, and the gate then fails
toward more checking) but it silently defeats the retry policy the phase exists to make correct,
and inflates `gate_errors` on a genuinely transient blip.

**Fix:**

```python
if isinstance(value, int) and 100 <= value < 600:
    return value
# ...and for the string branch, keep the existing 3-digit fullmatch.
```

### WR-06: zero-valued gate tunables crash the run or hang the worker forever

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/gates.py:77-81, 432-433`

**Issue:** `infra/DEPLOY-RUNBOOK.md` Step 15.1.b documents `NESTOR_TRIBUNAL_GATE_BATCH` and
`NESTOR_TRIBUNAL_GATE_CONCURRENCY` as operator-settable knobs. Neither is clamped:

- `NESTOR_TRIBUNAL_GATE_BATCH=0` → `range(0, len(claims), 0)` at line 432 raises
  `ValueError: range() arg 3 must not be zero`, which propagates out of `apply_gates` through
  `TribunalPipeline.run` to `execute_run`, marking the run `failed` after the full deep-research
  spend has already happened.
- `NESTOR_TRIBUNAL_GATE_CONCURRENCY=0` → `asyncio.Semaphore(0)` at line 433 blocks forever. There
  is no timeout on the gate stage (unlike `_SKEPTIC_TIMEOUT_S`), so the worker hangs holding the
  run's advisory lock until the 60-minute stale-run reclaim, then does it again.
- Any non-numeric value raises `ValueError` at **module import**, taking the whole image down
  rather than the one setting.

`grouping.py:353` already guards its equivalent with `size = max(1, _CLUSTER_BATCH)`; `gates.py`
does not.

**Fix:**

```python
def _int_env(name: str, default: int, *, minimum: int = 1) -> int:
    try:
        return max(minimum, int(os.environ.get(name, str(default))))
    except ValueError:
        log.warning("gates: %s is not an integer — using %d", name, default)
        return default

_GATE_BATCH = _int_env("NESTOR_TRIBUNAL_GATE_BATCH", 40)
_GATE_CONCURRENCY = _int_env("NESTOR_TRIBUNAL_GATE_CONCURRENCY", 4)
_GATE_RETRIES = _int_env("NESTOR_TRIBUNAL_GATE_RETRIES", 2, minimum=0)
```

### WR-07: the 15.1 CI gate cannot fail on a missing test file

**File:** `tribunal/cloudbuild.test-gates.yaml:40-53`

**Issue:**

```bash
FILES=$$(ls ... test_gate_replay.py ... 2>/dev/null || true)
if [ -z "$$FILES" ]; then
  echo "no 15.1 gate test files present yet — nothing to run"
  exit 0
fi
```

`ls` with a missing operand prints the files that *do* exist and returns non-zero; `|| true`
swallows that, `2>/dev/null` hides the error. So deleting or renaming `test_gate_replay.py` — the
phase gate itself — silently removes it from the run and the build stays **green**. Deleting all
ten produces an explicit `exit 0`. The wave-ordering rationale in the header comment (files
"arrive across waves 1-5") no longer applies: all ten files are now committed.

**Fix:** enumerate explicitly and let pytest fail on a missing path, or assert the count:

```bash
EXPECTED=10
FOUND=$$(ls nestor_pulse_sdk/tests/test_gate_replay.py ... 2>/dev/null | wc -l)
[ "$$FOUND" -eq "$$EXPECTED" ] || { echo "expected $$EXPECTED gate test files, found $$FOUND"; exit 1; }
python -m pytest nestor_pulse_sdk/tests/test_gate_replay.py ... -v -rs --tb=short -m "not live"
```

### WR-08: the funnel invariants are bare `assert`s — strippable, and they fail the run

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/gates.py:560-578`

**Issue:** The four invariants that are the phase's structural honesty guarantee are `assert`
statements. Two problems:

1. `python -O` or `PYTHONOPTIMIZE=1` removes them entirely. Nothing in the image or the runbook
   guarantees they are off, and the loss is silent — the funnel would just start lying again.
2. When one *does* trip, `AssertionError` propagates out of `apply_gates` → `run()` → `execute_run`,
   which marks the run `failed` (`worker.py:280-295`) after the entire deep-research spend. A
   bookkeeping inconsistency detected *after* the expensive work should not discard the work.

**Fix:** raise a named exception the worker can distinguish, or (better, given the phase's
fail-loud posture) log at ERROR, set `gate_errors`/`verification_degraded`, and continue:

```python
if funnel["distilled"] != funnel["kept"] + funnel["dropped"]:
    raise GateFunnelInconsistency(
        f"distilled != kept + dropped — a claim was neither kept nor dropped ({funnel})"
    )
```

### WR-09: the gate output-format spec is ambiguous and self-inflicts `gate_errors`

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/gates.py:164-165, 194-195`

**Issue:** The format line is

```
INDEX | KEEP|DROP | KEEP|NOT_FALSIFIABLE|NOT_LOAD_BEARING|BOTH
```

`|` is simultaneously the field separator and the alternation operator. A model that echoes the
alternation (`0 | KEEP|DROP | KEEP`) yields `parts = ["0","KEEP","DROP","KEEP"]`; `values[1]` is
`"DROP"`, which is not in `_MATERIALITY_ALLOWED[1]`, so the row is rejected whole and the claim
is defaulted into the queue with `gate_error=True`. The failure is safe but expensive: every such
line adds an unnecessary skeptic session and a false entry in the operator-facing "gate errors"
count. `grouping.py:138` and `:164` use unambiguous placeholders (`INDEX | ENTITY | ATTRIBUTE`,
`INDEX | CLUSTER_ID`), so this is a regression in prompt discipline within the same phase.

**Fix:**

```
Output EXACTLY one line per claim, in input order (no extra text). Use exactly three
fields separated by " | ":
INDEX | DECISION | REASON
  DECISION is one of: KEEP, DROP
  REASON   is one of: KEEP, NOT_FALSIFIABLE, NOT_LOAD_BEARING, BOTH
Example: 7 | DROP | NOT_LOAD_BEARING
```

### WR-10: bucket-2 claims are verdicted and can be scrubbed while the funnel reports them "not checkable"

**Files:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/group_skeptic.py:150-156`,
`tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:699-703`,
`tribunal/nestor_pulse_sdk/verification/report.py:96, 120-126`

**Issue:** A group is selected when *any* member is `VERIFY` (`_group_selected`, `pipeline.py:148`).
`_parse_group_verdict` then fills a verdict for **every** index in the group
(`group_skeptic.py:151-156`), including members the materiality gate `DROP`ped and members marked
`SKIP_STABLE`. `_flush_groups` appends all of them into `verdicts_by_claim`
(`pipeline.py:700-703`), so those claims reach `adjudicate_all`, can be refuted, land in
`dropped`, and get their passages removed by `scrub_research`.

The funnel, meanwhile, books them in bucket 2 (`not_checkable`, with a named reason —
`report.py:96, 120-126`). So a claim that was in fact checked *and removed from the report* is
published to the operator as "never checkable". The phase's stated contract is that every
distilled claim lands in exactly one bucket that describes what actually happened to it; this
breaks that in the "we did more than we said" direction.

**Fix:** either restrict verdict attribution to selected members —

```python
for i, c in enumerate(grp["claims"]):
    if (c.get("gate") or {}).get("strict") != "VERIFY":
        continue      # gated out: bucket 2 owns it
    v = vbi.get(i)
    if v is not None:
        verdicts_by_claim[id(c)].append(v)
```

— or add a `checked_incidentally` funnel line and subtract it from bucket 2 in `_accounting`.
The first is smaller and matches the documented accounting; the second keeps the free signal.

- **Claim conservation.** `apply_gates` labels but never shortens the list (verified against the
  three funnel invariants and `_classify`'s gather-order flattening); `_cluster_keys` never drops
  a claim across the untagged / failed-call / unparseable-cid / oversized-block-chunking paths;
