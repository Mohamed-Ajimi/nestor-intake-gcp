## Deviations from Plan

### 1. [Rule 3 - Blocking] Worktree was 110 commits stale — fast-forwarded to master

**Found during:** setup, before Task 1.
**Issue:** the branch sat 110 commits behind `master` (`8d249ea`) with **zero** unique commits. All
nine prior plans were absent. Had this gone unnoticed, the phase gate would have run against a tree
without the phase in it and the deploy would have shipped an image containing **none** of the gate
code — while this SUMMARY reported a green gate. That is the single highest-consequence stale base
of the phase, because this plan is the one that turns code into production behaviour.
**Fix:** `git merge --ff-only master` — strictly lossless (`git rev-list --count master..HEAD` = 0).
All nine dependency checks then passed before any build was submitted. **This is now 8 of 10 agents
cut stale in this phase** — the worktree cut point is systematically behind, not incidentally so.

### 2. [Rule 3 - Blocking] `$GOOGLE_PROJECT` is unset in this environment

**Found during:** Task 1.
**Issue:** every command in the plan uses `--project="$GOOGLE_PROJECT"`, which would expand to an
empty `--project=` and fail.
**Fix:** substituted the literal project id `project-cb01b861-cb4a-438d-b9a` in every `gcloud`
invocation (builds, deploys, describes), and the deploy scripts were given
`GOOGLE_PROJECT`/`REGION`/`INSTANCE_NAME` inline. Recorded at the top of `15.1-UAT.md` so a future
reader reproducing these commands is not confused by the literal id. **Committed in:** N/A (no repo
file changed by the substitution itself).

### 3. [Rule 2 - Missing critical documentation] The runbook lists an eleventh tunable the plan did not name

**Found during:** Task 2.
**Issue:** the plan's Step-15.1.b list names eight env vars. A grep of the merged tree found a
ninth/tenth the plan omitted — `NESTOR_TRIBUNAL_GATE_CONTEXT_CHARS` (2000, `gates.py`) and
`NESTOR_TRIBUNAL_GATE_BRIEF_CHARS` (1200, `pipeline.py`, added by plan 15.1-07). Both are live
tunables on the deployed image. A runbook that documents "every new tunable" while omitting two
would send an operator hunting through source during an incident.
**Fix:** the table lists all **ten**, each with its default and the file that reads it.
**Files modified:** `infra/DEPLOY-RUNBOOK.md` · **Commit:** `7da16d6`

### 4. [Rule 1 - Bug, documented not fixed] UAT item 2 rewritten to match what the operator will actually see

**Found during:** Task 3 (`read_first` inspection of `VerificationReport.tsx`).
**Issue:** the plan's item 2 asks the operator to confirm "the degradation sentence is visible at the
top of the report in words, not as an icon (G-10)". That check **cannot pass as written.** The
backend emits `report["verification_degraded_text"]` (the full sentence) and `report["accounting"]`
(the three buckets), but `grep -rn "verification_degraded\|accounting" frontend/src/` returns **no
binding** — no component reads either. What the operator will actually see is the two funnel numbers
(`verification_degraded`, `should_have_been_checked`), because `VerificationReport.tsx` iterates
`Object.entries(report.funnel)`, plus the D15 feed's closing row, which **does** carry the full
sentence with a red `AlertTriangle`.
**Resolution:** the item was written to describe the real behaviour, splitting what IS live from
what is not, and instructing the operator to **record what they see** rather than fail the check.
The gap is recorded in `15.1-UAT.md` § Known gaps item 1 and assigned to 15.2's R6, which is already
opening that surface. **Not fixed here:** the fix is a `VerificationReport.tsx` edit, and this plan's
`files_modified` is two files — writing frontend code from the phase-closure plan would have shipped
an unreviewed, untested UI change inside a deploy commit.
**Files modified:** `.../15.1-UAT.md` · **Commit:** `61cc484`

## Carried-forward gaps

Both are recorded in `15.1-UAT.md` § Known gaps with their full context, so 15.2 inherits them
rather than rediscovering them.

1. **`verification_degraded_text` is emitted but rendered by nothing.** Half of G-10 is live (the
   D15 feed's closing sentence, and the degradation as funnel numbers); the sentence at the top of
   the verification report is not. Frontend work, belongs with 15.2's R6.
2. **`superseded_note` is a declared pydantic contract that is not persisted end-to-end.**
   15.1-03 carries it in the parsed pipeline dict, 15.1-06 declared it on
   `VerificationVerdictItem`, but `_verdict_dto` does not emit it (deliberately, per T-15.1-25) and
   no column stores it. Wiring it needs a **storage decision** this phase had no mandate to make —
   Option A: a new `superseded_note TEXT` column (a real `0012` in the tribunal line); Option B: a
   sub-key on the existing `reconciliation` field (no migration, but it overloads a free-text field
   and needs a parse contract). Belongs to whoever owns the 15.2 migration; 15.2's D14 "Disputed &
   changed" section is the intended consumer.
