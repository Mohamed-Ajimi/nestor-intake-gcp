# Phase 15.1 Plan 07: Gate Wiring + Selector Rewire Summary

The gates are now the single answer to "which claims get checked"; stakes was demoted to the
depth lever it was always documented as, given an explicit shallow tier so the demotion does not
quietly cost money, and every claim that was selected but never checked is now counted and said
out loud.

## What Was Built

### Task 1 — the gate stage (commit `7617f97`)

`apply_gates` runs between `_propagate_stakes` and the `if _GROUP_VERIFY:` branch, on the full
claim list, per claim — so the recorded per-claim 456/424 numbers can reproduce and clustering
still happens afterwards (G-04 steps 1-2).

- A new `"gate"` D15 stage, cancel-checked on entry like every other fan-out, with a completion
  line reporting the funnel in one sentence (`N of M claims selected for checking · X not
  checkable · Y stable facts skipped`, plus a gate-error clause only when non-zero).
- `_gate_decision_context(mission_brief)` feeds the gate the sharpened research prompt plus the
  focus-area labels, bounded by `_GATE_DECISION_CONTEXT_CHARS` (1200, env-overridable via
  `NESTOR_TRIBUNAL_GATE_BRIEF_CHARS`). "Load-bearing" is meaningless in the abstract — the blind
  experiment judged materiality against *the LUKOIL BeNeLux dynamic-pricing report*, not against
  nothing. `gates.py` truncates again at its own 2000-char ceiling; this is the tighter of the two.
- `_build_funnel()` is the ONE place the funnel is shaped: the nine gate keys (imported from
  `gates._FUNNEL_KEYS`, not re-typed, so drift is impossible) plus `checked`,
  `should_have_been_checked`, `verification_degraded` and `verify_sessions`.
- The empty-claims early return now emits that same funnel, all zero (RESEARCH Pitfall 10). It
  previously returned a skeleton with no funnel at all, so a consumer had to know which path
  produced its input.

**Frontend stage-list check (required by the plan):** `grep -rn "hardcoded stage\|STAGES = \["
frontend/src/components/intake/ResearchRunProgress.tsx` matches exactly one line — line 35, a
COMMENT stating *"NO hardcoded stage count / no literal 9"*. `toStageRows()` iterates
`Object.entries(run.stage_detail)`, so the list length is whatever the run reports. **No
hardcoded stage list exists; the new `"gate"` stage renders with no frontend change and no
follow-up is needed.**

### Task 2 — the selector, the order, the depth tier, bucket 3 (commit `0b5098e`)

**Selector (G-02).** `_group_selected(group)` returns True when ANY member claim has
`gate.strict == "VERIFY"` — G-04 step 3 as one function. The verify queue is now
`[g for g in _corroboration_order(groups) if _group_selected(g)]`, and `total_passes` is its
length, so the operator feed reports the real queue. `_group_passes` stays in the file with a
docstring saying it is the A/B reference and is no longer the selector.

**Depth (RESEARCH Pitfall 9 — the open item plan 15.1-05 handed forward).** `_GROUP_DEPTH` gains
`"low": (2, 3, 2)` with a comment naming the reason. This is the plan's first named decision and
it is deliberate: low-stakes groups never ran before, so the map never needed the key; now that
the gates can let a load-bearing low-stakes claim through,
`.get(stakes, _GROUP_DEPTH["med"])` would have handed it **MED** depth without anybody choosing
that — turning "we check more claims" into "we spend more money" against a phase whose bar is
*~6× cheaper*. The `.get` fallback is left in place as belt-and-braces.
`test_group_depth_still_differentiates_by_stakes` asserts high > med > low on every element, so
deleting the tier now fails loudly instead of costing quietly.

**Ordering (G-04 step 4 / D9).** `_corroboration_order()` sorts by the number of DISTINCT
providers across members' `found_by`, lowest first, ties broken by original index. The comment
names D9 and states the direction explicitly because the intuition runs the other way. This is
not cosmetic: the budget governor truncates the queue from the tail, so the order decides which
checks survive a cap.

**The fallback branch — rewired, not deleted** (RESEARCH Open Question 2). The
`NESTOR_TRIBUNAL_GROUP_VERIFY=false` branch now builds `selected_claims` from
`claim["gate"]["strict"]` and runs a flat `_PER_CLAIM_SKEPTICS = 2` per selected claim. The
stakes triage lost its only production call; `triage.py` is untouched on disk and its unit tests
still pass. `_one_skeptic` was not touched — the coverage-gate re-entry uses it in BOTH modes,
which is exactly why deleting the branch would have broken the coverage gate.

**Bucket 3 (G-08).** `_book_unchecked(claims, cause)` counts and `log.warning`s at all three loss
sites — crashed/timed-out group session, budget cap (both branches), coverage re-entry that came
back empty — de-duplicated by claim identity so a claim lost twice is booked once. The funnel
then carries `checked = selected_verify - unchecked_selected`,
`should_have_been_checked = unchecked_selected` and `verification_degraded = unchecked_selected
> 0` onto `synthesis_bundle["verification"]["funnel"]` (where 15.1-09 picks it up) and onto the
returned `verification_report`.

### Task 3 — 10 selector proofs (commit `d13e880`)

`tests/test_gate_selector.py`, pure — no DB, no LLM, no mocking library, no monkeypatch. The
load-bearing ones: the static `triage_claims`-absence assertion (a behavioural test cannot prove
this negative — the old filter's only symptom was a live run where low-stakes claims silently
produced no verdicts); any-member cluster survival plus its bucket-2-not-bucket-3 counterpart;
the low-stakes-is-now-selected case; the three-tier depth ordering; corroboration ascending and
deterministic on ties; both funnel paths carrying the same 13 contract keys; and a wiring test
asserting the real queue line uses BOTH helpers, because a selector nobody calls proves nothing.

## Deviations from Plan

### 1. [Rule 3 - Blocking] Worktree was 94 commits stale — fast-forwarded to master

**Found during:** setup, before Task 1.
**Issue:** the branch sat at `a3a0c96`, 94 commits behind `master` (`3d85d05`), with zero unique
commits. All three wave dependencies (`gates.py`, the clusterer, `found_by`) plus 15.1-06's
`accounting` were absent.
**Fix:** `git merge --ff-only master` — lossless (`git rev-list --count master..HEAD` = 0). All
four dependency checks then passed. **This is now 5 of 7 agents cut stale in this phase** — the
worktree cut point is systematically behind, not incidentally so.

### 2. [Rule 1 - Bug] Bucket 3 counts SELECTED members of a lost group, not every member

**Found during:** Task 2.
**Issue:** the plan says to increment the accumulator "by the number of claims in that group". A
group is selected when ANY member verifies, so a lost group typically also contains members the
gates dropped or marked `SKIP_STABLE`. Counting those would put the same claims in bucket 2 AND
bucket 3, breaking the funnel identity `distilled == checked + (dropped + skipped_stable) +
should_have_been_checked` that 15.1-06's `test_three_buckets_sum_to_distilled` exists to hold —
i.e. it would have produced exactly the accounting dishonesty this phase closes, in the opposite
direction.
**Fix:** `_book_unchecked` filters on `gate.strict == "VERIFY"`. `_build_funnel` also clamps
bucket 3 to the selected queue, so an over-count cannot be published even if a future call site
gets the predicate wrong.
**Files modified:** `pipeline.py` · **Commit:** `0b5098e`

### 3. [Rule 2 - Missing correctness guard] Bucket 3 is reconciled against ground truth

**Found during:** Task 2.
**Issue:** three hand-placed counters can only count the losses somebody thought of. A group
session that RETURNS but omits an index (`verdicts_by_index.get(i) is None`) loses a selected
claim through none of the three sites, and would have been published as `checked`. On a number
whose whole purpose is "must never be silently empty", counter coverage is the wrong guarantee.
**Fix:** immediately before the funnel is built, `unchecked_selected` is recomputed from ground
truth — a selected claim with no verdict was not checked, whatever the cause — and a mismatch
between the counted and observed figures is logged. The site counters now serve their real job:
naming the CAUSE in the log at the moment of loss (V7). The published NUMBER comes from
observation.
**Files modified:** `pipeline.py` · **Commit:** `0b5098e`

### 4. [Scope boundary] `triage.py` was not given its docstring note

**Found during:** Task 2.
**Issue:** the plan's Task 2 asks for a one-line module-docstring note in `triage.py`, and its
`<verification>` explicitly permits the file either way — but `files_modified` lists only two
files and the orchestrator's success criteria state "only `pipeline.py` and
`test_gate_selector.py` touched".
**Resolution:** the stricter boundary was honoured. The note that the stakes triage lost its only
production caller lives in two places a reader will actually hit: the comment at the rewired
fallback branch in `pipeline.py`, and
`test_gate_selector.py::test_triage_claims_is_not_called_from_the_verify_path`, whose docstring
states that `triage.py` keeps its module and its unit tests and lost only its caller. **Follow-up
for whoever next opens `triage.py`:** add the docstring line, since a reader landing there
directly still has no in-file signal.
