  <action>
This is the phase's hardest engineering question and it gets its own task so the decision is
deliberate rather than an accident of batching. Today's tagger is embarrassingly parallel
because the `ENTITY|ATTRIBUTE` key space is GLOBAL. Real clustering is not: two claims in
different batches that state the same fact must land in the same cluster, and 1,162 claims
cannot fit one 4096-token call.

Implement option (b) from RESEARCH — **block-then-cluster** — the smallest change from today's
code and the only option that reuses an existing, tested pass:

  Stage 1 (unchanged): `_tag_batch` over batches of `_GROUPER_BATCH` (40) produces
    `(entity, attribute)` per claim. At fixture scale that is ⌈1162/40⌉ = 30 calls, matching
    the recorded `index.json` `grouping: 30` tally.
  Stage 2 (new): block claims by `_norm(entity)` ALONE — deliberately coarser than today's
    `entity│attribute` key, so `lukoil|verkoop_internationale_operaties` and
    `lukoil benelux|status_rapport` can still meet.
  Stage 3 (new): for each block holding more than one claim, ONE clustering call assigns each
    claim a block-local cluster id. Claims in a block of size 1, and claims whose entity tag is
    empty, skip stage 3 entirely (no call).
  Blob guard: a block larger than `_CLUSTER_MAX_BLOCK` is split into consecutive chunks of
    `_CLUSTER_BATCH`; cluster ids are namespaced `{block_key}#{chunk_index}#{cluster_id}` so
    ids from different chunks can never collide.

Write this as a `Cross-batch cluster identity` section appended to the module docstring's
design-constraints block, stating: the strategy, why the entity tag is the blocking key, the
namespacing rule, and the ONE accepted limitation — same-fact claims whose entity tags
normalise differently, or that fall in different chunks of an oversized block, will not merge.
Record that this limitation is measured (not asserted) by the hand-run August calibration
(G-05), never by a CI gate.

Add the new tunables next to the existing ones, following the `NESTOR_TRIBUNAL_*` +
`os.environ.get(..., default)` idiom so no Cloud Run env change is needed to deploy:
  `_CLUSTER_BATCH        = int(os.environ.get("NESTOR_TRIBUNAL_CLUSTER_BATCH", "40"))`
  `_CLUSTER_MAX_BLOCK    = int(os.environ.get("NESTOR_TRIBUNAL_CLUSTER_MAX_BLOCK", "60"))`
  `_CLUSTER_CONCURRENCY  = int(os.environ.get("NESTOR_TRIBUNAL_CLUSTER_CONCURRENCY", "4"))`
  `_CLUSTER_ENABLED      = os.environ.get("NESTOR_TRIBUNAL_CLUSTER", "true").lower() == "true"`
`_CLUSTER_ENABLED=false` must fall back to today's exact-key `entity│attribute` bucketing, so
the old path stays reachable for A/B without a code change. Keep `_norm` — it is the blocking
key function and the fallback path's bucketer.

No behaviour is wired yet in this task; it lands the docstring, the constants, and the
fallback switch.

Add `_CLUSTER_PROMPT` and `_parse_cluster_lines`, then rewire `group_claims`'s bucketing.

`_CLUSTER_PROMPT` follows `_TAG_PROMPT`'s exact contract: plain text, one output line per input
claim, in input order, index-addressed. Its instruction is "group claims that state the SAME
fact, however differently worded, in whatever language — including claims that state the same
fact with CONFLICTING values (those especially must share a group)". Output format:
`INDEX | CLUSTER_ID` where `CLUSTER_ID` is a small integer chosen by the model, and claims with
no partner get their own id. Preserve BOTH security properties of the input block: claim text
truncated to 240 chars, and output addressed by index — so injected claim text cannot address
another claim's slot.

`_parse_cluster_lines(text: str, n: int) -> list[int]` copies `_parse_tag_lines`'s STRUCTURE
exactly: pre-fill a list of length `n` with a sentinel meaning "unclustered" (`-1`), skip lines
without `|`, regex the leading integer index, bounds-check `0 <= idx < n`, ignore anything out
of range, never raise, never `json.loads`. An unparseable cluster id leaves the sentinel.

`_cluster_block(claims, audited, run_id, tenant_id) -> list[int]` copies `_tag_batch` verbatim
in shape: `_make_config()`, `kwargs = {"config": config} if config is not None else {}`,
`await audited.gemini_generate(run_id=…, tenant_id=…, model=_GROUPER_MODEL, contents=prompt,
**kwargs)`, the `resp.text` → `resp.candidates[0].content.parts[0].text` fallback, and a
batch-level `try/except Exception` (`# noqa: BLE001`) that logs a warning and returns
`[-1] * len(claims)`. The neutral default here is "every claim is its own singleton" — the same
never-drop semantics today's `("", "")` fallback provides.

Rewire `group_claims`:
  1. keep the existing tag fan-out unchanged (batches + `asyncio.Semaphore(_GROUPER_CONCURRENCY)`
     + `asyncio.gather`) producing `flat_tags`;
  2. if `not _CLUSTER_ENABLED`, run the existing exact-key `entity│attribute` bucketing loop
     unchanged and return;
  3. otherwise build blocks keyed by `_norm(entity)`; claims with an empty normalised entity go
     straight to `__singleton__:{i}` keys (the existing never-drop contract);
  4. chunk any block longer than `_CLUSTER_MAX_BLOCK` into `_CLUSTER_BATCH`-sized chunks; run
     `_cluster_block` over all chunks concurrently under `asyncio.Semaphore(_CLUSTER_CONCURRENCY)`;
     skip the call entirely for chunks of length 1;
  5. build the final key as `f"{block_key}#{chunk_index}#{cid}"`, and `__singleton__:{i}` for
     any claim whose cluster id came back as the `-1` sentinel;
  6. build the group dicts exactly as today — `entity` = first non-empty entity seen in the
     cluster (fall back to `claim.get("facet") or "?"`), `attribute` = first non-empty attribute
     seen (fall back to `"general"`), `claims` in original order, `stakes` = MAX across members
     using `_STAKES_ORDER`;
  7. preserve the deterministic output ordering convention: groups appear in first-member order.

Extend the closing INFO log to the one-line input→output convention with cluster-quality
numbers: claims in, groups out, multi-claim count, singleton count, blocks formed, cluster
calls made.

Do NOT change the `async def group_claims(*, claims, audited, run_id, tenant_id)` signature, the
five return-dict keys, or the MAX-stakes inheritance. `pipeline.py:350-352` and
`group_skeptic.py:171-176` both depend on them and are out of this plan's file scope.
