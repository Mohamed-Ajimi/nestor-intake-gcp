# Phase 15.1: Research Engine Redesign — Verification Gates - Context

**Gathered:** 2026-07-25
**Status:** Ready for planning

<domain>
## Phase Boundary

**Phase 15.1 replaces the verification stage's selection logic with the redesigned gate
package.** Six deliverables, all locked in the operator decision files (see canonical refs):

1. **Materiality gate** — per claim, two judgments: is it *falsifiable-specific* (checkable
   against the world) AND *load-bearing* for THIS client's decision. Both yes → keep.
2. **Error-likelihood gate** — of the survivors, skip stable-notorious facts where being
   wrong is essentially impossible; recorded as `skipped_stable`, never hidden.
3. **Canonical grouping** — real LLM clustering of same-fact claims so contradictory
   variants land in ONE skeptic session (D9/D11).
4. **Corroboration prioritization** — claims independently found by several researchers drop
   down the checking queue; single-source claims rise (D9).
5. **Fail-loud** — a run whose verification was gutted must not report green.
6. **"superseded" verdict** — a fourth verdict value carried into synthesis as a mandatory
   caveat (the KPAnG case).

Proven by replaying the recorded 1,162-claim fixture through the gates in tests. **No live
LLM runs** (Anthropic monthly cap resets 2026-08-01).

**Out of scope:**
- The four honest terminal states / park+resume machinery (R1–R7) — **15.2** (ENGINE-11).
  15.1 records verification degradation as a marker, it does not build a state machine.
- Question workshop, per-provider structured fact lists (D8), SerpAPI researcher stream
  (D10), report sections D13/D14 — **15.2**.
- Embedding machinery — Phase 19 (B-04 locked LLM-based clustering).
- Any client-visible verification surface — D-08 stands; the client PDF is hand-crafted
  by the superadmin (Phase 18).

**Hard constraints carried forward:**
- `verify_chain` stays green — frozen audit payload fields must not be renamed; new fields
  ADD only (EU AI Act Art. 12, deadline 2026-08-02).
- No live LLM runs before 2026-08-01.
- Author-by-construction + Cloud Build for tests/images (no local Python/Docker).
- Every new table/endpoint joins the cross-tenant denial suite day one.
- Phase-15 surfaces already consume this phase's output — `run.verification_summary`,
  the `verification_verdict` table, and `verification/report.py` exist and must keep
  working; 15.1 makes them carry REAL data instead of fixture-seeded data.

<decisions>
## Implementation Decisions

### Proof bar — what "proven" means (SC1)

- **G-01: Two tests, only one of them gates the phase.**
  - **CI test (closes the phase):** deterministic replay — feed the 1,162 fixture claims
    *plus the recorded KEEP/DROP/SKIP_STABLE answer key* through the REAL gate machinery
    and assert the funnel lands exactly on `distilled 1162 → kept 456 → dropped 706 →
    selected_verify 424 → skipped_stable 32 → verify_sessions 176`, and that those numbers
    propagate correctly to `run.verification_summary` and the verification report. Costs
    nothing, never flaky, proves plumbing + funnel wiring.
  - **Calibration test (informational, hand-run):** turns the REAL classifier loose on the
    fixture and REPORTS agreement % against the blind answer key. Written in 15.1, run by
    the operator after 2026-08-01. **Never a CI gate** — no pass/fail threshold, no red
    build from classifier wobble. Its number feeds the 15.2 live validation.
  - Rationale: the 456/424 labels came from blind LLM agents; a production LLM gate cannot
    hit them exactly. Demanding exact reproduction from a live classifier would park 15.1
    as incomplete until August and block 15.2.

- **G-02: The gates REPLACE stakes triage as the selector; stakes keeps only its depth role.**
  Today `triage.py` maps stakes low/med/high → 0/2/3 skeptics, silently waving low-stakes
  claims through unchecked. That second hidden filter is removed: the gates become the
  single answer to "which claims get checked". Stakes survives only as the DEPTH lever
  (`_GROUP_DEPTH`: turns / search uses / fetch uses per surviving session). One honest
  funnel; the recorded 176-session shape still reproduces because that came from
  group-level depth, not from selection.

### Grouping (SC2)

- **G-03: Replace exact-string bucketing with real LLM clustering.** Today `grouping.py`
  flash-tags each claim `ENTITY | ATTRIBUTE` then buckets by EXACT string match — 163 of
  177 groups were singletons, and four flat contradictions shipped (Aral 16% vs 21%;
  LUKOIL NL 46 vs ~70/75 stations; Zeeland "sold to Carlyle" vs "bought by TotalEnergies";
  Gunvor vs Carlyle). Near-miss labels across languages (`lukoil|verkoop_internationale_
  operaties` vs `lukoil benelux|status_rapport`) never met. The fix is to hand the AI the
  claim list and ask it to form groups of "claims stating the same fact, however worded".
  **This is the same mechanism already locked for 15.2's cross-provider merge (B-04), so
  build it once here and let 15.2 inherit it.** No embeddings.

- **G-04: Ordering is cluster-BEFORE-gate, per D11** ("the verification gates apply AFTER
  the merge"). Concretely for 15.1:
  1. cluster all 1,162 claims,
  2. run the gates **per claim** (so the recorded 456/424 per-claim numbers reproduce),
  3. a cluster survives if ANY member survives,
  4. prioritize surviving clusters by corroboration.
  Corroboration is a property of the cluster, so clusters must exist before prioritization.
  *(Corrects an earlier in-discussion mis-statement of "gate first, then cluster".)*

- **G-05: Contradiction proof follows the G-01 pattern.** The CI test proves grouping
  plumbing from recorded data; whether the four known contradiction pairs actually land in
  one group is measured by the hand-run August calibration, alongside the gate agreement %.

### "superseded" verdict (SC2)

- **G-06: `superseded` becomes a fourth verdict value** — `support | refute | insufficient
  | superseded`. Today the vocabulary has three words, so the KPAnG case returned **six
  "support" verdicts on true-but-obsolete claims** with the nuance stranded in a free-text
  `reconciliation` note that synthesis was free to ignore. Making it a verdict forces the
  skeptic to choose it and makes it visible to every count, screen and bucket.
  Note: `verification_verdict.verdict` is free `TEXT` (no enum/CHECK constraint), so no
  migration is required for the column itself — but the `emit_group_verdict` tool schema,
  `_parse_group_verdict`, adjudication, and the report shaper all need the new value.

- **G-07: A superseded claim STAYS in the report body with a forced inline caveat.**
  The caveat text is supplied from pipeline data ("this pattern applied until 1 April
  2026") — the writing model presents it, it does not phrase it from memory. It also
  surfaces in the "Disputed & changed" section (D14, built in 15.2). Rejected: pulling
  superseded facts out of the body (a reader asking "what was the rule before?" is left
  hunting, and silent omission is its own dishonesty).

### Accounting for gated-out claims (SC2)

- **G-08: Three honest buckets, every claim carrying its reason.** Today the report shaper
  computes `unverified = total_claims - claims_with_verdict`, which lumps "was never
  checkable" together with "should have been checked but the fact-checker crashed" — the
  exact P1 defect ("the honesty appendix cannot distinguish waved-through vs crashed vs
  400'd"). Replace with:
  1. **CHECKED** — has a verdict.
  2. **NOT CHECKABLE** — with the specific reason: `not_falsifiable` / `not_load_bearing` /
     `both` / `stable_known_fact`.
  3. **SHOULD HAVE BEEN CHECKED BUT WASN'T** — crashed, cap-killed, budget exhausted,
     gate error. **This bucket must never be silently empty and should be ZERO on a
     healthy run.** It is the phase's most important number.
  Rejected: flagging low-confidence gate drops for superadmin review — gate quality is
  already measured by the August calibration; don't add an unrequested review surface.

- **G-09: Nothing client-facing — verification accounting is superadmin-only.** No coverage
  paragraph, no funnel, no percentages in the delivered report. Coherent with D-08 and the
  Phase-18 delivery model: the superadmin hand-crafts the client PDF from raw output, so an
  auto-generated appendix would never reach the client as written anyway. The accounting
  exists to inform the operator.

### Fail-loud (SC2)

- **G-10: Statuses stay as they are; add a loud truth marker.** Today's vocabulary is only
  `queued | running | completed | failed | cancelled` — no `parked`, no `degraded` (those
  arrive with R6 in 15.2). A run keeps status `completed` but carries a
  `verification_degraded` marker plus the non-zero bucket-3 count, and **both are stated in
  words** at the top of the verification report and in the feed's closing summary — not a
  subtle icon.
  Rejected: adding a `completed_degraded` status now — **four API endpoints gate on
  `status == "completed"`** (`runs/api.py:587, 691, 947, 1046` — report download, audit
  bundle, verification report); miss one and the superadmin loses access to precisely the
  runs they most need to inspect. It also front-runs R6, which defines all four states
  together. Rejected: hard-failing a zero-verdict run — `failed` locks the report and audit
  bundle behind those same gates, discarding a ~$45 run's good research because the
  checking stage died.
  **15.2 promotes this marker into a real `completed-degraded` status as part of R6.**

- **G-11: A gate batch that fails after retries fails toward MORE checking, recorded.**
  Retry with backoff; if it still fails, its claims are treated as "assume worth checking"
  and sent to the fact-checkers, with a visible gate-error line in the funnel. Never
  silently drops a check. The existing budget governor is the backstop if a total gate
  failure would push the queue back toward ~950 sessions — it stops the spend, and the
  shortfall lands honestly in bucket 3.
  Rejected: skipping the affected claims (converts a transient hiccup into permanently
  unexamined passages); aborting the run on any gate error (disproportionate — throws away
  paid-for research because the cheapest step hiccuped).

### Corroboration (SC2)

- **G-12: Stop deleting the corroboration signal that already exists.** Two live bugs:
  1. `claim_distiller` builds `units: list[(provider_name, chunk)]` and knows exactly which
     researcher produced each chunk — then **discards the name**. Claims come back with only
     `{text, facet}`, and `facet` falls back to the provider name only when no focus-area
     label matched, so provenance is not reliably recoverable.
  2. `_dedupe_claims` collapses near-identical facts from DIFFERENT researchers and
     **throws the duplicates away** (2,976 raw → 1,162). Three researchers independently
     confirming a fact currently looks identical to one researcher asserting it alone.

  Fix: tag each distilled claim with its source provider, and change dedupe to **MERGE**
  duplicates into one claim carrying `found_by: [gemini, claude, openai]` rather than
  discarding them. Corroboration count = `len(found_by)`; cluster-level corroboration =
  distinct providers across the cluster. **The surviving claim count is unchanged (1,162),
  so the recorded fixture still reproduces exactly.**
  15.2's structured per-provider fact lists (D8) then sharpen this signal rather than
  introducing it.

### Amendments from research (operator-decided 2026-07-25, post-RESEARCH.md)

- **G-13: The CI test asserts FIVE gate-computed numbers, not six. `verify_sessions 176` is a
  recorded pass-through constant, not a gate output.** Amends G-01's funnel assertion.
  Research established (three agreeing artifacts: `recorded/index.json` stage tallies,
  `GROUPS.md` header, `REPORT.md` §3.5/§4.2) that 176 is the number of group-skeptic passes
  that *returned* on the 2026-07-22 run, where 776 further attempts were hard-400'd by the
  Anthropic usage cap — covering only 198 of 1,162 claims. It measures an incident, not the
  funnel. The other five (`distilled 1162 / kept 456 / dropped 706 / selected_verify 424 /
  skipped_stable 32`) come from the blind selection experiment and ARE gate outputs.
  Concretely: the CI replay asserts those five as **computed by the real gate machinery**;
  `verify_sessions: 176` stays in `RECORDED_FUNNEL_COUNTS` unchanged (two existing tests
  compare that dict by full equality — do not disturb them) and gains an inline comment
  marking it incident-derived and explicitly NOT a gate assertion.
  Rejected: asserting `424 → 176` (makes the phase pass only when the new machinery
  reproduces an outage's session count); deleting the key (churns two green tests for no
  gain).

- **G-14: `_verification_appendix` is NOT touched in 15.1 — operator ruling, question closed.**
  Research raised the appendix's `n_claims - n_unverified` "Independently fact-checked" line
  (the arithmetic G-08 replaces, which counts never-checked claims as checked) as a possible
  narrow fix. **The operator ruled the concern does not apply: the client never receives this
  generated report — only the final report the superadmin submits.** G-09 therefore stands
  unqualified and this surface is out of scope. The plan must include the negative test
  (`_verification_appendix` output unchanged by this phase) and must not modify it.

### Claude's Discretion

- Gate model + batching (follow the `grouping.py` convention: gemini-2.5-flash, thinking
  disabled, plain-text line output, batches of ~40, bounded concurrency).
- Exactly how the gate prompt is grounded in the client's brief/context pack — "load-bearing"
  is only meaningful relative to that client's decision (the blind experiment's rule was
  "falsifiable-specific AND load-bearing **for the LUKOIL BeNeLux dynamic-pricing report**").
- Where the three buckets and the gate-error line are stored — additive keys on
  `run.verification_summary` and/or per-claim fields; must not rename any existing funnel
  key (Phase-15 surfaces + `test_hash_chain_replay.py` assert on them).
- Cluster size caps / blob-group guards; retry and backoff parameters for the gate pass.
- How the calibration test samples (full 1,162 vs a subset) and how it reports agreement.
- Whether the fixture replay drives `loader.py`'s `RECORDED_FUNNEL_COUNTS` or asserts
  against it — as long as the constant stays the single source of the recorded numbers.

## Existing Code Insights

### Architectural finding the planner MUST internalize

**The report is written from scrubbed PROSE, not from claims.** From `pipeline.py` Stage 8:
providers write prose essays → `claim_distiller` **extracts** assertions out of that prose
(claims are *probes*, not report content) → fact-checking runs on the probes → only claims
that are **refuted** (or lose a conflict) enter `dropped`, and `scrub_research` then
physically deletes the passages that state or depend on them → synthesis writes from the
scrubbed prose. The code calls this *subtractive verification*: "synthesis runs on the full
research prose so no information is lost to a claim cap."

Three consequences:
1. **The gates delete nothing from the report.** Dropping 706 claims from checking removes
   no prose. It only redirects the checking budget.
2. **No coverage percentage is honest.** The report contains far more statements than the
   distiller ever extracted, so "X of Y statements verified" has a false denominator. This
   is why G-09 chose superadmin-only.
3. **An unchecked claim leaves its passage standing, untouched.** Only refutation triggers
   scrubbing. So G-08's bucket 3 is not an accounting line — it counts **passages that
   shipped unexamined**. That is how last run published Aral at both 16% and 21%.

### Reusable Assets
- **`grouping.py`'s flash-tagging pattern** — batched (`_GROUPER_BATCH=40`), bounded
  concurrency, `thinking_budget=0`, plain-text line output (never JSON mode — "citations ⊗
  structured-outputs = 400"), all egress via `audited.gemini_generate`. The gate classifier
  and the new clusterer should be built to this exact shape.
- **Phase-15 verification surfaces already exist and are tested**: `run.verification_summary`
  (JSONB, migration 0011), the `verification_verdict` table (FORCE RLS + tenant policy),
  `shape_verification_report` (already has `superseded` / `unverified` / `reconciled`
  buckets), the superadmin-only proxy routes, and the frontend report. 15.1 fills them with
  real data — **it should not need new surfaces**.
- **`loader.load_recorded_run`** — seeds a full recorded run with NO GCS access, from the
  in-package extracts. The CI replay test builds on it.
- **Budget governor + `_group_passes` depth map + advisory locks** — G-11's backstop and
  G-02's retained depth lever already exist.

### Established Patterns
- Hand-written async loops over agent SDKs (Tribunal convention — no agent frameworks).
- Frozen audit payload + hash chain: new fields ADD, never rename. `test_hash_chain_replay.py`
  explicitly asserts `cache_creation_tokens` / `cost_pending` / `verification_summary` are
  additive and NOT chain members — new 15.1 fields must follow the same proof.
- Recorded seq is `seq=0` on every blob (Pitfall 6) — order audit records by GCS mtime.
- Plain-language operator decision files are the requirement source of truth for this phase.
- Tests run in Cloud Build (no local Python/Docker) — the fixture must resolve via the
  in-package `recorded/` copy.

### Integration Points
- Gates sit between `claim_distiller` and the verify stage in `pipeline.py`; the funnel they
  produce writes to `run.verification_summary` (existing keys unchanged, new keys additive).
- The 4th verdict flows `emit_group_verdict` → `_parse_group_verdict` → `verdicts_by_claim`
  → adjudicate → `persist_tribunal_claims` / `verification_verdict` → report shaper → the
  Phase-15 superadmin report + D15 feed.
- Corroboration provenance originates in `claim_distiller`'s `units` tuples and must survive
  `_dedupe_claims` to reach clustering and queue ordering.

## Specific Ideas

- The operator's plain-language test for the whole phase: **a run must never again report
  "completed — green" while its fact-checking stage was gutted.** 776 cap rejections in 55
  seconds produced a green run last time; that is the failure this phase exists to kill.
- The four shipped contradictions are the concrete grouping bar: Aral 16% vs 21% share,
  LUKOIL NL 46 vs ~70/75 stations, Zeeland "sold to Carlyle" vs "bought by TotalEnergies",
  Gunvor vs Carlyle. If clustering works, each pair collides in one session.
- The KPAnG case is the concrete superseded bar: six "support" verdicts on an intraday
  pricing pattern the reconciliation note itself called "superseded since 1 April 2026".
- The economic bar: ~950 checks → ~150. Roughly 6× cheaper *and* aimed at the claims that
  can embarrass the operator, on a run that cost ~$43–45.
- The gate is a judgment, not a rule — the 456 were chosen by agents reading each claim and
  thinking about it. No regex/heuristic gate will reproduce them.
