# Phase 15.1: Research Engine Redesign — Verification Gates - Research

**Researched:** 2026-07-25
**Domain:** Tribunal verification pipeline (Python 3.11 / async / no framework) + deterministic fixture replay testing
**Confidence:** HIGH (all findings are direct reads of this repo's source at stated line numbers; zero external dependency research needed)

## Summary

This phase is **entirely internal-code work**. No new packages, no new external libraries, no version research. Every decision (G-01…G-12) is already locked; what the planner needs is the exact call-site map, the fixture contract, and the test seam — all of which are below, line-referenced.

Three findings materially change how the plan must be written:

1. **`run.verification_summary` has NO production write site.** It is created by migration `0011`, declared on the ORM at `db/models/run.py:101`, read by `verification/report.py:234`, and written *only* by the test fixture loader. The live pipeline builds a funnel-shaped dict at `pipeline.py:712-724` (inside `synthesis_bundle["verification"]`) and persists it as an `Output(format='synthesis_cache')` row — never onto the `run` column. **SC1's "propagate to `run.verification_summary`" requires building that write path from scratch**, not extending one.

2. **`verify_sessions = 176` is an incident artifact, not a funnel output.** The recorded run attempted ~952 group-skeptic passes; 176 completed and **776 hard-400'd on the Anthropic monthly cap** (`recorded/REPORT.md` §3.5/§4.2). The 176 completed sessions covered **198 of 1,162 claims**. So `RECORDED_FUNNEL_COUNTS` is a *composite*: `distilled/kept/dropped/selected_verify/skipped_stable` come from the blind selection experiment (what the gates *would* have done), while `verify_sessions` comes from the broken live run. A CI test that asserts "424 selected → 176 sessions" as a causal chain would be asserting a relationship that does not exist in the data. See **Pitfall 1** for the honest framing.

3. **The test seam already exists and needs no new abstraction.** Every LLM-touching function in this codebase takes `audited` as a keyword argument and calls duck-typed methods (`audited.gemini_generate(...)`, `audited.anthropic_messages(...)`). Six existing test files drive real production code through hand-written fake `audited` objects. The gate classifier and the new clusterer should follow the identical shape; the CI replay test injects a fake `audited` whose `gemini_generate` returns the recorded answer key rendered as the gate's own plain-text line format. **Recommendation: do NOT introduce a new protocol/injection layer.** See **Pattern 2**.

**Primary recommendation:** Build the gate stage as two new modules (`gates.py`, and clustering either replacing or living beside `grouping.py`) that copy `grouping.py`'s exact conventions verbatim — `gemini-2.5-flash`, `thinking_budget=0`, plain-text `INDEX | ... | ...` lines, batch 40, `asyncio.Semaphore(4)`, all egress via `audited.gemini_generate`, best-effort per-batch failure handling. Insert the stage in `pipeline.py` between line 304 (`_propagate_stakes`) and line 339 (`if _GROUP_VERIFY:`). Add a new `run.verification_summary` write helper alongside `_write_output` (`pipeline.py:783`) using the same raw-SQL + `set_tenant_context` pattern.

**Proof bar — what "proven" means (SC1)**

- **G-01: Two tests, only one of them gates the phase.**
  - **CI test (closes the phase):** deterministic replay — feed the 1,162 fixture claims *plus the recorded KEEP/DROP/SKIP_STABLE answer key* through the REAL gate machinery and assert the funnel lands exactly on `distilled 1162 → kept 456 → dropped 706 → selected_verify 424 → skipped_stable 32 → verify_sessions 176`, and that those numbers propagate correctly to `run.verification_summary` and the verification report. Costs nothing, never flaky, proves plumbing + funnel wiring.
  - **Calibration test (informational, hand-run):** turns the REAL classifier loose on the fixture and REPORTS agreement % against the blind answer key. Written in 15.1, run by the operator after 2026-08-01. **Never a CI gate** — no pass/fail threshold, no red build from classifier wobble. Its number feeds the 15.2 live validation.
  - Rationale: the 456/424 labels came from blind LLM agents; a production LLM gate cannot hit them exactly. Demanding exact reproduction from a live classifier would park 15.1 as incomplete until August and block 15.2.

- **G-02: The gates REPLACE stakes triage as the selector; stakes keeps only its depth role.** Today `triage.py` maps stakes low/med/high → 0/2/3 skeptics, silently waving low-stakes claims through unchecked. That second hidden filter is removed: the gates become the single answer to "which claims get checked". Stakes survives only as the DEPTH lever (`_GROUP_DEPTH`: turns / search uses / fetch uses per surviving session). One honest funnel; the recorded 176-session shape still reproduces because that came from group-level depth, not from selection.

**Grouping (SC2)**

- **G-03: Replace exact-string bucketing with real LLM clustering.** Today `grouping.py` flash-tags each claim `ENTITY | ATTRIBUTE` then buckets by EXACT string match — 163 of 177 groups were singletons, and four flat contradictions shipped (Aral 16% vs 21%; LUKOIL NL 46 vs ~70/75 stations; Zeeland "sold to Carlyle" vs "bought by TotalEnergies"; Gunvor vs Carlyle). Near-miss labels across languages (`lukoil|verkoop_internationale_operaties` vs `lukoil benelux|status_rapport`) never met. The fix is to hand the AI the claim list and ask it to form groups of "claims stating the same fact, however worded". **This is the same mechanism already locked for 15.2's cross-provider merge (B-04), so build it once here and let 15.2 inherit it.** No embeddings.

- **G-04: Ordering is cluster-BEFORE-gate, per D11** ("the verification gates apply AFTER the merge"). Concretely for 15.1:
  1. cluster all 1,162 claims,
  2. run the gates **per claim** (so the recorded 456/424 per-claim numbers reproduce),
  3. a cluster survives if ANY member survives,
  4. prioritize surviving clusters by corroboration.
  Corroboration is a property of the cluster, so clusters must exist before prioritization. *(Corrects an earlier in-discussion mis-statement of "gate first, then cluster".)*

- **G-05: Contradiction proof follows the G-01 pattern.** The CI test proves grouping plumbing from recorded data; whether the four known contradiction pairs actually land in one group is measured by the hand-run August calibration, alongside the gate agreement %.

**"superseded" verdict (SC2)**

- **G-06: `superseded` becomes a fourth verdict value** — `support | refute | insufficient | superseded`. Today the vocabulary has three words, so the KPAnG case returned **six "support" verdicts on true-but-obsolete claims** with the nuance stranded in a free-text `reconciliation` note that synthesis was free to ignore. Making it a verdict forces the skeptic to choose it and makes it visible to every count, screen and bucket. Note: `verification_verdict.verdict` is free `TEXT` (no enum/CHECK constraint), so no migration is required for the column itself — but the `emit_group_verdict` tool schema, `_parse_group_verdict`, adjudication, and the report shaper all need the new value.

- **G-07: A superseded claim STAYS in the report body with a forced inline caveat.** The caveat text is supplied from pipeline data ("this pattern applied until 1 April 2026") — the writing model presents it, it does not phrase it from memory. It also surfaces in the "Disputed & changed" section (D14, built in 15.2). Rejected: pulling superseded facts out of the body.

**Accounting for gated-out claims (SC2)**

- **G-08: Three honest buckets, every claim carrying its reason.** Today the report shaper computes `unverified = total_claims - claims_with_verdict`, which lumps "was never checkable" together with "should have been checked but the fact-checker crashed". Replace with:
  1. **CHECKED** — has a verdict.
  2. **NOT CHECKABLE** — with the specific reason: `not_falsifiable` / `not_load_bearing` / `both` / `stable_known_fact`.
  3. **SHOULD HAVE BEEN CHECKED BUT WASN'T** — crashed, cap-killed, budget exhausted, gate error. **This bucket must never be silently empty and should be ZERO on a healthy run.** It is the phase's most important number.
  Rejected: flagging low-confidence gate drops for superadmin review.

- **G-09: Nothing client-facing — verification accounting is superadmin-only.** No coverage paragraph, no funnel, no percentages in the delivered report. Coherent with D-08 and the Phase-18 delivery model.

**Fail-loud (SC2)**

- **G-10: Statuses stay as they are; add a loud truth marker.** A run keeps status `completed` but carries a `verification_degraded` marker plus the non-zero bucket-3 count, and **both are stated in words** at the top of the verification report and in the feed's closing summary — not a subtle icon. Rejected: adding a `completed_degraded` status now — **four API endpoints gate on `status == "completed"`** (`runs/api.py:587, 691, 947, 1046`); it also front-runs R6. Rejected: hard-failing a zero-verdict run. **15.2 promotes this marker into a real `completed-degraded` status as part of R6.**

- **G-11: A gate batch that fails after retries fails toward MORE checking, recorded.** Retry with backoff; if it still fails, its claims are treated as "assume worth checking" and sent to the fact-checkers, with a visible gate-error line in the funnel. Never silently drops a check. The existing budget governor is the backstop. Rejected: skipping the affected claims; aborting the run on any gate error.

**Corroboration (SC2)**

- **G-12: Stop deleting the corroboration signal that already exists.** Two live bugs: (1) `claim_distiller` builds `units: list[(provider_name, chunk)]` and then discards the name; (2) `_dedupe_claims` collapses near-identical facts from DIFFERENT researchers and throws the duplicates away (2,976 raw → 1,162). Fix: tag each distilled claim with its source provider, and change dedupe to **MERGE** duplicates into one claim carrying `found_by: [gemini, claude, openai]`. Corroboration count = `len(found_by)`; cluster-level corroboration = distinct providers across the cluster. **The surviving claim count is unchanged (1,162), so the recorded fixture still reproduces exactly.**

### Pattern 1: The flash-classifier convention (copy verbatim from `grouping.py`)

**What:** Every cheap in-pipeline LLM classification step in this codebase follows one shape.
**When to use:** the materiality gate, the error-likelihood gate, and the new clusterer — all three.

```python
# Source: tribunal/nestor_pulse_sdk/pipeline/tribunal/grouping.py:36-56, 117-146, 173-182
_GROUPER_MODEL = "gemini-2.5-flash"
_GROUPER_BATCH = int(os.environ.get("NESTOR_TRIBUNAL_GROUP_BATCH", "40"))
_GROUPER_CONCURRENCY = int(os.environ.get("NESTOR_TRIBUNAL_GROUP_CONCURRENCY", "4"))

def _make_config():
    """gemini-flash config with thinking disabled (mirrors the distiller)."""
    try:
        from google.genai import types as genai_types  # noqa: PLC0415
        return genai_types.GenerateContentConfig(
            max_output_tokens=4096,
            temperature=0.0,
            thinking_config=genai_types.ThinkingConfig(thinking_budget=0),
        )
    except Exception:  # noqa: BLE001 — SDK may not support ThinkingConfig
        return None

async def _tag_batch(claims, audited, run_id, tenant_id):
    block = "\n".join(f"{i} | {(c.get('text') or '')[:240]}" for i, c in enumerate(claims))
    prompt = _TAG_PROMPT.format(claims_block=block)
    config = _make_config()
    kwargs: dict = {"config": config} if config is not None else {}
    try:
        resp = await audited.gemini_generate(
            run_id=run_id, tenant_id=tenant_id, model=_GROUPER_MODEL,
            contents=prompt, **kwargs,
        )
    except Exception as exc:  # noqa: BLE001
        log.warning("grouping: tag batch failed (%d claims): %r", len(claims), exc)
        return [("", "")] * len(claims)          # ← best-effort fallback, never raise
    text = getattr(resp, "text", None)
    if not text:                                  # ← candidates fallback is MANDATORY
        cands = getattr(resp, "candidates", None) or []
        if cands:
            parts = getattr(getattr(cands[0], "content", None), "parts", None) or []
            if parts:
                text = getattr(parts[0], "text", None) or ""
    return _parse_tag_lines(text or "", len(claims))

# Fan-out
batches = [claims[i:i + _GROUPER_BATCH] for i in range(0, len(claims), _GROUPER_BATCH)]
sem = asyncio.Semaphore(_GROUPER_CONCURRENCY)
async def _run(batch):
    async with sem:
        return await _tag_batch(batch, audited, run_id, tenant_id)
tagged = await asyncio.gather(*(_run(b) for b in batches))
```

Non-negotiable elements: `thinking_budget=0` (thinking tokens silently truncate output), **plain-text line output — never JSON mode** (`citations ⊗ structured-outputs = HTTP 400`), the `resp.text` → `resp.candidates[0].content.parts[0].text` fallback, batch-level try/except that returns a neutral default instead of raising, and all egress through `audited.gemini_generate` (audit hash chain, D-07). [CITED: `grouping.py:13-21` module docstring]

**G-11 delta from this pattern:** today's fallback on a failed batch is `("", "")` → singleton group. The gate's fallback must be **"assume worth checking"** (claim enters the verify queue) **and** increment a `gate_errors` funnel key. Add retry-with-backoff around the `gemini_generate` call before falling back.

### Pattern 2: The LLM test seam — a duck-typed fake `audited` object

**What:** Production functions accept `audited` as a kwarg and only ever call `audited.gemini_generate(...)` / `audited.anthropic_messages(...)`. Tests pass a hand-written object with those methods. **No mocking library, no monkeypatching of module globals, no protocol class.**
**When to use:** the G-01 CI replay test, and every unit test for the new gate/cluster modules.

```python
# Source: tribunal/nestor_pulse_sdk/tests/test_tribunal_grouping.py:32-45
class _FakeGeminiResp:
    def __init__(self, text: str) -> None:
        self.text = text

class _FakeGrouperAudited:
    """Returns a canned plain-text tag block for gemini_generate."""
    def __init__(self, text: str) -> None:
        self._text = text
        self.calls = 0

    async def gemini_generate(self, *, run_id, tenant_id, model, contents, **kwargs):
        self.calls += 1
        return _FakeGeminiResp(self._text)

# Driving REAL production code with it:
groups = _run(group_claims(claims=self._claims(), audited=audited,
                           run_id=uuid.uuid4(), tenant_id=uuid.uuid4()))
```

**Recommended concrete seam for G-01 (the single most important design decision in this phase):**

Build `_AnswerKeyGateAudited` in the test module. It implements `gemini_generate`; on each call it:
1. parses the prompt's `INDEX | CLAIM_TEXT` block back out of `contents` (the gate prompt renders it the same way `grouping.py:125-127` does);
2. maps each claim text back to its 1-based fixture id (build `text → id` from `claims-distilled-full.tsv` once at module scope);
3. looks up the recorded decision from `claims-classified-full.tsv` / `keep-strict.tsv`;
4. renders those decisions in the gate's own plain-text line format and returns them as `.text`.

This drives **the real `gates.py` code** — the real batching, the real semaphore, the real parser, the real funnel arithmetic, the real `pipeline.py` wiring — with zero LLM calls and zero flakiness. It satisfies G-01's "REAL gate machinery, recorded answer key" literally.

**Anti-recommendation:** do NOT make the gate accept an injectable `classifier: Callable` parameter used only by tests. That parameter would be a second, untested production code path, and it would bypass the batching/parsing/fallback logic that the CI test is supposed to prove.

### Anti-Patterns to Avoid

- **JSON response mode for any gate/cluster call.** `citations ⊗ structured-outputs = HTTP 400`. Plain-text lines only. [CITED: `grouping.py:16`, `steps.py:576-577`]
- **Omitting `thinking_budget=0`.** Thinking tokens silently consume `max_output_tokens` and truncate output after 2–3 lines. [CITED: `steps.py:570-574`]
- **Letting a gate batch failure raise.** Every existing batch helper catches and returns a neutral default. G-11 makes the neutral default "keep for checking" + a recorded error count.
- **Renaming any existing key in `run.verification_summary`.** `test_hash_chain_replay.py:848-849` and `test_verification_report_endpoint.py:56-61` assert `distilled` / `verify_sessions` and full-dict equality with `RECORDED_FUNNEL_COUNTS`. Additive only.
- **Adding a new run status.** `ck_run_status` CHECK constraint exists (`db/models/run.py:121`, last edited by migration `0007`); `RunStatus` Literal at `runs/schemas.py:39-42` validates FROM the DB row, so an unlisted status turns reads into HTTP 500 (CR-03). G-10 already forbids this.
- **Adding `superseded` to the `_payload_for_row` hashed audit payload.** It is not audit-payload data, but any new *column* must stay out of the frozen 11 fields.
- **Using `id(claim)` as a durable key.** `verdicts_by_claim` is keyed by `id(claim)` (`pipeline.py:312`) — valid only within one process. It is flattened to `claim.get("text")[:80]` before the bundle is serialised (`pipeline.py:693-696`). Any new per-claim gate result must follow the same rule or be stored on the claim dict itself.

## Common Pitfalls

### Pitfall 1: `verify_sessions = 176` is an incident artifact, not a gate output
**What goes wrong:** the CI test is written as `assert funnel == {… "selected_verify": 424, … "verify_sessions": 176}` on the *output of the new gate pipeline*, implying 424 selected claims produce 176 sessions.
**Why it happens:** `RECORDED_FUNNEL_COUNTS` presents six numbers as one funnel. They come from two different sources.
**The evidence:**
- `recorded/REPORT.md` §3.5: "176 group-skeptic calls reached the API and returned … raw tally across **198 claim-slots**".
- `recorded/REPORT.md` §4.2: "**776x** `400 … usage limits`" in a 55-second burst — these are "the coverage-gate re-entry / remaining group passes that never got a response".
- `recorded/GROUPS.md` header: "One row per group-skeptic **PASS** (176 total)". Summed `#claims` across its 176 rows = **198**.
- ⇒ ~176 + 776 ≈ **952 group passes were attempted** over the 1,162 claims (the "~950 checks" in STAKEHOLDER-NOTES). 176 completed; 964 of 1,162 claims were never checked.
- `recorded/REPORT.md` §3.4's "30 tagging calls → **176 groups**" is a mis-statement in the forensic doc; it is 176 *completed sessions*, not 176 groups.

**How to avoid:** treat the funnel as two provably-different classes in the CI test:
- **Computed by the new gate pipeline and asserted exactly:** `distilled=1162`, `kept=456`, `dropped=706`, `selected_verify=424`, `skipped_stable=32`. These come from the answer key through real gate machinery — legitimate, deterministic, and exactly what G-01 describes.
- **A recorded constant asserted as a pass-through:** `verify_sessions=176`. Assert it survives into `run.verification_summary` and the report unchanged (which is what `loader.build_verification_summary()` and the two existing tests already do). Do **not** assert the new clusterer produces 176 clusters — nothing in the data supports that, and forcing it would require tuning cluster granularity to hit a number produced by an API outage.

**Warning signs:** a plan task that says "assert the clusterer yields 176 groups", or any test that derives `verify_sessions` from cluster count.

### Pitfall 2: the `superseded` name collision in the report shaper
**What goes wrong:** G-06 adds `superseded` as a verdict class; `report.py:135-149` **already produces a `superseded` list** with a different meaning (reconciliation-derived scoped/temporal findings), and `schemas.py:280` + `VerificationReport.tsx:302` + `research.ts:104` all bind to that existing meaning.
**Why it happens:** Phase 15 shipped a `superseded` *section* before Phase 15.1 defines a `superseded` *verdict*.
**How to avoid:** decide explicitly. Safest: add `verdicts.superseded` (new list inside `VerificationVerdictGroups`, which needs a new pydantic field at `schemas.py:231-236`) and leave the top-level `report["superseded"]` semantics untouched. Then `counts` gains `superseded_verdicts` distinct from the existing `superseded`.
**Warning signs:** `test_verification_report_endpoint.py:85-91` (`test_reconciled_or_superseded_present_from_real_reconciliation`) starts failing or starts passing for the wrong reason.

### Pitfall 3: unknown verdict values are silently swallowed today
**What goes wrong:** `report.py:123-133` classes anything that is not `support`/`refute` into `insufficient`. A `superseded` verdict would be counted as insufficient and never surface.
**How to avoid:** add the explicit branch AND a negative test asserting an unrecognised verdict string does not land in `insufficient` silently (or, at minimum, that `superseded` lands in its own bucket).
**Also:** `_parse_group_verdict` at `group_skeptic.py:109-113` passes `v.get("verdict","insufficient")` through with no validation — a model typo (`"supersede"`) would flow all the way to the DB (free TEXT, no CHECK). Consider normalising at the parse boundary.

### Pitfall 4: G-12's corroboration cannot be proven by fixture replay
**What goes wrong:** a plan task says "prove `found_by` from the recorded fixture".
**Why it happens:** `claims-distilled-full.tsv` has **no provider column** — only `facet`, `claim_text`, `evidence`. All 1,162 rows carry one of the three focus-area labels, so the `facet`-falls-back-to-provider-name path never fired. Furthermore the fixture holds only **post-dedupe** claims (1,162); the 2,976 raw distiller lines were never committed.
**How to avoid:** prove G-12 with **synthetic unit tests** on `_dedupe_claims` and `_parse_distiller_response` (multi-provider inputs constructed in the test), and prove the *count preservation* against the fixture (see Pitfall 5). Do not promise fixture-derived `found_by` numbers.
**Warning signs:** a task that says "assert cluster corroboration counts against the recorded run".

### Pitfall 5: the "1,162 stays 1,162" merge must be proven, not assumed
**What goes wrong:** `_dedupe_claims` (`steps.py:707-724`) is rewritten from discard-to-merge and accidentally changes the output length (e.g. by keeping the last occurrence instead of the first, or by mutating `seen` semantics), which breaks the whole fixture-replay premise.
**How to avoid:** the merge must preserve **exactly** the current behaviour on the output list — first occurrence kept, same order, same normalisation regex (`re.sub(r"[^a-z0-9 ]","",text.lower())` then `re.sub(r"\s+"," ",…).strip()`) — and only mutate the kept claim's `found_by`. Add a property test: for any input list, `len(new_dedupe(x)) == len(old_dedupe(x))` and `[c["text"] for c in new] == [c["text"] for c in old]`.
**Warning signs:** the replay funnel reports `distilled != 1162`.

### Pitfall 6: `claim_id` is NULL in the recorded verdict rows
**What goes wrong:** G-08's three buckets are computed by joining `verification_verdict` rows to `claim` rows, then the CI test finds `claims_with_verdict == 0` and every claim lands in bucket 3.
**Why it happens:** `loader.py:264` sets `claim_id=None` ("the recorded run predates claim.id linkage"), documented at `verification_verdict.py:17-19`. `report.py:151-156` already works around this.
**How to avoid:** drive the three buckets from the **funnel dict** (which the gate stage owns and which the fixture supplies), not from row joins. Keep the row-join path as the live-run refinement.

### Pitfall 7: the hash-chain additive proof pattern
**What goes wrong:** a new column is added to `audit_log` or a new field enters `_payload_for_row`, and every existing chain breaks.
**How to avoid:** 15.1 should add **no audit_log column**. If it does, follow the exact proof already in the suite:
```python

Extend that tuple with any new column name. `verify_chain` must still return `(True, None)`.
**Warning signs:** `test_chain_green_after_cost_migration` fails, or `len(frozen_fields) != 11`.

### Pitfall 8: mixed line endings and embedded tabs in the fixture TSVs
**What goes wrong:** `keep-strict.tsv` is LF-only while the other two are CRLF; and 74 rows of `claims-distilled-full.tsv` contain more than 2 tabs.
**How to avoid:** `line.rstrip("\r\n")` + `line.split("\t", 2)` (never a bare `split("\t")`, never `csv.reader` without `newline=""`).
**Warning signs:** distilled count ≠ 1162, or a `decision` value like `"VERIFY\r"`.

### Pitfall 9: the `_GROUP_DEPTH` map has no `"low"` key
**What goes wrong:** under G-02, low-stakes groups now survive the gates and enter the verify queue. `pipeline.py:371` does `_GROUP_DEPTH.get(stakes, _GROUP_DEPTH["med"])`, so they silently get **med** depth (4 turns / 5 searches / 3 fetches) — a real cost increase over today's zero.
**How to avoid:** decide explicitly whether low-stakes surviving groups get a new shallow depth tuple or med. This is inside Claude's Discretion but must be a conscious task, not a fallback accident.
**Warning signs:** cost projection for the post-gate run comes out higher than the "~6× cheaper" economic bar.

### Pitfall 10: the empty-claims early return has a divergent shape
`pipeline.py:288-295` returns a hand-built `verification_report` skeleton (`{"verdicts":{}, "dropped_count":0, "budget_marker":"", "coverage":{…}}`) that does not match the full-path shape at 857-867 and carries no funnel. New keys must be added in **both** places or the zero-claim path silently reports a different shape.

    strict: dict[int, str] = {}
    for line in (SEL / "keep-strict.tsv").read_text(encoding="utf-8").split("\n")[1:]:
        line = line.rstrip("\r")              # this file is LF-only, rstrip is harmless
        if not line:
            continue
        cid, decision = line.split("\t")
        strict[int(cid)] = decision           # VERIFY | SKIP_STABLE
    return key, strict
```

## Open Questions

1. **How does the clusterer preserve cross-batch identity?**
   - What we know: today's tagger is batch-parallel because the key space (`ENTITY|ATTRIBUTE`) is global. Real clustering over 1,162 claims cannot fit in one 4096-token call.
   - What's unclear: whether to do (a) two-pass — batch-local clusters then a label-merge pass, (b) block-then-cluster — cheap entity tag to form candidate blocks, then cluster within blocks, or (c) a larger `max_output_tokens` with fewer, bigger batches.
   - Recommendation: this is the phase's hardest design task and is explicitly inside Claude's Discretion. The planner should make it its **own task with an explicit design note**, not fold it into "implement clustering". Option (b) reuses the existing `_TAG_PROMPT` output as a pre-filter and is the smallest change from today's code.

2. **Does the per-claim skeptic fallback branch (`pipeline.py:445-503`) survive G-02?**
   - What we know: it is guarded by `NESTOR_TRIBUNAL_GROUP_VERIFY=false` and is documented as the "A/B baseline". It is the only caller of `triage_claims`.
   - What's unclear: whether removing `triage_claims` means deleting the branch or rewiring it to the gate result.
   - Recommendation: rewire, don't delete — the branch is also the vehicle for `_one_skeptic`, which the coverage-gate re-entry (`pipeline.py:552`) uses in **both** modes.

3. **Where exactly do the three buckets live — funnel keys, per-claim fields, or both?**
   - What we know: Claude's Discretion; the fixture cannot support per-claim attribution (`claim_id` is NULL, Pitfall 6).
   - Recommendation: **funnel keys are mandatory** (that's what the CI test can prove). Per-claim fields are a live-run refinement — carry them on the claim dict and into `rejected_claims`-style ledgers if cheap, but do not make the phase gate depend on them.

4. **Does extending `RECORDED_FUNNEL_COUNTS` break the two full-dict-equality assertions?**
   - What we know: `test_hash_chain_replay.py:849` and `test_verification_report_endpoint.py:59` both do `== RECORDED_FUNNEL_COUNTS`. As long as `build_verification_summary()` returns `dict(RECORDED_FUNNEL_COUNTS)`, extending the constant keeps both green.
   - Recommendation: extend the constant *and* the fixture's `build_verification_summary` together in one task, and re-run both existing tests in the same task's verification step.

5. **What depth do low-stakes groups get once the gates let them through?**
   - See Pitfall 9. Unanswered by CONTEXT; inside Claude's Discretion; has a real cost consequence against the "~6× cheaper" bar.

6. **Does `_verification_appendix` gain anything?**
   - G-09 says nothing client-facing; the appendix is client-facing. Reading G-09 strictly: **no change**. But `_verification_appendix`'s line 988 (`n_claims - n_unverified` labelled "Independently fact-checked") is the *exact* text REPORT.md §4.3 calls dishonest. Leaving a known-false sentence in the delivered report while fixing the superadmin surface is a defensible-but-uncomfortable outcome.
   - Recommendation: raise this to the operator as a **narrow question** — "should the client-facing appendix's one misleading line be corrected (not expanded) in 15.1?" — rather than silently deciding either way.
