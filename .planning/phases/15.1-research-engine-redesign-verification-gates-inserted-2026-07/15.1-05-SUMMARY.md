# Phase 15.1 Plan 05: Verification Gates — Summary

Built `apply_gates()`: two per-claim LLM gates (falsifiable-specific AND load-bearing for
this client's decision, then stable-notorious skip) that fail toward MORE checking and never
retry a usage-cap 400.

## What Was Built

**`tribunal/nestor_pulse_sdk/pipeline/tribunal/gates.py`** (586 lines, new)

The module copies `grouping.py`'s flash-classifier convention verbatim — model, thinking
disabled, plain-text line output never JSON mode, batching, `asyncio.Semaphore` fan-out,
`resp.text` → `candidates[0].content.parts[0].text` fallback, a single `audited.gemini_generate`
egress point — and inverts exactly one thing: the neutral default.

- **`_MATERIALITY_PROMPT`** — `INDEX | KEEP|DROP | KEEP|NOT_FALSIFIABLE|NOT_LOAD_BEARING|BOTH`.
  States the two tests explicitly and grounds test 2 in a `{decision_context}` slot rendered
  above the claims block, following the blind experiment's rule shape ("falsifiable-specific
  AND load-bearing for &lt;the client's decision&gt;").
- **`_STABILITY_PROMPT`** — `INDEX | VERIFY|SKIP_STABLE`. SKIP_STABLE only for facts where being
  wrong is essentially impossible; anything carrying a number, date, status or recent event is
  VERIFY; "when in doubt, VERIFY" is stated in the prompt.
- **`_parse_gate_lines`** — structure copied from `_parse_tag_lines`: pre-filled list of length
  `n`, regex-extracted index, `0 <= idx < n` bounds check, never JSON, nothing propagates out.
  The pre-fill is the KEEP-for-checking default and a parallel all-`True` "was defaulted" list,
  so an omitted, out-of-range, pipe-less or unknown-word answer sends the claim to the
  fact-checkers and books a gate error.
- **`_is_transient` + `_status_of`** — retries 429 / 5xx / timeouts / connection resets only.
  Cap and billing wording is never transient whatever status it claims, and an unrecognised
  error is treated as hard, so it costs one attempt instead of a storm.
- **`_gate_batch`** — `_GATE_RETRIES` extra attempts with `_GATE_BACKOFF_S * 2**attempt` sleeps,
  retrying only on `_is_transient`. On final failure it logs a warning naming the batch size and
  the exception (`%r`) and returns the KEEP-for-checking default for every claim with every index
  flagged as a gate error.
- **`apply_gates`** — zero-claim early return with all nine funnel keys at zero; gate 1 over all
  claims; gate 2 over gate 1's survivors only (dropped claims keep `strict: None`); the decision
  written onto `claim["gate"]`; `selected` built in input order; the funnel computed from the
  per-claim decisions and then checked by four asserts carrying consequence-naming messages; one
  INFO log line in the house `distilled -> kept / dropped -> selected_verify / skipped_stable`
  shape.

**`tribunal/nestor_pulse_sdk/tests/test_gate_failure_modes.py`** (314 lines, 7 tests, new)

Pure tests driving the real `apply_gates` through hand-written duck-typed fakes — no DB, no live
LLM, no mocking library. The fakes tell the two gates apart by the presence of `SKIP_STABLE` in
the prompt.

## Key Decisions

**The gate is a judgment, not a rule.** No regex or heuristic reproduces the recorded 456 keeps —
those came from agents reading each claim — so this is a real LLM classification pass built to
the in-repo convention, not a scoring function.

**Per-field allowed vocabularies.** The plan sketched `_parse_gate_lines(..., allowed: tuple[str, ...],
default: str, fields: int)`. Implemented as `allowed: tuple[tuple[str, ...], ...]` with a
`default: tuple[str, ...]`, one vocabulary per output column. With a flat vocabulary the line
`3 | BOTH | KEEP` would have been accepted with a reason word sitting in the decision slot;
per-field vocabularies make that structurally impossible. `fields` is implied by `len(default)`.

**Partial garble is rejected whole.** A row where any field falls outside its vocabulary is
discarded entirely and takes the KEEP-for-checking default, rather than being half-applied. Half
a decision is not a decision the funnel can account for.

**An unattributable DROP is converted to a KEEP.** `DROP | KEEP` passes per-field validation (both
tokens are individually legal) but is not an accountable drop, so `apply_gates` rewrites it to
KEEP + `gate_error`. This closes the one remaining path by which a claim could have left the queue
without a reason attached to it.

**Empty `decision_context` renders a placeholder, not a blank line.** "Load-bearing" is only
meaningful relative to a decision; an empty slot would leave the model guessing. The placeholder
names the fallback (the evident subject matter of the claims) and instructs it to prefer KEEP.

## Security Properties Preserved

Both controls named in the threat register survive into both gate prompts:

| Threat | Control |
|--------|---------|
| T-15.1-17 prompt injection | claim text truncated to 240 chars; every answer addressed by INDEX, so injected text cannot address another claim's slot. The direction an injection would push (KEEP) is also the safe default. Both prompts also instruct that in-claim text is material to be judged, never a command. |
| T-15.1-18 untrusted parser | pre-filled list, regex index, `0 <= idx < n`, per-field allowed vocabularies, never JSON, nothing propagates out |
| T-15.1-19 silent verification loss | KEEP-for-checking default + `gate_errors` in the funnel; proven by `test_gate_batch_failure_sends_claims_to_checking` |
| T-15.1-20 self-inflicted DoS | `_is_transient` refuses cap/billing errors and all 4xx; bounded retries with exponential backoff; proven by `test_usage_cap_400_is_not_retried` |
| T-15.1-22 audit hash chain | single `audited.gemini_generate` egress point; module imports nothing from `db/`; no audit column touched |

## Deviations from Plan

**1. [Task boundary] Tasks 1 and 2 landed in one commit.**
- **Found during:** Task 1
- **Issue:** Task 1 (prompts, parser, batch helper) and Task 2 (`apply_gates`) are two halves of
  one module. Committing Task 1 alone would have committed a module with no public entry point,
  and splitting it after the fact would have meant fabricating an intermediate state that never
  existed.
- **Resolution:** One `feat` commit covering both, with a message that says so. Task 3 is its own
  commit. Three commits total including this SUMMARY.
- **Commit:** 3769ef4

**2. [Rule 2 - Missing correctness guard] `_parse_gate_lines` takes per-field vocabularies.**
- **Found during:** Task 1
- **Issue:** The plan's flat `allowed: tuple[str, ...]` would have accepted a reason word in the
  decision column (`3 | BOTH | KEEP`), producing a decision the funnel cannot classify.
- **Fix:** `allowed` is a tuple of per-column vocabularies; `default` is a per-column tuple;
  `fields` is derived. Structure, bounds check and never-raise discipline are unchanged.
- **Files modified:** `gates.py`
- **Commit:** 3769ef4

**3. [Rule 2 - Missing correctness guard] Unattributable DROP converted to KEEP + gate_error.**
- **Found during:** Task 2
- **Issue:** `DROP | KEEP` is legal per-column but has no drop reason, so it would have landed in
  the `both` bucket by fallthrough — an invented reason, exactly the accounting dishonesty this
  phase closes.
- **Fix:** `apply_gates` rewrites it to KEEP + `gate_error` (fail toward checking).
- **Files modified:** `gates.py`
- **Commit:** 3769ef4

**4. [Test ergonomics] The test module zeroes `gates._GATE_BACKOFF_S` at import.**
- **Found during:** Task 3
- **Issue:** With the 2.0s base backoff, the always-failing fakes would have spent ~30s of suite
  time asleep proving nothing.
- **Fix:** Plain module-attribute assignment (no mocking library, no monkeypatch fixture) with a
  comment stating the retry COUNT is what is under test. The constant is read at call time.
- **Files modified:** `test_gate_failure_modes.py`
- **Commit:** 62c8912

## Notes for Plan 15.1-07 (wiring)

- `apply_gates` is claim-level and cluster-agnostic. Per G-04 the pipeline clusters first, calls
  this per claim, then reduces cluster survival from member results.
- `decision_context` should be fed the client's brief / context pack. It is optional and
  truncated; passing nothing degrades gracefully but weakens the load-bearing test.
- The returned `claims` list is the SAME objects that went in. Nothing needs re-keying, and the
  decisions cross the pipeline's pause/serialise boundary because they live on the claim dicts.
- Tunables need no Cloud Run env change to deploy: `NESTOR_TRIBUNAL_GATE_BATCH` (40),
  `_CONCURRENCY` (4), `_RETRIES` (2), `_BACKOFF_S` (2.0), `_CONTEXT_CHARS` (2000).
- RESEARCH Pitfall 9 is still open and is 15.1-07's call: under G-02 low-importance groups now
  survive into the verify queue and `_GROUP_DEPTH` has no `"low"` key, so they would silently
  inherit `med` depth.
