<objective>
Give `verification_verdict` its first production writer.

Purpose: this is the larger of the two SC2 gaps and the reason the operator report contradicts
itself. `persist_tribunal_claims` (`citations/extractor.py:282-390`) inserts `claim`, `source` and
`claim_source` rows only; it reads `verdicts_by_claim` solely to mine `evidence_refs`. Grep for
`VerificationVerdict(` outside `tests/` returns nothing but the ORM class definition. So
`build_verification_report` (`report.py:365-388`) queries zero rows on every real run,
`verdicts.{support,refute,insufficient,superseded}` is permanently `[]`, `counts.verdicts_total`
is `0`, and `VerificationReport.tsx` renders the honest gate-computed `funnel.checked` beside
`unverified.count == total_claims` in the SAME payload. 15.1-CONTEXT.md's Integration Points
promised this phase would "fill [the verification_verdict table] with real data instead of
fixture-seeded data"; it did not happen.

**Wave numbering:** the gap-closure set CONTINUES phase numbering — plans 01-10 hold waves 1-6,
closure plans hold waves 7-9. This plan is wave 8 because it needs plan 15.1-11's
`superseded_note` column and plan 15.1-13's `_flush_groups` edits already on disk.

Output: verdict rows written in the same transaction as the claims they belong to, linked by
`claim_id`, tenant-scoped, covering refuted claims as well as survivors — and a suite that still
passes, because the two existing monkeypatched doubles are widened in the same plan that widens
the real signature.
</objective>
