### Gaps Summary

SC1 and SC3 are solidly proven — the gate/replay machinery is real, tested against actual code paths, and the audit hash chain is provably unbroken. SC2 is where this phase falls short of its own stated goal, in exactly the place the phase's own code review (15.1-REVIEW.md) flagged: the **gating half works, the publishing half does not.**

Two confirmed, independent defects compound to make "a superseded verdict available" false for any real production run:

1. **`superseded_note` is dead data** (partially disclosed in 15.1-UAT.md § Known gaps item 2) — produced by the skeptic, never consumed by synthesis, the API, or storage. A superseded claim ships with zero caveat, which is precisely the KPAnG failure G-06/G-07 exist to close.
2. **No production writer for `verification_verdict` exists at all** (NOT disclosed in 15.1-UAT.md's Known Gaps — this is new information surfaced by this verification, re-confirming the code review's CR-02 independently) — meaning `verdicts.{support,refute,insufficient,superseded}` is permanently `[]` on a real run, and the frontend renders a directly self-contradicting payload: `funnel.checked = N` next to `unverified.count = total_claims`.

Because #2 was not captured in 15.1-UAT.md's Known Gaps (which frames the persistence problem narrowly as "superseded_note lacks a column," not as "no verdict is ever persisted at all"), the phase's own closing record understates the size of this gap. The fix the code review sketches (a `VerificationVerdict` insert alongside `persist_tribunal_claims`, in the same transaction, keyed to the freshly-inserted claim row) is the minimum needed to make SC2 true in production, independent of the `superseded_note` storage decision.

**This looks partially intentional but incompletely disclosed.** The `superseded_note` gap (CR-01) was explicitly documented as a deferred, scoped decision in 15.1-UAT.md and in two plan SUMMARYs (15.1-03, 15.1-06) with clear reasoning (no migration this phase). If the operator wants to accept that specific sub-gap as scoped-out for 15.1 and carried to 15.2, an override can be added:

```yaml
overrides:
  - must_have: "SC2 — a superseded verdict is available with a forced inline caveat (G-07)"
    reason: "superseded_note storage decision (new column vs reconciliation sub-key) deliberately deferred to 15.2, which already owns the R6 migration and the D14 'Disputed & changed' consumer — documented in 15.1-UAT.md Known Gaps #2"
    accepted_by: "{name}"
    accepted_at: "{ISO timestamp}"
```

However, the **absence of any `verification_verdict` writer** (CR-02) is not a scoped, documented deferral — it is a gap CONTEXT.md's own Integration Points section expected 15.1 to close ("15.1 fills [verification_verdict and shape_verification_report] with real data instead of fixture-seeded data") and did not. This should be closed with a plan, not overridden, because it makes the entire verdict-reporting surface non-functional on every real run and produces a directly self-contradicting operator-facing payload.

Recommend `/gsd:plan-phase 15.1 --gaps` to plan:
1. A `VerificationVerdict` write path alongside `persist_tribunal_claims` (or a documented fallback that suppresses/annotates the `unverified` block when `counts.verdicts_total == 0`).
2. Either wire `superseded_note` into `contested_notes` + `_verdict_dto`, or formally override/defer it to 15.2 per the suggestion above.

The remaining warnings (WR-01, WR-02, WR-03, WR-10, WR-11 from the code review) do not block SC2 as severely as the two items above but should be triaged into the same closure plan or explicitly deferred to 15.2, since several bear on the "fail-loud"/honest-accounting promise this phase is named for.
