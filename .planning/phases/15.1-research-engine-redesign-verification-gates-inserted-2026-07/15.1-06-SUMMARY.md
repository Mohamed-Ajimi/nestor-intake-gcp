# Phase 15.1 Plan 06: Honest Verification Accounting Summary

Replaced the verification report's two-way `unverified` arithmetic with G-08's three honest
buckets, made a gutted run say so in a full sentence while keeping status `completed` (G-10),
gave the `superseded` verdict its own class without disturbing the identically-named shipped
key (G-06), and pinned the client-facing appendix shut with a negative test (G-14).

## What Was Built

### Task 1 — the `superseded` verdict class (commit `c2a9539`)

`verification/report.py` gained a fourth branch in the verdict-classing chain, placed between
`refute` and the catch-all `else`. Before it existed, a `superseded` verdict — "this was true
and has since changed", the fourth value plan 15.1-03 taught the skeptic to emit — fell through
to `else: insufficient` and reached the operator as "we could not tell". The `refute`-with-
evidence sub-rule is untouched, and the final `else` remains as the catch-all for genuinely
unknown strings.

It emits `report["verdicts"]["superseded"]` and `report["counts"]["superseded_verdicts"]`.

**The name collision is now documented at four sites** (the accumulator declaration, the branch
itself, the `verdicts` emission, and the `counts` emission), each naming both keys and why they
are not the same thing:

| Key | Meaning | Bound by |
|---|---|---|
| `report["superseded"]` (top level) | a reconciliation-derived scoped/temporal finding carrying a canonical value | `runs/schemas.py`, `VerificationReport.tsx`, `research.ts`, `test_verification_report_endpoint.py` |
| `report["verdicts"]["superseded"]` (new) | the G-06 verdict class | this plan; 15.2's D14 |

The top-level derivation at the old lines 135-149 was not touched — `git diff` shows no hunk
there, and `test_reconciled_or_superseded_present_from_real_reconciliation` still passes.

`runs/schemas.py` gained `superseded: list[VerificationVerdictItem] = []` on
`VerificationVerdictGroups` and `superseded_note: str | None = None` on
`VerificationVerdictItem`, each with a class docstring naming pydantic v2's `extra="ignore"`
default as the reason the field must be explicit. `RunStatus` was not touched.

### Task 2 — three buckets and the degradation marker (commit `99a832a`)

Two new pure helpers in `report.py`, both driven by the **funnel** and never by a verdict-row
join (`claim_id` is NULL on every recorded row, so a join reports `claims_with_verdict == 0`
and dumps all 1,162 claims into bucket 3):

`_accounting(funnel)` returns

```
checked                              <- funnel["checked"]
not_checkable.not_falsifiable        <- funnel["not_falsifiable"]
not_checkable.not_load_bearing       <- funnel["not_load_bearing"]
not_checkable.both                   <- funnel["both"]
not_checkable.stable_known_fact      <- funnel["skipped_stable"]
not_checkable.total                  <- the sum of those four
should_have_been_checked             <- funnel["should_have_been_checked"]
gate_errors                          <- funnel["gate_errors"]
```

and returns **`None`** — not a dict of zeros — when `funnel` is `None` *or* any gate key is
absent. A pre-15.1 run therefore reads as "no gate data" rather than falsely certifying a clean
bucket 3.

`_degradation(funnel, accounting)` returns `(verification_degraded, verification_degraded_text)`.
The flag comes from `funnel["verification_degraded"]` when present and is **derived from
`should_have_been_checked > 0`** when the funnel predates the key — omission cannot be a route
to reading green. The text is a full sentence, e.g.

> VERIFICATION DEGRADED -- 226 of 1162 claims were selected for fact-checking but were not
> checked (crash, usage cap, budget exhaustion or gate error). Their supporting passages are
> still in the research text: only a refutation removes a passage, so an unchecked claim ships
> unexamined. This run's verification is incomplete -- do not read it as green.

Gate errors, when non-zero, are appended as an additional sentence — never as a substitute for
the bucket-3 count.

All three keys (`accounting`, `verification_degraded`, `verification_degraded_text`) are
top-level, so `VerificationReport`'s `extra="allow"` would carry them regardless; they were
declared as explicit fields anyway so the API contract is self-documenting.

**`unverified` is byte-unchanged** — `accounting` is a sibling. `VerificationReport.tsx` binds
to `unverified.{count,claims_with_verdict,total_claims}` and needs no edit. No coverage
percentage was added anywhere: the delivered report is written from scrubbed prose, not from the
claim list, so any denominator would be false (G-09's rationale).

### Task 3 — 17 proofs (commit `97af431`)

`tests/test_verification_buckets.py` (12 tests) and `tests/test_fail_loud.py` (5 tests), both
pure — no Postgres, no LLM, no network, no mocking library.

The load-bearing ones:

- **`test_three_buckets_sum_to_distilled`** — 198 + 738 + 226 == 1162. A claim that falls out of
  the sum is a claim nobody can account for.
- **`test_bucket_three_is_the_headline_number`** — 226 on the recorded incident, with the
  comment explaining that this counts *passages that shipped unexamined*, because only a
  refutation triggers scrubbing.
- **`test_healthy_funnel_reports_zero_bucket_three`** — the control: 0 and not degraded.
- **`test_accounting_is_none_without_a_funnel`** — both `funnel=None` and a legacy funnel
  missing the gate keys.
- **`test_client_appendix_unchanged`** (G-14) — imports `_verification_appendix`, calls it with
  a fixed input, and asserts none of `should_have_been_checked` / `not_checkable` /
  `verification_degraded` / `gate_errors` / `accounting` (plus the prose forms) appear. Carries
  a positive control (`## Verification`, the two count lines) so it cannot pass on an empty
  string, and a comment recording that reopening this surface requires reopening G-14.
- **`test_degraded_run_still_reports_completed_status`** (G-10) — asserts `RunStatus` is exactly
  its seven pre-existing values and contains neither `completed_degraded` nor `degraded`.
- **`test_gate_errors_alone_do_not_hide_bucket_three`** — a funnel with both non-zero reports
  both, and the buckets still sum to `distilled`.
- **`test_new_keys_survive_the_pydantic_boundary`** — round-trips the shaped dict through
  `VerificationReport(**report).model_dump()` (see Deviation 2).

`pipeline/tribunal/pipeline.py` is absent from the change set, as G-14 requires.

## Deviations from Plan

### 1. [Rule 3 - Blocking] Worktree was 84 commits stale — fast-forwarded to master

**Found during:** setup, before Task 1.
**Issue:** the branch sat at `a3a0c96`, 84 commits behind `master` (`cb828b0`), with zero unique
commits. Both wave-1 dependencies (the 13-key `RECORDED_FUNNEL_COUNTS`, plan 15.1-03's
`superseded` verdict) were absent, as was `cloudbuild.test-gates.yaml`.
**Fix:** `git merge --ff-only master` — lossless (`git rev-list --count master..HEAD` = 0). The
three dependency checks then passed. This is the same trap plan 15.1-01 hit; it is now 2 for 2
across waves, so the worktree cut point is systematically stale rather than incidentally so.

### 2. [Rule 2 - Missing critical verification] Added `test_new_keys_survive_the_pydantic_boundary`

**Found during:** Task 3.
**Issue:** the plan's warning demanded the nested-pydantic drop be proven "with an endpoint
round-trip in `cloudbuild.test-critical.yaml`" — but the only endpoint test file
(`test_verification_report_endpoint.py`) is **not** in this plan's `files_modified`, and editing
it would have breached the parallel-execution boundary. Without a round-trip somewhere, the
`extra="ignore"` trap (T-15.1-26) would be mitigated by construction but unproven, and the plan's
own `<must_haves>` treats the boundary as a key link.
**Fix:** the round-trip was written inside this plan's own file, validating the shaped dict
through `VerificationReport(**report).model_dump()` and asserting `accounting`,
`verification_degraded_text` and `verdicts.superseded` all survive. This exercises the exact
pydantic models the endpoint returns, so it proves the same property without touching another
plan's file. Verified green in build `f64d7e3b`.

### 3. [Minor] Two acceptance greps are unsatisfiable as literally written

Both are documentation-detection artifacts, not implementation gaps:

- `grep -c "google.cloud\|from google.cloud\|storage\|blob" report.py` **cannot** return 0: the
  module's pre-existing docstring (lines 16-21) states in prose that there is "intentionally no
  `google.cloud`, `storage`, `gcs`, or `blob` import anywhere in this file". The intent —
  no such import — was verified instead with an import-line grep, which matches nothing. No
  import was added; the shaper is still pure, which is what lets all 17 tests run with no
  Postgres.
- `grep -n "superseded: list\[VerificationVerdictItem\]" schemas.py` returns **2** lines, not 1:
  the new field on `VerificationVerdictGroups` (line 254) and the **pre-existing** top-level
  `VerificationReport.superseded` (line 309), which has always used that same type annotation.
  The criterion's intent (one new field, inside `VerificationVerdictGroups`) holds.

### 4. [Minor] `superseded_note` is a forward-declared contract, not yet a live value

The plan asked for `superseded_note` on `VerificationVerdictItem` "so the G-07 caveat text
survives the round trip". It was added — but `_verdict_dto` does **not** emit it, and it was
deliberately left alone: the threat register's T-15.1-25 states `_verdict_dto` is not modified,
and plan 15.1-03 kept `superseded_note` in the parsed pipeline dict rather than adding a
`verification_verdict` column. So the field currently declares the contract for 15.2's D14
section rather than carrying data. Wiring it end-to-end needs a persistence decision (a column
or a `reconciliation` sub-key) that belongs to whoever owns that migration.

## Notes for Downstream Plans

- **Read `accounting`, not `unverified`,** for coverage questions. `unverified` is retained only
  because the frontend binds to it; its two-way arithmetic is the defect this plan routes
  around, not a second opinion.
- **`accounting is None` means "this run has no gate data"** — a pre-15.1 run. It does not mean
  zero. Any consumer that treats `None` as `0` re-introduces the P1 defect.
- **Never join verdict rows to claims to rebuild these buckets.** `claim_id` is NULL on the
  recorded rows and on any run that predates claim linkage.
- **15.2's R6**: promote `verification_degraded` into a terminal status by changing `RunStatus`,
  the `ck_run_status` CHECK constraint, and all four `status == "completed"` endpoint gates
  together. `test_degraded_run_still_reports_completed_status` will fail when you do — that is
  the intended tripwire, and updating it is part of R6's work.
- **G-14 stays closed** unless the operator reopens it. `test_client_appendix_unchanged` is the
  enforcement mechanism; deleting it to make a change pass would silently reverse an operator
  ruling.
