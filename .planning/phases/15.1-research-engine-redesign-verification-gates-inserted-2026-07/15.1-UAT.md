### 3. No production writer existed for `verification_verdict`

> **NOT DISCLOSED IN THE ORIGINAL KNOWN GAPS.** This was surfaced by `15.1-VERIFICATION.md` after
> the original pass was recorded as complete, not by the phase's own closing record. It is written
> here in full because it was the most serious of the three: the phase shipped an operator surface
> that was structurally incapable of showing data.

Migration `0011` created the `verification_verdict` table and `verification/report.py` read from it,
but **nothing ever wrote a row**. The consequences on every real run, stated plainly:

- `report["verdicts"]["support" | "refute" | "insufficient" | "superseded"]` was permanently `[]`.
- `counts.verdicts_total` was permanently `0`.
- The report published `funnel.checked` (a non-zero number of claims the engine *did* check) directly
  beside `unverified == total_claims` — i.e. it simultaneously claimed to have checked N claims and
  to have verified none of them. Both numbers came from the same report.

> **RESOLVED 2026-07-25.** Plan 15.1-14 added `_insert_verdict`, the first production writer, called
> from two sites inside `persist_tribunal_claims` (which Stage 7 runs on every Tribunal run):
>
> - **Survivors** carry the `claim_id` of the claim row inserted for them moments earlier in the same
>   transaction — `test_survivor_verdicts_are_linked_to_the_claim_row_just_inserted`.
> - **Dropped (refuted / conflict-lost) claims** get **no claim row** but **do** get a verdict row
>   with `claim_id NULL`, so `report["verdicts"]["refute"]` stops being structurally empty —
>   `test_dropped_claim_verdicts_are_written_with_a_null_claim_id`.
> - The insert runs **after** `set_tenant_context` inside the caller's transaction, proved at runtime
>   rather than by source order — `test_tenant_context_is_set_before_any_verdict_insert`.
> - A malformed verdict dict defaults to `insufficient` rather than binding `NULL` into a `NOT NULL`
>   column, so a junk model payload cannot abort a paid run —
>   `test_a_malformed_verdict_dict_does_not_raise_and_defaults_the_verdict`.
>
> **Standing regression guard:** plan 15.1-12's `verdicts_total == 0` fallback. If the verdict table
> is ever empty again, `unverified` is recomputed from the gate funnel instead of silently reporting
> `N of N` — `test_verdict_publication.py::test_unverified_falls_back_to_the_funnel_when_no_verdict_rows`.
> The zero-verdict state can no longer masquerade as a verified run.
>
> All 11 write-path tests are recorded PASSED in build `e6398d72` (see § Gap-closure phase gate).
> **The first live run after 2026-08-01 remains the true proof** — these are no-DB unit assertions.

### 4. The `superseded` verdict class had no rendering site

> **NOT DISCLOSED IN THE ORIGINAL KNOWN GAPS EITHER.** Found during gap-closure planning review. It
> is the subtlest defect of the three, because Phase 15.1's own new feature caused it.

The trace, honestly:

1. `report.py` classes verdicts through an **`if/elif` chain**, so a `superseded` verdict goes

### WR-01 — the coverage gate is unreachable dead code

**File:** `tribunal/nestor_pulse_sdk/pipeline/tribunal/pipeline.py:570, 845-890`

**What the defect actually is.** `verdicts_by_claim` is seeded with **every** claim at line 570
(`{id(c): [] for c in claims}`). `adjudications` is then built at lines 848-852 as
`{id(c): True for c in claims if id(c) in verdicts_by_claim}` — which, given that seeding, is `True`
for every claim **unconditionally**. `check_coverage` fails a claim only when
`id(claim) not in adjudications` (`coverage_gate.py:61`), so:

- `coverage["pass"]` is **always** `True`;
- `coverage["uncovered"]` is **always** empty;
- the re-entry `while` at line 861 **never executes**;
- the phase's own new bucket-3 site (c) at lines 886-888 **can never fire**;
- `reentry_count` is permanently `0`, so `_verification_appendix`'s re-run line never renders.

The inline comment at lines 846-847 states the **opposite** of the actual behaviour.

**What it costs to leave open.** A high-stakes claim whose group skeptic crashed is supposed to get a
last-chance re-entry with three more skeptics. That recovery **does not exist**. Importantly, this
does **not** break truth-telling: the claim is still caught by the separate ground-truth
reconciliation at line 916 and booked honestly in bucket 3, so the funnel stays accurate. What is
missing is a *recovery mechanism* the phase's own comments (lines 909-911) claim to rely on.

**Recorded fix** (so 15.2 does not re-derive it):

```python
adjudications: dict[int, Any] = {
    id(c): True for c in claims if verdicts_by_claim.get(id(c))
}
```

…plus correcting the comment at 845-847.

### WR-10 — verdicts attributed to gate-DROPped group members

**Files:** `pipeline/tribunal/group_skeptic.py:150-156`, `pipeline/tribunal/pipeline.py:699-703`,
`verification/report.py:96, 120-126`

**What the defect actually is.** A group is selected when *any* member is `VERIFY`
(`_group_selected`, `pipeline.py:148`). `_parse_group_verdict` then fills a verdict for **every**
index in the group — including members the materiality gate `DROP`ped and members marked
`SKIP_STABLE`. `_flush_groups` files all of them into `verdicts_by_claim`, so those claims reach
`adjudicate_all`, **can be refuted**, land in `dropped`, and have their passages removed by
`scrub_research`.

The funnel meanwhile books them in **bucket 2** (`not_checkable`, with a named reason). So a claim
that was in fact checked — and even **removed from the report** — is published to the operator as
"never checkable". This breaks the phase's stated invariant that every distilled claim lands in
exactly one bucket describing what happened to it, in the **"we did more than we said"** direction.

**Recorded fix — both options the review offers:**

```python
# Option 1 (smaller, matches the documented accounting): skip dropped members
for i, c in enumerate(grp["claims"]):
    if (c.get("gate") or {}).get("strict") != "VERIFY":
        continue      # gated out: bucket 2 owns it
    v = vbi.get(i)
    if v is not None:
        verdicts_by_claim[id(c)].append(v)
```

**Option 2:** add a `checked_incidentally` funnel line and subtract it from bucket 2 in `_accounting`
— larger, but keeps the free signal rather than discarding it.

reliability work, D13/D14 report changes) and will be editing these exact lines. Fixing them now
would mean writing code 15.2 then rewrites, and — for WR-10 — making a funnel-semantics choice that
belongs with the person changing the funnel. Neither is a truth-telling defect: WR-01 leaves the
funnel honest and removes only a recovery path, and WR-10 errs by under-claiming what was checked.
**They belong to the same 15.2 plans that touch `pipeline.py`'s verify stage.**

### 8. The August calibration — informational only, never a gate

**Command (operator-run, from the repo root, after 2026-08-01 and after raising the Anthropic cap):**

```bash
pytest -m live nestor_pulse_sdk/tests/test_gate_calibration.py -s
```

The file is fenced **three** ways, so all three must be undone deliberately: the `live` marker, an
inline env-gated `pytest.skip` as the first statement of each test (set the opt-in env var named in
the skip message), and `-m "not live"` in `cloudbuild.test-gates.yaml`. `-s` is required — these
tests **print**, they do not assert.

**What to look at — two reports:**

1. **`test_gate_agreement_against_the_blind_answer_key`** — turns the REAL classifier loose on an
   evenly-strided sample of the 1,162 recorded claims (default 300; strided because the distilled
   TSV is ordered by facet, so the first N would be one topic) and prints: overall agreement %, the
   KEEP/DROP confusion matrix, agreement per DROP reason, VERIFY/SKIP_STABLE agreement among the
   recorded KEEPs, the gate's own funnel, and both disagreement lists — **the costly direction
   first** (recorded KEEP → gate DROP: a material claim that would ship unexamined), then the cheap
   one (recorded DROP → gate KEEP: money wasted, nothing hidden).
2. **`test_known_contradiction_pairs_cluster_together`** — runs the real clusterer over the full
   population and reports cluster count, singleton share (against the **92%** singleton baseline
   that let four flat contradictions ship), and, per pair, whether the two variants collided:

   | Pair | The contradiction that shipped |
   |---|---|
   | Aral | 16% vs 21% market share |
   | LUKOIL NL | 46 vs ~70/75 stations |
   | Zeeland | "sold to Carlyle" vs "bought by TotalEnergies" |
   | Gunvor vs Carlyle | conflicting acquirer |

   A probe that matches nothing prints `NOT FOUND IN FIXTURE` with its match counts — that is
   fixture drift, not a clustering failure.

**What a good/bad result means:** there is **NO threshold and NO pass/fail** (G-01, G-05). High
agreement means the live classifier reproduces the blind agents' judgment; low agreement means the
gate prompt needs work — but neither turns a build red. This was a deliberate design decision: the
456/424 labels came from blind LLM agents reading each claim, a production gate cannot hit them
exactly, and the honest response to a red build caused by classifier wobble is to weaken the check.
The enforcement is mechanical — `grep -c "assert"` on that file returns **0** (see § G-01 boundary
evidence above).

**Where the numbers go:** straight into **Phase 15.2's live validation V-01 / V-02 / V-03**. Record
the agreement table and the four pair results verbatim; do not summarise them into a verdict.
