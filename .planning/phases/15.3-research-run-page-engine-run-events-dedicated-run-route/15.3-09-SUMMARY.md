# Phase 15.3 Plan 09: Statuses, Affordances and the Combined Deploy Record — Summary

The run page now tells the truth about every state a run can reach, carries all four affordances
the design of record drops, and rides one deploy procedure that covers both migration lines with an
attribution record attached.

## What was built

**The eight statuses.** `RunStatusCard.tsx` is an exhaustive switch: each of the eight status
literals appears exactly once as a case, plus a default that names the raw value rather than
rendering nothing. The two traps carried from the embedded card are re-encoded and documented in
the module comment:

- `completed_degraded` **shares the success branch**. Inside it, the degraded test controls the
  border colour, the icon, the title and the sentence — nothing else. There is no status test
  around any affordance, which is exactly how a ~$45 run keeps its output.
- `parked` gets **its own branch**, with no output affordance and no chain control anywhere in it.

`cancelled` is distinct from `failed` (a deliberate stop reported as a failure is a lie the operator
will not trust twice) and `needs_input` is distinct from `parked` (they look alike and mean opposite
things about what the next click costs).

**The feed survives every terminal state.** This was the defect worth the plan on its own: in the
embedded card the failed and cancelled branches render an error and a button and nothing else — no
feed call appears in them at all — so the two states whose evidence matters most are the only two
that discard it. On the page the card and the feed are **siblings**, and the feed's only guard is
whether events exist. No status branch can reach it, so this is true by construction rather than by
remembering to add it to two more branches.

**The four affordances** (D-10), each preventing its named harm:

1. **Audit-body drill-down** — the EU AI Act Art. 12 record, opened beneath the exact row whose call
   it records, through `RunFeed`'s `renderAfterRow` seam. Re-clicking closes it; the panel adds no
   scroll container of its own. The handler is passed only when both ids resolved — no stub.
2. **Chain lock** — three states, not two. A chain that failed to verify renders a locked panel
   with a re-check and **no output control at all in that branch**: the element is absent, not
   disabled. All three panels are additionally gated on a success-terminal status, mirroring the
   seam's own `is_research_success(status) AND verified` gate. The local override survives the
   normal case of opening an old run whose stream closed long ago.
3. **Resume on a paused run**, and only resume — the fresh-attempt affordance enumerates `failed`,
   `cancelled` and `needs_input`, so a paused run can never be offered a retry that discards
   checkpoints the engine has already paid for.
4. **Stop asks first** — the button opens the confirmation and does nothing else; the request is
   issued from the confirming action's handler alone. The copy states that the cost so far is not
   refunded and the run cannot be continued afterwards.

**The runbook.** § Step 15.2.k now covers plans 15.2-20…26 **and** 15.3-01…09 as one ordered
procedure, extended in place. Both migration lines are named with their own literal proof lines and
their own version tables; the engine gate count is corrected from a stale 27 to the 30 the config
actually asserts; the backend and three frontend gates join the same preflight; each image gains a
note of what 15.3 puts in it and what skipping it would cost. The safety ordering is restated **as
unchanged**. The combined deploy record at the end carries two separately labelled change lists and
the operator-affirmed no-behaviour-change sentence.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug] A finished run's header clock ran away**

- **Found during:** Task 2
- **Issue:** `useElapsed(started_at, !isTerminal)` still computes `now − started_at` on its single
  tick when inactive. For a run that completed three days ago the header read a four-digit figure
  presented as the run's elapsed time.
- **Fix:** a finished run (terminal **and** carrying a completion stamp) shows the fixed span
  between its own two timestamps; the label switches to a duration label. A run that stopped
  without a completion stamp keeps the counter. The hook is still called unconditionally.
- **Files:** `frontend/src/routes/admin.pulse.runs.$runId.tsx`, the three locales
- **Commit:** `907e195`

**2. [Rule 2 — Missing correctness] Two live regions would announce each status change twice**

- **Found during:** Task 2
- **Issue:** Task 1 requires the live region on the card. The header already carried one over the
  same status text, so both would announce.
- **Fix:** the header status line keeps its visible content and loses the region attributes; the
  card is the page's single live region. 15.3-08's mitigation of T-15.3-82 (the feed declares none;
  the page's is scoped to status and phase) is unaffected — the region simply moved within the page.
- **Files:** `frontend/src/routes/admin.pulse.runs.$runId.tsx`
- **Commit:** `907e195`

**3. [Rule 3 — Blocking] `RESEARCH_TERMINAL` was not exported**

- **Found during:** Task 2
- **Issue:** Task 2's criterion requires the route to import the set from `research.ts`, but it was
  a module-local const there. Three unlinked copies existed (transport, embedded card, route).
- **Fix:** exported it from `research.ts` and imported it in the route, which removes the route's
  copy. The embedded card's copy was left alone — it is outside this plan's file set and touching it
  risks the intake page for no gain here. Two copies remain where there were three.
- **Files:** `frontend/src/lib/api/research.ts`, the route
- **Commit:** `907e195`

**4. [Rule 3 — Blocking] Continuing a paused run had no way to reach the page**

- **Found during:** Task 4
- **Issue:** `onReload` was specified as "reuse whatever the route already does to refresh" — the
  route does nothing; its only data source is an SSE connection. A paused run's connection is
  already closed (the pause is terminal for the stream), so after a successful continuation no frame
  would ever arrive and the page would sit on the paused card while the run demonstrably moved.
- **Fix:** `useActiveResearchRun` gained an **optional** `reopenKey` folded into its effect deps.
  Omitting it is byte-for-byte the previous behaviour, so the embedded card is unaffected. It is
  bumped by a completed operator action only — not a timer, and not a second polling loop.
- **Files:** `frontend/src/components/intake/ResearchRunProgress.tsx`, the route
- **Commit:** `381de21`

**5. [Rule 1 — Bug] The runbook claimed no route was added**

- **Found during:** Task 5
- **Issue:** § 15.2.k step 1 stated "No `routeTree.gen.ts` regeneration: 15.2-25 adds no route".
  True for 15.2 alone; false for the combined deploy — 15.3-08 adds `/admin/pulse/runs/$runId` and
  its regenerated route table is already committed. An operator reading the old note could ship a
  frontend whose route table predates the page, producing a 404 that looks like a backend fault.
- **Fix:** the note is corrected and marked as changed, with a guard added to step 0 that prints
  `run route registered`.
- **Files:** `infra/DEPLOY-RUNBOOK.md`
- **Commit:** `5c42217`

### Resolved conflicts between task texts

**6. Elapsed, cost and phase on the running card**

Task 1 lists "elapsed, cost, current phase" on the running card. Task 2 states the header's stats
stay and forbids duplicating them into the card, and carries the testable criterion *"the elapsed
and cost figures appear once each on the page"*. The merge note records that the task bodies were
carried over verbatim from three former plans, so the tension is an artifact of the merge. Resolved
toward the testable criterion: the numbers live in the header, the words and the actions live in the
card. `elapsed` remains on the declared props contract and is documented as deliberately unrendered.
For the same reason the success card shows completed-at only — total cost and duration would both be
second copies of header figures, and the duration now IS the header figure for a finished run.

**7. `RunStatusCard`'s `run` prop widened to nullable**

The declared interface says `run: ResearchRun`. The page has a genuine cold-open window in which no
frame has arrived — the window an operator lands in when clicking through from the trigger — and a
non-nullable prop would leave that window with no card at all, defeating the queued branch the plan
explicitly specifies. The prop is a superset of the declared shape, so any caller conforming to the
interface still type-checks.
