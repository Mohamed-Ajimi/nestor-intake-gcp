# Phase 15.3 Plan 08: The Dedicated Run Page Summary

**A deep-research run now has its own URL that can be closed, bookmarked and reopened, showing
its full persisted history with an elapsed timer that counts from the run's own `started_at`
rather than from page load — and the feed on it reads as the operator's design reads.**

This is the first thing in phase 15.3 the operator can actually look at. The seven engine
plans built the events; this plan built the surface that shows them.

## The Three Things That Had To Be Right

**1. The clock derives from the run, not from mount.** `grep -c "useState(0)"` in the route is
**0**. The elapsed value comes from `useElapsed(run.started_at, !isTerminal)` in
`runClock.ts`, whose body was moved out of `ResearchRunProgress.tsx` **byte-identically** —
verified by diffing the extracted function against the deleted one, for all four helpers, not
just asserted. The prototype's `setSecs(s => s+1)` pattern appears nowhere. Closing the page
and reopening it re-derives from the same timestamp, which is the whole of D-01.

**2. The route is flat.** `frontend/src/routes/admin.pulse.runs.$runId.tsx` →
`/admin/pulse/runs/:runId`, a leaf under the existing `admin.pulse` layout, which already
wraps its own outlet in `<ProductShell>`. `grep -c "Outlet"` in the route is **0**. Nesting
under `admin.pulse.intakes.$id.tsx` would have turned that leaf into a parent needing an
outlet — the Phase-18 trap — and would have tied the URL to an intake id a bookmark does not
carry. The generated route tree carries `/admin/pulse/runs/$runId` after the build.

**3. i18n is green in all three locales.** `node scripts/i18n-audit.mjs` exits 0 with CHECK
A/B/C all clean. Every new string goes through `t()` and every new key was added to en, nl AND
fr in the same edit. The 107 CHECK D advisories are entirely pre-existing — **zero** originate
in any file this plan created or touched (checked by filtering the audit output on the new
paths).

## What Was Built

**Task 1 — transport + clock** (`0b6b877`)

`research.ts` gained `RunEventKind`, `RunEvent`, `RunEventPage`, `ResearchRun.event_seq` (named
in comment as the FEED CURSOR), and the two verbs. Both are one-shot `apiFetch` calls —
`grep -c "fetch("` inside the two function bodies is **0**, so the transport is not forked.
`RunEvent.kind` is a plain `string`, matching the backend's deliberate choice for the same
reason: a newer engine revision emitting a thirteenth kind during a rolling deploy must not
turn the live run an operator is watching into a broken page.

`useRunEvents` backfills the whole history (paged, `has_more`-driven, capped at 10 × 500) and
thereafter fetches only when `cursor > afterSeq`. It de-duplicates on `seq`, never rewinds
(`Math.max` against `next_after_seq`, belt-and-braces on top of 15.3-02's anti-rewind
property), and silent-degrades on every failure path.

**Task 2 — the route** (`0ae2f96`)

Cold open resolves run → intake through `locateResearchRun` and **only** through it; the route
accepts no intake parameter, because a bookmarked URL will not carry one and a URL-supplied
tenant hint is what TENANT-02 forbids. One full-height column: fixed header, exactly one
scrolling region, footer ticker while live. The live region is scoped to status and phase; the
feed body carries none. All eight run statuses are handled, each as a literal `t()` call so
CHECK B actually covers them, plus an `unknown` fallback.

**Task 3 — the way in** (`91766cb`)

`OpenRunLink` defined once, rendered at **4** sites — active, completed/degraded, parked, and
failed/cancelled. The failure branches matter most: those two cards drop the feed entirely
today, so "failed" and nothing else is exactly what the deeper page fixes. Styled as the
card's existing secondary action, not competing with Resume/Retry/Stop. Nothing was removed:
all four branch conditions are still present and `ResearchRunProgress` is still mounted on the
intake detail route.

**Task 4 — the feed** (`cc50c53`)

Grouping folds consecutive same-`stage` events. `grep -c "ENGINE_STAGES\|deep_research\|
research_division\|synthesize"` in `RunFeed.tsx` is **0** — no stage list, count or order
anywhere, so an added engine phase costs this component nothing. Rendering is a lookup with a
default branch that returns a plain mono line, never `null`. Dispatch headers with indented
agent children, per-phase summaries composed only from the meta each event carries, the live
badge on `meta.is_live`, and completed phases auto-collapsing to a two-line preview with a
reopen toggle. `grep -c "setInterval"` is **1** — one blink timer for the whole feed, where
the prototype has one per row.

**Task 5 — mount it** (`22e8071`)

Placeholder deleted (`grep -ci "placeholder\|replace me"` in the route is **0**). Scroll count
is **1** in the route and **0** in `RunFeed`. Three distinct empty states, the truncation
banner, and a footer ticker whose phase label prefers the latest divider's human label over
the raw `current_stage` key.

## The Cold-Open Case

A newly triggered run has `status='queued'` and **no** `tribunal_run_id`. 15.3-07 deliberately
does not 404 `locate` in that window, but the events verb *does* 404 (there is nothing to
page). The page handles this without treating it as an error: `locate` succeeds, the SSE frame
arrives with `event_seq: null`, `useRunEvents` issues no request at all (its cursor guard
short-circuits on `null`), and the feed renders `emptyQueued` — "this run is queued, the engine
has not started it yet". No error card, no spinner that never resolves, and no assumption
anywhere that a run has an engine id.

## Deviations from Plan

**1. [Rule 3 - Blocking] `useActiveResearchRun` had to be exported**

- **Found during:** Task 2
- **Issue:** Task 2's `read_first` names `useActiveResearchRun` as "the SSE-first hook this
  page reuses", but the hook was module-private in `ResearchRunProgress.tsx`, and neither
  Task 2's nor Task 3's `<files>` list anticipated the one-word change needed to import it.
- **Fix:** Added `export` plus a comment recording why it is shared. The alternative —
  re-implementing the stream/terminal/cleanup mechanics on the page — would have created a
  second opinion about when a run ended, which is precisely what D-05 chose one transport to
  avoid.
- **Files modified:** `frontend/src/components/intake/ResearchRunProgress.tsx`
- **Commit:** `0ae2f96`

**2. [Rule 1 - Bug] My own comments in `RunFeed.tsx` quoted two gated strings verbatim**

- **Found during:** Task 4, by the structural checks before committing
- **Issue:** The security and accessibility comments asserted the absence of the raw-HTML
  injection prop and of a live-region attribute — by naming both verbatim. A source scan
  enforcing T-15.3-72/80/82 greps for exactly those tokens, so the comments claiming they were
  absent were themselves the only occurrences. This is the same self-trip two other executors
  hit this phase, and the third instance of it.
- **Fix:** Both restated descriptively, with a note in each explaining that the token is
  described rather than spelled *because* the check is a source scan. Counts are now 0 and 0.
- **Files modified:** `frontend/src/components/research/RunFeed.tsx`
- **Commit:** `cc50c53` (fixed before the task was committed)

**3. `useRunEvents` returns three fields, not the two the `<interfaces>` block declares**

The interface block states `{ events, loading }`, but Task 1's own action text requires it to
"stop with a flag the page can render as 'history truncated'" and Task 5's acceptance criterion
requires that state to be a reachable branch. It returns `{ events, loading, truncated }`.
Recorded as an interface completion rather than silently widening a declared contract.

**4. The summary line does NOT reuse `research.feed.summaryCard`**

The plan asked to reuse it "where they fit". It does not fit: `summaryCard` is a single
composed string interpolating duration, actions and cost **together**, whereas the design of
record shows each part only when the event carries it (`{line.worked && …}`, `{line.actions !=
null && …}`). Reusing it would have forced placeholder values for parts the engine did not
emit. Granular keys were minted under `research.runPage.feed.*` instead. `research.feed.showLess`,
`research.feed.scrollToLatest`, `research.feed.viewAudit`/`hideAudit`, `research.elapsed`,
`research.cost` and `research.costFallback` **are** reused, so only the genuinely
differently-shaped strings are new.

**5. Task 3's helper-deletion criterion reads 1, not 0 — prefix false positive**

`grep -c "function useElapsed\|function fmtDuration\|function fmtCost\|function fmtDate"` on
`ResearchRunProgress.tsx` returns **1**. The single match is `fmtDurationSecs`, a *different*
helper (seconds → "Xm Ys") that was never part of the move and is still used by
`StageSummaryCard`. Anchoring on the exact signatures —
`grep -c "function useElapsed(\|function fmtDuration(\|function fmtCost(\|function fmtDate("` —
returns **0**. The load-bearing property (the four moved copies are gone) holds; the criterion's
pattern was simply loose. Same class as 15.3-07's `async def` count of 6.

**6. `getIntake` is called for the header's client name**

Not named in the plan's interfaces. It is an existing space-scoped verb, called with the
*resolved* intake id, and its failure is non-blocking — the header falls back to a generic
title and the run still renders. No new surface.

## Volume Behaviour — INSPECTED, NOT TESTED

**This is recorded as inspected because it was inspected. Nothing here was measured, and no
downstream reader should treat it as proven.** There is no frontend test framework in this
repo; nothing drove cursor ticks and counted requests, and nothing counted renders.

**Delta-only fetch (T-15.3-74).** What was established: the guard `if (cursor <=
afterSeqRef.current) return;` is present, sits before any call, and `cursor == null`
short-circuits earlier still. What was **not** established: that it holds under every
re-render, StrictMode double-invoke, or a cursor advancing while a backfill is mid-flight (an
`inFlightRef` guard exists for that last case, and it too is only read, not exercised).

**Memoisation (T-15.3-81).** `React.memo` wraps both the row and the group, and grouping is
`useMemo`'d on the events array identity. Because a presence check is defeated by an inline
object or callback prop — the exact failure the boundary exists to prevent — **every prop
crossing both boundaries was read individually**:

| Prop | Kind | Stable because |
|---|---|---|
| `events` | reference | slice of the `useMemo`'d groups; recomputed only when events change |
| `event` | reference | parsed once, only ever appended, never rebuilt |
| `isComplete`, `canDrill` | primitive | booleans |
| `cursorSeq` | primitive | `number \| null` |
| `drilldownAuditId` | primitive | `string \| null` |
| `onDrill`, `renderAfterRow` | reference | `useCallback` with `[]`, backed by render-assigned refs so a caller's inline arrow cannot leak through |

No inline object or arrow is passed to either memoised component. Additionally, only the
**last** group ever receives a non-null `cursorSeq`; every earlier group receives a constant
`null`, so the 530 ms blink cannot invalidate the history's memo. The honest proof, if this
ever needs to be real, is a Vitest render-count assertion across appended events — separate
work, deliberately not smuggled in here.
