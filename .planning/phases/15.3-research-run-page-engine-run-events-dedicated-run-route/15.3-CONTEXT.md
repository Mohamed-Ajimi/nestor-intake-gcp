## Phase Boundary

**Phase 15.3 gives a deep-research run its own page, and gives the engine the events that
page needs to show.** It exists because the operator, watching the aborted `d6bb3aae` run,
could not tell what the engine was doing.

Today the entire run — 30–60 minutes, 14 engine phases, dozens of dispatched agents, tens of
dollars — renders as **one card embedded partway down `/admin/pulse/intakes/:id`**. It has no
URL, cannot be shared or bookmarked, scrolls away with the page, and its activity feed is a
28rem scroll area nested inside the page's own scroll. A failed agent displays the word
"failed" and nothing else. There is no log view anywhere in the product; engine logs are
reachable only through Cloud Logging by an engineer.

**Two deliverables, in this order (the order is an operator decision — see D-02):**

1. **Engine run-events.** The engine emits an ordered, durable event per meaningful action —
   dispatch, tool load, search/fetch, reasoning step, stream configuration, agent
   start/finish/retry/fail, per-stage summary — persisted and readable, so a feed can be
   reconstructed after the fact rather than only watched live.
2. **A dedicated run page.** A standalone route rendering those events as a streaming feed,
   per the operator's design of record in `docs/design/prototypes/ResearchRunImproved.tsx`.

**Why the order matters.** The operator's design uses twelve line kinds. Six of them —
`thinking`, `tool`, `search`, `plan`, `streams`, `dispatch` — have **no data source in the
engine today**. Building the UI first would mean shipping a page whose feed is roughly half
the density of the approved design, then redesigning it when the events arrive. The operator
chose to build the events first so the page is built once, against the full model.

**Deploy coupling.** This phase ships in the **SAME deploy batch as Phase 15.2's gap fixes**
(operator decision, D-03). It does not block 15.2's operator deploy procedure — it must
simply be merged to `master` before that procedure's image build step, since the runbook
builds four images at one `$SHA` and anything on `master` rides along.

**Out of scope:**
- **The V-01 live run itself** — that is Phase 15.2 plan 15.2-18 Task 4, on a fresh intake.
- **Client-visible research surfaces.** D-08 stands: no client route may import any of this.
  The run page is superadmin-only by placement AND by API authorization.
- **Replacing `ResearchRunProgress.tsx` on the intake detail route.** The embedded card stays
  as the intake-page summary; the new page is an additional, deeper surface reached from it.
  Removing the card is a separate decision after the operator has used the page.
- **Q&A chat over run output** — Phase 19.
- **Cost caps / budget governor** — Phase 20 (16-D-02 keeps the governor uncapped).
- **Engine behaviour changes.** This phase adds observability. It must not alter what the
  pipeline decides, dispatches, or produces.

## Hard constraints carried forward

- **Tenant isolation is enforced server-side at the API layer** (CLAUDE.md). Every new read
  verb is space-scoped and existence-hiding: a cross-tenant, user-role or null-space caller
  gets **exactly 404** — never 403, never 200 — matching every other research verb. Proven by
  test, never asserted. The broken-RLS class of bug must not recur.
- **`frontend/src/components/ui/` (shadcn) is not modified directly.**
- **Three locales are a HARD CI gate.** `frontend/scripts/i18n-audit.mjs` CHECK B fails the
  build when a literal `t("key")` does not resolve in en, nl AND fr.
- **`package-lock.json` IS committed — always `npm ci`, never `npm install`.** CLAUDE.md's
  "no lockfile committed" line is stale and wrong; following it caused a Radix/React #185
  production break on 2026-07-21.
- **No local Python and no Docker on the dev machine.** Backend/engine tests run on Cloud
  Build. `gcloud` is available. Never claim a test run that was not performed.
- **Read the `collecting:` block, not the exit status.** `tribunal/cloudbuild.test-engine.yaml`
  now asserts `collecting: N of N expected files`; any new engine test file must be added to
  that list AND to the expected count, or the gate silently runs nothing.

## Implementation Decisions

> **Numbering note.** `D-01`…`D-12` are this phase's. They are distinct from Phase 15.2's
> `D-01`…`D-16`, from the aborted-run defects `D-A`…`D-M`, from the engine brainstorm's
> `D1`–`D15`/`R1`–`R7`, and from Phase 16's `16-D-NN`.

### Scope and sequencing

- **D-01 [OPERATOR]: A run gets its own page — openable, closeable, re-openable, with its own
  URL.** Closing and reopening must show true progress, including an elapsed timer that does
  not restart. The operator's words: *"running a deep research should open its own page,
  showing the logs of each agent through every step … users can close the page and reopen it
  to check advancement, timer shouldn't restart each time u check on the page."*

- **D-02 [OPERATOR]: Engine events are built BEFORE the UI.** Chosen over shipping a
  real-data-only page first. Consequence accepted: no UI lands until the event pipeline
  exists, so the first visible result is later but is the full design.

- **D-03 [OPERATOR]: This ships in the SAME deploy batch as the 15.2 gap fixes.** Chosen over
  deploying 15.2 alone, getting the clean V-01 run, and shipping this after.
  **Accepted risk, recorded because it will matter during V-01:** the next live run will
  exercise a changed engine *and* a changed frontend simultaneously, so an unexpected result
  is harder to attribute to a cause. **Mitigation required of this phase:** the deploy record
  must state exactly what shipped together, so attribution remains possible after the fact.

### Event model and transport

- **D-04 [ASSISTANT — CORRECTABLE]: Run events live in a new append-only table, not in
  `stage_detail`.** Mechanism, because this is the crux: `runs/stages.py::set_stage` writes
  `stage_detail = COALESCE(stage_detail,'{}') || CAST(:entry AS JSONB)` — a **merge keyed by
  stage**. A stage that reports twice overwrites itself. There is no ordering and no history,
  so the intermediate states a feed is made of are gone by the time anything reads them.
  A feed showing "Dispatching 3 agents → three indented children → one completes" cannot be
  reconstructed from it at all. An append-only `run_event(run_id, seq, ts, stage, kind, text,
  meta)` gives ordering via `seq`, survives the run, and is what makes reopening the page
  work. Rejected: appending to `stage_detail` (unbounded growth of a hot row, still no
  ordering guarantee, and every write rewrites the whole blob).

- **D-05 [ASSISTANT — CORRECTABLE]: Delivery extends the EXISTING SSE stream, plus a REST
  backfill read.** `openResearchStream` already exists, already reconnects with bounded
  backoff, and already closes deterministically on terminal status. A second transport would
  mean two connections that can disagree about when a run ended. The REST read is what
  satisfies D-01's reopen requirement: the page backfills the full event history, then
  subscribes for new events. Rejected: a separate polling endpoint (a second source of truth
  for "is it over"); WebSockets (nothing else in the stack uses them).

- **D-06: An event write MUST NEVER be able to fail a run.** The emit path is best-effort and
  swallows its own errors, exactly as `set_stage` already does
  (`log.warning("set_stage failed …")`). Observability is not permitted to break the thing it
  observes. A run that loses events is degraded; a run that dies because of an event write is
  a regression.

- **D-07: Events are redacted on the same rule as every other outbound string.** Event text
  goes through `pipeline/tribunal/pii.py::scrub_pii` (shipped by 15.2-23). No event may carry
  a credential, a personal identifier, or an unbounded prompt body. This is the D-I lesson
  applied to a new surface: the scrub belongs at the choke point, not at the input.

### Frontend

- **D-08: The route is FLAT — `/admin/pulse/runs/:runId`, file
  `frontend/src/routes/admin.pulse.runs.$runId.tsx`.** Nesting it under
  `admin.pulse.intakes.$id.tsx` would turn that leaf route into a parent requiring an
  `<Outlet/>`, which is the trap that cost a cycle in Phase 18. A flat route also gives the
  run the genuinely standalone URL D-01 asks for.

- **D-09: The elapsed clock derives from `run.started_at` — never from mount.** The
  prototype's `setSecs(s => s+1)` from `useState(0)` counts from page load and therefore
  restarts at `00:00` on every visit, which is the exact behaviour D-01 exists to eliminate.
  Use the existing `useElapsed(startedAt, active)` helper. Plan 15.2-24 carried
  `started_at`/`completed_at` across the seam specifically to make this possible; this phase
  is its first consumer.

- **D-10: Four affordances the prototype drops are carried over, non-negotiably.** Each is
  load-bearing, not decorative:
  - **audit body drill-down** — the EU AI Act Art. 12 record;
  - **`chain_status` handling** — a `broken` chain MUST lock the download and offer
    re-verify; the prototype's "Download output" button is unconditional and would hand out
    raw output whose hash chain failed;
  - **resume on `parked`** — a retry starts a fresh attempt and discards every checkpoint the
    engine already paid for;
  - **Stop confirmation** — the cost incurred so far is not refunded and the run cannot be
    continued afterwards; the prototype's Stop fires immediately.

- **D-11: All eight run statuses are handled.** `queued`, `running`, `completed`,
  `completed_degraded`, `failed`, `cancelled`, `parked`, `needs_input`. The prototype models
  three (idle/running/done). Note the two traps already encoded in `ResearchRunProgress.tsx`
  and re-stated here so the new page does not reintroduce them: `completed_degraded` renders
  the SUCCESS card (a degraded run still cost ~$45 and keeps its download, verification
  report and frozen feed), and `parked` renders its OWN card (routing it to the failure card
  would offer a retry that throws away paid checkpoints).

- **D-12: Convert to the app's idiom — Tailwind utilities and `t()` for every string.** The
  prototype is 100% inline styles and hardcoded English. The design tokens it uses are
  already the real ones from `frontend/src/styles.css`; only the delivery mechanism changes.
  Preserve the interaction design exactly: streaming feed with a blinking cursor on the
  latest line, explicit dispatch headers with indented agent children, completed phases
  auto-collapsing to a two-line preview, per-phase summary lines, the `live` badge, and one
  full-height page with a single scroll.
</decisions>

## What exists, and what has to be built

**The stage vocabulary already has human labels and the UI has never used them.**
`ENGINE_STAGES["tribunal"]` defines 14 stages, each `{key, label}` — "Adaptive intake",
"Question workshop", "Deep research", "Skeptic verification", "Final synthesis" and so on.
`ResearchRunProgress` renders the raw key (`Current phase: deep_research`). The new page
should use the labels, and must remain **data-driven with no hardcoded stage count** — the
current component's best property, and the reason adding engine stages costs the UI nothing.

**What `stage_detail` provides today**, per item: `{name, status, task_prompt?, cost_usd?,
facts?, retry?{attempt,max,wait_s}, audit_id?}`, plus an optional per-stage
`summary{duration_s, actions, cost_usd, items_read?}`. Item status is one of `pending`,
`running`, `done`, `retry`, `failed`. This covers the prototype's `agent_run`/`agent_done`/
`agent_retry`/`agent_fail`, `summary` and `divider` line kinds — and nothing else.

**What must be newly emitted** for `dispatch`, `thinking`, `tool`, `search`, `plan` and
`streams`. The emit sites are known from the run forensics: angle dispatch and stream
assignment in `pipeline/tribunal/research_division.py`; SerpAPI search and page fetch in
`pipeline/tribunal/own_researcher.py`; provider poll transitions in
`audit/audited_llm_client.py`; workshop candidate/tournament rounds in
`pipeline/tribunal/workshop.py` and `workshop_rank.py`; brief parsing in
`pipeline/tribunal/brief_input.py`. `pipeline/tribunal/pipeline.py::set_stage` is the
existing choke point 15.2-24 instrumented and is the natural home for stage-level events.

**Alembic.** The tribunal head after 15.2 is `0014`. A `run_event` table is `0015`. Migration
proof is the literal `Running upgrade 0014 -> 0015` line; `exit(0)` is never proof.

**Volume is a real design input.** A 24-angle run with per-poll events could emit a few
thousand rows. The write path must be cheap, non-blocking and batched or fire-and-forget; the
read path must paginate. An unbounded `SELECT *` for a completed run is not acceptable, and
neither is a feed that re-renders every row on each SSE tick.
</code_context>

<specifics>
## Specifics worth stating

- **Entry point.** The intake detail route needs a way into the new page. The minimal correct
  thing is a link on the existing `ResearchRunProgress` card ("Open run"), which keeps the
  card as the summary and the page as the depth.
- **Accessibility.** The current component sets `role="status"` and `aria-live="polite"` on
  its cards. A streaming feed needs equivalent treatment, and a live region that announces
  every one of a thousand events is worse than none — scope the live region to the run's
  status and phase, not to the feed body.
- **The failed/cancelled cards currently DROP the feed entirely** — the two states that most
  need evidence are the only ones that discard it. The new page must show the feed for every
  terminal state, `failed` and `cancelled` included.
- **A long poll must be visibly distinguishable from a stall, in the feed itself.** This is
  the withdrawn-D-C lesson: on 2026-07-27 log silence and flat CPU were read as a stall, and
  the run was mid-long-poll and resumed on its own. The page should say so in words.
</specifics>
