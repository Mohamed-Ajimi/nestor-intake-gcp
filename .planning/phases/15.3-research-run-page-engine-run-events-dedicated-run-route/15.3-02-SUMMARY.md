# Phase 15.3 Plan 02: Run-Event Read Surface Summary

A run's persisted activity is now readable: one bounded, seq-ordered, tenant-scoped
endpoint (`GET /api/runs/{run_id}/events`) plus an additive `event_seq` cursor on the
metrics the intake poll driver already fetches every ~3 seconds.

## What Was Built

**Task 1 — schemas** (`runs/schemas.py`, commit `7e0bb63`)

`RunEventItem` mirrors migration 0015's `run_event` columns on the wire; `id` and
`tenant_id` are deliberately absent (the tenant key is never a wire value and `seq` is
the only cursor anyone needs). `RunEventPage` carries `events` + `next_after_seq` +
`has_more`. `RunMetrics` gained `event_seq: int | None = None`, placed directly beneath
the `started_at`/`completed_at` pair added by 15.2-24 and documented in the same
register: additive, so an older engine revision simply omits it.

**Task 2 — the endpoint** (`runs/api.py`, commit `32e8571`)

`get_run_events` is declared beside `get_run_audit_body`, well above the `/{run_id}`
catch-all. It resolves the run through `Depends(get_db_session)` only, clamps its
bounds, and issues one `text()` query with `limit + 1` bound as `:lim`. It has no
status gate — a failed, cancelled or parked run is exactly the run whose feed an
operator needs, and today's cards dropping that feed is the defect this ends.

`get_run_metrics` gained one `SELECT max(seq) FROM run_event WHERE run_id = :rid`.

**Task 3 — the proofs** (`tests/test_run_events_api.py` + gate, commit `856cb0d`)

23 pure, keyless, DB-free tests. The fake session behaves like a tiny in-memory
`run_event` table that HONOURS the `:after` and `:lim` binds the handler sends — a fake
that ignored them would let a handler which forgot to clamp, or forgot to request the
probe row, still pass every paging assertion.

## The Isolation Property, and How It Is Proven

The requirement was that a denied caller gets EXACTLY 404, and that a missing run and a
foreign run take the IDENTICAL path so the response shape leaks nothing.

Proving "two cases are indistinguishable" by comparing two identical fakes is a
tautology, so the proof is structural as well as behavioural:

| Property | How it is pinned |
|---|---|
| Cross-tenant run is exactly 404 | Real FastAPI stack, `run=None` (RLS miss) → `status_code == 404` asserted as the integer |
| The denial fires at the tenant wall | `session.calls == 1` — `run_event` is **never queried** on a denied request |
| Missing and foreign are identical | Both bodies compared with `==`; and the handler is proven to contain **exactly one** `HTTPException(` and **one** `scalar_one_or_none` |
| No empty-200 leak | No `RunEventPage(` construction exists **before** the 404 raise (index check) |
| No forbidden arm can be added | The forbidden literal is built at runtime from `str(403)` and asserted absent from the handler's full source |
| Nothing to spoof | The signature carries no `tenant_id` / `space_id` / `org_id` parameter |

**Scope boundary, stated rather than dropped.** The executor brief also asked for
user-role and null-space callers to be proven 404. Those dimensions do not exist at
this layer: `Identity.role`, `space_id` and the superadmin gate are the intake side's
(`backend/app/api/research_routes.py`), and the tribunal engine's only isolation
dimension is the JWT-trusted tenant + the FORCE-RLS GUC. The role/null-space denial
arms for this feed belong to the **15.3-07 intake proxy**, which is the layer that has
an `Identity` to check. What this layer owns — that no caller-supplied tenant of any
kind reaches the query — is proven above and documented in the test file's scope note.

## Boundedness

`limit=99999` → 1000 events returned, and the fake records that the handler asked for
`lim=1001`, which is what makes the probe row a fact rather than a comment. `limit=0`
and `limit=-5` clamp to 1. `after_seq=-999` floors to 0. A non-integer `after_seq` or
`limit` is a 422 before the handler body runs. No `COUNT(*)` is issued anywhere.

The anti-rewind property has its own test: an empty page returns the cursor the caller
passed in, never 0. Returning 0 would send a live client back to the start of the run
on every quiet tick — the single most expensive way to get cursor paging subtly wrong.

## Deviations from Plan

**1. [Rule 3 - Blocking] `scalar_one()` instead of `scalar()` for `MAX(seq)`**
- **Found during:** Task 2
- **Issue:** `test_stage_logging.py::_FakeResult` (landed by 15.2-24) implements
  `scalar_one_or_none` and `scalar_one` but **not** `scalar`. Adding a fourth query to
  `get_run_metrics` that called `.scalar()` would have broken three pre-existing tests
  with `AttributeError`.
- **Fix:** Used `.scalar_one()`, which is also the more correct call: an aggregate
  without `GROUP BY` always returns exactly one row, and on a run with no events that
  row is NULL → `None`. The pre-existing fake needed no edit.
- **Files modified:** `tribunal/nestor_pulse_sdk/runs/api.py`
- **Commit:** `32e8571`

**2. Task 1 and Task 2 `<automated>` verify commands could not be run as written**
- Both are `cd tribunal && python -c ...`. **This machine has no Python** (a recorded
  project constraint). Rather than skip the checks or claim a run that did not happen,
  both assertions were folded into the pytest file, which DID run in Cloud Build:
  `test_run_metrics_carries_an_additive_event_seq` +
  `test_event_kind_is_a_plain_str_not_a_literal` cover Task 1's check, and
  `test_events_route_is_declared_before_the_catch_all` covers Task 2's. This is
  strictly stronger — the checks now run on every future build instead of once.

**3. Three test-harness defects found and fixed by the first gate run (build `e05ef432`)**
- The first Cloud Build run was RED: 3 failed, 752 passed. All three were defects in
  the new test file, none in the handler — worth recording because the handler passed
  every case it actually reached.
  - `_Session` sequenced its executes cumulatively (`calls == 1`), so a test that
    invoked the handler twice against one session fed the *page* result into the *run
    resolve*. Fixed to alternate on `calls % 2`.
  - Two source gates counted tokens in the full source including the docstring, so a
    docstring that explained *why* `scalar_one_or_none` is there inflated the count to
    2 and failed its own assertion. Fixed with a `_handler_code()` helper that strips
    the docstring for **structural** claims — while the forbidden-status gate keeps
    scanning the full source, because a docstring quoting that number is exactly what
    it must catch.

## Threat Mitigations Applied

| Threat ID | Disposition | Where it landed |
|---|---|---|
| T-15.3-10 | mitigate | `scalar_one_or_none()` → `HTTPException(404, "run not found")`; no forbidden arm, pinned by a runtime-constructed source gate |
| T-15.3-11 | mitigate | One denial arm, one resolve, no page constructible before the guard; bodies compared for equality |
| T-15.3-12 | mitigate | `limit` clamped 1..1000, `limit + 1` probe, ordered index range scan on `idx_run_event_tenant_run_seq` |
| T-15.3-13 | accept | `max(seq)` is an index-only backward scan; the handler already runs three counts at that cadence |
| T-15.3-14 | mitigate | Typed query params (422 before the body), explicit `int()` coercion + clamp, bound `:rid`/`:after`/`:lim` — no interpolation, asserted |
| T-15.3-15 | accept | No new dependency; `fastapi` and `httpx` were already pinned in `requirements.txt` |

No new security-relevant surface was introduced beyond the endpoint the threat model
already covers, so there are no threat flags to raise.
