## Critical Anti-Patterns

| # | Anti-pattern | severity |
|---|---|---|
| 1 | Believing `--min-instances=0` stops a Cloud Run worker from running | blocking |
| 2 | Deploying `tribunal-worker` while any run is still `status='running'` | blocking |
| 3 | Accepting a green exit code as proof a gate or migration did anything | blocking |

**1 — `min-instances=0` does NOT prevent a boot.** Deploying a revision starts a container to
health-check it, and `tribunal-worker` begins its Postgres poll loop the moment it boots. On
2026-07-28 that was enough: the worker deployed at 08:22:57Z, claimed run `d6bb3aae` within seconds,
and re-executed ~15 minutes of paid pipeline before Cloud Run scaled the idle instance away at
08:37:40Z. The instance being "paused" is about *steady state*, not about deployment. The only safe
protection is **not having a claimable run when you deploy**.

**2 — resolve the run first, deploy the worker LAST.** `DEPLOY-RUNBOOK` § 15.2.k currently has this
**WRONG**: it deploys the worker at step 4 and cancels the stuck run at step 6. Following it as
written is what caused the incident. A related trap in `deploy-worker.sh`: its single
`gcloud run deploy` sets `--min-instances=1` **and** `NESTOR_WORKER_STALE_MINUTES=60` in one atomic
command, so a plain re-run unpauses AND re-arms reclaim simultaneously. Commit `37aea7b` added a
`MIN_INSTANCES` override (default still 1) — necessary but **not sufficient**, per anti-pattern 1.

**3 — read the log, never the exit status.** The engine gate asserts `collecting: 30 of 30 expected
files`; anything else means the tree is not this phase. A migration is proven ONLY by its literal
`Running upgrade X -> Y` line — and note that `cloudbuild.test.yaml` **never prints alembic output
at all**, so intake migrations must be verified via `information_schema` + `alembic_version` instead.
Two independent gate blind spots were found this phase; see [[gate-integrity-traps]].

## The 401 defect — fixed but not deployed

Quick task `260728-ftv`, commit `31a7f71`. The intake poll driver retried `5xx` and treated **every**
`4xx` as fatal. A transient `401` from Cloud Run's **edge** during a `tribunal-api` rollout (no 401
ever reached the app) finalized the run `failed` while the engine kept working.

**It was worse than a wrong badge: the Stop button only renders on the ACTIVE card, so the false
terminal state removed the operator's ability to stop the real run.**

Now `401`/`403` retry on a **separate 10-minute budget** (200 x 3.0s). Sharing the `5xx` budget would
have given 9 seconds against an observed >=8m06s outage. `400`/`404`/`409` stay fatal, pinned by a
test that queues a recovery entry behind the 404 so widening the arm fails loudly. Also found: the
`5xx` path had shipped **completely unpinned** — the "existing 5xx test" did not exist.
