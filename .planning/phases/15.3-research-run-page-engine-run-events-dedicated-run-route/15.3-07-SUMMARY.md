# Phase 15.3 Plan 07: Run-Event Proxy + Locate Verb Summary

The operator surface can now read a run's persisted activity feed through the intake
backend — and a bookmarked `/admin/pulse/runs/{runId}` can find its own intake from a
cold open — with the role and null-space denial arms that plan 15.3-02 explicitly could
not prove now discharged as the exact integer 404.

## The Inherited Obligation, and How It Was Discharged

15.3-02 built the engine endpoint and was asked to prove that a cross-tenant, a
user-role AND a null-space caller each get exactly 404. It could prove only the first,
and said so rather than quietly narrowing the claim: the tribunal engine has no
`Identity` — no role, no `space_id` — so its only isolation dimension is the JWT tenant
plus the FORCE-RLS GUC. `Identity.role`, `_superadmin_gate` and `space_id` live on the
intake side. It wrote the handover into its test file's scope note and its SUMMARY so
the obligation could not evaporate at the seam.

It is discharged in `backend/tests/test_research_events_proxy.py`, over **both** new
verbs, in a matrix parameterised on the caller:

| Caller | events | locate | Why this cell exists |
|---|---|---|---|
| user-role, OWNS the intake's space | 404 | 404 | D-08: a client can never reach the run page, and the gate is existence-hidden |
| **null-space** (`space_id=None`) | 404 | 404 | **Proves the DEPENDENCY ORDER.** Swap `_superadmin_gate` and `get_tenant_repo` and this cell alone turns forbidden — which leaks that the endpoint exists — while every other cell stays green |
| cross-space user | 404 | 404 | the classic BOLA/IDOR arm |

Every cell asserts the exact integer, via a helper that first pins out 403 by name
("confirms the run exists to a caller who must not learn that") and 200 by name ("not a
denial at all"), because `!= 200` or `>= 400` would let either regression through. Each
cell also asserts the denial made **no seam call**: a feed page fetched behind a 404
would still be a cross-tenant read — the caller merely would not get to see it.

Four more arms cover what the role gate structurally cannot, and these need the
connect-as `app_superadmin` engine (a non-superuser LOGIN role, so the RLS assertions
are not vacuous): unknown intake, unknown run, a run borrowed from a **different
intake**, and — the strongest — **another space's run read under this intake's path**.
That last one is the test that would fail if someone deleted the
`run.intake_id != intake_id` cross-check as "redundant with the scoped repo": a
superadmin has genuine cross-space reach by design (D-05, `_scope` is a no-op for them),
so nothing about the role stops it. The cross-check does.

## What Was Built

**Task 1 — the seam verb** (`tribunal_client.py`, commit `078d4e5`)

`get_run_events` cloned from `get_audit_body`'s shape: same `_headers` / `_mint_id_token`,
same `_TIMEOUT_S`, same `raise_for_status()`, same verbatim `.json()`. `after_seq` and
`limit` travel as httpx `params=`, never interpolated into the URL path — `seq` is
caller-controlled, and interpolating a caller-controlled value into a request path is how
an extra segment gets built by accident. `limit` is clamped 1..1000 client-side with the
engine's identical window named as the authority; a test records what actually left the
process (`limit=99999` → `1000`, `after_seq=-999` → `0`), because a clamp that exists only
in a docstring is not a clamp.

**Task 2 — the two routes** (`research_routes.py`, commit `06343b5`)

`get_research_events` is `get_research_audit_body` arm for arm: gate dependency declared
before `get_tenant_repo`, in-body role re-check, intake 404, run-scope 404, WR-03
no-engine-id 404, seam call outside any held DB session, then engine-404 → 404 and
everything else (including a transport failure with no response object at all) → 502.
It reshapes nothing, so a field the engine adds later reaches the page with no change here.

`locate_research_run` is declared **above every** `/{intake_id}/...` route and directly
beneath `_superadmin_gate` (a `Depends` default is evaluated at def time, so any earlier
would be a NameError at import). It **composes** the proven scoping rather than inventing
any: gate + role re-check, the space-scoped `ResearchRunRepository.get`, then a second,
space-scoped resolve of the run's own intake. It returns `{intake_id, research_run_id}`
and nothing else.

**Task 3 — the proofs** (`test_research_events_proxy.py`, commit `14ab9a9`)

28 tests: the 6-cell denial matrix, 6 superadmin scope arms, 4 happy/forwarding paths,
4 seam-failure mappings, the route-order assertion, and 7 structural gates.

## The One Place the Plan Was Wrong, and Why

**The plan's denial cell (g) — "a run whose `tribunal_run_id` is NULL" — was to be run
over BOTH verbs. Applying it to `locate` would have broken the feature this plan exists
to enable.**

`trigger_research` inserts the mirror row with `status='queued'` and **no**
`tribunal_run_id`; the poll driver mirrors the engine id in later. So a run carries a
NULL engine id for exactly the window in which an operator opens the run page. A WR-03
404 on `locate` would 404 the cold-open bookmarkable URL (D-01) on **every single new
run** — and it would deny nothing, because "which intake owns this run" is knowable
without the engine ever having heard of it, and `locate` makes no seam call at all.

So the asymmetry is deliberate and pinned in **both** directions:
`test_events_run_without_engine_id_404` (events → 404, and `/api/runs/None/events` never
leaves the process) and `test_locate_resolves_a_run_without_engine_id` (locate → 200 with
both ids). Neither half can now be "tidied" into the other by someone pattern-matching
the two handlers.

The same reasoning applies to cell (c) for `locate`. "A superadmin with a run belonging
to a different space" is a 200 by design — the superadmin is a global operator with no
own space, and the existing verification/bundle happy paths already establish that. The
meaningful cross-space arm is therefore expressed on the events verb, where mixing spaces
across the `intake_id`/`run_id` pair genuinely is a denial. The cross-space **caller**
arm (a space-B user) is proven for both verbs in the matrix.

## The Route-Order Test Is Defence in Depth, Not a Fix

`research/runs/{run_id}/locate` and `{intake_id}/research/{run_id}/events` differ at the
literal second segment, so there is no live shadowing bug — the plan-checker traced this
and the test confirms it. It is kept because a shadowed `locate` would 404 a perfectly
authorized caller with a response byte-identical to the existence-hidden one: invisible in
review, invisible in every log, and indistinguishable from a working denial. It asserts
ORDER (`index(locate) < min(index of any parameterised intake route)`), not existence, and
it does **not** stand in for any cell of the denial matrix.

## Notes for the Next Plan

- **`locate` is the cold-open entry point.** 15.3-08/09 should call it first when the
  route has a `runId` and no intake in hand, then use the returned `intake_id` for every
  other research verb. It works for a `queued` run with no engine id yet (proven), so the
  page can open the instant the operator clicks Start.
- **The events proxy returns the engine page verbatim**, including `next_after_seq` and
  `has_more`. `next_after_seq` on an empty page is the cursor the caller passed in, never
  0 (15.3-02's anti-rewind property) — do not reset it client-side on a quiet tick.
- **`limit` is bounded at 1000 in two places.** The engine's clamp is the authority.
- **Nothing was deployed and no live run was started.** `tribunal-worker` remains paused
  at `--min-instances=0`; no `gcloud run services update` was issued. Run `d6bb3aae` was
  not touched. The only cloud action was `gcloud builds submit` against
  `cloudbuild.test.yaml` (twice).
- **`cloudbuild.test.yaml` was NOT edited** — it runs `pytest tests -m integration` over
  the whole directory, so a new test file is collected automatically (unlike the engine
  gate, which needs its `EXPECTED_FILES` count reconciled).
