    docstring, borrowing `verificationGate.ts`'s argument and sharpening it for this question:
    `RESEARCH_TERMINAL` answers *"when does the stream stop"*, which is a different question that

    this rule must tell those three apart because each licenses different words on screen. Importing
    it would make an edit made for the stream's reasons silently rewrite what the operator is told.

    Document each mapping in the docstring with its own reason:

    - `running`, `queued` → `running`. `queued` is a run that has been accepted and not yet started;
      the operator's action is the same as for `running` (wait, or upload artifacts), and it becomes
      `running` within seconds. Called out explicitly so the small imprecision is a recorded decision
      rather than an oversight.
    - `completed`, `completed_degraded` → `finished`. A degraded run is FINISHED; its degradation is
      announced by the verification report's own G-10 sentence, not by pretending it is still
      working. Routing it anywhere near the failure treatment strips evidence off a run already paid
      for in full (the same trap `RunStatusCard.tsx:20-27` records).
    - `failed`, `cancelled` → `stopped`. Nothing is running, and the run did not finish. The banner
      must say neither "running" nor "finished".
    - `parked`, `needs_input` → `paused`. Nothing is running and the run is not over: it is waiting
      on a HUMAN. `parked` closes the stream precisely because that wait may be hours long.
    - everything else, including `null` and `undefined` → `unknown`. During a rolling deploy an
      unheard-of status is the NORMAL state of the world. And the hook that feeds this rule holds
      `null` in three ordinary situations — before the first SSE frame arrives, when the intake never
      had a run, and when the stream is unavailable — none of which means the work ended. A default
      of `finished` would reintroduce the reported defect with the sign flipped.
