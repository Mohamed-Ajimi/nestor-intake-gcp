<objective>
Backend rules and storage for the superadmin rerun (D-23.6-01, D-23.6-03) and the internal
chosen-run label (D-23.6-02 revised).

1. `trigger_research` stops capping superadmins, and stops requiring a status step-back: from
   `in_research` or `delivered` a new run starts whenever no run of that intake is in flight, and
   the intake status is left exactly as it was (a delivered intake stays delivered).
2. Migration 0018 adds `research_runs.chosen_at` (nullable timestamptz) with a partial unique
   index so at most one run per intake is marked chosen; `ResearchRunRepository.set_chosen` moves
   the mark atomically. The HTTP verbs that use it are plan 02.

Purpose: one click must be able to start another paid run on the same approved inputs, without
the client losing their delivered report, and the operator must be able to record which run the
final report is based on.
Output: migration 0018, model + repository changes, trigger rule change, tests (RED first).

Storage decision (Claude's discretion per CONTEXT): a flag column on the RUN (`chosen_at`), not a
pointer column on the intake. Reasons: no intakes <-> research_runs FK cycle (research_runs already
cascades from intakes, and D-23.5-06 intake delete must keep working unchanged), no change to the
widely-read `intakes` table, and the "one chosen per intake" rule becomes a DB invariant via a
partial unique index, the same technique 0016 uses. The newest-finished DEFAULT is display-only
and is never stored (UI-SPEC UI-8) — nothing in this plan writes `chosen_at` except `set_chosen`.
</objective>
