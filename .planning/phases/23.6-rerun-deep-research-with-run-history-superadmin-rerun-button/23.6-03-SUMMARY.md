# Phase 23.6 Plan 03: Run-history data layer, pure rules and copy Summary

The run-history decisions (chosen-run badge, Rerun visible/disabled, choose/zip row gates, and what a failed-rerun toast may claim about money) now live in one pure, 39-test module. Next to it are the two typed API calls for the frozen 23.6-02 contract, a single shared `statusLabel`, and all 34 approved `intakeDetail.runs.*` strings in nl/fr/en.

## Deviations from Plan

**1. [Plan-directed] The "in-flight code" wording in the UI-SPEC is not implemented as an error code.**
- UI-SPEC "Rerun confirm" outcomes say an error "with an in-flight code (409 `RESEARCH_IN_FLIGHT`)" gets `runs.toast.rerunInFlight`.
- As the plan instructs, nothing was added to `frontend/src/lib/i18n/error-codes.ts` and the backend was not changed. The 409 carries no machine code, so plan 04 must call `classifyRerunFailure(beforeIds, refetchedRunsOrNull)` after a failed trigger:
  - `in_flight` gives `runs.toast.rerunInFlight`.
  - `maybe_started` gives `intakeDetail.toast.researchStartFailed`.
  - `failed` gives `runs.toast.rerunFailed`.

**2. [Formatting note, not a change]** `prettier --check` flags the new files, but it flags already-committed files such as `triggerOutcome.ts` the same way (CRLF working-copy line endings on this Windows checkout). Not a gate, and nothing was reformatted.

Otherwise the plan was executed as written.
