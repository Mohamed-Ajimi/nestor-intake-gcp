2. `ResearchRun` (`frontend/src/lib/api/research.ts:249-273`) carries NO `verification_summary`
   field, so the page CANNOT know from the run row whether a report exists. The gate must
   therefore be on STATUS, and `VerificationReport` must own its own empty/error state — which
   it does: `VerificationReport.tsx:223-240` fetches on mount and sets an inline error plus a
   `toast.error(t("verification.loadError"))` when the fetch fails. Mounting it lazily behind a
   toggle means a run with no report costs one request and shows one honest error line.

3. The run page already resolves both ids it needs: `intakeId` from
   `locateResearchRun(runId)` (route lines 52-71) and `runId` from `Route.useParams()`.

4. The page's structural rule (route lines 274-284) is that THE CARD AND THE FEED ARE SIBLINGS,
   deliberately not nested inside a status branch, so evidence survives on failed and cancelled
   runs. D-11 says to follow that rule here: gate on whether a verification report CAN exist,
   not on which `RunStatusCard` branch is rendering. The report therefore goes on the PAGE,
   between the card and the truncation notice — never inside `RunStatusCard.tsx`.
</measured_facts>

  <action>
Create `frontend/src/lib/research/verificationGate.ts` exporting one function:

`canHaveVerificationReport(status: string): boolean`

It returns true for exactly these five statuses and false for everything else, including any
status this build has never heard of: `completed`, `completed_degraded`, `failed`, `cancelled`,
`parked`.

The set is ENUMERATED, never derived from `RESEARCH_TERMINAL` and never expressed as a negation.
The docstring must say why, in these terms:

- `completed` and `completed_degraded` — a degraded run still cost around forty-five dollars and
  keeps everything a clean run keeps, including its verification report. This is the same trap
  `RunStatusCard.tsx:20-27` records.
- `failed` and `cancelled` — these are the two states whose evidence matters MOST and the two
  the embedded intake card throws away. D-11 and the page's card/feed sibling rule exist
  precisely to stop that, and the verification report is evidence in the same sense the feed is.
  A run that failed after the verify stage has real verdicts; refusing to show them repeats the
  defect this phase is closing.
- `parked` — a park happens AFTER paid work. Whatever verification had completed is still real.
- `queued`, `running` — the pipeline has not reached the verify stage, so there is nothing to
  fetch and offering the affordance would be an offer the page cannot keep.
- `needs_input` — the clarification pause fires BEFORE research (16-CONTEXT D-01/D-01b says it
  never fires for seam runs at all), so like `queued` there is nothing behind it.
- An UNKNOWN status returns false: a rolling deploy makes an unheard-of status the normal state
  of the world, and defaulting a new status INTO an affordance is how an offer the seam refuses
  reaches the screen.

Then create `frontend/src/lib/research/verificationGate.test.ts` asserting the function over
ALL EIGHT statuses individually plus at least one invented string. Write eight named assertions,
not one loop over a table — the point is that a future edit that flips `failed` or `cancelled`
fails a test whose NAME says what was lost.

Add no dependency, edit no config file.
