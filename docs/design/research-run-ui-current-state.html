01 · contextWhere this lives today, and why that is the core problem

There is no research page. The entire run — a process that costs real money and runs for 30–60 minutes across 14 stages and dozens of dispatched agents — renders as one card embedded partway down the admin intake detail route (/admin/pulse/intakes/:id), stacked among the intake's other panels. Everything below is that single card in its various states.

What this means in practice.
  • The run competes for attention with every other panel on the intake page. It has no URL of its own, so it cannot be bookmarked, shared with a colleague, or opened in a second tab.
  • Scrolling the intake page scrolls the run away. There is no persistent header showing status, elapsed time or cost.
  • The activity feed is capped at max-height: 28rem with its own inner scrollbar — a scroll area inside a scroll area.
Requested change. A run should open its own page, be closeable and re-openable, and show real progress on return.

02 · data modelWhat the UI is actually driven by

Worth knowing before redesigning: the feed is fully data-driven. The component hardcodes no stage count — it renders whatever stage_detail the run reports, so adding engine stages costs the UI nothing. Any new design should preserve that.

Anatomy. Left border #FF2D87. Spinner + eyebrow + body on the left; elapsed clock, running cost and Stop stacked right. Then the raw current-stage key, then the feed.
  • Agent card = icon + name + a result line assembled from whatever the item carries: done · 21 facts · $2.40. Optional expandable task prompt, retry chip, audit link.
  • Summary card closes out a stage: Worked for 3m 12s · 47 actions · $1.87 · 128 items read.
  • Failed agents show no reason. The card says "failed" and stops there — no error text, no link.
Known problems in this state.
  • No stage grouping. Agent cards from all 14 phases render as one flat list. There is no phase heading, no progress-through-phases indicator, nothing to tell you that the run is 4 of 14 phases in.
  • No logs. This feed is the only window into the run. There is no log view anywhere in the product — engine logs are readable only through Cloud Logging by an engineer. "Failed" with no reason is where an operator's understanding ends.
  • Parallel dispatch is invisible. Angles #1–#6 are dispatched concurrently across four research streams, but they render as a flat sequential list. Nothing shows what runs in parallel, which stream an agent belongs to, or how many are in flight.
  • Inner scroll. The feed is capped at 28rem and scrolls inside the page's own scroll.
  • Nothing is filterable. No way to show only failures, only a phase, or only one research stream.

A3 · Stop confirmation

the only way to stop a run, shipped 27 Jul 2026

Stop research?

This stops the research that is currently running. The costs incurred so far are not refunded, and the run cannot be continued afterwards — you can only start a completely new research run. Continue?

Uses the same AlertDialog as the research trigger. While the request is in flight the Stop button shows a spinner and the label "Stopping…".
Note. This is brand new. Until last week the only way to stop a run was to pause the entire Cloud Run worker service — which did not stop the run and nearly caused a fresh worker to re-execute it at full cost.

07 · briefWhat the redesign has to solve

Collected from the operator, plus what the states above expose. Nothing here is designed yet — this is the problem list to design against.

#RequirementToday
1 A run gets its own page. Openable, closeable, re-openable, with its own URL. One card embedded in the intake detail route. No URL, not shareable, scrolls away.
2 Closing and reopening shows true progress. The elapsed timer must not restart on each visit. The clock falls back to Date.now() whenever started_at is missing, so it restarts from zero on every page load. A fix landed 27 Jul 2026 — written, not yet deployed.
3 Logs are visible in the product. An operator should be able to see what the run is doing and why something failed. No log view exists. The activity feed is the only window. A failed agent shows the word "failed" and nothing else. Engine logs are Cloud Logging only.
4 Agent dispatch is legible. Show what runs in parallel, across which research streams, grouped by phase. A flat, ungrouped, chronological list. Four concurrent research streams and 14 engine phases are all flattened into one column with no headings.
5 Failure states keep their evidence. The failed and cancelled cards drop the feed entirely — the states that most need history are the ones that discard it.
6 Phase progress is visible. "4 of 14, currently Deep research." A raw key: Current phase: deep_research. The engine's human labels exist and are never used.

Constraints worth keeping

things the current build gets right
  • Fully data-driven. No hardcoded stage count — the feed renders whatever the run reports. Adding engine phases costs the UI nothing. Preserve this.
  • The frozen feed. After a completed run the feed stays clickable, audit drill-downs included. It is a genuine replay of what happened.
  • Every optional field degrades cleanly. A legacy item with only {name, status} renders as a plain card with no cost, prompt, retry or audit affordance.
  • Three locales. Every string exists in en, nl and fr and is gated in CI. New copy needs all three.
  • Superadmin-only by placement. No client-facing route imports this component.
  • Design language. IBM Plex Mono for all chrome/metadata, Plex Sans for body, Plex Serif for headings. Flat, no rounded corners, no shadows, 4px left border as the state signal.
